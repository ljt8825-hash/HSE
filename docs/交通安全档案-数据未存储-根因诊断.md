# 三级菜单「交通安全档案」数据未存储 — 根因诊断报告

- 诊断时间：2026-09-04
- 诊断人：高级开发工程师
- 结论：**根因已确认 — 后端为纯内存存储，未落数据库**

---

## 一、结论（一句话）

「交通安全档案」的后端接口 `/site-mgmt/driver-assessments` 采用**纯内存数组**存储数据，
**没有任何数据库表**。数据只存在于 Node 进程的堆内存中，
**后端进程任何一次重启 / 崩溃 / 热重载，数据立即全部丢失**。

---

## 二、证据链

### 1. 后端实现：内存数组，非数据库

文件：`server/routes/site-mgmt.js`

```js
// 第 21~31 行
const memoryStores = {
  violations: [], fireEquipment: [], gridAreas: [],
  gridInspectionRecords: [], objectives: [],
  driverAssessments: [],        // ← 交通安全档案
  driverViolations: [], driverMonthly: [],
};
```

GET / POST / PUT / DELETE 四个端点（第 476 / 516 / 550 / 564 行）**全部只操作该数组**，
响应 message 均带「（内存模式）」字样。

### 2. 数据库无对应表

对 PostgreSQL `public` schema 全量检索（driver / assess / traffic / archive 关键字），
**不存在任何交通安全档案表**。检索到的 `hse_assessment_*` 系列属于「HSE 责任制考核」，
`hse_driver_inspection_records` 属于车辆检查，均与本模块无关。

`server/controllers/` 目录下也**没有**对应 controller
（仅有 checkLedgerFactory / transferStations / vehicleChecks / vehicles）。

### 3. 实测复现：写入能成功，但重启即丢

用 admin JWT 直连 API 实测（已清理测试记录）：

| 步骤 | 结果 |
|---|---|
| GET 列表（写入前） | 44 条，成功 |
| POST 一条完整记录 | 成功，返回 id=45，字段完整 |
| GET 列表（写入后） | 45 条，新记录可读回 |

→ **写入链路本身完全正常**，不是前端 bug、不是接口报错、不是字段丢失。

### 4. 时间线吻合：重启 → 数据清空

| 时间 | 事件 |
|---|---|
| 08:38:46 | 后端进程（PID 21148）启动，内存数组初始化为空 |
| 08:46:37 ~ 08:46:44 | 44 条记录**在 8 秒内被批量重建**（同步花名册驾驶员） |
| — | 44 条的业务字段（评估等级 / 评估日期 / 有效期）**全为空** |

`createdAt` 分布（UTC 00:46:37~00:46:44 = 北京 08:46:37~08:46:44）：

```
2026-09-04T00:46:37: 5 条    2026-09-04T00:46:41: 5 条
2026-09-04T00:46:38: 6 条    2026-09-04T00:46:42: 6 条
2026-09-04T00:46:39: 6 条    2026-09-04T00:46:43: 5 条
2026-09-04T00:46:40: 5 条    2026-09-04T00:46:44: 6 条
```

逐条 `create` 的节奏特征 → 即前端「同步花名册驾驶员」批量新建的结果，
**不是用户手工录入的数据**。真正的考核内容在重启时已随内存一起消失。

### 5. 排除项

以下可能性已逐一排除：

- ❌ `initMemoryData()` 每次请求重置 → 有 `memoryInitialized` 守卫，仅首次执行
- ❌ 定时任务清空内存 → `site-mgmt.js` 无非业务 timer / cron
- ❌ 多进程内存不共享 → 仅 PID 21148 单进程监听 5800
- ❌ 前端保存逻辑缺陷 → `handleSubmit` 传完整 `formModel`，实测写入成功
- ❌ 认证 / 权限导致写入失败 → 实测 POST 返回 `code:0 创建成功`

## 三、影响范围（比想象更大）

同一个 `site-mgmt.js` 文件是**混合模式**：

| 模块 | 端点 | 存储 | 重启后 |
|---|---|---|---|
| 网格区域 / 网格记录 | `/grid-areas`、`/grid-records` | ✅ 数据库 | 数据保留 |
| 违章违规 | `/violations` | ⚠️ 内存 | **丢失** |
| 消防器材 | `/fire-equipment` | ⚠️ 内存 | **丢失** |
| **交通安全档案** | `/driver-assessments` | ⚠️ 内存 | **丢失** |
| 驾驶员违章记录 | `/driver-violations` | ⚠️ 内存 | **丢失** |
| 驾驶员月度考核 | `/driver-monthly` | ⚠️ 内存 | **丢失** |

> ⚠️ **特别提示**：2026-09-03 完成的「驾驶员月度考核」列重构（三检表管理 / 灯牌污损 /
> 灯具失效 / 安全监控 / 消防管理 五列）同样落在这个内存模块上。
> 目前录入的数据**后端一重启就会清空**，需要一并迁移到数据库。

## 四、修复方案

### 方案：新建数据库表 + 改造为 DB 模式（推荐）

1. **建表** `driver_assessment`
   字段：`archive_no / name / id_card / license_type / department / vehicle_no /
   assessment_date / assessment_result / assessment_level / assessment_type /
   control_measures / status / expiry_date / phone / remark /
   created_by / created_by_name / created_at / updated_at / is_deleted`

2. **新增 controller** `server/controllers/driverAssessments.js`
   复用现有 `checkLedgerFactory.js` / `transferStations.js` 的落地模式
   （字段白名单 + 参数化查询 + 软删除）。

3. **改造端点** `site-mgmt.js` 第 476~575 行的 5 个端点改查 DB，
   保留内存数组作为 DB 故障时的降级。

4. **前端零改动** — API 契约（camelCase 字段）保持不变。

5. **同步迁移** `driver-violations`、`driver-monthly`（同一类问题，建议一并做）。

**工期**：交通安全档案单模块约 1 个改动批次；三个模块一起约 2 个批次。
**风险**：低（增量改造，前端契约不变；可保留内存降级兜底）。
