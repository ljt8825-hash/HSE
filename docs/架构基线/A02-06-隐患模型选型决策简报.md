## 1. 问题的一句话表述

> **隐患域的模型问题不是「三选一」，而是「四套落地 + 六张空表 + 一条不在 PostgreSQL 里的生产链路」。**
> 而现有讨论（A/B/C 三选一）**漏掉了第四条通道**：H5 移动端经 Cloudflare Worker 写入**飞书多维表格**，
> 已在生产运行，PostgreSQL 侧没有任何接收表。

### 2.4 本轮修正：C 不是「零写入空壳」，是「有写入代码但从未触发」

A02-05-04 表述为「`hse_rectifications`0 + `hse_reviews`0 = **零写入空壳**」。本轮回查源码后修正：

| 项 | 事实 | 证据 |
|---|---|---|
| `hse_rectifications` 写代码 | **存在** | `server/services/workflowService.js:79` `INSERT INTO hse_rectifications (...)` |
| `hse_reviews` 写代码 | **存在** | `server/services/hazardService.js:1059` `INSERT INTO hse_reviews (...)` |
| 触发条件 | `hse_tasks.task_type = 'rectification'` **且** `status = 'completed'` | `hseTasksService.js:139-152` |
| 实际情况 | **`hse_tasks` 表 0 行** | [事实] |

⇒ **C 模型的写入链存在、接口存在、但入口表为空 ⇒ 永不触发。**
这个区别很重要：**「没有写入路径」需要新建；「有路径但入口为空」只需接线。处置成本差一个量级。**

### 2.5 ★第四条通道：H5 → Cloudflare Worker → 飞书多维表格（本轮新发现）

**这是本轮最重要的发现，且它推翻了 A02-01 硬约束第 7 条。**

| 层 | 事实 | 证据 |
|---|---|---|
| 前端 | H5 有**完整隐患闭环 UI**：新建隐患（含拍照三阶段）、隐患列表、隐患详情、复查、待办、指派、整改 | `grid-mobile-cloudflare/frontend/check.app.js`：`openHazardForm()` @4721、`submitHazard()` @4985、`hazardShowPhase("photo")` @4851、`#btn-hazard-review` @4549 |
| 前端接口调用 | **9 个**：`/api/mobile/hazard/` 下 `submit`、`ai-fill`、`list`、`detail`、`review`、`todos`、`assignable`、`assign`、`rectify` | `check.app.js` @4834 / 5049 / 5114 / 5182 / 5313 / 5335 / 5398 / 5426 / 5516 |
| 后端 | Worker **已实现全部 9 个路由**，且 `submit`/`assign`/`rectify`/`review` 四个写接口在 `hazardGate` 白名单内 | `worker/index.js:790`、`:4779` 路由分发、`:3196` `handleHazardSubmit` |
| 存储目标 | **飞书多维表格**，表 ID 取自 `cfg.hazardSheetId`，未配置时直接返回 `HAZARD_TARGET_NOT_CONFIGURED` 503 | `worker/index.js:3207` |
| PostgreSQL 侧 | **无任何接收表 / 无同步脚本**（全仓检索 `hazardSheetId` 仅 Worker 内 7 处） | [事实] |
| 业务闸门 | 「隐患整改闭环全部路由均在 handler 内经 `hazardGate` 限定**安环管理部**」 | `worker/index.js:4779` 注释 |
| 交付标记 | `CF-WPS-100` 隐患闭环写接口 / `CF-WPS-102` | 同上 |

**为什么 A02-01 会漏掉它**（值得记录，因为这是方法论缺陷，不是偶然）：

> `A02-01-HSE业务域与数据边界全量归位审计.md:62` 的来源判定规则原文：
> 「H5 ⇒ `views/mobile/**` 的 POST/PUT」

该规则只看 **Vben 前端**的 `views/mobile/**`，**没有把 Cloudflare Worker 纳入扫描范围**。
因此 A02-01 `:207`「H5 13 页壳，仅 **2 个写接口**」、`:362` 硬约束第 7 条
「H5 只产生 2 类事实（巡查、三违），任何"移动端全业务"设计都与现状不符」——
**这两条在当前代码下不成立**。

> **这直接改变了隐患模型选型的题干**：
> 「未来隐患是否由 H5 录入」不是一个待决定的假设，而是**已经发生、已在生产运行、但数据不在 PG 里**。
> 选型必须回答的是：**飞书侧那批隐患数据，最终要不要、以及怎么进 PG？**

### 2.6 A 模型的真实数据形态（迁移可行性）

`hazards` 110 行，关键字段填充率：

| 字段 | 填充 | 对迁移的意义 |
|---|---:|---|
| `measure`（整改措施） | **110 / 110** | ✅ 可迁移到 C 的 `hse_rectifications.measure`（NOT NULL） |
| `fixer`（整改人文本） | 97 / 110 | ✅ 可解析 |
| `fix_date` | 69 / 110 | ✅ 可迁移到 `completed_at` |
| `status` | closed 60 / discovered 50 | ✅ 可映射 |
| `rectification`（整改说明） | **2 / 110** | ❌ 几乎全空 |
| `verify_user` / `verify_date` | **0 / 0** | ❌ 无复查 |
| `rectify_date` / `actual_rectify_date` | **0 / 0** | ❌ 全新 |
| `responsible_dept`（责任部门文本） | **0 / 110** | ❌ 全空 |
| `review_result` | **0 / 110** | ❌ 无复查结论 |
| `hazard_category` | **0 / 110（全空）** | ❌ 无分类 |
| `level`（等级） | **110 / 110 全为「一般」** | ⚠️ 无分级 |
| `hazard_source` | **110 / 110 全为 `daily_check`** | ⚠️ 无区分度 |

> 两点必须记录：
> 1. **等级 100% 为「一般」** ⇒ 任何"按等级设不同整改时限"的方案在当前数据下**等价于统一时限**。
> 2. **`hazard_category` 全空** ⇒ 按类别统计/分析全部无依据，隐患分析类需求当前无数据基础。

### 2.7 迁移的技术阻塞（B 模型的 NOT NULL 约束）

`hazard_record` 42 列中，以下列为 `NOT NULL`：

```text
hazard_code / task_id / employee_id / hazard_level / hazard_category
description / responsible_id / deadline_date / status / is_closed
```

⇒ 把 `hazards` 的 110 行迁入 B，必须为每行补齐：
- `task_id`（NOT NULL）—— 而 `hse_tasks` **0 行**，无法生成合法 task_id；
- `employee_id` / `responsible_id`（NOT NULL）—— 而隐患 9 个关联 ID 列 **0/110**，无 ID 可迁；
- `hazard_category`（NOT NULL）—— 而 A 的分类字段**全空**；
- `hazard_level`（NOT NULL）—— A 只有「一般」，可凑但不真实。

> **结论：迁入 B 在当前数据下不是"迁移"，是"重新造数"。**

## 4. 四个真实业务问题逐项取证

任务书 §三-3 要求核实四个业务需求。本轮逐项查证，**能给出事实的给事实，不能的标待核**。

### 4.1 是否需要「一条整改关联多条隐患」？

| 项 | 事实 |
|---|---|
| A | 整改内嵌在 `hazards` 单行内 ⇒ 天然 1 隐患 : 1 整改 |
| B | `rectification_task.hazard_id` 单值 ⇒ 1 整改 : 1 隐患（多条 task 可指向同一 hazard，即 1 隐患 : N 整改） |
| C | `hse_rectifications.hazard_id` 单值 ⇒ 同上 |
| 多对多 | **全库无中间表**（`risk_hazard_links` 是风险—隐患，且 0 行） |

> ⇒ **三套模型都只能表达「一条隐患 → 多条整改」，都不能表达「一条整改覆盖多条隐患」。**
> 若业务确实需要后者（例如"一次线路整改同时消除 5 条同类隐患"），**A/B/C 都不够，需 M:N 中间表**。
> **但本轮没有任何证据表明业务存在这个需求** —— 110 条隐患、69 条已整改，全部是逐条整改。
> ⇒ **登记为待业务确认（Q1），不作推荐。**

### 4.2 是否需要「复查留痕」？

| 项 | 能力 | 实际数据 |
|---|---|---|
| A | `review_result` / `review_date` / `reviewer_id` / `verify_user` / `verify_date` 五个字段 | **全部 0 / 110** |
| B | `review_record` 表（`review_result` / `review_score` / `is_final` / `reviewer_id`） | **1 行**（测试夹具） |
| C | `hse_reviews` 表（`result` / `score` / `comment` / `is_recurred` / `new_hazard_id`） | **0 行** |

> ⇒ **三套都能表达复查，三套都没有真实复查数据。**
> 「能不能留痕」不是选型问题（都能）；「要不要把复查作为关闭的必要条件」是**业务决策**，
> 已在 `DEC-A0205-04` 登记（四方案 A/B/C/D，其中方案 D「三条件含复查通过」的结果是 **0 条已整改**）。
> ⇒ 本简报不重复裁决该项，只在 §6 提示其与选型的耦合。

### 4.3 是否由 H5 承担隐患录入？—— **已经在承担，但数据不进 PG**

见 §2.5。补充三点影响：

1. **H5 闭环的字段口径与 A/B/C 都不同**：Worker 侧用 `category` / `level` 且**校验必须命中服务端权威清单**（`HAZARD_CATEGORIES`），
   而 A 表的 `hazard_category` 全空、`level` 全「一般」 ⇒ **两端字段语义不一致**。
2. **存在重复提交防护**：Worker 有 `hazardCidCache` / `hazardCidInflight`（幂等键 `sub|cid`），说明该链路**被当作正式生产功能在维护**，不是试验品。
3. **有 AI 识图填充**：`/api/mobile/hazard/ai-fill` 把现场照发给模型回填表单 ⇒ 若最终弃用该通道，这部分能力一并作废。

> ⇒ **待核（N1）**：飞书隐患表现有行数、字段、与 `hazards` 110 行是否有重叠。本轮无飞书访问授权，**不推测**。
> ⇒ **这是选型前最需要补的一份证据。**

### 4.4 历史数据能否安全迁移？

| 目标 | 可行性 | 阻塞点 |
|---|---|---|
| A 保持不动 | ✅ 最安全 | 无 |
| A → B | ❌ **不可行** | `task_id` / `responsible_id` / `hazard_category` 均为 NOT NULL，而源数据无对应值（§2.7） |
| A → C | ⚠️ 部分可行 | `measure` 110/110 可迁；`status` 可映射；但 `responsible_person_id` 无源（关联 ID 全 0），`department_id` 无源 |
| A 不动 + B 作子表 | ✅ 可行 | 需给 B 三表加 `hazard_id` 外键指向 A（**属新增字段，受 A02-01 §11 第 4 条约束，须先获批**） |

## 5. 四个方案逐项比较

> 任务书列出的 A/B/C/D 四选项。逐项给出：做法、优点、缺点、真实数据支撑、写入路径、引用范围、迁移风险、运维成本。

### 方案 A｜保留 `hazards` 为唯一事实源，其他模型按批准原则退役

| 维度 | 内容 |
|---|---|
| **做法** | A 唯一；B 四表 / C 两表 / 6 张零行表全部标记退役（归档或删除） |
| **优点** | ① 成本最低、零迁移；② 110 行真实数据不动；③ 前端活页面不动；④ 立即消除"四套模型"歧义 |
| **缺点** | ① **永久放弃"一整改多隐患"与"复查闭环"能力**（若业务未来需要，要重开）；② 飞书通道的隐患数据无处落；③ `hazards` 46 列里有 20 余列从未使用（`rectification` 2%、`verify_*` 0%），退役后这些列成为永久死列 |
| **真实数据支撑** | ✅ 强（110 行 + 69 条整改） |
| **写入路径** | Excel 导入 + Web 表单（活） |
| **引用范围** | `hazardService.js` / 隐患页 / 考核 HZD-001 |
| **迁移风险** | **零** |
| **运维成本** | 最低 |
| **需确认** | ① 是否接受"无复查闭环"？② 是否接受"一次整改只能对一条隐患"？③ 6 张零行表是否同意整表清理？ |

### 方案 B｜保留 `hazards` 为事实主表，未来按业务需要另行设计整改与复查模型

| 维度 | 内容 |
|---|---|
| **做法** | A 不动；不打 B/C 的现成表，**等业务明确需求后重新设计**整改表与复查表 |
| **优点** | ① 不背历史包袱（B 的 42 列里 `task_id NOT NULL` 就是包袱）；② 可以按真实业务设计（一整改多隐患、复查留痕都能支持）；③ 与 `DECISION-018 §3` 方向一致（A 为事实源 + 子实体） |
| **缺点** | ① **需求未清就无法开工** ⇒ 隐患样板第一段之后的页面全部停摆；② 重新设计意味着又一次 DDL；③ 「另行设计」容易被理解为"等以后"，实际可能无限期拖延 |
| **真实数据支撑** | ✅（A 的 110 行是唯一可用底座） |
| **写入路径** | 需新建（A02-01 §11 第 4 条：**选型前禁止新表/新字段**，故选 B 必须先有"选型已批准"这个前提） |
| **引用范围** | 不影响现有引用；考核 HZD-002 继续为 0（因 C 表空） |
| **迁移风险** | 低（A 不动） |
| **运维成本** | 中（一次新设计） |
| **需确认** | ① 新设计的边界（几条表）？② 何时做（是否阻塞样板）？③ 与飞书通道如何对接？ |

### 方案 C｜保留 `hazards` 为事实主表，评估启用现有 `hse_rectifications` 和 `hse_reviews`

| 维度 | 内容 |
|---|---|
| **做法** | A 不动；给 `hse_rectifications` / `hse_reviews` 补写入路径（接线 + 补 `hazard_id` 外键），启用 C |

## 7. 专业建议（**建议，待负责人批准**）

### 7.1 建议结论

> **建议采用方案 B 的变体：A 为唯一事实源，B 的三表作为"整改子实体"挂在 A 上（补 `hazard_id` 外键），C 暂不启用、改为只读视图，6 张零行表整表标注退役。**
>
> 但这**不是四选一里的现成选项**，它是把 `DECISION-018 §3` 的建议补上三处修正后的版本。

### 7.2 为什么不是纯 A、纯 B、C 或 D

| 判断 | 理由（均基于实测） |
|---|---|
| **不建议 D** | 技术不可行（NOT NULL 无源）+ 迁移后无消费方（唯一接口必然 500、前端 0 调用）+ 要背 9 行夹具的历史 |
| **不建议纯 C** | 0 行 = 零业务验证。启用它等于同时启用 4 个已在读的消费方，而 `is_overdue` 谁维护、逾期怎么算都没有现成规则；且它依赖 `hse_tasks`（0 行），一旦启用就把隐患域和任务域绑死 |
| **不建议纯 A（全退役）** | 会把"复查闭环"和"一整改多隐患"永久关死，而这两个能力是否被需要尚未由业务确认（Q1/Q2）。全退役是不可逆的 |
| **不建议纯 B（完全另设计）** | 「另行设计」缺少触发条件，容易无限期拖延；而隐患是 `DECISION-015` 选定的首个样板域，拖住它等于拖住整个前端优先路线 |

### 7.3 建议方案的三个关键设计点（每点都有实测依据）

1. **A 保持为事实源，不改 A 的 46 列** —— 因为 A 的列里已有 20+ 是死列（`rectification` 2%、`verify_*` 0%），
   再加列只会加深"宽表"问题。整改/复查**出表**是正确方向。
2. **B 的三表作为子实体**，但必须：
   - 去掉 `task_id NOT NULL`（否则 0 行 `hse_tasks` 使整条链不可用）；
   - 补 `hazard_id` 外键指向 `hazards(id)`，删除策略取 `RESTRICT`（与 `hse_reviews` 先例一致，历史保护）；
   - 清空 9 行夹具（否则永远无法区分测试与真实）。
   > ⚠️ 以上三项**全部是新增/修改字段与外键**，受 `A02-01 §11 第 4 条` 约束，**必须"选型已批准"后才可实施**。
3. **C 改为只读视图**，不改结构、不接写入 —— 因为已有 4 个消费方在读它，
   直接弃表会打断 `assessmentScheduler` / `statisticsService` / `hse-chain` / `hse-statistics`；
   而 0 行数据使得"改成视图"零数据损失。

### 7.4 与飞书通道的处置建议（本简报独有的第四个问题）

> 无论选哪个模型，**都必须回答"飞书侧隐患数据进不进 PG"**。建议：
> **先取证（N1），再决定**。若飞书表有存量数据，则选型需增加"导入/同步通道"这一维度，
> 现有 A/B/C/D 四选项**都不包含这个维度**。
