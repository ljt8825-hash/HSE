## 二、B1 裁决｜待整改 / assigned

- **业务裁决**：不将 `assigned` 作为 PG canonical 生命周期状态；最终生命周期**不增加**独立「已分派」状态。
- 「谁负责整改」通过**责任人 / 责任部门 / 责任组织**等责任字段表达，而非一个状态位。
- **建议生命周期**：
  ```
  discovered → processing → pending_review → closed
  ```
- 注意：这不取消「分派」业务动作。未来若需分派功能，可增加：`assign` 动作、责任人字段、分派时间、分派记录/事件；但**不得仅为了表示责任人而增加 assigned 状态**。

---

## 三、B2 裁决｜待验收 / pending_review

- **业务裁决**：PG canonical 状态 = `pending_review`；业务中文名称统一 = **「待复查」**。
- Feishu 当前「待验收」属于**来源系统词汇**（Worker/H5 业务侧用语），**暂时不修改 Feishu/Worker**。
- **禁止**直接把 Worker 文案改成「待复查」。
- 未来 Feishu→PG 映射时再统一处理（见 §14 延期说明）。

---

## 四、B3 裁决｜closed / 已闭环

- **业务裁决**：PG canonical = `closed`；业务中文名称 = **「已闭环」**。
- 重要规则：`closed` 表示**「该隐患已经完成当前闭环流程」**。
- 但：**「数据库 status=closed」不能反向证明历史记录一定经过独立复查。**
- 尤其当前历史数据：60 条 closed；`hse_reviews = 0`。**这些历史数据不得伪造 review 记录。**
- 因此：**「状态」与「闭环证据」必须分离**（详见 §10）。

---

## 五、B4 裁决｜pending_review 的业务名称

- **业务裁决**：`pending_review` = **「待复查」**；不使用「待验收」作为 PG canonical UI/业务名称。
- 理由：本系统主要服务于环卫、市政、绿化等日常安全管理。该动作的业务本质是——整改完成后，由具有相应权限的人员对整改结果进行**复查确认**，不是工程项目意义上的正式验收。

---

## 六、B5 裁决｜已整改

- **业务裁决**：**「已整改」 ≠ closed**。
- 推荐流程：
  ```
  待整改 → 整改中 → 提交复查 → 待复查 → 复查通过 → 已闭环
  ```
- 整改人员完成整改，只能证明「整改动作完成 / 提交复查」，**不能单独证明「隐患已经闭环」**。
- 因此：**不得把「已整改」直接映射为 PG closed**（当前代码 `NON_LIFECYCLE_STATUS` 将 已整改→closed，属待治理差距，见 §12）。

---

## 七、B6 裁决｜expired

- **业务裁决**：`expired` **不作为** PG canonical 生命周期状态。
- `expired` 是根据：**当前时间 / 隐患发现时间 / 整改期限 / 当前生命周期状态** 计算出来的**「期限属性」**。
- 建议模型：
  ```
  生命周期状态：discovered / processing / pending_review / closed
  期限属性：   normal / expiring / expired / resolved
  ```
- **expired 不得进入 `hazards.status`**。

---

## 八、B7 裁决｜closed reopen

- **业务裁决**：**允许 closed 重新打开**，但必须是**受控动作**。
- 推荐：
  ```
  closed → reopen → discovered
  ```
- reopen 必须：
  1. 有权限控制；
  2. 必须填写重新打开原因；
  3. 保留原 closed / review 历史；
  4. 形成事件或审计记录；
  5. 不删除原有复查记录；
  6. 不直接覆盖历史记录。
- **本任务不实现 reopen。**

---

## 九、目标业务状态机（裁决后状态机）

```
            ┌─ reviewPass ─▶ closed
            │
discovered ─┴─▶ processing ─▶ pending_review
                                   │
                                   └─ reviewFail ─▶ processing

closed ──reopen──▶ discovered
```

- `expired` **不属于**上述生命周期状态（见 §7，作为期限属性派生）。
- 生命周期仅 4 态：`discovered` / `processing` / `pending_review` / `closed`。

---

## 十、状态与证据分离原则

1. `hazards.status` 仅表达**当前生命周期位**，不承载「是否经过独立复查」的证明。
2. **复查证据**独立存放于 `hse_reviews`（reviewer_id / review_date / review_result / review_code）。
3. `status = closed` **不反向推导**「已完成独立复查」。
4. 历史 60 条 closed 因 `hse_reviews = 0`，其 `closed` 仅表示「当时被标记为已闭环」，不构成复查证据。
5. 后续统计「复查通过率」必须依赖 `hse_reviews`，不得由 `status` 派生。

---

## 十一、历史数据处理原则

正式登记当前 `safety_dashboard_dev` 实况：

| 项目 | 数量 |
|---|---|
| closed | 60 |
| discovered | 50 |
| processing | 0 |
| pending_review | 0 |
| hse_reviews | 0 |
| hse_rectifications | 0 |

**60 条历史 closed 禁止**：
1. 批量补造 `hse_reviews`；
2. 虚构 reviewer；
3. 虚构 review_date；
4. 虚构 review_result；
5. 因 `status=closed` 就认定已经完成独立复查。

后续若要处理历史数据：必须**另立历史数据治理任务**。**本任务不处理。**

## 十七、安全设计原则（后续开发必须遵守）

1. Feishu 状态**不能**直接覆盖 PG canonical `status`；
2. Worker 生产链路**不因本任务**修改；
3. Feishu→PG 映射**另立 B03**；
4. 历史 closed **不补造**验收证据；
5. review evidence 与 status **分开**；
6. expired 与 lifecycle status **分开**；
7. reopen **必须留痕**；
8. 「已整改」**不能**自动变成 closed；
9. 不允许通过前端隐藏按钮代替后端权限控制；
10. 后续状态流转**必须以后端状态机为权威**。
