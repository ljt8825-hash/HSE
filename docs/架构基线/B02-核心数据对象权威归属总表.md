## 1. 本轮方法（与 A02-05 的差异）

| 项 | A02-05 做法 | B02 做法 | 原因 |
|---|---|---|---|
| 数据量 | 部分沿用 A02-01 | **366 张 public 表逐表 `COUNT(*)`**（生成 `UNION ALL` 脚本一次执行，非 `n_live_tup`） | `pg_stat_user_tables.n_live_tup` 在本库对多表失准（`employee` 显示 0 实为 3417） |
| 写入源 | 表格结论为主 | **静态 SQL 全量抽取**（`INSERT INTO <t>` 198 张 / `UPDATE <t> SET` 134 张）+ 动态表名写入单列 | 「0 处静态 INSERT」不等于「无写入」，动态表名必须单独识别 |
| 读取源 | 以页面/模块推断为主 | 前端 api 模块 → 端点 → 路由 → 服务的**抽样贯通**（重点域逐个核实） | A02-05 存在「页面已建」但前端 0 调用的误判先例 |
| 重复判定 | `DUP` 单标签 | **D1~D7 七分类**（见 B02-03） | 字段相似 ≠ 重复 |
| 外部系统 | 归入「EXTERNAL 通道」 | 独立成表（H5/Feishu/WPS/PG/Web/Excel 六源） | 外部系统可能是事实源，也可能只是镜像 |

### 1.1 本轮新增的三个取证手段

1. **动态表名写入识别**（`grep -E "(INSERT INTO|UPDATE) \\\$\{"`）→ 发现 `checkLedgerFactory.js`（检查台账工厂，按 `table` 变量写）与 `importExcelService.js:1304`（按 `moduleConfig.targetTable` 写）两条**通用写入通道**。这解释了「表有数据但静态 SQL 计数为 0」的现象。
2. **导入模块映射抽取**（`importShared.js`，26 个模块）→ 得到「模块 → targetTable → 是否内存模式 → 写库白名单列数」的完整对照（见 §3）。
3. **空壳表存在性对照**（`information_schema` vs `targetTable`）→ 6 个导入目标表在库中**不存在**。
