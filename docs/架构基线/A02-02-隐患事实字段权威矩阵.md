## 4. `status` 的语义割裂（单列展开）

| 观察 | 事实 |
|---|---|
| 值域 | 仅 `closed`(60) / `discovered`(50) |
| 状态机定义（`hazardService.js:140-145`） | `discovered` → `processing` → `pending_review` → `closed` |
| 实际到达的中间态 | `processing` 0 行、`pending_review` 0 行 |
| `closed` 是否经 `review(pass)` | 否 —— `review_result` 0/60、`review_date` 0/60、`reviewer_id` 0/60、`hse_reviews` 0 行 |
| `closed` 是否经 `close()` | 否 —— `close()` 会写 `updated_at=CURRENT_TIMESTAMP`，而 60 行的 `updated_at` 与 `created_at` **精确相等** |
| `closed` 的真实来源 | `p3-04-02-migrate-legacy-status.js:112` 词汇迁移（该 SQL 不含 `updated_at`） |
| 迁移前的值 | `已完成`（由第 1 代导入的 `statusMap {'是':'已完成'}` 产生，该映射已于 P3-04-00.2 移除） |

> **`status` 是事实字段（值真实存在），但 `closed` 的业务含义不是"复查通过"，而是"Excel 某列填了 是"。**
> 任何把 `status='closed'` 读作"已复查/已验收/已闭环合规"的下游逻辑，都建立在错误语义上。

## 5. 能否计算「是否超期」——字段组合穷举

| 组合 | 所需字段 | 是否齐备 | 结论 |
|---|---|---|---|
| 绝对期限法 | `deadline` 或 `deadline_date` vs `fix_date` / `now()` | ❌ 期限 0/110 | **不可计算** |
| 相对期限法 | `hazard_date` + `deadline_days` vs `fix_date` | ⚠️ 字段齐备，但 `deadline_days` 全 30（默认值） | **可算，但不是事实**（属业务规则推导） |
| 状态标记法 | `is_overdue` 类布尔列 | ❌ **本表无此列** | **不可计算** |
| 验收日期法 | `verify_date` vs 期限 | ❌ `verify_date` 0/110 | **不可计算** |
| 整改提交时点法 | `rectify_date` vs 期限 | ❌ `rectify_date` 0/110 | **不可计算** |
| 外部任务超期标记 | B 模型 `rectification_task` / C 模型 `hse_rectifications.is_overdue` | ❌ 两表均 0 行 | **不可计算** |

**判定：**

> **当前事实数据不足，无法计算「超期」。**
> 唯一字段齐备的路径是 `hazard_date + deadline_days`，但 `deadline_days` 全为列默认值 30，不代表任何一条隐患的真实整改期限设定；把它当期限使用属于**引入未获业务确认的规则**，不得用于考核。

## 6. 需求字段 vs 实际字段（缺口对照）

按 HZD-002 的 `calc_formula`（超期整改任务条数 × 3）与 `rule_config`（`transmit` / `max_deduct` / `deduction_per_unit`）反推所需字段：

| 需求 | 需要的字段 | `hazards` 实况 | 缺口 |
|---|---|---|---|
| 判定"超期" | 期限（绝对日期） | `deadline` 0、`deadline_date` 0 | ❌ **缺** |
| 判定"未完成" | 完成标记 / 完成日期 | `fix_date` 69（有值即可视作完成，但 41 条无值） | ⚠️ 部分 |
| 定位"责任人" | `employee_id` | `responsible_id` 0、`fixer_id` 0 | ❌ **缺** |
| 定位"上级（传导）" | 责任人的组织关系 | 无 `responsible_id` ⇒ 无法起查 | ❌ **缺** |
| 计"条数" | 行级唯一键 | `id` / `no` / `description`（109 唯一 / 110 行） | ✅ 有 |
| 限"上限 30 分" | 无需字段（代码内计算） | — | ✅ |
| 归属周期 | 事件日期 | `hazard_date`（隐患日期）或 `fix_date` | ⚠️ 该用哪个未定 |

> 结论：7 项需求中 3 项硬缺（期限、责任人、上级起查点），1 项语义未定（周期归属日期）。

## 8. 本章结论

```text
HAZARDS 总列数 = 46
真实有值（业务事实）= 12 列
默认值/常量冒充 = 5 列（level / hazard_source / deadline_days / related_risk_ids / status 的 closed 部分）
全空 = 27 列 + 2 个系统时间列

事实字段清单（可安全用于业务口径）=
  id, no, hazard_date, description, measure, checker(文本), fixer(文本), fix_date, remark

不可用于考核的字段 =
  deadline(空), deadline_date(空), responsible_id(空), fixer_id(空), reviewer_id(空),
  review_result(空), review_date(空), rectify_date(空), verify_date(空)

可计算"超期" = ❌ 否（无期限事实）
唯一齐备但不可用的组合 = hazard_date + deadline_days（default 30，非业务设定）
```
