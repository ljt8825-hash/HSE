# A02-04-05｜考核事实归属与架构缺口清单

> 审计对象：考核域全部事实载体（7 张有数据表 + 4 张空壳表 + 1 张旧模型残留表 + 3 套自算服务）
> 审计方式：**只读**。基于 A02-04-01~04 四份实测数据 + 代码行号证据，做事实归属判定与缺口分级。
> 本文**不设计、不修复、不重构**，只给「现状是什么、缺口在哪、影响谁」。
> CODE CHANGE = 0 / DDL = 0 / DML = 0 / CONFIG CHANGE = 0 / PRODUCTION CHANGE = 0。

---

## 1. 结论摘要

考核域存在 **4 个并行事实模型**，其中只有 **1 个**同时满足「有写入口 + 进总分 + 可追溯」：

| 模型 | 载体 | 行数 | 有写入口 | 进总分 | 页面可见 | 定性 |
|---|---|---:|---|---|---|---|
| **A** | `hse_assessment_deduction` + `target.score_total` + `score(AUTO_TOTAL_SNAPSHOT)` | 940 + 925 + 942 | ✅ | ✅ | ✅ | **唯一事实源** |
| **B** | `hse_assessment_score` 的 2728 条指标行 | 2728 | ❌ **无** | ❌ **否** | ✅ | **僵尸数据（只读遗产）** |
| **C** | `assessment_records`(5) + `metric_rule`(0) + `score_detail`(0) | 5 | ❌ | ❌ | ❌ | **旧模型残留 + 空壳** |
| **D** | 无表（服务层硬编码自算） | — | ❌ | ❌ | ✅ | **页面幻觉（两套算法）** |

> 隐患域的问题叫「A/B/C 三模型」；考核域的问题更严重：**多了一个 D —— 根本没有表，纯靠页面自己算。**

## 2. 模型 A：唯一事实源

### 2.1 构成

```text
事实层  hse_assessment_deduction      940 行（有效 663 / 14,441.00 分）
           ↓  computeCategoryCappedScore()（类别封顶）
快照层  hse_assessment_score          942 行（metric_code='AUTO_TOTAL_SNAPSHOT'）
           ↓  recalculateTarget()
结果层  hse_assessment_target         925 行（score_total / grade）
```

### 2.2 可追溯性

| 字段 | 效果 |
|---|---|
| `source_table` | 938/940 非空（99.8%） |
| `source_id` | 177/940 非空（**18.8%**） |
| ⇒ 能追到「哪一条业务记录」 | **18.8%** |
| ⇒ 只能追到「哪张表」 | **81.2%** |
| `metric_id` | 783/940 非空（83.3%），157 行孤儿码无指标定义 |

### 2.3 模型 A 的硬缺口

| 缺口 | 事实 |
|---|---|
| 快照无来源 | `AUTO_TOTAL_SNAPSHOT.data_sources` **0/942 非空**（全 NULL）⇒ 汇总不可解释 |
| 无审核闭环 | 940 行中 `pending 818 / approved 122`，`rejected`/`adjusted` **0** ⇒ 审核功能 87% 未使用 |
| 从未冻结 | `frozen` 状态 **0 行**（cycle 与 target 均 0） |
| 排名永不生成 | `rank_all`/`rank_township` **0/925 非空** |
| 上限设计失效 | manager 上限合计 **195** > 总分 100；admin **200** > 100；2 类 `max_deduct IS NULL` |

## 3. 模型 B：2728 条僵尸指标行

### 3.1 判定依据（四重证据，全部来自 A02-04-01 §6.3）

| 证据 | 结论 |
|---|---|
| 全仓 `insert into hse_assessment_score`（大小写不敏感）仅 **2 处**，均写 `AUTO_TOTAL_SNAPSHOT` | **代码无法写入指标行** |
| 2728 行 `created_at` 只落在 3 个秒级时间点（2026-08-27 08:55:59 / 17:36:03 / 17:36:20） | **一次性批量灌入** |
| 18 个指标码含 `RSK-001`（表不存在）/`INC-001`（无载体）/`NEG-001~003`（REPLACED） | **不管有无实现一律铺行** |
| 2728 行中扣分非零的仅 **2 行 / 13.00 分** | **99.93% 是零值占位** |

### 3.2 为什么叫「僵尸」而不是「历史数据」

| 特征 | 说明 |
|---|---|
| 不能再生 | 重跑评分只更新 942 条快照，指标行原封不动 |
| 不能更新 | 无 UPDATE 语句引用它们（只有 `syncTargetScoreSnapshot` 更新快照行） |
| 不影响结果 | 总分链完全不读指标行（`computeCategoryCappedScore` 只 SELECT deduction） |
| 但会误导 | 页面/接口若按指标维度展示，用户会看到 18 个指标各得多少分 —— **而这些分数与最终总分无因果关系** |

### 3.3 模型 B 的具体危害：`HZD-001` 的 13 分

| 项 | 值 |
|---|---|
| 指标行扣分 | 刘金涛 12.35 / 张康 0.65，合计 **13.00** |
| 指标行终分 | 7.65 / 19.35 |
| 快照扣分（同 target 同周期） | **0.00** |
| 人级总分 | **100.00** |
| 等级 | **A** |
| 隐患整改率（刘金涛） | **38%** |

> **结论：隐患整改 38% 的部门经理，考核 100 分 A 级。**
> 这不是业务判断，是「指标行算出的扣分被总分链丢弃」这一技术事实的直接结果。

### 5.2 三套扣分算法对照

| 事实类型 | A（真实） | D-1（死代码） | D-2（页面在用） |
|---|---|---|---|
| 事故 | 100 分/条（否决） | ×15 | 3/10/20/50/100 |

| 结果落库 | ✅ | ❌ | ❌ |

## 7. 重复统计风险

| 风险 | 事实 | 影响 |
|---|---|---|
| **A 内部重复** | 快照行 `raw_value = deduction_total`（同一数存两列）；`score_auto = score_total`（925/925 恒等） | 若有人把 `raw_value` 当「原始值」再求和，会重复计扣分 |
| **A 与 D-2 重复** | 分析页 `deduction` 与 `hse_assessment_deduction` 描述同一业务 | 两个数字，用户无法判断哪个是权威 |
| **A 与 A02-01 表重复** | A02-01 §3 列 29 指标「实际扣分」663（有效）vs A02-02 §5.2 列 940（全表） | 合法口径差异，但易被误读为矛盾 |
| **B 内部无重复** | 指标行 `(target, cycle, metric_code)` 无重复组 | ✅ |
| **B 与 A 不重复** | 指标行 2728 与快照 942 是不同 `metric_code`，无重叠 | ✅ 但**B 也不贡献 A** |
