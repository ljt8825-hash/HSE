## 1. 分类口径

任务书 §十六要求对每个数据对象标记六类之一：**事实源 / 派生源 / 展示源 / 历史源 / 测试源 / 待核实**。
本文的口径定义先写明，避免"事实源"被泛化使用：

| 标签 | 判定标准（必须同时满足） |
|---|---|
| **事实源** | ① 业务动作直接写入；② 有唯一标识；③ 不允许人工改写；④ 是其他一切的取数起点 |
| **派生源** | 只由事实源计算/聚合而来，本身不承载新事实 |
| **展示源** | 只读呈现，删掉不丢失任何业务事实 |
| **历史源** | 曾承载事实但写入路径已停/已废弃，数据保留供追溯 |
| **测试源** | 承载联调/试用数据，正式业务不应依赖 |
| **待核实** | 证据不足或来源无法闭环 |

> 关键区分：**"有表 = 事实源"不成立**。PG `hazards` 有 110 行真实业务描述，但写入路径已停 3 个月，
> 按本文口径它是**历史源**，不是当前事实源。

## 3. 按域重排（避免把不同域混成一张表）

隐患域与巡查域共用"隐患"这个词，但**不是一个域**。混排会导致错误的"打通"结论。

### 3.1 隐患域（Hazard）

```text
事实源候选 ─┬─ 飞书 隐患表 tblnyMjxtxjpP08q   （2 条，唯一有活写入）
            └─ PG hazards                      （110 条，写入已停 → 历史源）
                        │
展示源 ─────────────────┴─► Web 页面 / overview 聚合 / 导出
```

| 对象 | 标签 | 理由 |
|---|---|---|
| 飞书隐患表 | **事实源（候选）** | 唯一由业务动作直接写入；但仅 2 条，规模不足以证明它是"主"事实源 |
| PG `hazards` | **历史源** | 写入路径已停；数据是历史回填 |
| Web 隐患页 | **展示源** | 只读 |
| PG `hazard_record` 4 表 | **历史源 / 空载体** | 有结构无数据 |
| PG `hse_rectifications`/`hse_reviews` | **待核实** | 有代码无入口 |
| 仓库 Excel | **历史源** | 66 条的源 |

### 3.2 巡查 / 三违域（Grid Inspection）

```text
WPS 多维表格 ──Pull──► PG grid_inspection_records ──► Web / 考核
（事实源）              （事实源副本）                （展示 + 派生）
                              ▲
手机 H5 ──► 飞书主台账 ──╳────┘   ← 同样没有同步，且是另一个域
（事实源）
```

| 对象 | 标签 | 理由 |
|---|---|---|
| 飞书主台账 1608 条 | **事实源** | H5 巡查/三违的真实落点，持续增长至 2026-10-27 |
| WPS 多维表格 | **事实源** | 桌面端巡查登记的源；同域双事实源（已知问题） |
| PG `grid_inspection_records` | **事实源（WPS 的副本）** | 08/09 月数据来自 WPS Pull + Excel 导入；10 月 0 |
| `grid_record_sync_map` | **派生源** | 映射与 hash |

> ⚠️ 注意：**飞书主台账与 WPS 多维表格是同一业务域的两个事实源**，且互不同步。
> 这不是 B00 要解决的问题，但它决定了"隐患域"与"巡查域"的结论不能互相套用。

## 5. 关键判断：PG `hazards` 是不是"事实源"？

任务书 §九要求记录"事实源候选"，但不得直接决定最终架构。这里给出**判断依据**而非结论：

### 5.1 支持它是事实源的证据

- 110 行是真实业务描述（"柴胡店收运车570Q左刹车灯不亮、右转向不亮"），不是造数（`is_demo` 全 false）
- 有 `conflictKey='description'` 的业务去重规则
- 有状态流转（`discovered` 50 / `closed` 60）

### 5.2 反对它是事实源的证据

- **写入路径已停**：最后一次导入 2026-08-24；`import_logs` 无 9 月/10 月作业
- **3 个字段是列默认值**：`hazard_source='daily_check'`、`level='一般'`、`status` 初值 `'discovered'`
  → 不是业务方填的，是 DDL 默认值
- **60 条 closed 无一条有复查证据**：`review_result`/`verify_date`/`rectify_date` 全 0/110（A02-05 C1 结论）
- **无唯一业务编号列**：连"隐患编号"都没有，只有整型序号 `no`（且 110 行只有 66 个不同值）
- **无人员 ID、无组织、无区域**：`finder_id`/`checker_id`/`responsible_dept`/`township`/`hazard_category` 全空
- **44 条源文件不在仓库**：来源不可闭环

### 5.3 结论（分类，非裁决）

> **PG `hazards` = 历史源。**
> 理由是判据可验证：写入停止 + 默认值冒充业务值 + 关闭无证据 + 无唯一键 + 来源部分不可闭环。
> 它**不满足**本文 §1 的"事实源"四条判据中的②（唯一标识）③（不允许人工改写）④（其他一切的取数起点）。

**这不等于"应该迁到飞书"或"应该废弃 PG"。** 选型留给 B02。

## 6. 与 A02-05「12 域」结论的对接

A02-05 把隐患域判为 🔴 不可用（D4），依据是"多套模型 + 事实源不明确"。本表把这条结论具体化：

| A02-05 表述 | 本表细化 | 是否修正 |
|---|---|---|
| D4 隐患域「事实源不明确」 | **事实源其实明确**：飞书隐患表是唯一活写入方，PG 是历史源 | **需修正**：不明确的是"应该用哪个"，不是"哪个在写" |
| D4「多套模型」 | 实测为 **4 通道 + 11 表**（A02-06 已修正） | 沿用 A02-06 |
| "H5 已上线，隐患数据未回 PG" | **成立，且更严重**：飞书隐患表只有 2 条，与 PG 110 条零重叠 | 补强证据 |
| "H5 → 飞书 已上线运营" | **分域看**：主台账 1608 条为证；隐患子模块仅 2 条 | **需补充限定语** |

> ⚠️ 「H5 → 飞书 已上线运营」这句话在隐患域需要加限定：
> **通道是通的、代码是在跑的、但隐患业务量接近于零。**
> 报送材料若写"H5 已实现隐患闭环管理"，与"隐患表 2 条记录"这一事实存在张力，建议 B04 时一并核对口径。

## 8. 判定

```text
隐患域事实源      = 1 活（飞书隐患表，2 条）+ 1 停（PG hazards，历史源，110 条）
隐患域事实源冲突  = 无（两套互不同步、无重叠，故无冲突，但也无一致性可言）
隐患域派生/展示   = Web 页面读 PG；读取的是历史快照
巡查域事实源      = 2 并存（飞书主台账 1608 / WPS 多维表格，Pull 已停）
最终权威源        = 未裁决（留 B02）
A02-05 D4 结论    = 需修正一处措辞："事实源不明确" → "有唯一活写入方，但业务量近乎为零"
```
