## 1. 问题的一句话表述

> **跨模块关联"同一个人"，系统里有四种写法（`employee_id` / `employee_code` / 姓名 / 身份证），
> 没有任何一处规定"哪一种为准"。现在有一条**正在产生扣分**的链路选了其中最弱的一种（姓名），
> 而这条链路决定了全部考核扣分的 77.92%。**

>    说明主数据本身未与测试数据隔离（对应冻结条件 9 的 PARTIAL）。

### 2.3 正在运行的归因链路（问题最集中的地方）

`server/services/gridCompletionService.js:229-238` —— 计算「实巡次数」，供 `HSE-KPI-SAF-004` 扣分：

```js
`SELECT personnel_name,
        COUNT(*) FILTER (WHERE inspection_date >= $1 AND inspection_date < $2)::int AS yc,
        COUNT(*) FILTER (WHERE inspection_date >= $3 AND inspection_date < $4)::int AS mc
 FROM grid_inspection_records
 WHERE personnel_name = ANY($5)
   AND inspection_date >= $1 AND inspection_date < $2
 GROUP BY personnel_name`
```

实测 `grid_inspection_records`（2069 行）：

| 列 | 填充 | 说明 |
|---|---:|---|
| `personnel_name` | **2069 / 2069 = 100%** | 归因唯一依据 |
| `employee_code` | **0 / 2069 = 0%** | 列存在但从未写入 |
| `inspector_employee_id` | **17 / 2069 = 0.8%** | 形同未用 |
| `grid_id` | **1741 / 2069 = 84.1%** | 有值但**未参与归因** |
| `source_channel` | **0 / 2069** | 无法分辨来源 |
| `attribution_status` | **0 / 2069** | 无归因状态 |

**姓名匹配的实际准确率（本轮首次量化）**：

| 口径 | 结果 |
|---|---|
| 不同姓名数 | 63 |
| 姓名层：可唯一匹配 | 62 / 63 |
| 姓名层：未匹配到任何人 | 1 |
| 姓名层：对应多人（歧义） | **2** |
| 记录层：唯一命中 | **1995 / 2069 = 96.4%** |
| 记录层：歧义（同名多人） | **73** |

> ⇒ **2069 条巡查记录中有 74 条（3.6%）的归因不可靠**。
> 这 74 条对应的扣分，可能记到了同名的另一个人头上，也可能漏扣。**系统不会报错。**

## 4. 四个方案逐项比较

> 任务书 §三-2 要求每个方案说明：优缺点、历史数据处理、重名与离职风险、
> 对 SAF-004 的影响、跨模块改造范围、需业务负责人确认的事项。

### 方案 A｜统一使用 `employee_id`

| 维度 | 内容 |
|---|---|
| **做法** | 所有业务表的人员关联一律用 `employee.id`；`employee_code` / 姓名降为可选展示 |
| **优点** | ① 结构最强，可加 FK，DB 层可约束；② 改名/换工号不影响历史；③ 重名无歧义；④ `employee` 已有 40 条 FK 先例，模式不新创 |
| **缺点** | ① 只改 ID 不解决"怎么从台账拿到 ID"——Excel 台账通常只有姓名或工号；② 175 张只有 `*_name` 的表全部要加列；③ 业务方看不到 ID，报表仍要 join |
| **历史数据处理** | 必须建立"名称/工号 → id"解析并**记录解析依据与置信度**。按姓名解析的，重名 236 组必须 fail-closed（不猜），进人工清单；`violations` 1451 行（姓名空串 91%）基本无法回填，只能标 NA |
| **重名风险** | 高，但可控 —— 只在"解析"环节出现，解析后结构上不可能歧义 |
| **离职人员风险** | ✅ **最优**：`id` 不因离职失效，历史事实继续指向同一个人；但现有 `employment_relationship_status` 全空，无法标记在职状态，需补 |
| **对 SAF-004 影响** | 姓名匹配换成 id 匹配。口径（1 分/次）不变，但**74 条（3.6%）歧义/未命中的记录会从"错挂"变成"可判定"**。若要求 fail-closed，这 74 条会变成"未归因"，扣分总额可能下降 |
| **跨模块改造范围** | 60 表已有 `employee_id`（可直接用）；**27 表有 `employee_code` 需改键**；**175 表 `*_name` 需加列**；13 处 `personnel_id` 需统一命名；导入白名单 27 模块中 3 处显式列清单需改。**规模最大** |
| **需负责人确认** | ① 历史记录允许"无 id"（NA）吗？② 解析不出来的走人工清单由谁处理？③ 是否同步引入 FK 约束（会阻塞脏数据写入）？ |

### 方案 B｜统一使用 `employee_code`

| 维度 | 内容 |
|---|---|
| **做法** | 所有关联用 8 位工号；ID 只作内部主键 |
| **优点** | ① **业务方看得懂**，Excel 台账通常有工号列；② 已有 27 表在用；③ 比姓名稳定得多 |
| **缺点** | ① **148 人无 code（4.3%）**，这批人无法用 code 关联；② **21 条格式异形**（3/9/11/14/15 位），说明 code 不是严格受控编码；③ `uk_employee_code` 是**部分唯一索引**（`is_deleted=false`）⇒ 软删后 code 可被复用，历史记录的 code 可能指向两个人；④ 仍要 join 才能拿到 id，等于多一跳 |
| **历史数据处理** | 需先补 148 人 code、清洗 21 条异形、评估"软删复用"影响；巡查表虽有 `employee_code` 列但 **0/2069 填充**，仍要全量回填 2069 行 |
| **重名风险** | ✅ 规避（code 唯一）；但 code 缺失的 148 人退回姓名，重名问题在这 148 人内仍然存在 |
| **离职人员风险** | ⚠️ 若 code 被复用（软删后可复用），离职者的历史记录会"继承"给新员工 —— **这是本方案最严重的隐患**，需业务确认 code 是否永久不复用 |
| **对 SAF-004 影响** | 归因从"姓名匹配"改为"code 匹配"，准确率取决于回填质量；对 148 无 code 者仍要走姓名兜底 |
| **跨模块改造范围** | 27 表已有 `employee_code`；需新增约 60 表的 code 列；175 表 `*_name` 同样要加列。**规模与方案 A 接近，但多一层"外部键→内部键"映射** |
| **需负责人确认** | ① 工号是否**永久唯一、离职不复用**？② 148 无工号人员如何处置（补录 / 用身份证兜底）？③ 是否接受"部分唯一索引"带来的复用风险？ |

### 方案 C｜内部 `employee_id` + 业务展示 `employee_code` + 姓名仅展示

| 维度 | 内容 |
|---|---|
| **做法** | 事实键 = `employee.id`（FK）；业务键 = `employee_code`（录入/核对用）；姓名 = 展示缓存，由写入层生成 |
| **优点** | ① 结构上最稳（事实键可约束）；② 业务方仍用熟悉的工号；③ 改名不影响；④ **与 `DECISION-003` 完全一致**，不是新方案；⑤ 解析顺序已有约定（phone → code → name，fail-closed） |
| **缺点** | ① 需要"三层"治理：写入层必须统一生成缓存列，否则缓存会与事实不一致（这正是 `DECISION-003` 提到的"文本缓存列生成器"尚未设计）；② 三列并存，新开发者容易写错层；③ 解析链依赖 phone（**59% 缺失**），实际可用顺序要重排 |
| **历史数据处理** | 与方案 A 相同（需解析 + fail-closed + 人工清单），额外需要"缓存列生成器"改造，把现有 268 个 `*_name` 列改为"由写入层维护" |
| **重名风险** | ✅ 最低（解析阶段 fail-closed，落库后事实键唯一） |
| **离职人员风险** | ✅ 最优；但需补在职状态字段（现 `employment_relationship_status` 全空） |
| **对 SAF-004 影响** | 同方案 A；额外好处是 `personnel_name` 保留为缓存，页面显示不变、无需改前端 |
| **跨模块改造范围** | 最大（= 方案 A + 缓存生成器 + 解析服务） |
| **需负责人确认** | ① 是否确认 `DECISION-003` 有效并转入实施？② 缓存列由谁生成（服务层统一 / 触发器）？③ phone 缺 59% 时解析顺序如何调整？ |

### 方案 D｜维持现状，仅对关键链路增加校验与告警

| 维度 | 内容 |
|---|---|
| **做法** | 不动结构；在 `gridCompletionService` 等关键点加"匹配到多人/未匹配"的检测与告警 |
| **优点** | ① **零改造**，可在 1 天内上线；② 立刻让 74 条歧义记录可见；③ 不改导入模板，不影响现有台账流程 |
| **缺点** | ① 只让问题可见，不解决"这分是谁的"；② 无法支撑任何按人/按部门的可靠统计（隐患责任传导、部门排行仍然恒空）；③ 冻结条件 4/6 继续 BLOCKED；④ 74 条歧义记录若"跳过"，会导致扣分总量下降（可能被理解为放宽考核） |
| **历史数据处理** | 不处理。歧义记录保持原状 |
| **重名风险** | ⚠️ 高，但**已知**（236 组 / 496 人 / 74 条记录） |
| **离职人员风险** | 不涉及（仍按姓名匹配） |
| **对 SAF-004 影响** | 扣分口径与总额不变；但可产出"扣分不可靠清单"，供人工复核 |
| **跨模块改造范围** | 最小：1 处服务 + 1 个告警出口 |
| **需负责人确认** | ① 是否接受"扣分继续按姓名匹配"？② 74 条歧义记录是"跳过"还是"人工指定"？③ 这个方案是过渡还是长期？ |

### 6.1 建议结论

**建议采纳方案 C，但分三步走，且第一步不是改代码。**

```text
第 0 步（不需决策，纯核实）
  先把 DECISION-003 的法律地位定下来：
    —— 它已写入决策日志 ⇒ 按日志规则"已生效"
    —— 但状态写"未开始" ⇒ 实际未执行
    —— 二者不矛盾，但必须在同一份文件里说清"生效范围与实施进度"
  若负责人认可 DECISION-003，则方案选择结束，后续只是实施问题；
  若不认可，才需要走 A/B/C/D 四选一。

第 1 步（结构先行，不动历史数据）
  ① 给 27 张已有 employee_code 的表补 employee_id 列（可空）
```

### 6.2 建议理由（三条，均基于本轮实测）

1. **不能选 D**：74 条（3.6%）归因不可靠不是"潜在风险"，是**正在发生并已进入考核结果**（11,253 分）。
   冻结条件 6 的判定理由原文就是「存在运行中的错误链路，不是潜在风险」。
2. **不能只选 B**：`uk_employee_code` 是**部分唯一索引**，软删后 code 可复用 ⇒ 离职者历史会被"继承"。
   在没有"工号永久不复用"的书面规则前，B 会制造新的、更隐蔽的错误。
3. **C 不是新方案，是已有决策**：选 C 的实质成本最低——它不需要说服任何人接受新思路，
   只需要确认 `DECISION-003` 并把它拆成可执行步骤。反之若另选 A 或 B，还要先宣布 DECISION-003 作废。

### 6.3 建议里最重要的一条

> **不要在没有"解析服务"的情况下直接回填 ID。**
> 回填是单向的：一旦把错误的 ID 写进 2069 条巡查记录和 110 条隐患，
> 后续所有按人统计都会"看起来正常但全错"，比现在"明显缺 ID"更难发现。
> 解析服务必须先于回填，且必须保留解析依据列（否则无法复核）。
