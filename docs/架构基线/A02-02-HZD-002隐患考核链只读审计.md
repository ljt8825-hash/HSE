### 5.2 `closed` 在代码中有几个写入方

| # | 位置 | SQL | 前置状态 | 是否写 review 字段 |
|---|---|---|---|---|
| 1 | `hazardService.js:1039-1048` `review(pass)` | `SET status=$1, reviewer_id, review_result, review_date` | `pending_review` | ✅ **写**（同时 `INSERT hse_reviews`，`:1059`，同事务） |
| 2 | `hazardService.js:1114-1121` `close()` | `SET status='closed', rectification=COALESCE(...)` | `pending_review` | ❌ **不写** |
| 3 | `p3-04-02-migrate-legacy-status.js:112`（离线脚本） | `UPDATE hazards SET status='closed' WHERE status='已完成'` | 词汇迁移 | ❌ 不写 |

`update()` 显式禁止写 status（`hazardService.js:847-849`）；导入白名单排除 status（`importShared.js:483`、`importExcelService.js:1276/1359`）。

> 所以 60 条 `closed` 只可能来自 #2 或 #3。

### 5.3 排除 #2（`close()`），确认是 #3（词汇迁移）

`close()` 要求源状态为 `pending_review`，而 `pending_review` 只能由 `submitReview()` 产生，`submitReview()` 只能由 `rectify()`（→`processing`）产生，`rectify()` 会写 `corrector_id`、`rectification`、`rectify_date=CURRENT_DATE`。

| 反证 | 60 条 closed 的实况 | 若走 #2 应有的值 |
|---|---|---|
| `rectify_date` | **0/60** | 必须有值（`CURRENT_DATE`） |
| `corrector_id` | **0/60** | 若无入参则 NULL（可能） |
| `rectification` | **0/60** | 若无 `closeNote` 则保持原值（可能） |
| `updated_at` | **= created_at（精确）** | 必然 > created_at |

`updated_at` 与 `created_at` 精确相等，而 `close()` 的 SQL 含 `updated_at = CURRENT_TIMESTAMP` ⇒ **不可能是 `close()` 产生的**。

而迁移脚本的 SQL **不含 `updated_at`** ⇒ 与观测完全吻合。

### 5.4 `closed` 的真实血缘

```text
Excel 列「是否整改完成」= 是
   ↓  第 1 代状态映射（statusMap: {'是':'已完成'}，已于 P3-04-00.2 移除）
hazards.status = '已完成'
   ↓  p3-04-02-migrate-legacy-status.js:112（词汇迁移，不写 updated_at）
hazards.status = 'closed'      ← 当前 60 行
```

> **`closed` 的业务语义 = "Excel 里那一列填了 是"，不是"复查通过"。**

### 5.5 三条必须分开写的事实 / 推导

```text
事实：hazards.status = 'closed'（60 行）
事实：hazards.review_result IS NULL（110/110）
事实：hazards.review_date IS NULL、reviewer_id IS NULL（110/110）
事实：closed 行的 updated_at 与 created_at 精确相等
事实：hse_reviews = 0 行（正式复查证据表为空）

推导（禁止用于考核/统计口径）：
  不能因为 status='closed' 就认定已经复查
  不能因为 status='closed' 就认定已按时整改
  不能把 60 记作"已复查 60 条"
```

### 5.6 该语义已经被下游当作"已关闭"消费

| 消费点 | 用法 |
|---|---|
| `routes/overview.js:167` | `SELECT COUNT(*) FROM hazards WHERE status='closed'` |
| `hazardService.js:559-562` `stats()` | 分别统计 4 个状态计数 |
| `hazardService.js:623` | `AND h.status != 'closed'`（列表过滤未闭环） |

## 6. 那 2 条真实存在过的 `HAZARD_OVERDUE` 事件

这是全库唯一一次 HZD-002 链路被真实执行，必须交代清楚。

### 6.1 事件日志实况

```sql
SELECT id, event_type, status, created_at, processed_at, error_message
FROM hse_assessment_event_log
WHERE event_type IN ('HAZARD_OVERDUE','HAZARD_RESOLVED');
```

| id | event_type | status | created_at | payload 关键值 | 结果 |
|---|---|---|---|---|---|
| 502 | HAZARD_OVERDUE | **pending** | 2026-08-27 15:50:10 | `rectificationId=-999002`、`hazardId=-999002`、`responsiblePersonId="6692"` | `error_message = 字段 v.supervisor_position 不存在` |
| 505 | HAZARD_OVERDUE | **success** | 2026-08-27 15:51:38 | `rectificationId=-999012`、`responsiblePersonId="6692"` | 无错误，但 **0 扣分** |

全库 `HAZARD_RESOLVED` = **0 条**。

### 6.2 这两条事件的来源

`rectificationId` 为负数（`-999002` / `-999012`），而 `rectification_task` 0 行、`hse_rectifications` 0 行 ⇒ 是**测试夹具构造的临时 ID**，来源行已不存在。属 2026-08-27 的联调痕迹，不是业务数据。

### 6.3 为什么 505「success」却 0 扣分

| 检查 | 结果 |
|---|---|
| `getEmployeeWithManager(6692)` | ✅ 命中（`v_employee_org_full` 中 6692 有 1 条 `relation_status='active'`，员工 黄殿兴 / 00179501） |
| `findAssessmentTarget(cycle, 6692)` | ❌ **6692 不在 2026-08 周期（cycle 24）的考核对象中** |
| 6692 的考核对象记录 | 13 条，分布于其他 13 个周期，**不含 cycle 24** |
| `applyTransmission`（直属上级） | 未产生扣分行 |

> 结论：该事件被正常消费（`status=success`），但因为在"责任人非本周期考核对象 + 无有效上级传导"这条静默路径上返回 `affected: 0`，**没有产生任何扣分**。
> 这说明 `onHazardOverdue` 的 `success` 状态**不代表有扣分**——事件日志的成功率不能当作指标命中率使用。

### 6.4 事件 502 的错误暴露了什么

`字段 v.supervisor_position 不存在` —— 说明 2026-08-27 时 `getEmployeeWithManager` 的 SQL 曾查询 `v.supervisor_position`，而 `v_employee_org_full` 视图无此列。当前代码（`assessmentScoringEngine.js:560-566`）已不再查询该列。

> 502 至今仍是 `pending` 且 `processed_at` 已有值 ⇒ 不满足重放条件（重放只捞 `failed` 或 `processing AND processed_at IS NULL`），将成为**永久悬挂事件**。

## 8. 三个结论

### 结论 A｜事实源

> **当前隐患真正有数据的事实源是单表 `hazards`（110 行），但它是"台账快照"，不是"整改闭环"。**

| 维度 | 实况 |
|---|---|
| 表 | `public.hazards`（46 列 / 110 行 / `is_deleted` 全 false / `is_demo` 全 false） |
| 真实有值的字段 | **8 个**：`id`、`no`、`hazard_date`(110)、`description`(110)、`measure`(110)、`checker`(110)、`fixer`(97)、`fix_date`(69)、`remark`(2) |
| 默认值字段（有值但非业务设定） | `level`（全 `一般`）、`hazard_source`（全 `daily_check`）、`deadline_days`（全 30）、`related_risk_ids`（全 `[]`）、`is_deleted`、`is_demo`、`created_at`、`updated_at` |
| 全空字段 | **30 个**，含全部 FK（`responsible_id`/`fixer_id`/`checker_id`/`corrector_id`/`reviewer_id`/`finder_id`/`responsible_dept_id`/`grid_id`/`related_risk_id`）、全部期限（`deadline`/`deadline_date`）、全部复查（`review_result`/`review_date`）、全部验收（`verify_date`/`verify_user`）、全部整改时点（`rectify_date`/`actual_rectify_date`）、全部分类（`township`/`category`/`hazard_category`/`hazard_type`/`hazard_level`/`post_name`/`area`）、`location`(2 行)、`rectification`(2 行) |
| 缺失的关键事实 | **期限**（无法算超期）、**责任人 ID**（无法定位考核对象）、**复查证据**（无法判合格/验收） |
| 唯一来源 | **IMPORT**（`file_records` id=315，`2026-08-24 23:36:10`，`status=imported`，13 秒后 110 行同时落库） |

### 结论 B｜HZD-002 定性

> **B = 逻辑存在，但事实数据缺失**

| 选项 | 是否成立 | 理由 |
|---|---|---|
| A 逻辑完整 / 数据完整 / 可正常计算 | ❌ | 事实数据缺失（C 表 0 行、A 表无期限） |
| **B 逻辑存在，但事实数据缺失** | ✅ **成立** | 指标定义、调度器、事件处理器、扣分写入、传导逻辑**全部存在且可运行**（2026-08-27 有 2 条事件被真实消费证实）；但 C 表 0 行、A 表 `deadline`/`deadline_date` 均 0/110，无任何可计算的事实 |
| C 事实存在，但考核读取链错误 | ❌ | C 的前提"事实存在"不成立。读取链确实也错（读 C 而非 A），但即使改正也仍为 0 —— 主因是事实缺失，不是读错表 |
| D 逻辑与事实均不完整 | ❌ | 逻辑是完整的（有定义/有调度/有处理器/有扣分写入/有幂等/有传导） |
| E 指标定义本身需业务重新确认 | ⚠️ 部分 | `max_deduct=30`、`transmit=true`、3 分/条 与另外两套口径（5 分/项）冲突，**需要业务确认**，但这不是"无法计算"的主因 |

补充说明（不进定性，但必须记录）：

1. `onHazardOverdue` 的 `sourceTable` 硬编码为 `'hse_rectifications'`（`:371`），而 B 模型事件来源是 `rectification_task` ⇒ 即使扣分成功，`source_table` 也会指向错误的表。
2. `success` 状态 ≠ 有扣分（§6.3 已证）。

### 结论 C｜是否允许进入修复阶段

> **BLOCKED BY BUSINESS DECISION**

修复前必须先由业务裁定以下 5 项（本轮只列问题，不提供方案）：

| # | 待裁事项 | 为什么不定就不能修 |
|---|---|---|
| 1 | **期限语义**：隐患的"整改期限"是外部台账给定的绝对日期，还是 `hazard_date + deadline_days` 推导？ | 决定 `deadline_date` 是否需要外部导入、`deadline_days` 是否有效、41/50 这两个推导数是否可用 |
