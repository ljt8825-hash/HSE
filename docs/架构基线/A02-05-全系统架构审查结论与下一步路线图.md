## 3. 三条核心结论

### 结论一：8 个域不具备冻结条件，不是因为没审计，而是因为结构未定

12 域按可用性重估：

```text
可用（B）   4 域  D0 平台支撑 / D3 检查巡查 / D5 事故应急 / D7 制度标准
未收敛（C） 5 域  D1 基础主数据 / D6 教育培训 / D8 专项管理 / D9 保障经营 / D11 综合分析
不可用（D） 3 域  D2 风险管控（外部 BLOCKED） / D4 隐患治理 / D10 责任与考核
```

关键证据：
- **D1** 组织三表并存，被引用最多的 `hse_org_unit`(13 表) 写入口**已被注释**（`app.js:517`）
- **D4** 隐患 9 个关联 ID 字段**全为 0/110**
- **D9** 保险双表**姓名重叠 99.9%**、超龄双表**身份证重叠 98.9%**（不是新旧代际，是同一批事实重复存储）
- **D10** 从未冻结过任何周期（`frozen` = 0）；2728 条指标行**无写入口**
- **D11** 总览读历史表，事故显示 **3** 而事故页 **110**（相差 36.7 倍）

### 结论二：最严重的不是"数字错"，而是"数字无法复核"

| 层级 | 状态 | 证据 |
|---|---|---|
| 数字层 | ✅ 多处一致 | 隐患总数 110 在 DB/API/前端三方一致；总分 `score_total` ≡ `100 − 快照扣分` 856/923 |
| 语义层 | ❌ 不一致 | 「待整改 50」含 22 条原件记为已整改；「已整改」有 60/69/66 三个值 |
| 期限层 | ❌ 不一致 | 驾驶舱超期 0（`deadline_date` 全空）vs 隐患页超期 50（`deadline_days` 默认 30） |
| 天数层 | ❌ 错误 | `EXTRACT(DAY FROM AGE())` 丢月/年 ⇒ 真实 206 天显示 23 天，页面永远 ≤ 31 |
| 归因层 | ❌ 靠文本 | 占总扣分 **77.9%** 的 SAF-004 靠 `personnel_name` 姓名匹配算"实巡次数" |

⇒ **可以给用户一个数字，但给不出这个数字的来源。** 这是全系统级的可信度问题。

### 结论三：能靠改代码修的，比想象的少

39 项缺口按性质拆分（每项取主性质，见 A02-05-02 §4）：

| 性质 | 数量 | 能否独立修复 |
|---|---:|---|
| 数据事实 | 9 | ⚠️ 需先定口径（补什么、以谁为准） |
| 数据模型 | 10 | ❌ 需先选型/退役决策 |
| 计算逻辑 | 6 | ✅ 其中 3 项纯技术（超期天数 / 上限 NULL / 地板归零） |
| 页面展示 | 7 | ⚠️ 需先有正确数据源 |
| 跨模块架构 | 7 | ⚠️ 部分可独立（路由遮蔽 / 死接口下线） |
| **合计** | **39** | |

另：**20 项业务决策**不属于缺口（是缺口的成因），单独登记于 A02-05-04。

**真正"不需要任何决策就能改"的只有 6 项**：
超期天数计算、`management-performance` 缺列、`/results/ranking` 路由遮蔽、
`dashboard/metrics` 时间维度、`import_logs` 无写入方、3 个内存导入模块。

⇒ **修完这 6 项，10 条冻结条件仍然 0 条通过。** 因为条件卡在决策与数据事实，不在代码缺陷。
