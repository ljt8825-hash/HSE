# 1. 项目定位

本系统定位为：

> **安环管理部内部使用的 HSE 综合管理、台账、统计、考核、分析后台。**

本系统不是企业统一审批平台，也不是现场作业人员主要使用的移动端系统。

系统主要解决：

1. 各类 HSE 台账分散的问题；
2. 不同台账之间缺乏关联的问题；
3. 人员、车辆、地点等基础数据重复维护的问题；
4. 月度/季度/年度统计需要人工汇总的问题；
5. 安全考核依赖人工整理的问题；
6. 数据形成后无法形成统一分析的问题；
7. 不同业务模块之间跳转过多、缺少统一业务视图的问题。

核心能力：

> **数据集中 + 业务关联 + 自动统计 + 配置化考核 + 综合分析 + 统一展示。**

---

# 2. 外部系统边界

本系统不替代现有外部系统。

## 2.1 钉钉

钉钉承担：

- 审批流程
- 领导审批
- 流程节点
- 企业原有审批机制

本系统原则上接收：

> 已经形成、已经批准或已经实施的数据。

例如安全生产费：

```text
钉钉审批 → 审批完成 → 数据进入HSE后台 → 安全生产费台账 → 统计/考核/分析
```

本系统不重新建设一套审批流程。

# 3. 移动端/H5边界

现场人员主要通过：

- 手机H5
- 移动端
- 外部系统
- Excel固定模板

产生或提交业务数据。

典型数据：三违、隐患、现场检查、事故信息、培训记录、现场照片、其他现场事实。

后台主要负责：

```text
数据接收 → 标准化 → 台账 → 关联 → 统计 → 考核 → 分析
```

# 5. 为什么采用前端优先

本项目使用者是安环管理部。项目不能长期停留在数据库、Service、API、状态机、数据迁移，而用户看不到实际系统。

因此需要优先建立**可视化前端平台骨架**，让业务人员能够看到系统菜单、页面、台账、查询、详情、统计、考核、关联关系。

但是：**前端设计不能脱离未来的数据模型。** 前端设计过程中必须同步考虑：数据库如何存储、哪些字段属于主数据、哪些属于业务事实、哪些数据与其他模块关联、哪些字段应该引用统一主数据、哪些由系统计算、哪些来源于 Excel / H5 / 钉钉或其他外部系统。

# 9. 页面类型统一规范

整个系统不允许每个模块自己设计一套页面。统一采用以下 5 类页面：

| 类型 | 结构 |
|---|---|
| **A. 工作台** | 页面标题 → 核心指标卡 → 重点预警 → 趋势图 → 分布图 → 待处理事项 → 快捷入口 |
| **B. 台账** | 页面标题 → 统计卡片 → 搜索区域 → 操作区域 → 数据表格 → 分页 |
| **C. 详情** | 返回 → 基本信息 → 业务信息 → 关联信息 → 附件 → 时间线 → 操作记录 |
| **D. 分析** | 指标卡 → 趋势 → 结构 → 区域 → 人员/车辆/地点 → 明细 |
| **E. 地图** | 风险地图、网格管理、区域安全、其他空间化数据 |

# 12. 表格规范

统一使用 Naive UI + VXE Table 数据表格体系。要求：

- 固定表头
- 行高统一
- 重要字段优先
- 操作列固定右侧
- 支持列显示/隐藏
- 支持刷新 / 分页 / 排序 / 条件筛选 / 导出

# 14. 颜色体系

视觉定位：**专业、克制、轻量、清晰的企业管理后台。** 不采用过度鲜艳的"安全大屏"风格。

| 语义 | 颜色 | 用途 |
|---|---|---|
| 主色 | **蓝色系** | 主按钮、选中状态、链接、当前菜单、主要信息 |
| 成功 | 绿色 | 已完成、正常、已关闭、通过 |
| 警告 | 橙黄色 | 临期、待处理、需要关注 |
| 危险 | 红色 | 重大风险、逾期、事故、严重问题、删除等危险操作 |
| 信息 | 灰蓝色 | 普通状态、辅助信息 |

> 🔴 **本条款与现行代码和冻结约束均冲突**：`components/hse/theme.ts` 主色为 `hsl(144,57%,45%)` **安全绿**，并注明"配色语义（冻结基线）：主色 / 成功 = 安全绿"；`01-强制设计约束.md` §3 亦为"绿色为主色/成功，蓝色为信息"。主色改蓝等于全站换肤，影响 152 个业务页。**未经正式授权不得实施**，见 §50-C1。

# 15. 状态颜色必须统一

```text
正常/已完成   → success
进行中        → primary/info
待处理/待复查 → warning
逾期/严重     → error
草稿/未开始   → default
```

同一状态不得在不同模块使用不同颜色。

> 现状：`components/hse/statusColors.ts` 已实现该规范，但**只覆盖隐患、事故 2 个域**，且被业务页直接引用次数为 **0**（仅经 `HseStatusTag` 间接生效）。三违、培训、检查、费用、保险、考核 6 个域的状态色仍未定义，见 §51。

# 16. UI视觉原则

**避免**：大面积渐变、过度圆角、大量阴影、过度卡片化、大面积红色、大面积深色背景、花哨动画。

**推荐**：白色/浅灰工作区、清晰边界、轻量卡片、小圆角、适度阴影、紧凑但不拥挤、数据优先、信息层级清楚。

---

# 17. 导入设计

所有导入统一为 **标准导入 + AI导入**。

**标准导入**：下载模板 → 上传 → 字段校验 → 数据预览 → 错误提示 → 确认 → 导入结果

**AI导入**（用于用户提供格式不完全统一的 Excel）：上传Excel → AI识别表头/字段 → 映射到系统字段 → 预览 → 人工确认 → 导入

> 现状：`HseImportDialog` 已实现标准导入 5 步（32 页在用）；**AI导入仅 1 个页面存在**（`ledger/training`），无通用组件，见 §49.3。

---

# 18. 固定Excel模板

必须支持企业已有固定格式。固定模板**不得**为了适应数据库而强制改变。

```text
企业固定Excel → 字段映射 → 系统标准数据 → 业务事实
```

后续需逐个审查用户提供的真实 Excel。每个 Excel 必须判断：是否入数据库、哪些字段入库、哪些只是展示、是否保留原始文件、是否需要版本、是否可导出原格式、与哪些主数据关联、与哪些业务台账关联。

---

# 19. 数据关联原则

前端设计时必须同步考虑后端。

- **人员**（主数据）→ 培训、三违、事故、保险、职业健康、资格、考核 引用
- **车辆**（主数据）→ 交通安全、三违、事故、检查、保险 引用
- **地点**（主数据）→ 风险、检查、隐患、三违、事故、消防、应急 引用

> 🔴 现状与原则相反：`vehicles` 表**入向外键 0 条**，且表内嵌 **20 个保险/保费列**（`insurance_*` / `compulsory_*` / `commercial_*` / `third_party_*` / `total_premium` / `vehicle_tax`），而本该独立的 `vehicle_insurances` 为 **0 行 0 代码引用**。即"车辆持有保险"而非"保险引用车辆"。见上位基线 §10 与 §P0-3。

# 20. "不要跳转太厉害"的设计原则

```text
人员 → 培训 / 三违 / 事故 / 资格 / 保险
车辆 → 保险 / 检查 / 三违 / 事故 / 驾驶关系
地点 → 风险 / 检查 / 隐患 / 三违 / 事故
```

原则：**模块是入口，数据对象是核心。** 业务对象详情页应聚合相关业务摘要，而非要求用户在多模块间跳转。

# 21. 考核引擎是核心能力

```text
隐患台账 ─┐
三违台账 ─┤
检查台账 ─┤
培训台账 ─┤
事故台账 ─┤
交通台账 ─┤
          ↓
      考核计算引擎 → 考核结果 → 排名/分析/报表
```

考核规则不得硬编码。

## §47 一级菜单实况：现存 19 个业务菜单，而非 11 个

### 47.1 导航真源确认

`menus` 表**不是导航菜单**——dev 库中该表仅 7 行，内容为动作级权限按钮（创建角色 / 编辑角色 / 删除角色 / 创建菜单 / 编辑菜单 / 删除菜单 / 导出审计日志，全部 `hidden=t`、`parent_id` 全空），属于 RBAC 权限点。
