## 2. 决策二：DEC-A0205-12（身份主数据）

**建议：确认既有 DECISION-003 的路线并转入可实施状态——`employee.id` = 内部唯一业务主键；`employee_code` = 展示/业务编码；`name` = 展示字段；`phone_hash`/`id_card_hash` = 外部系统身份匹配辅助键。**

### 为什么是 employee.id 而不是 employee_code

- id：PK 硬唯一、40+ FK 已绑定、软删不复用（评分 20/25）。
- code：唯一性是**部分索引**（`WHERE is_deleted=false`）⇒ 软删后编码可复用，作为内部主键会出现「同一个 code 先后指向两个人」；且飞书侧无工号形态（命中 0）。code 的现役 0 重复只说明「当前干净」，不构成主键资格。

### 为什么不能使用 name

现役重名 **233 组 / 482 人（14.1%）**，最大组 6 人；grid_records 姓名路由 3.6% 不可靠（A02-06 实测）。name 只能作降级路由（且必须配合部门等消歧）。

### 为什么 phone_hash 不能成为内部主键

- 员工侧覆盖率仅 **38.4%**（2105 人无 phone_hash）；
- 手机号可变更、无变更留痕；飞书匹配率 84.9% 已证其「辅助键」价值，但 1 人多号/1 号多人的生命周期问题无约束保护；
- 它的正确角色 = 外部系统（飞书）↔ PG 的**等值匹配桥**，与 id_card_hash（94.3%）互补：**手机号缺则用身份证，身份证缺则用手机号**。

### 技术匹配 ≠ 业务归属（§十二回执）

62/73 与 1291/1369 只回答「这个标识对应哪一行 employee」。以下仍需业务裁决，本轮一律未裁：

Q-3  「排查人=当前在册员工」的业务规则（离职/外包人员排查有效性）→ 业务规则，非技术

## 3. 决策三：REGION-MASTER（新增决策项）

**建议：建立独立区域主数据（乡镇词典 17 行起步），区域与组织分设两维；三系统（PG/WPS/飞书）统一映射到该词典。**

### 依据

1. 独立区域主数据 = **0 套**；乡镇规范全称只存在于 hse_org_unit.org_name 一处。
2. 自由文本漂移实测：violations 简称混用（柴胡店/刘营伍/张大庄）+ 组织名混入 26 行；hse_assessment_target 全列组织名冒充；accidents 84% 空值+无效值；hazards/department/grid_areas 的 township 专用列全空。
3. 三系统无可机器比对的共同区域键（B01-关系矩阵 §3）。
4. 组织兼区域的结构性混用（12 个 town_center）使「作业中心管辖范围」与「地理区域」无法分开演进。

### 建议形态（仅概念，不建表）

```text
REGION 词典：region_code / region_name(全称) / region_type(乡镇/街道) /
             parent(县) / status / 映射别名表（柴胡店→柴胡店镇 等 3+ 组）
关系模型：   作业中心(hse_org_unit.town_center) --管辖--> REGION（多对一/多对多显式化）
             业务表区域列 --FK--> REGION（新增表/列属 D 节段，须经授权）
三系统映射： PG township 归一 ← 词典；WPS grid_areas.area 别名映射；
             飞书「片区|班组」与「隐患位置」由同步层映射（不改 H5/飞书）
```

### 分级判断（任务书 §二十一-3）

```text
是否建立独立区域主数据   → 建议：是
是否继续自由文本         → 建议：否（存量清洗、增量约束）
区域与组织是否独立       → 建议：独立（管辖关系显式建模）
H5/Feishu/WPS 是否统一映射 → 建议：是，映射在 PG 侧词典+同步层完成，不动 H5/飞书
```
