# A02-03-04｜隐患页面统计与数据库一致性审计

> 审计对象：所有涉及隐患计数的页面 / 接口 / 服务
> 审计方式：**只读**。后端 SQL 逐条提取 + 数据库模拟执行 + 前端取数代码比对
> 目的：回答「页面上的数字从哪来、和数据库差多少、差在哪」。
> CODE CHANGE = 0 / DDL = 0 / DML = 0 / CONFIG CHANGE = 0 / PRODUCTION CHANGE = 0。

---

## 1. 一句话结论

> **隐患模块有 7 处统计口径、4 套数据源（`hazards` / `hazard_record` / `deadline_date` / `deadline_days`）、3 个页面互相矛盾。**
> **最刺眼的一对：驾驶舱「超期隐患」= 0（读 `deadline_date`，全空），隐患页「超期提醒」= 50（用 `deadline_days` 默认 30 天推导）。同一系统，同一指标，一个 0 一个 50。**

### 3.1 统计卡片：四层比对

| 层 | 内容 |

| 待复查 0 | `stats.pendingReview` | 状态机第三步 | 正确（从未发生） |

### 3.3 超期提醒：50 条、超期天数显示错误

```sql
-- hazardService.js:1168-1178  remindersOverdue()
SELECT h.*, e.name AS responsible_name,
       ROUND(EXTRACT(DAY FROM AGE(CURRENT_DATE, h.hazard_date + (h.deadline_days || ' days')::interval)))::int AS overdue_days
FROM hazards h
LEFT JOIN v_employee_current e ON h.responsible_id = e.employee_id
WHERE h.is_deleted = false
  AND h.status != 'closed'
  AND h.hazard_date IS NOT NULL
  AND h.hazard_date + (h.deadline_days || ' days')::interval < CURRENT_DATE
```

**实测结果：50 条**（= 全部 `discovered`）。

**两个缺陷：**

| # | 缺陷 | 证据 |
|---:|---|---|
| 1 | **50 条超期全部来自 `deadline_days` 默认值 30**，业务上从未设定任何期限 | `deadline_days` 110/110 全 = 30；`deadline`/`deadline_date` 均 0/110 |
| 2 | **「超期天数」计算丢失月/年分量** | `EXTRACT(DAY FROM AGE(...))` 只取 interval 的 day 部分 |

**超期天数实测对比：**

| `no` | `hazard_date` | 按默认 30 天的"期限" | **真实超期天数** | **页面显示** |
|---:|---|---|---:|---:|
| 1 | 2026-03-05 | 2026-04-04 | **206 天** | 23 |
| 2 | 2026-04-28 | 2026-05-28 | **152 天** | 30 |
| 6 | 2026-04-28 | 2026-05-28 | **152 天** | 30 |
| 7 | 2026-04-28 | 2026-05-28 | **152 天** | 30 |

```text
2026-03-05 + 30 天 = 2026-04-04
今天 = 2026-10-27
真实差 = 206 天 → AGE() = 6 mons 23 days → EXTRACT(DAY) = 23   ← 页面显示 23
2026-04-28 + 30 天 = 2026-05-28 → AGE() = 4 mons 29 days → 显示 30
```

> **页面上的「超期天数」永远 ≤ 31，无论实际超期多久。** 这是展示层硬缺陷，与"期限是否成立"是两个独立问题。

### 5.2 两处 SQL 缺陷（即便被调用也会错）

```js
// routes/dashboard.js:123-124
currentSql:  `SELECT COUNT(*) FROM hazards WHERE created_at >= $1${departmentId ? ' AND department = $2' : ''}`
```

| 缺陷 | 证据 | 后果 |
|---|---|---|
| **① 时间维度用 `created_at`** | 110 行 `created_at` 全部 = 2026-08-24 23:36:23（仅 2 个不同值） | 按"本月"（2026-10）查 → **0**；按"本年"查 → 110 |
| **② 引用不存在的 `department` 列** | `hazards` 46 列中只有 `responsible_dept`/`responsible_dept_id`，**无 `department`** | 一旦传 `departmentId`，SQL 直接报错 |

**实测（`getPeriodRanges` 默认 `month` → `currentStart = 2026-10-01`）：**

| 查询 | 值 |
|---|---:|
| `created_at >= '2026-10-01'`（本月） | **0** |
| `created_at >= '2026-09-01'`（上月） | **0** |
| `created_at >= '2026-08-01'`（8 月） | **110**（全部） |
| `hazard_date >= '2026-10-01'`（正确口径） | 0 |
| `hazard_date = 2026-06`（正确口径） | **66** |

> **若该接口被前端启用，隐患趋势图会呈现"8 月骤增 110、9-10 月归零"的假象，而业务的真实分布是 2–7 月。**

## 11. 本章判定

```text
统计口径数量 = 7 处（hazards.status / deadline_days 推导 / deadline_date / created_at /
                     responsible_id / hazard_record+rectification_task / 快照）

PAGE/DB CONSISTENCY = 不一致（分层结论）
  数字层（总数/已关闭）：一致 —— DB 110/60 = API 110/60 = 前端 110/60
  语义层：不一致 —— 「待整改 50」含 22 条已整改
  期限层：不一致 —— 超期 0（驾驶舱）vs 50（隐患页）
  天数层：不一致 —— 真实 152/206 天 vs 显示 30/23 天
  跨页层：不一致 —— 驾驶舱读 B 模型、AI 页无表、考核 0

页面取数准确性 =
  隐患页统计卡片 = 数字准、标签错
  隐患页超期提醒 = 数字来自默认 30 天推导 + 天数计算缺陷
  隐患页三张排行 = 2 张恒空
```
