## 文档用途

本文件是 HSE 平台的**长期架构档案**，用于记录：

- 用户与 AI 讨论形成的架构决定（DECISION）
- 具体实施任务（WORK）
- GitHub 提交（commit SHA）
- 验收结果
- 未决事项
- 后续行动

### 为什么需要这份文件

本仓库历史文档存在两个问题，导致"决策不可追溯"：

1. **同一议题多次反复**：如"人员身份用哪个 ID"、"培训完成以台账还是明细为准"，在不同报告中给出过不同口径，但没有任何地方记录"最终定了什么、为什么"。
2. **文档与代码脱节**：`HSE系统建设决策基线与AI协同开发记录_Sprint11.md` 记录的路径是 `F:\deploy\hse-dashboard\安全看板vben`、技术栈是 Ant Design Vue；实际已是 `G:\hse-dashboard` + Naive UI。旧决策无人宣布失效，新决策无处登记。

因此本文件确立一条规则：**任何影响架构边界的决定，只有写进本文件才算生效。**

# 决策记录

## DECISION-001

**日期**：2026-10-27

**议题**：HSE 平台采用分层业务架构，基础主数据与业务域分离。

**背景**：截至 2026-10-27，DEV 库有 **263 张系统表**，其中 **103 张零行**；同时存在 17 项重复主数据/数据归属冲突（详见基线 §11）。根因是没有分层约束，任何新需求都新建一套表。典型症状：

- 人员：`employee`(3417) 之外还有 `personnel`(0)、`org_personnel`(0)、`org_personnels`(0)；
- 保险：`personnel_insurance`(2474) 与 `personnel_insurances`(1330) 双表并存，后者**零代码引用**；
- 区域：`grid_areas`(63) 与 `risk_area_dict`(17) 各建一套；
- 车辆：主数据表里塞了 20 个保险/保费列，而独立保险表 `vehicle_insurances` 是 0 行 0 引用。

**讨论结论**：

| 方案 | 问题 |
|---|---|
| A. 保持现状，按需求继续加表 | 冲突已达 17 项，再加会把 `public` schema 彻底变成垃圾场（现有 48 张 Excel 残留表已是明证） |
| B. 全库推倒重设计 | 会破坏已 FROZEN 的 6 个模块（网格巡查链、隐患 C1、风险 02/03/04、培训 S1），违反"不推倒重来"原则 |
| C. 分层 + 定归属 + 增量归位（选定） | 需一次性投入做归属认定，但不动已冻结模块 |

**最终决定**：采用 **7 层架构**，层与层之间用「拥有 / 引用」关系约束：

```text
L0 平台支撑 → L1 基础主数据 → L2 HSE核心业务 → L3 专项安全 → L4 保障经营 → L5 责任与考核 → L6 综合分析智能
```

并确立归属规则：**主数据只有唯一拥有者（人员=employee / 组织=hse_org_unit / 岗位=position / 网格=grid_areas）；业务域只允许存 `*_id` 引用，不得自建主数据表。**

**为什么这样决定**：

1. 代码里已经事实上这样跑了——31 张表用外键引用 `employee`、13 张引用 `hse_org_unit`、7 张引用 `position`。分层不是发明，是把既有事实显式化。
2. 263 张系统表里只有 **78 张（29.7%）**有出向外键，**185 张（70.3%）一张外键都没有**；全库共 185 条外键。说明"归属"从未被物理约束过，必须用文档 + 后续 DDL 双重固化。
3. 选 7 层而非任务书草案的 5 层，是因为 L0（`users/roles/role_menu/menus/sys_operation_log`）与 L5（`hse_assessment_*` 24 表 / 3670 条评分）**已经存在且体量超过多数业务域**，若压进"系统管理"和"综合分析"两个小格子，重构时必被踩坏。

**影响范围**：全平台。所有新建表必须先在本基线 §10 归属矩阵声明归属。

**涉及模块**：全部。

**是否需要代码修改**：否（本次只立文档）。后续新增表结构时必须遵守。

**TRAE任务**：建立《HSE平台总体业务架构基线 V1.0》

**GitHub Commit**：见 WORK-001

**验收状态**：进行中（文档已产出，**待业务签字确认 7 层与归属矩阵**）

**后续动作**：业务确认分层与归属；确认后本决策生效，后续 DDL 评审以此为依据。

## DECISION-002

**日期**：2026-10-27

**议题**：后续采用「总体架构 → 前端可视化/台账 → 数据模型 → 后端 → 联调 → 验收」的实施方式。

**背景**：历史做法是"后端建表 → 写 API → 前端拼页面"，产出结果是：

- **8 张检查域表全 0 行**（`inspection_plan/task/record/checklist_template/checklist_item` + `hse_inspection_plans/tasks/executions`）——表建好了，从没有人用；
- **消防器材**：`fire_equipment` 表 0 行，前端页面已建，而 `/api/overview` 的消防统计**直接查 Excel 残留表** `t_08_现场管理_消防器材管理台账_无照片`（`server/routes/overview.js:44`）；
- **供应链安全**：只有一个页面 `views/hse/supply-chain`，无表无 API；
- **安全生产费后半段**：申请/承诺/实际/分摊四表全 0 行，而前端 5 个预算页面早已建好。

即"数据模型在没有可视化验证的情况下先被固化"，直接导致 103 张零行表。

**讨论结论**：

| 方案 | 问题 |
|---|---|
| A. 维持后端先行 | 已证明会产出空壳表和空壳页面 |
| B. 前端先行、后端跟随页面 | 会把页面字段直接变成 DB 列，导致"前端台账反向决定数据库结构"（另一个坑） |
| C. 架构先行 + 前端台账作为需求表达 + 归属确认后再建模型（选定） | 多一道确认工序，但能同时避免空壳与反向决定 |

**最终决定**：强制链路

```text
① 总体架构 → ② 业务域（定边界）
→ ③ 页面/台账设计 → ④ 字段与数据关系 → ⑤ 导入模板
→ ⑥ 后端数据模型 → ⑦ API → ⑧ 联调 → ⑨ 验收
```

三条硬规则：
1. 没有台账设计，不开工 DDL；
2. 没有导入模板（含 ≥1 个月真实样例），不开工导入功能；
3. 页面可以先行作为需求表达工具，但**不得据页面直接生成 DB 列**。

**为什么这样决定**：本平台的固定表格来源极多（48 张 `t_0X_*` 表可证），台账是用户唯一真正理解的数据形态。以台账为需求载体，能同时解决"字段是否必要"和"导入映射"两个问题。而保留 ④ 这一步，是为了阻断"页面字段 = 数据库列"的直连。

**影响范围**：所有新开发与重构；**不追溯**已 FROZEN 模块。

**涉及模块**：新开发与待重构模块（消防、特种设备、保险理赔、检查管理、费用后半段）。

**是否需要代码修改**：否（流程约束）。

**TRAE任务**：建立《HSE平台总体业务架构基线 V1.0》

**GitHub Commit**：见 WORK-001

**验收状态**：进行中（待业务确认流程可执行）

**后续动作**：选消防器材管理作为首个试点域，跑通全链路（见基线 §17-Q15 步 3）。

## DECISION-003

**日期**：2026-10-27

**议题**：人员、车辆、地点、组织等高复用实体原则上只建立统一主数据，业务模块通过引用使用。

**背景**：现状是"每域自带一份实体快照"：

| 域 | 人员怎么存 | 车辆怎么存 | 地点怎么存 |
|---|---|---|---|
| 隐患 `hazards` | `checker`(文本) + `checker_id` + `fixer`(文本) + `fixer_id` + `verify_user`(文本) + `reviewer_id` | 无 | `location`(文本) + `township`(文本) + `grid_id`(无外键) + `area`(文本) |
| 事故 `accidents` | `involved_person`(文本) + `personnel_id` + `handler`(文本) + `handler_id` | `involved_vehicle`(文本) + `vehicle_id`(**无外键**) | `location`(文本) + `township`(文本) |
| 三违 `violation_records` | `violator_name` + `violator_id` + `inspector_name` + `inspector_id` + `handler_name` + `handler_id` + `punisher_name` + `punisher_id` + `violator_id_card` | `vehicle_type_or_cleaner`(文本) | `location`(文本) + `area_team`(文本) + `grid_level`(文本) |
| 培训 `training_records` | `name` + `id_card` + `personnel_id` + `employee_id`（**四套**） | 无 | `dept`(文本) + `dept_id` + `dept_name` |

**讨论结论**：

| 方案 | 问题 |
|---|---|
| A. 立即清理所有文本列 | 会打断大量存量查询与报表，且 `violations`(1451) 等历史数据无 ID 可回填 |
| B. 保持双写 | 双写不同步就会产生"同一人在事故里叫张三、在三违里叫张 三"这类脏数据 |
| C. 明确唯一业务键 + 文本列降级为"展示缓存"（选定） | 需要写入层统一生成缓存列 |

**最终决定**：

1. **唯一业务键**：人员 `employee.id`（解析顺序沿用飞书花名册约定 phone → employee_code → name，fail-closed）；组织 `hse_org_unit.id`；岗位 `position.id`；网格 `grid_areas.id`。
2. **文本列定位降级**：`checker`/`fixer`/`involved_person`/`violator_name` 等一律定性为**展示缓存**，只能由写入层根据 ID 生成，禁止人工填写成为事实。
3. **新增业务表禁止**再建 `xxx_person` / `xxx_vehicle` / `xxx_location` 快照表。
4. **车辆**：先补主数据地位（补外键、剥离 20 个保险/保费列，见 DECISION-006 关联项），再要求各域引用。

**为什么这样决定**：31 张表已用外键引用 `employee`，说明"引用"模式本来就是主流；双写是历史增量而不是设计。把文本列定性为缓存，既不用回填历史数据，又能阻止新脏数据产生。

**影响范围**：隐患、事故、三违、培训、检查、保险、考核 7 个域的全部写入路径。

**涉及模块**：hazardService、accidentService、violationService、trainingRecordService、inspectionCenterService、insurancePersonnelService。

**是否需要代码修改**：是（分阶段；本次不动）。

**TRAE任务**：无（待专项任务书）

**GitHub Commit**：未提交

**验收状态**：未开始

**后续动作**：先做一次"文本缓存列生成器"的统一改造设计，再逐域接入；`violations` 历史表冻结只读，不做回填。

| C. 保留能力 + 归位边界 + 逐步收敛（选定） | 需要逐域排期 |

**为什么这样决定**：6 项 FROZEN 成果都有独立验收报告与数据证据，是可复用资产；而 17 项冲突多数是"表结构/引用关系"问题，可以在不改语义的前提下收敛。

**影响范围**：培训、三违、检查、隐患、风险、事故、费用、考核 8 个域。

**涉及模块**：见上表。

## DECISION-005

**日期**：2026-10-27

**议题**：生产环境暂不进入观察/验收阶段，所有模块和台账完成总体重构并由用户明确授权后再进入生产阶段。

**背景**：

1. 生产库当前**存在无法验证的状态**：事故 `accidents.status` 的真实分布不可得（`hse-db` DNS 不可解析、本机无 docker）→ RC-1 = BLOCKED。
2. 生产与 DEV 是**近孪生但不等价**：本机 `safety_dashboard` 与 `safety_dashboard_dev` 曾同为 110 行、id 48..159，逐行 diff 仅 2 行差异（id=124 状态翻转、id=151 软删）。这种"几乎相同"最危险——容易被误当同一环境。
3. 生产已积累真实业务数据（`training_plans` 35 行全为 seed 直插、审批字段全 NULL；34 approved 未回填），任何结构调整都会与真实数据纠缠。
4. `config/db.js` **默认连生产**，历史上已造成"开发操作打到生产"的风险面。

**讨论结论**：

| 方案 | 问题 |
|---|---|
| A. 边重构边上生产验证 | 生产数据不可回滚；且当前连"生产状态是什么"都测不到 |
| B. 完全冻结生产、停止一切上线 | 会影响已在跑的业务（网格巡查同步、月度考核 cron） |
| C. 生产维持现状运行，重构全部在 DEV 完成并通过验收后，再单独授权上线（选定） | 需要明确"哪些算上线动作" |

**最终决定**：

1. **生产维持现状**：已上线的功能继续跑（网格巡查 WPS-PG 同步、月度考核调度、培训台账自动生成）。**不因本次架构重构做任何生产变更**。
2. **重构全部在 DEV 完成**：DDL 只准作用于 `safety_dashboard_dev`；执行前必须硬设 `DB_NAME` 并首条 SQL 断言 `current_database()`，不符即中止。
3. **进入生产的唯一条件**：① 对应模块在 DEV 完成 ⑨ 验收；② 有独立回归证据；③ **用户明确书面授权**。
4. **本决策不解除的既有 P0**：生产 DB 口令轮换、`FS_APP_SECRET` 轮换、生产 migration 授权。这些仍需单独处理。

**为什么这样决定**：当前连生产真实状态都无法取证（RC-1 BLOCKED），在此前提下做生产变更等于盲改。先完成 DEV 侧收敛与验收，是唯一可控路径。

**影响范围**：全部生产环境操作。

**涉及模块**：全部。

**是否需要代码修改**：否。

## DECISION-006

**日期**：2026-10-27

**议题**：架构分层采用 7 层，而非任务书草案的 5 层（新增 L0 平台支撑层、L5 责任与考核域）。

**背景**：任务书 §四~§八 提出 5 层结构（基础主数据 / HSE核心业务 / 专项安全 / 保障经营 / 综合分析），把「考核」放在综合分析层的子项。但实际代码与该草案冲突：

- `hse_assessment_*` 共 **24 张表**，`hse_assessment_score` **3670 行**、`deduction` **940 行**、`target` **925 行**、`event_log` **717 行**；
- 有独立调度器 `services/assessmentScheduler.js`（每日全量校验 + 网格巡查校验两个 cron）；
- 有独立服务群 13 个 `assessmentMonthly*Service.js` + `assessmentScoringEngine.js`；
- 有独立门户页 `views/hse/assessment-portal` + 10 个 `mirror/*` 镜像页；
- 而 L0 侧 `sys_operation_log` **4929 行**，是所有写操作的实际留痕点。

**讨论结论**：

| 方案 | 问题 |
|---|---|
| A. 严格按任务书 5 层 | 考核域 24 表无归属，会被塞进"综合分析"，与其"分析不拥有事实"的原则（任务书 §八）直接矛盾 |
| B. 无限扩层 | 层次失去约束力 |
| C. 7 层（选定） | 与任务书草案有差异，需显式记录 |

**最终决定**：

```text
L0 平台支撑（认证/权限/审计/通知/工作流/文件/导入）
L1 基础主数据
L2 HSE 核心业务
L3 专项安全管理
L4 保障/经营管理
L5 责任与考核   ← 新增
L6 综合分析与智能
```

并且**明确原则**：任务书 §八"综合分析层尽可能从业务事实实时计算，不重复成为事实数据源"——正因为考核拥有自己的事实数据（扣分/评分/事件日志），它**不能**放在分析层。这是从原则推导出的必要修正，不是对任务书的随意偏离。

**为什么这样决定**：分层的目的是约束数据归属。把"拥有 24 张事实表"的域放进"不应拥有事实"的层，会让整个归属矩阵自相矛盾，后续所有 DDL 评审都会失去依据。

**影响范围**：层级定义、归属矩阵、状态总表的一级域划分。

**涉及模块**：`hse_assessment_*` 全域、`sys_operation_log`、权限相关表。

**是否需要代码修改**：否。
