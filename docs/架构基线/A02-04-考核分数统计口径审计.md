# A02-04-02｜考核分数统计口径审计

> 审计对象：`hse_assessment_deduction` → `hse_assessment_score(AUTO_TOTAL_SNAPSHOT)` → `hse_assessment_target.score_total` 全链
> 审计方式：**只读**。逐 target 三方比对 + 源代码读实现。共 12 组校验 SQL。
> 核心命题：**「有分数」≠「分数口径唯一」≠「分数可解释」**
> CODE CHANGE = 0 / DDL = 0 / DML = 0 / CONFIG CHANGE = 0。

## 2. 三层结构：事实 → 快照 → 人级总分

```text
【第 1 层 · 扣分事实】hse_assessment_deduction（940 行 / 有效 663 / 14,441.00 分）
        │  来源：规则引擎 adapter 月度扫描、事件服务、Excel 月度对齐回补
        │  口径：is_deleted=false AND deduction_source IN ('auto','chain_transmission')
        │        AND review_status <> 'rejected'
        ▼
【第 2 层 · 类别封顶】computeCategoryCappedScore()
        │  Σ_类别 min(该类扣分合计, hse_assessment_category_limit.max_deduct)
        │  特例：三违管理类别改用活源聚合 getEmployeeSanweiTotal()
        │  特例：否决项 > 0 → scoreAuto = 0
        ▼
【第 3 层 · 汇总快照】hse_assessment_score.metric_code='AUTO_TOTAL_SNAPSHOT'（942 行）
        │  raw_value = deduction_total = 封顶后扣分
        │  original_score = 100；final_score = 100 − 扣分
        ▼
【第 4 层 · 人级总分】hse_assessment_target
           score_auto  = max(0, 100 − 封顶后扣分)      ← 代码：assessmentScoringEngine.js:387-389
           score_total = COALESCE(score_manual,0) + score_auto + COALESCE(score_bonus,0)
                                                       ← 代码：assessmentScoringEngine.js:453
```

**关键：这条链上不经过任何指标行。** `recalculateTarget()` 只调 `computeCategoryCappedScore()`，后者只 `SELECT ... FROM hse_assessment_deduction`，**从不读 `hse_assessment_score` 的指标行**。

## 3. 校验一：快照扣分 vs 扣分明细求和

对每个 `(target_id, cycle_id)` 组合比对快照的 `deduction_total` 与扣分明细求和。

| 比对口径 | 相等数 / 总对数 | 一致率 |
|---|---:|---:|
| 对**全表含软删**求和 | 809 / 942 | 85.9% |
| 对**有效（`is_deleted=false`）**求和 | **921 / 942** | **97.8%** |
| 用 `confirmed_score` 优先（approved/adjusted） | **921 / 942** | **97.8%** |
| 与两种口径都不等 | **21** | 2.2% |

### 3.1 结论
**快照扣分 = 有效扣分求和**。这一点被 921/942 精确命中确认，不是近似。
`confirmed_score` 口径与 `suggested_score` 口径结果相同，因为 approved 的 122 条里 `confirmed_score` 仅 57 条非空、且与 `suggested_score` 不同的只有 **3 条**，差异未落在可分辨区间。

### 3.2 21 条不一致的构成

| 类型 | 行数 | 特征 |
|---|---:|---|
| 孤立周期 30~42 | 13 | 快照有 106/15 分，扣分明细求和 = 0 |
| cycle 53 中 target 不存在（1527/1529/1636/1638/1749/1753） | 6 | 快照 5.00 分，无对应扣分 |
| **cycle 53 中 target 存在但数值不符** | **2** | 见下表 |
| 合计 | **21** | |

| cycle | target | 快照扣分 | 明细求和 | 差异 |
|---:|---:|---:|---:|---:|
| 53 | 1301 | **6.00** | **156.00** | 快照少 150 分 |
| 53 | 1311 | **160.00** | **155.00** | 快照多 5 分 |

> 这 2 条是**真实的口径漂移**（快照未随扣分明细同步），不是孤儿数据。它们与 §8 的 cycle 53 事故同源。

## 4. 校验二：总分 = 100 − 快照扣分？

| 结果 | 行数 / 923 | 占比 |
|---|---:|---:|
| 成立 | **856** | 92.7% |
| 不成立 | **67** | 7.3% |

### 4.1 67 条不成立的全部原因：地板截断

| 检查 | 结果 |
|---|---|
| 67 条中 `score_manual` 非零 | **0** |
| 67 条中 `score_bonus` 非零 | **0** |
| 67 条满足 `score_total = 100 − 快照扣分 + manual + bonus` | **0** |
| 67 条的共同特征 | **快照扣分 > 100**，`score_total` 一律为 `0.00`，`grade` 一律为 `E` |

样例：

| target | cycle | 姓名 | `score_total` | 快照扣分 | grade |
|---:|---:|---|---:|---:|---|
| 559 | 27 | 张华平 | 0.00 | 102.00 | E |
| 568 | 27 | 谢俊章 | 0.00 | 106.00 | E |
| 605 | 28 | 王臣祥 | 0.00 | 110.00 | E |
| 812 | 45 | 张卫新 | 0.00 | 115.00 | E |
| 830 | 45 | 谢俊章 | 0.00 | 115.00 | E |
| 1210 | 51 | 李振恒 | 0.00 | 118.00 | E |

**⇒ 完整公式确认为：`score_total = max(0, 100 − 快照扣分)`，无人工干预项。**
856 + 67 = 923 ✅ 全覆盖。

## 6. 类别上限配置：合计 > 100 的结构性缺陷

`hse_assessment_category_limit` 共 12 行，按 `target_role` 分套：

### 6.1 manager 套（6 类）

| 类别 | `max_deduct` | 规则数 |
|---|---:|---:|
| 安全文化建设 | 20.00 | 1 |
| HSE教育培训 | 30.00 | 2 |
| 现场管理-驾驶员管理 | 20.00 | 1 |
| 现场管理-转运站管理 | 10.00 | 2 |
| 三违管理 | 15.00 | 3 |
| 否决项 | 100.00 | 1 |
| **合计** | **195.00** | 10 |

### 6.2 admin 套（4 类 + 2 行 NULL）

| 类别 | `max_deduct` | 规则数 |
|---|---:|---:|
| 目标职责 | 30.00 | 2 |
| HSE教育培训 | 30.00 | 3 |
| 三违管理 | 40.00 | 1 |
| 否决项 | 100.00 | 1 |
| 网格管理 | **NULL** | 0 |
| 网格管理 | **NULL** | 0 |
| **合计（可封顶部分）** | **200.00** | 7 |

### 6.3 两条缺陷

**① 上限之和远超总分 100。**
manager 195、admin 200。只要各类都有扣分，合计必然 > 100，结果一律 `score_total = 0`、`grade = E`。
⇒ **`E` 档的 75 人里，67 人是这样产生的**；剩下 8 人是真实低分（未跌破 0）。

**② `max_deduct IS NULL` ⇒ 完全不封顶。**
代码 `assessmentScoringEngine.js:375-378`：

```js
const cap = await getCategoryCap(cat, executor, role);
const capped = Number.isFinite(cap) ? Math.min(raw, cap) : raw;   // ← NULL → NaN → 取 raw，无上限
```

「网格管理」两行 `max_deduct` 为 `NULL`，一旦扣分被归入该类别，**没有任何上限**。这为 §8 的 cycle 53 事故提供了可解释路径（但本文未验证 cycle 53 的扣分是否确实归入该类别）。

## 7. 校验四：指标行扣分是否进入总分

### 7.1 全表唯一非零的指标行

```sql
SELECT cycle_id, metric_code, count(*), sum(deduction_total)
FROM hse_assessment_score
WHERE metric_code <> 'AUTO_TOTAL_SNAPSHOT' AND deduction_total <> 0
GROUP BY 1,2;
```

| cycle_id | metric_code | 行数 | 扣分合计 |
|---:|---|---:|---:|
| 28 | `HSE-KPI-HZD-001` | **2** | **13.00** |

**2728 条指标行中，只有 2 条扣分非零，其余 2726 条全部为 0。**

### 7.2 这 13 分去哪了

| target | 姓名 | 指标行扣分 | 指标行 final | 同 target 快照扣分 | 快照 final | `score_total` | `grade` |
|---:|---|---:|---:|---:|---:|---:|---|
| 595 | 刘金涛 | **12.35** | 7.65 | **0.00** | 100.00 | **100.00** | **A** |
| 596 | 张康 | **0.65** | 19.35 | **0.00** | 100.00 | **100.00** | **A** |

> 刘金涛 2026-06 隐患整改率 **38%**，`HZD-001` 已算出扣 **12.35 分**，最终考核 **100.00 分 / A 级**。
> **扣分算出来了，但 100% 被人级总分丢弃。**

### 7.3 机理

| 环节 | 事实 |
|---|---|
| 指标行由谁写 | **无代码路径**（见 A02-04-01 §6.3） |
| 总分由谁算 | `computeCategoryCappedScore()` → 只读 `hse_assessment_deduction` |
| 扣分明细表里有 `HZD-001` 吗 | **0 行**（A02-02 §6.3 已确认隐患域扣分 0 行） |
| ⇒ 结论 | **指标行与总分是两条互不相通的平行链**。指标行是「装饰性明细」，总分只认扣分明细表。 |

### 7.4 对既有结论的修正

| 既有结论 | 本文修正 |
|---|---|
| A02-02 §2.1：「`HZD-001` 实际产出 **0**」 | **表述需收窄**：`hse_assessment_deduction` 中 0 行 ✅；但 `hse_assessment_score` 中 **有 2 行、13.00 分**。准确说法是「扣分明细表 0 行，指标评分表 2 行 13 分，且未进入人级总分」 |
| A02-02 §8：「隐患域在考核体系中的实际贡献 = 0 行扣分 / 0 分」 | **在扣分明细口径下成立**；在指标评分表口径下为 **2 行 / 13 分（仍为 0 有效贡献，因未入总分）** |
| A02-01 §3「合计实际扣分 663 行」 | ✅ 复核一致（有效口径 663 / 14,441.00 分） |
| A02-02 §5.2「940 行 / 15 个 metric_code」 | ✅ 全表口径正确；但有效口径只有 **9 个码**（`NEG-001/002/003` 各 6 行全为软删） |

## 8. 排名口径：不存在

### 8.1 事实

| 检查 | 结果 |
|---|---:|
| `rank_all` 非空 / 925 | **0** |
| `rank_township` 非空 / 925 | **0** |
| 有排名需求的页面 | `views/hse/assessment-monthly/targets.vue:118-119`（「乡镇排名」「总排名」两列） |
| 数据库里有排名吗 | **没有** ⇒ 这两列**永远空白** |

### 8.2 为什么永远为空：冻结流程结构上不可达

`rank_all` / `rank_township` **只在冻结事务内写入**（`assessmentMonthlyFreezeService.js:56-79`，`ROW_NUMBER() OVER (ORDER BY score_total DESC)`）。

而冻结的前置门禁（同文件 `:34-46`）：

```js
// 还有 N 个对象未完成审核，不可冻结
if (parseInt(pendingResult.rows[0].cnt) > 0) { ROLLBACK; return 409; }
```

实测每个周期的「未审核有效扣分」数量：

| cycle | 年月 | 状态 | 未审核扣分 |
|---:|---|---|---:|
| 24 | 2026-08 | pending_review | 3 |
| 27 | 2026-07 | pending_review | 32 |
| 28 | 2026-06 | pending_review | 43 |
| 43 | 2026-09 | in_progress | 60 |
| 44 | 2025-08 | pending_review | 66 |
| 45 | 2025-09 | in_progress | 29 |
| 46 | 2025-10 | in_progress | 46 |
| 47 | 2025-11 | in_progress | 25 |
| 48 | 2025-12 | in_progress | 29 |
| 49 | 2026-01 | in_progress | 26 |
| 50 | 2026-02 | in_progress | 29 |
| 51 | 2026-03 | in_progress | 28 |
| 52 | 2026-04 | in_progress | 31 |
| 53 | 2026-05 | pending_review | **101** |

**14 个周期，最少 3、最多 101，全部 > 0。** ⇒ **冻结永远返回 409，rank 永远不写。**

### 8.3 三处排名口径并存

| # | 位置 | 取数 | 当前可用性 |
|---:|---|---|---|
| 1 | 数据库 `target.rank_all` / `rank_township` | 冻结时 `ROW_NUMBER()` 写入 | **永久 NULL** |
| 2 | 导出 `assessmentMonthlyExportService.js:40` | `ORDER BY rank_all ASC, score_total DESC` | `rank_all` 全 NULL ⇒ **排序退化为 `score_total DESC`**（`NULLS` 默认在 DESC 后，实际等价于仅按分数排） |
| 3 | 导出 `:207` | `ORDER BY t.score_total DESC NULLS LAST` | 按分数现排，**与 #1 不是同一口径** |

> 同一份导出里，两个方法用两套排序：一个依赖恒 NULL 的 `rank_all`，一个直接按 `score_total`。结果虽大概率相同，但**语义不同**（排名 vs 分数）。

## 10. 口径答案汇总（同一问题，五套答案）

**问题：「某人某月考核得了多少分？」**

| # | 口径 | 取数 | 2026-06（cycle 28）示例 |
|---:|---|---|---|
| 1 | 人级总分 | `target.score_total` | 刘金涛 **100.00** |
| 2 | 汇总快照 | `score WHERE metric_code='AUTO_TOTAL_SNAPSHOT'` 的 `final_score` | 刘金涛 **100.00**（与 1 恒等） |
| 3 | 扣分明细反推 | `100 − Σ有效扣分` | 刘金涛 **100.00**（无扣分） |
| 4 | **指标行反推** | `Σ 指标行 final_score` | 刘金涛 `HZD-001` **7.65** + 其余 17 项… |
| 5 | 导出排名序 | `ORDER BY score_total DESC` | 按分数排序，无绝对位次 |

**问题：「某人为什么得这个分？」**

| 口径 | 可解释性 |
|---|---|
| 扣分明细 | ✅ 可逐条追溯（但 `source_id` 81.2% 为空，只能追到表） |
| 汇总快照 | ❌ `data_sources` 0/942 全 NULL，无来源信息 |
| 指标行 | ❌ 与总分无因果关系，且 74% 的行无代码可产生 |

> **这是考核域最核心的架构缺口：分数可信、但不可解释。**
> 用户看到的 100 分，无法从任何一处数据完整还原出「为什么是 100 分」。

## 11. 本章判定

```text
人级总分事实源              = 唯一（hse_assessment_target.score_total）
总分公式                    = max(0, 100 − 类别封顶后扣分)，无人工项
  score_manual / score_bonus 实际参与 = 0（925 行全 NULL）

快照 = 有效扣分求和         = 921 / 942（97.8%）
  不一致                    = 21（孤立周期 13 + 悬挂 target 6 + 真实漂移 2）
总分 = 100 − 快照扣分        = 856 / 923（92.7%）
  不成立的 67 条            = 全部地板截断（扣分 > 100 → 0），非另有算法

类别封顶
  manager 上限合计          = 195（> 总分 100）
  admin 上限合计            = 200（> 总分 100）
  max_deduct IS NULL 类别   = 2 行（网格管理）⇒ 不封顶
  封顶实际削减              = 102.00 分（占有效扣分 0.71%）

指标行 → 总分的因果          = 不存在
  指标行非零扣分            = 2 行 / 13.00 分（HZD-001 / 2026-06）
  该扣分进入总分            = 否（对应 2 人 score_total=100.00 / grade=A）

排名
  rank_all 非空             = 0 / 925
  rank_township 非空        = 0 / 925
  根因                      = 冻结门禁不可达（14 周期未审核数 3~101 全 > 0）
  冻结过的周期              = 0

口径数量（"得多少分"）      = 5 套（其中 2 套不可解释）

CODE CHANGE = 0   DDL = 0   DML = 0   CONFIG CHANGE = 0
```
