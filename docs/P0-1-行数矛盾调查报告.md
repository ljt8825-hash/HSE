## 一、问题概述

Sprint-B v2.1 的 B-2 迁移源表 `hse_employee_relation` 的行数存在一组无法互证的矛盾数字：

| 数字 | 出处环境（文档自称） | 出现位置 |
|------|---------------------|---------|
| **1,304** | 生产审计环境（Pre-risk）+ 当前本地开发环境（实测） | Pre-risk 审计 §1.2；TRAE-Step1 §3.1 |
| **3,156** | 测试环境 / Dry Run（模拟生产配置） | Dry Run R2 §3.4（`her_current_count`） |

- 差值：**1,852 条**，约为 2.4 倍。
- 现状：**无任何文档对 1,304 ↔ 3,156 的差异来源做出解释或标注**（跨文档综合分析报告 §1.2-A 已记录此矛盾，但仅指出"未对齐"，未归因）。
- 风险定性：**P0**。B-2 迁移依赖"动态基线校验"（`actual_migrate_count` 对比 `her_current_count` 基线，允许 ±2%）；若生产实际行数与沿用基线不符超过 2%，迁移 SQL 会直接 `RAISE EXCEPTION` 失败。错误基线将导致生产迁移在 Step 2 即中止。

## 三、差异分析

针对用户提出的 4 类可能原因逐一排查：

### 3.1 假设 A：不同环境（生产 vs DR / 测试）数据量差异

- **证据支持度：高（最可能）**
- Dry Run R2 报告头明确写"执行环境：测试环境（模拟生产配置）"；Pre-risk 审计与 TRAE-Step1 指向"生产审计环境 / 当前本地环境"。
- TRAE-Step1 §3.1 A 组在当前本地环境实际查询得 `hse_employee_relation = 1,304`，与 Pre-risk 审计 1,304 **完全一致** → 说明"1,304 所在环境"的数据量是稳定且可复现的。
- 3,156 仅出现在 Dry Run 测试环境，且该环境据文档描述进行了"模拟生产配置"的种子数据准备（Dry Run R2 全流程含 B-0 恢复 1,287、B-2 迁移 3,156，量级明显大于生产审计环境）。
- **推论**：两环境数据量本身不同，3,156 是测试环境种子数据规模，1,304 是生产审计/本地环境规模。差异来源为**环境数据基数不同**，而非同一环境的统计偏差。

### 3.2 假设 B：统计口径不同（含/不含 is_deleted、is_current）

- **证据支持度：低（基本可排除）**
- 1,304 的口径：Pre-risk §1.2 记为"总数 1,304，全部 is_deleted=false、is_current=true"；TRAE-Step1 §3.1 B 组实测 1,304 行**全部**满足 `is_deleted=false AND is_current=true AND status='active'`。
- 3,156 的口径：Runbook Check 0.12 定义 `her_current_count = COUNT(*) FROM hse_employee_relation WHERE is_current=true AND is_deleted=false`；B-2 迁移 SQL 同样 `WHERE is_deleted=false AND is_current=true`。
- **两处口径逐字一致**（均 `is_current=true AND is_deleted=false`）。若在同一环境用同一口径查询，结果应一致。故"统计口径不同"**不是**差异原因——差异在于环境数据量，而非筛选条件。

### 3.3 假设 C：时间差异（Dry Run 后数据新增/删除）

- **证据支持度：低**
- Pre-risk 审计、Dry Run R2、TRAE-Step1 的编制/执行日期均为 **2026-07-28**（同日）。
- 若 3,156 与 1,304 来自同环境不同时间点，需有"当日数据被大量插入/删除"的证据，但无任何文档提及 `hse_employee_relation` 在 7-28 当日发生过批量变更。
- 反而，TRAE-Step1 在当前环境实测 1,304 且无重复、无软删、无历史版本 → 该环境数据是"干净稳态"，不支持"同日被改大"的猜测。
- **推论**：时间差异可能性低；更可能是两数字是不同环境各自稳态的快照。

### 3.4 假设 D：Dry Run 基线包含了 `hse_employee_org` 的数据

- **证据支持度：低（可排除）**
- B-2 迁移 SQL 源仅 `FROM hse_employee_relation her`，**不含** `hse_employee_org`（见 Baseline-Validation-Fix §2.3、Runbook §7.1）。
- Runbook Check 0.8「数据差异基线」将 `heo / ea / her / ea_only` **分列**为四个独立指标，`her` 是独立 metric，不与 `heo` 合并。
- 数值反证：1,304 + 1,285（hse_employee_org 数）= 2,589 ≠ 3,156；`her ∪ heo` 并集员工数（TRAE-Step1 §3.1 E 组）= 1,343 ≠ 3,156。即 3,156 **不等于**两表任何简单合并，排除"基线混入旧表"的假设。
- **推论**：3,156 纯粹是 `hse_employee_relation` 在测试环境的行数，未混入 `hse_employee_org`。

### 3.5 附加排查：3,156 是否可能是重复/笛卡尔积

- Dry Run R2 §3.4 Step 1.5 脏数据检查 `duplicate_count = 0`（无重复当前关系）。
- TRAE-Step1 §3.1 D 组在当前环境查 `HAVING count(*) > 1` 返回 0 行（无重复 employee_id）。
- 两环境均无重复证据 → 3,156 不是脏数据/重复导致，就是测试环境该表确有 3,156 行。

## 四、结论

### 4.1 数字可信度判定（事实 + 评价）

| 数字 | 可信度 | 依据 |
|------|--------|------|
| **1,304** | **高** | 双源互证：Pre-risk 审计（生产审计环境）+ TRAE-Step1 本地环境真实 SQL 实测，结果一致；且当前环境数据呈"干净稳态"（无软删/无重复/无历史版本），可复现。 |
| **3,156** | **中（仅限测试环境）** | 仅 Dry Run R2 单源声明，测试环境产物；无执行 SQL 文本留痕、无独立佐证；但数量本身（测试环境 3,156 行）自洽（基线=实际=回滚量，偏差 0%）。**不可外推为生产行数**。 |

### 4.2 矛盾根因结论（评价，已标注）

> **根因：环境数据基数不同，而非统计口径、时间、或表合并问题。**
> 1,304 来自生产审计/本地环境，3,156 来自 Dry Run 测试环境，二者是不同数据库实例的各自稳态快照。文档体系从未在"基线锁定"环节声明"基线必须在目标生产库重新采集"，导致 Dry Run 测试环境的 3,156 被当作可复用的生产基线引用，埋下生产迁移中止风险。

### 4.3 生产执行证据缺口（事实）

- B-2 执行报告、Step0 执行报告均为**空白模板**，未填实际 her 基线值。
- 即：截至目前，**没有任何文档证明生产环境已实际执行 B-2 并得到真实 `her_current_count`**。若"DBA 签字"是基于这些空白模板，则签字缺乏实际执行数据支撑（与跨文档分析报告中"签字空白却给 PASS"的治理缺口一致）。

## 五、建议

### 5.1 立即执行（生产迁移前强制，P0）

1. **生产库重新基线化（不可省略）**
   - 在生产目标库执行 Runbook Check 0.12 / Check 0.8，采集真实 `her_current_count`（`SELECT COUNT(*) FROM hse_employee_relation WHERE is_current=true AND is_deleted=false`）。
   - **严禁**将 Dry Run 的 3,156 直接写入 `migration_baseline` 作为生产基线。
   - 将真实值填入 `Sprint-B-Step0-Execution-Report.md` 的 her= 栏（当前为空白）。

2. **动态基线校验阈值确认**
   - 若生产真实行数 = 1,304（与本地/审计一致），则 `migration_baseline.her_current_count` 必须 = 1,304；任何沿用 3,156 的写法都会使 B-2 在 Step 2 触发 `RAISE EXCEPTION`（偏差 ≈ 59% ≫ 2%）。
   - 反之若生产实际有 3,156，则基线填 3,156，但需解释为何生产数据量远大于前期审计（可能生产库有额外历史数据）。

### 5.2 短期补证（P1）

3. **调查 Dry Run 测试环境 3,156 的来源**
   - 若可访问 Dry Run 测试库，查询该环境 `hse_employee_relation` 的创建时间分布、`created_by` 分布、是否有批量种子脚本，确认 3,156 是否为测试种子数据。
   - 产出一份"差异归因说明"文档，补入 Production-Ready-Report 或单独附录，闭合跨文档分析的遗留项。

4. **填实执行报告**
   - 若生产迁移已执行：将 Step0 / B-2 执行报告的实际值（her 基线、插入记录数、偏差%）补全，并由 DBA 现场签字（禁代签）。
   - 若尚未执行：按 5.1 新基线执行，再填实报告。空白模板+签字=无效放行。

### 5.3 流程改进（P2，防止复发）

5. **在 Runbook 中增加"基线绑定目标环境"约束**
   - 明确：`migration_baseline` 的 `her_current_count` 必须由"本次生产执行所在库的 Check 0.12 实时采集"，禁止从 Dry Run 报告复制数值。
   - 建议在 Step 0 报告新增一行"基线来源库标识（IP/库名）"，使基线可追溯。

6. **统一口径声明**
   - 在所有涉及 `hse_employee_relation` 计数的文档顶部加一行："本数字对应环境 = ___，统计条件 = `is_current=true AND is_deleted=false`"，避免读者混淆环境。
