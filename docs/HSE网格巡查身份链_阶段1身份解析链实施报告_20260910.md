## 三、身份解析链路

```text
req.user.id                      （authMiddleware 注入，唯一认证身份来源）
   ↓
public.users.id                  （显式 schema，且 is_active = true）
   ↓
public.users.employee_id         （阶段0 落地：bigint NULL，部分唯一索引）
   ↓
public.employee.id               （显式 schema，存在性 + 未失效校验）
   ↓
{ ok:true, userId, employeeId, employeeName }
```

任一步失败 → 立即返回结构化失败结果，**不回退、不猜测**。

对外暴露两个入口：

| 函数 | 入参 | 用途 |
|---|---|---|
| `resolveAuthenticatedEmployee(userId, { client, logger })` | 用户 ID | 核心解析，支持注入事务 `client` |
| `resolveAuthenticatedEmployeeFromRequest(req, opts)` | Express Request | 只读取 `req.user.id`，阶段2 路由推荐入口 |

## 四、resolver 实现说明

1. **显式 schema**：SQL 一律写 `public.users` / `public.employee`，不依赖 `search_path`（当前为 `"$user", public`），杜绝未来 schema 歧义。
2. **每次实时查库**：不在 JWT / 会话中缓存 `employee_id`，绑定关系变更即时生效，也避免"改绑定需重新登录"的运维陷阱。
3. **只 SELECT**：模块内无任何 `INSERT/UPDATE/DELETE/ALTER`（静态审计命中 0）。
4. **注入式事务支持**：`opts.client` 允许调用方传入连接，测试可在事务内构造数据后 `ROLLBACK`，生产零残留。
5. **日志脱敏**：异常详情仅写服务端日志（仅含 `e.message`），对外 `message` 为固定安全中文提示，不含 SQL、内部路径、`password_hash`、手机号。
6. **不返回敏感字段**：成功只回 `userId / employeeId / employeeName`；用户表查询只取 `id, employee_id` 两列。

## 五、Fail-Closed 规则

| 失败码 | HTTP | 触发条件 | 对外提示 |
|---|---|---|---|
| `AUTH_USER_REQUIRED` | 401 | `req.user` 缺失或 `req.user.id` 不是正整数 | 未获取到登录身份，请重新登录后再操作。 |
| `AUTH_USER_NOT_FOUND` | 401 | `public.users` 中查不到该 id，或 `is_active = false` | 当前登录账号不存在或已停用，请联系管理员处理。 |
| `EMPLOYEE_NOT_BOUND` | 403 | 用户存在但 `employee_id IS NULL`（**含姓名可匹配的情形**） | 当前登录账号未绑定员工档案，请联系管理员完成绑定。 |
| `EMPLOYEE_NOT_FOUND` | 409 | `employee_id` 在 `public.employee` 中不存在 | 当前登录账号绑定的员工档案不存在，请联系管理员处理。 |
| `EMPLOYEE_DELETED` | 409 | 该员工 `is_deleted = true` | 当前登录账号绑定的员工档案已失效，请联系管理员处理。 |
| `IDENTITY_LOOKUP_FAILED` | 503 | 查询异常（fail-closed，禁止吞异常继续） | 身份解析服务暂不可用，请稍后重试。 |

**严禁的旁路（代码层面已物理杜绝）**：`realName → employee.name`、模糊/contains 匹配、姓名+部门、姓名+手机、同名任选其一。解析器源码不含 `real_name`、`v_employee_current` 任何引用（静态审计命中 0）。

> 说明：`EMPLOYEE_DELETED` 是在规格「至少验证 employee.id 确实存在」之上的**加强**门禁，符合本链路 fail-closed 原则；若业务上需要允许绑定已删除员工，可单独评审移除。

## 八、姓名兜底禁止验证（本阶段最重要）

采用**对照组**证明，而非仅断言：

| 组 | 输入 | 结果 |

```text

+ realName 在花名册唯一可匹配
= FAIL（禁止姓名兜底）
```

## 十四、风险与观察项

1. **【观察】解析器当前无生产调用方**：仅测试脚本引用。这是阶段1 的预期终点，但它意味着 fail-closed 尚未在真实链路上生效——阶段2 接入前，`POST /api/site/grid-records` 的 PG 分支仍无身份概念。
2. **【观察】并存双链路**：旧 WPS 链路用姓名兜底、新链路 fail-closed。在阶段4 完成账号绑定前，若直接把新解析器接到旧 WPS 入口，会导致**所有未绑定账号（含 admin）创建巡查全部失败**——切换必须与账号初始化同批进行，不可提前。
3. **【观察】`EMPLOYEE_DELETED` 为规格外加强门禁**：若后续业务需要允许绑定已删除员工，需单独评审。
4. **【观察】`is_active=false` 与"用户不存在"合并为同一错误码** `AUTH_USER_NOT_FOUND`：为避免账号枚举而刻意不区分，若运维排障需要区分，可在服务端日志补充。
5. **【遗留，非本阶段】** `site-mgmt.js:1534` grid-records 列表用 `SELECT *`，响应会多带 `inspector_employee_id: null`（阶段0 已记录，良性，按纪律未顺手改）。
6. **【风险·低】** 每次解析为 2 次单表主键查询（均可走索引），高频调用下无明显开销；若未来出现性能敏感场景，可在请求级（`req` 上）做一次性缓存——但**禁止**缓存进 JWT。

## 十五、下一阶段建议（阶段2）

1. `POST /api/site/grid-records` 的 **PG 分支**在 INSERT 前调用 `resolveAuthenticatedEmployeeFromRequest(req)`，失败整单拒绝（返回其 `httpStatus` + `message`）。
2. 成功时把 `employeeId` 写入 `inspector_employee_id`；**不**从请求体读取任何 `inspectorEmployeeId`（前端不得传、不得覆盖）。
3. 白名单 UPDATE 中**不包含** `inspector_employee_id`，保证历史身份不可变。
4. 切换策略建议：与阶段4（账号绑定初始化）**同批灰度**，避免未绑定账号大面积失败；先内部账号验证，再推广网格负责人。
5. 保留 WPS 分支现状直到阶段4 完成，不做单边切换。
