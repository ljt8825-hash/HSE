**文档版本**：v1.0  
**编制日期**：2026-07-28  
**编制依据**：《人员中心数据一致性审计报告》2026-07-28  
**适用范围**：HSE 系统「人员管理」模块后端重构  
**约束条件**：不直接修改前端页面代码

## 一、问题确认

基于对数据库结构、ORM/代码链路、人员导入流程、模块关联关系的完整审计，当前已确认以下五类核心问题：

### 1.1 employee / personnel 多主表问题

- 系统内同时存在 `employee` 表（v59 Sprint5.1 统一主表）和 `personnel` 表（早期独立路由 `personnel.js` 使用）
- `personnel` 表字段集与 `employee` 重叠度高（name、id_card、phone、dept、position 等），但无外键关联到 `employee`
- 前端部分页面仍通过 `/personnel` 接口查询人员，形成独立的「第二人员主数据」
- **风险**：同一员工在两个表中可能拥有不同的 `id`，导致业务模块关联时数据不一致

### 1.2 employee_assignment 与 hse_employee_org 双任职关系问题

| 维度 | employee_assignment | hse_employee_org |
|---|---|---|
| 创建时间 | Sprint6.3-A-2（统一员工关系模型） | Sprint5.1（v59 原始设计） |
| 结构 | 扁平：`org_unit_id` + `operation_unit_id` + `position_id` | 树形：`group_id/region_id/enterprise_id/project_id/team_id` |
| 当前写入方 | `hse-employee-import-v2.js`（花名册 V2） | `hse-employee.js`（员工管理 V1） |
| 当前读取方 | `v_employee_current`、预警中心、风险画像、驾驶舱 | 员工档案详情中的「组织关系历史」 |

- **风险**：V1 调岗写入 `hse_employee_org` 后，预警中心/风险画像因只读 `employee_assignment` 而查不到任职关系；V2 导入写入 `employee_assignment` 后，员工档案的「组织变更历史」查询不到记录

### 1.3 deleted_at 与 is_deleted 字段冲突问题

- 当前所有人员相关表的真实结构仅定义了 `is_deleted BOOLEAN NOT NULL DEFAULT FALSE`
- 代码中多处（`hse-employee-import-v2.js` 的 `clear-all`、`delete batch`）执行 `UPDATE ... SET is_deleted = true, deleted_at = CURRENT_TIMESTAMP`
- `deleted_at` 列在 `employee`、`employee_assignment`、`employee_import_pending`、`employee_import_batch`、`hse_employee_org` 表中均**不存在**
- **直接后果**：执行「清空人员信息」操作时，数据库抛出 `列 "deleted_at" 不存在` 错误

### 1.4 花名册导入失败原因

**报错 1**：`Cannot read properties of null (reading 'target_position_id')`

- 位置：`hse-employee-import-v2.js:639`
- 根因：当 Excel 行的 `raw_position` 为空字符串时，`matchPosition()` 返回 `null`，后续代码直接访问 `posMatch.target_position_id`
- 同文件 L609 使用了正确的 `posMatch?.target_position_id || null`，但 L639 遗漏了可选链

**报错 2**：`employee` 表 INSERT 语句包含 `name_encrypted`、`source`、`status` 三个**不存在的字段**
- 位置：`hse-employee-import-v2.js:941-945`
- 根因：V2 导入代码假设了 `employee` 表有这些字段，但 `v59` 真实定义中不存在
- 该错误在正式入库流程（`/batch/:batchId/import`）中触发，导致无法完成导入

### 1.5 业务模块关联不统一问题

| 模块 | 关联字段 | 是否统一使用 employee.id | 问题 |
|---|---|---|---|
| 员工档案 | `employee_id` | 是 | 查询来源为 `v_employee_current`，底层是 `employee_assignment` |
| 三违管理 | `violator_id` + `violator_name` | 否 | `violator_id` 允许为 NULL，此时仅靠姓名展示，无法联动 |
| 培训管理 | `employee_id` + `personnel_id` | 否 | 双字段并存，`personnel_id` 实际为工号，前端可能只填其一 |
| 风险画像 | `employee_id` | 是 | 基于 `employee_assignment` 查询，与 V1 调岗数据不同步 |
| 事故管理 | `employee_id` | 是 | 通过 `employee.id` 关联 |
| 隐患管理 | `employee_id` | 是 | 通过 `employee.id` 关联 |

## 二、目标架构设计

### 2.1 最终目标

形成唯一的人员主数据中心：

```
employee（员工身份主表）
    ↓
employee_assignment（统一任职关系表）
    ↓
organization / position / team（组织、岗位、班组）
```

### 2.2 表职责定义

| 表名 | 职责 | 是否保留 |
|---|---|---|
| `employee` | 唯一员工身份主表（姓名、身份证、手机、出生日期等） | 保留，作为根 |
| `employee_assignment` | 唯一任职关系表（组织单元、作业单元、岗位、上级、起止时间） | 保留，替代 `hse_employee_org` |
| `department` | 五级组织树（集团/区域/企业/项目/班组） | 保留 |
| `position` | 岗位定义 | 保留 |
| `hse_employee_org` | 原 V1 任职关系表 | **冻结，不再写入，仅保留读取兼容** |
| `personnel` | 旧独立人员表 | **冻结，标记 deprecated** |
| `employee_history` | 人事变动审计记录 | 保留 |

### 2.3 employee_assignment 是否替代 hse_employee_org

**结论：employee_assignment 替代 hse_employee_org，但保留 hse_employee_org 作为只读兼容视图来源。**

**理由**：
1. `employee_assignment` 是 Sprint6.3 后明确的「统一员工关系模型」，预警中心、风险画像、驾驶舱已全部基于该表开发
2. `hse_employee_org` 的五级组织字段（`group_id/region_id/.../team_id`）可通过 `org_unit_id` 关联到 `department` 表获得等效信息
3. 直接删除 `hse_employee_org` 会破坏 V1 员工档案页面的「组织关系历史」查询，需逐步迁移

**保留口径（已统一）**：
- `hse_employee_org` 已于 Sprint-C Phase 1 完成迁移，生产代码 0 处写入操作
- 历史数据已通过 Sprint-B B-2 迁移至 `employee_assignment`（`remark` 字段标记来源）
- `hse_employee_org` 永久冻结为只读审计表，禁止 INSERT/UPDATE/DELETE/DROP/TRUNCATE，仅允许 SELECT
- 前端「组织关系历史」查询应从 `employee_assignment` + `employee_history` 获取
- 旧表保留用于审计、回溯、历史数据查询，**不设废弃时间点**（详见 Sprint-C Legacy_Table_Lifecycle_Report）

## 三、数据库调整方案

### 3.1 是否修改 employee 表

**否。**

`employee` 表当前字段（v59 + v60）已满足身份主数据需求：

```text
id, employee_code, id_card, id_card_hash, name, gender, birth_date,
phone, phone_hash, person_category, person_type, is_public_welfare,
id_address, created_at, updated_at, is_deleted
```

V2 导入代码中错误地写入了 `name_encrypted`、`source`、`status`，应**修正代码**而非修改表。

### 3.2 是否修改 employee_assignment 表

**否。**

当前字段已满足统一任职关系需求：

```text
id, employee_id, org_unit_id, operation_unit_id, position_id, supervisor_id,
is_current, status, is_primary, start_date, end_date, remark,
created_by, created_at, updated_at, is_deleted
```

### 3.3 是否保留 hse_employee_org

**保留，永久冻结只读（仅审计用途）。**

- 不删除表，不删除数据，不执行 DROP / TRUNCATE / ALTER
- `hse-employee.js` 中的写入接口（调岗、分配组织关系）已于 Sprint-C Phase 1 完成迁移至 `employee_assignment`
- 查询接口（员工详情中的 org 信息）已切换至 `employee_assignment` + `hse_org_unit`
- 通过 `hse_employee_org_ReadOnly_Change.sql` 创建 BEFORE 触发器，阻断 INSERT/UPDATE/DELETE
- 保留期限：**永久**（与 `hse_employee_relation` 同等处理，不设废弃时间点）
- 详见：Sprint-C-v1.0/03_Governance/Legacy_Table_Lifecycle_Report.md

### 3.4 是否废弃 personnel

**是，标记 deprecated，冻结写入。**

- `personnel.js` 的 POST/PUT/DELETE 接口返回提示：「人员管理已迁移至员工主数据中心，请使用 /employees 接口」
- 前端页面不改，但后端不再接受 personnel 表的新增/修改
- 现有数据保留，仅做查询兼容

### 3.5 是否需要新增字段

**不需要新增业务字段。**

但需补充 `deleted_at` 审计字段（见 3.6 重新评估）。

### 3.6 重新评估 deleted_at 方案

#### 方案 A：继续使用 is_deleted（不改表结构）

**做法**：将代码中所有 `, deleted_at = CURRENT_TIMESTAMP` 移除，仅保留 `is_deleted = true`。

**优点**：
- 零数据库变更，风险最低
- 与现有 v59/v60 所有表结构保持一致
- 不影响已有视图、索引、查询

**缺点**：
- 无法记录「何时被删除/清空」，审计能力不足
- 后续如需审计删除时间，仍需补列
- 代码中已经写了 `deleted_at`，说明设计意图上期望有此字段

#### 方案 B：增加 deleted_at 列

**做法**：为 `employee`、`employee_assignment`、`employee_import_pending`、`employee_import_batch` 增加 `deleted_at TIMESTAMPTZ` 列。

**优点**：
- 保留精确删除时间，满足审计需求
- 与代码中已有的 `deleted_at = CURRENT_TIMESTAMP` 语句匹配
- 为后续数据恢复、操作追溯提供时间依据

**缺点**：
- 需要执行 4 条 `ALTER TABLE`，有数据库变更风险
- 所有基于 `WHERE is_deleted = false` 的查询不受影响，但新增列后需确认无隐式依赖
- 需同步更新迁移脚本，确保新环境自动包含该列

#### 推荐方案：方案 A（继续使用 is_deleted）

**理由**：
1. 项目当前处于「修复报错」阶段，首要目标是恢复功能可用，而非增强审计
2. 增加列属于结构变更，需重启/验证所有基于这些表的查询，引入额外回归测试成本
3. `updated_at` 字段已存在，可通过 `updated_at` 近似推断删除时间，满足基本审计需求
4. 如果后续 Sprint 有明确审计增强需求，可单独立项补充 `deleted_at` + 触发器
5. 修改代码比修改数据库结构风险更低、回滚更容易

**执行**：将 `hse-employee-import-v2.js` 中 6 处 `deleted_at = CURRENT_TIMESTAMP` 删除。

## 五、业务模块影响分析

### 5.1 员工档案

- **当前查询**：通过 `/employees/:id` 获取 employee 基本信息 + `hse_employee_org` 当前组织关系
- **影响**：V1 调岗后，`hse_employee_org` 仍有数据，短期内无异常；长期需将档案页的 org 查询切换到 `employee_assignment`
- **行动**： Sprint B 中将 `hse-employee.js` 的员工详情查询改为优先查 `employee_assignment`

### 5.2 三违管理

- **当前查询**：`violation_records.violator_id` 关联 `employee.id`
- **影响**：`violator_id` 为 NULL 的记录无法联动员工档案
- **行动**：Sprint C 中编写回填 SQL，根据 `violator_name` + `id_card` 回查 `employee.id` 补全 `violator_id`
- **修改范围**：仅后端查询与回填，不修改前端

### 5.3 培训管理

- **当前查询**：`training_records.employee_id` + `personnel_id` 双字段
- **影响**：`personnel_id` 为工号，`employee_id` 为主键，两者可能不一致
- **行动**：Sprint C 中确认所有培训记录已有 `employee_id`，将 `personnel_id` 标记为展示冗余；新增记录时强制要求 `employee_id`
- **修改范围**：后端接口校验 + 数据回填

### 5.4 风险画像

- **当前查询**：基于 `employee_assignment` 关联三违、培训、事故数据
- **影响**：V1 调岗数据写入 `hse_employee_org`，风险画像查询不到最新任职关系
- **行动**：Sprint B 中统一写入 `employee_assignment` 后，风险画像数据自动同步，无需修改查询逻辑

### 5.5 事故管理

- **当前查询**：通过 `employee_id` 关联
- **影响**：无，已统一使用 `employee.id`
- **行动**：无需修改

### 5.6 隐患管理

- **当前查询**：通过 `employee_id` 或 `responsible_person_id` 关联
- **影响**：无，已统一使用 `employee.id`
- **行动**：无需修改

## 六、数据迁移方案

### 6.1 迁移顺序

```
Step 1: employee 确认
    ↓ 确认 employee 表为唯一身份主表， personnel 不再写入
Step 2: employee_assignment 生成
    ↓ 将 hse_employee_org 中 is_current=true 的数据映射到 employee_assignment
Step 3: hse_employee_org 处理
    ↓ 冻结写入，保留只读
Step 4: personnel 冻结
    ↓ 停止写入，保留查询兼容
Step 5: 业务数据回填
    ↓ 补全 violation_records.violator_id、training_records.employee_id
```

### 6.2 迁移 SQL 思路

#### Step 2：hse_employee_org → employee_assignment 映射

```sql
-- 将当前有效的 hse_employee_org 记录映射到 employee_assignment
-- 注意：org_unit_id 需要通过 team_id/project_id/enterprise_id 找到对应的 hse_org_unit.id
-- 如果找不到对应 org_unit，则 org_unit_id 设为 NULL，remark 标记来源

INSERT INTO employee_assignment (
    employee_id, org_unit_id, position_id, supervisor_id,
    is_current, is_primary, status, start_date, end_date,
    remark, created_at, updated_at, is_deleted
)
SELECT 
    eo.employee_id,
    -- 通过 team_id → project_id → enterprise_id 找到对应 org_unit
    COALESCE(
        (SELECT id FROM hse_org_unit WHERE dept_ref_id = eo.team_id LIMIT 1),
        (SELECT id FROM hse_org_unit WHERE dept_ref_id = eo.project_id LIMIT 1),
        (SELECT id FROM hse_org_unit WHERE dept_ref_id = eo.enterprise_id LIMIT 1)
    ) AS org_unit_id,
    eo.position_id,
    eo.supervisor_id,
    eo.is_current,
    true AS is_primary,
    COALESCE(eo.status, 'active') AS status,
    eo.start_date,
    eo.end_date,
    'migrated_from_hse_employee_org' AS remark,
    eo.created_at,
    eo.updated_at,
    eo.is_deleted
FROM hse_employee_org eo
WHERE eo.is_current = true
  AND eo.is_deleted = false
  AND NOT EXISTS (
      SELECT 1 FROM employee_assignment ea
      WHERE ea.employee_id = eo.employee_id AND ea.is_current = true
  );
```

#### Step 5：业务数据回填

```sql
-- 三违管理：根据姓名回查 employee_id
UPDATE violation_records vr
SET violator_id = e.id
FROM employee e
WHERE vr.violator_id IS NULL
  AND vr.violator_name = e.name
  AND e.is_deleted = false;

-- 培训管理：根据 personnel_id（工号）回查 employee_id
UPDATE training_records tr
SET employee_id = e.id
FROM employee e
WHERE tr.employee_id IS NULL
  AND tr.personnel_id = e.employee_code
  AND e.is_deleted = false;
```

### 6.3 数据校验方法

1. **employee 唯一性校验**：
   ```sql
   SELECT employee_code, COUNT(*) FROM employee WHERE is_deleted = false GROUP BY employee_code HAVING COUNT(*) > 1;
   ```

2. **employee_assignment 覆盖率校验**：
   ```sql
   SELECT COUNT(DISTINCT employee_id) FROM employee_assignment WHERE is_current = true AND is_deleted = false;
   -- 应与 hse_employee_org 中 is_current=true 的员工数一致
   ```

3. **业务模块关联完整性校验**：
   ```sql
   SELECT COUNT(*) FROM violation_records WHERE violator_id IS NULL AND is_deleted = false;
   SELECT COUNT(*) FROM training_records WHERE employee_id IS NULL AND is_deleted = false;
   ```

4. **v_employee_current 视图一致性校验**：
   ```sql
   SELECT COUNT(*) FROM v_employee_current;
   -- 应与 employee_assignment 中 is_current=true 的员工数一致
   ```

### 6.4 失败回滚方案

- **数据库层面**：所有迁移 SQL 在事务中执行（`BEGIN; ... COMMIT;`），任一步骤失败自动 `ROLLBACK`
- **代码层面**：Sprint A/B/C/D 分批实施，每批独立 Git commit，可逐批 revert
- **数据层面**：迁移前执行 `pg_dump` 备份 `employee`、`employee_assignment`、`hse_employee_org`、`personnel` 四张表
- **兼容层面**：`hse_employee_org` 和 `personnel` 冻结而非删除，回滚时只需恢复代码写入逻辑，无需恢复数据
