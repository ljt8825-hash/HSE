## 1. 数据库结构关键差异（阻断性问题）

提示词原假设与真实库存在重大出入，实测如下：

| 假设（提示词） | 真实库（psql 实测） | 影响 |
|---|---|---|
| 存在 `employees` 表 | **无 `employees` 表**，花名册通过视图 `v_employee_current` 暴露 | 关联数据源须替换 |
| `personnel_id` 是 `employees.id` 外键 | `personnel_insurance.personnel_id` 与 `employee_id` **完全不相交**，非外键 | 不能用 id 关联 |
| `personnel_insurance` 仅存 `person_name` 快照 | 实际已有 `department` / `position` 冗余列 | 快照比对可行 |
| `personnel_insurance` 无 `id` | 实有 `id` 主键（BIGINT 字符串） | C6 批量按 `id` 回写 |

**决策**：以 `v_employee_current`（`employee_id / name / org_name / position_name / employee_deleted`）
为花名册唯一数据源，关联键采用 **`person_name`**（因 `personnel_id` 不可关联）。
该决策经用户确认（q-0 → 适配真实库）。

## 2. C1–C8 实现与实测

### C1（P0）列表以花名册为准
- `GET /personnel` 改用 `LEFT JOIN LATERAL (SELECT ... FROM v_employee_current ev WHERE ev.name = p.person_name AND ev.employee_deleted=false ... LIMIT 1) e ON true`
- `name/department/position` 优先取 `e.*`（花名册最新值），回退到快照 `p.*`
- 实测：返回结构正确，姓名字段随花名册刷新

### C2（P0）stats 部门分布基于关联后实际部门
- `byDepartment` 改为 `COALESCE(e.e_department, p.department, '未分配')` 分组
- 实测返回 **22 个**新架构部门（如「宁城街道作业中心」而非快照「宁城街道片区」）

### C3（P1）syncStatus 字段
- 计算逻辑：`e_name IS NULL → missing`；`e.e_department IS NOT DISTINCT FROM p.department AND e.e_position IS NOT DISTINCT FROM p.position`（且 name 一致）→ `synced`；否则 `unsynced`
- **分布实测**：`missing=9` / `synced=1` / `unsynced=1230`
  - `missing`：花名册无对应姓名（多为离职/重名清理/姓名变更）
  - `unsynced=1230` 多为**组织架构重构差异**（如快照「宁城街道片区」vs 花名册「宁城街道作业中心」），属预期

### C4（P1）同步状态筛选
- 列表新增 `syncStatus` 查询参数，SQL `WHERE` 用 `CASE` 表达式过滤；内存降级模式同步过滤

### C5（P1）departments 数据源修正
- `GET /personnel/departments` 改从 `v_employee_current` 关联取 `DISTINCT COALESCE(e.e_department, p.department)`

### C6（P1）批量同步接口
- 新增 `POST /personnel/sync-from-roster`（`requireRole admin/safety_manager`）
- 按 `ids` 逐条 `UPDATE personnel_insurance SET person_name=e.name, department=e.org_name, position=e.position_name FROM v_employee_current e WHERE p.id=$1 AND e.name=p.person_name`
- **事务测试**：`BEGIN; UPDATE ... RETURNING id;` → `UPDATE 1` → `ROLLBACK;` 数据无变化，安全
- 返回 `{ synced, failed[], errors[] }`

### C7（P2）前端同步按钮
- 列表表头「同步花名册 (N)」批量按钮（`handleSyncSelected`）
- 详情 Drawer 基本信息页「同步花名册信息」单条按钮（`handleSyncDetail`）
- 状态列 `Tag`：`synced=green 已同步` / `unsynced=orange 待同步` / `missing=red 花名册缺失`

### C8（P2）pending-list 排除已生成人员
- `GET /personnel/pending-list` 数据源改 `v_employee_current`，并 `AND e.name NOT IN (SELECT person_name FROM personnel_insurance WHERE is_deleted=false AND person_name<>'')`
- `generate-from-pending` 数据源同步改 `v_employee_current`，写入 `employee_id`

## 5. 遗留与建议（非本次范围）

1. `unsynced=1230` 绝大多数为**组织重构口径差异**（片区→作业中心）。建议后续
   与花名册负责人确认统一命名，而非盲目一键 sync 覆盖，避免把合法的架构演进误判为脏数据。
2. `personnel_id` 与 `employee_id` 不相交，长期建议新增真实外键列
   （`employee_id`）以替代 `person_name` 文本关联，提升关联健壮性。
3. 后端 `server/` 无 `node_modules`/`pg`，本次以 psql 直连验证；**联调需在具备依赖的环境启动后端后复测 C6 真实写入**。

## 附录：2026-08-05 迁移执行补充（修复前端报错）

### 报错现象
前端 `localhost:5173/insurance/personnel` 控制台出现：
- `获取人员列表失败: ...`
- `获取统计失败: ...`

后端 API 实测返回：
```json
{"code":-1,"message":"字段 p.employee_id 不存在"}
```

### 根因
Codex 提示词 05~12 已把 `server/routes/insurance.js` 重构为以 `personnel_insurance.employee_id` 作为关联键，但迁移脚本 `server/sql/personnel_insurance_employee_id_migration.sql` 按设计「仅创建，未执行」。真实库中该列不存在，导致所有以 `employee_id` 做 JOIN 的查询失败。

> 注意：本库真实员工主表为 `employee`（单数），`v_employee_current` 由其派生；2026-08-02 验证时所说的「无 employees 表」指无复数表，不影响后续 Codex 以 `employee.id` 为稳定 ID 的设计。

### 执行步骤
1. **备份**：`pg_dump -F p -f G:/hse-dashboard/_backups/safety_dashboard_employee_id_migration_20260805_173150.sql`（21MB）。
2. **结构迁移**：执行 `server/sql/personnel_insurance_employee_id_migration.sql`。
   - 阶段一：添加可空 `employee_id BIGINT`、索引 `idx_personnel_insurance_employee_id` / `idx_personnel_insurance_emp_type_current` / `idx_personnel_insurance_unique_active`。
   - 阶段四：添加并 VALIDATE FK `fk_personnel_insurance_employee` → `employee(id)`（执行时 employee_id 全 NULL，VALIDATE trivially 通过）。
3. **安全回填**：运行 `G:/hse-dashboard/_backups/personnel_insurance_safe_backfill.sql`：
   - 仅对 `person_name` 在 `v_employee_current` 中**唯一匹配**的记录写入 `employee_id`；
   - 同名多候选、无匹配、会导致 `idx_personnel_insurance_unique_active` 冲突的 active 保单保持 NULL。
