## 一、背景

人员管理模块（花名册）已全线竣工（提示词-78 至 112），现进入保险管理模块检查。保险管理模块包含 4 个子模块（人员保险 / 车辆保险 / 超龄人员 / 其他保险），共约 39 个后端端点。

**关键发现（探查阶段）**：
1. 保险模块使用 `format*` 函数做字段映射（非 camelKeys），但 `formatOverage` 返回 snake_case，与 `formatPersonnelIns` 返回 camelCase **不一致**
2. 保险模块后端代码**未引用 `employee_id` 或 `employee_code`**，与花名册无数据关联
3. 附件/版本端点使用 `camelKeys`（6 处），需检查是否与前端字段名对齐

## 三、检查任务

### Task 1: 字段映射一致性检查（P0）

#### 1.1 formatOverage snake_case vs 前端 camelCase 错位

**后端** `server/routes/insurance.js` `formatOverage`（约 942-970 行）返回 snake_case：
```js
{ personnel_id, id_card, birth_date, hire_date, person_type, control_type, ... }
```

**前端** `apps/web-antd/src/api/hse/insurance.ts` 声明的类型为 camelCase。

**检查方法**：
1. 读取 `apps/web-antd/src/api/hse/insurance.ts` 中 `OveragePersonnel` 类型定义，列出所有字段名
2. 读取 `apps/web-antd/src/views/insurance/over-age/index.vue` 中 columns 的 `dataIndex`，列出所有字段名
3. 对比 `formatOverage` 返回的 snake_case 键名 vs 前端期望的 camelCase 键名
4. 标注所有不匹配的字段

#### 1.2 formatPersonnelIns 字段完整性

**检查方法**：
1. 读取 `apps/web-antd/src/views/insurance/personnel/index.vue` 中 columns 的 `dataIndex`
2. 对比 `formatPersonnelIns` 返回的字段名，确认无遗漏
3. 检查 `personnel_insurance` 表是否有未被 format 映射的列（如 `employee_id`）

#### 1.3 formatVehicle 字段完整性

**检查方法**：
1. 读取 `apps/web-antd/src/views/insurance/vehicle/index.vue` 中 columns 的 `dataIndex`

#### 1.4 formatOtherInsurance 字段完整性

**检查方法**：
1. 读取 `apps/web-antd/src/views/insurance/other/index.vue` 中 columns 的 `dataIndex`
2. 对比 `formatOtherInsurance` 返回的字段名，确认无遗漏

#### 1.5 camelKeys 附件/版本端点

**后端** `insurance.js` 中 6 处 camelKeys 使用（行 1169/1177/1217/1235/1289/1297）。

**检查方法**：
1. 读取 `insurance_attachments` 和 `insurance_versions` 表的列定义

### Task 2: 与花名册数据关联检查（P1）

#### 2.1 人员保险 ↔ 员工花名册关联

**当前状态**：`personnel_insurance` 表通过 `personnel_id` 关联 `over_age_personnel` 表，与 `employee` 表无直接关联。

**检查方法**：
1. 查询 `personnel_insurance` 表结构：`SELECT column_name, data_type FROM information_schema.columns WHERE table_name = 'personnel_insurance'`
2. 确认是否有 `employee_id` 或 `employee_code` 列
3. 检查前端 `personnel/index.vue` 中员工姓名显示方式（是否使用 `EmployeeName` 组件）
4. 如果无 `employee_id`：记录为"人员保险与花名册无数据绑定"，属于架构遗留问题

#### 2.2 超龄人员 ↔ 花名册关联

**当前状态**：`over_age_personnel` 表有 `personnel_id` 列，同样与 `employee` 无直接关联。

**检查方法**：
1. 查询 `over_age_personnel` 表结构
2. 确认是否有 `employee_id` 或 `employee_code` 列
3. 如果无：记录为"超龄人员保险与花名册无数据绑定"

#### 2.3 车辆保险 ↔ 花名册关联

**当前状态**：`vehicles` 表与员工无关，属独立模块。

**检查方法**：确认车辆保险模块不需要员工关联（属于资产保险，非人员保险）。

#### 3.2 人员保险与超龄人员关联完整性

**检查方法**：
```sql
-- personnel_insurance 中 personnel_id 指向不存在的 over_age_personnel 记录
SELECT pi.id, pi.personnel_id, pi.person_name
FROM personnel_insurance pi
LEFT JOIN over_age_personnel oap ON oap.id = pi.personnel_id AND oap.is_deleted = false
WHERE pi.is_deleted = false AND pi.personnel_id IS NOT NULL AND oap.id IS NULL;
```

**检查方法**：抽样 5 条记录，确认 `calcExpiryStatus` 计算正确（expired / expiring / normal / unknown）。

## 五、注意事项

1. **后端端口**：5800（5666 被 Windows 保留区间拦截）
2. **JWT 探测**：使用 `crypto` 手搓 HS256 JWT（免 jsonwebtoken 依赖），后端无热重载须重启再探
3. **formatOverage 是最大嫌疑**：它是唯一返回 snake_case 的格式函数，与前端 camelCase 类型定义必然冲突
4. **保险模块无 employee_id 引用**：这是架构级问题，与方案A类似的"无数据交互"问题，需在诊断报告中明确标注，但不建议本次修改（属独立架构改造）
5. **不改任何代码**：本提示词为纯诊断，只生成检查报告，不修改任何文件
6. **约束遵守**：不修改前端、路由、菜单、其他业务模块
