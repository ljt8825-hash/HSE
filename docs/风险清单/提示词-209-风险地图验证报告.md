## 一、关键发现：数据现状

### 1.1 `risk.area` 字段实际内容
查询 `risk_sources` 表 `is_deleted=false` 的 56 条记录，`area` 字段**全部为"生产运营部"**，无乡镇级区域信息。该字段是"管控部门"而非"所属乡镇"。

### 1.2 坐标字段实际内容
56 条记录的 `lng/lat` **全部为 null**。后端 API 不做运行时 backfill，直接透传数据库值。提示词-208 的 `isHashPlaceholder` 对 null 返回 `true`（视为占位），`snapRiskToRoad` 以"宁津中心"为锚点做吸附，导致所有"最近"判定塌缩到距宁津中心最近的单一要素。

### 1.3 location 文本分析
56 条 location 中不含任何乡镇名（如"时集镇""大曹镇"等），仅含道路代码（G104/S339）、场所类型（转运站/绿化带/镇驻地）和通用描述（路灯/焊接/维修等）。

## 二、实现方案：ID 反推乡镇锚点

### 2.1 核心原理
`backfill-risk-coords.js` 策略 5（哈希兜底）的分配规则：
```js
const idx = Math.abs(id) % TOWNSHIP_CENTERS.length;
const center = TOWNSHIP_CENTERS[idx];
const coord = jitter(center, id); // center + sin/cos 偏移
```
即使坐标为 null（未执行过 backfill 写库），**id 本身就编码了所属乡镇信息**。通过 `id % TOWNSHIP_CENTERS.length` 可确定性还原该风险点"应当属于"哪个乡镇。

### 2.2 新增函数 `inferTownshipAnchor(risk)`
位置：`map.vue` 第 1047-1060 行。

```js
function inferTownshipAnchor(risk) {
  // 精确坐标（非 null 且不匹配 jitter 模式）不推断
  if (risk.lng != null && risk.lat != null && !isHashPlaceholder(risk)) return null;
  // null 坐标或占位坐标：按 backfill 确定性规则 idx = id % len 反推乡镇
  const idx = Math.abs(risk.id || 0) % TOWNSHIP_CENTERS.length;
  const t = TOWNSHIP_CENTERS[idx];
  return [t[1], t[2]];
}
```

对 null 坐标风险点同样生效，因为 backfill 的分配规则不依赖坐标值，仅依赖 ID。

### 2.3 锚点改进
位置：`map.vue` 第 1109-1122 行。

改进前：null 坐标 → anchor = 宁津中心（导致全部塌缩）。  
改进后：null 坐标/占位坐标 → anchor = `inferTownshipAnchor(risk)`（所属乡镇中心）；精确坐标 → 原坐标；完全无法判断 → 宁津中心兜底。

### 2.4 乡镇匹配优先级提升
位置：`map.vue` 第 1196-1198 行。

对于能推断乡镇的风险点，**直接返回该乡镇中心**作为 township 匹配结果，不再走"距锚点最近乡镇"搜索。这确保 ID 反推的乡镇归属优先于距离计算。

## 九、独立风险提示：回填脚本执行将摧毁坐标分级体系

> ⚠️ **最高危遗留风险**。本报告 §八 原将上述回填动作标记为"兼容、无需修改"，但经独立 dry-run 验证，该判断在"保留业务分级"层面是**误导性**的。特此单列章节澄清，结论以本节为准。

### 9.1 根因：两边"认识世界的方式"根本不同

| 维度 | `map.vue`（前端吸附） | `backfill-risk-coords.js`（回填写库） |
|------|----------------------|----------------------------------------|
| 站点识别 | 宽松正则 `/转运站\|中转站/` | 全名精确匹配 `text.includes("大曹镇转运站")` |
| 公园识别 | 宽松正则 `/公园\|草坪\|绿化带/` | 全名精确匹配 `text.includes("中心公园")` |
| 道路识别 | 正则 `G(\d{3})` 提取道路代码 | **无道路匹配级**（只有转运站/设施/公园/乡镇名/哈希） |
| 兜底 | 距锚点最近要素 | `id % 12` 乡镇 |

前端靠"宽松关键词"认得出"垃圾中转站水平压缩站""绿化带、公园、道路两侧树木"这类**通用描述**；回填脚本靠"完整全名"逐一比对，二者对当前数据的识别能力完全不对等。

### 9.2 实测证据（回填 `--dry-run`，仅 SELECT 不写库）

```
策略1（转运站全名匹配）: 0
策略2（设施全名匹配）:    0
策略3（公园全名匹配）:    0
策略4（乡镇名匹配）:      0
策略5（哈希兜底 id%12）:  61
```

当前 56 条（dry-run 抓到 61 条，含 5 条已删除但坐标仍 null 的）location 全是通用描述，**不含任何完整站名/园名** → 回填精确匹配 **0 命中** → 全部落入策略 5（乡镇）。即回填脚本的"精确全名匹配"在当前数据上一条都匹配不上。

### 9.3 后果推演：一跑回填即归零

若将来有人执行 `backfill-risk-coords.js --execute`：

1. 全部 61 条 null 坐标被写入"乡镇中心 ±800m 抖动"坐标（回填查询 `WHERE lng IS NULL OR lat IS NULL` **未加 `is_deleted=false`**，故含 5 条已删除但坐标仍 null 的记录，会被一起写库）；
2. `map.vue` 读到这些坐标 → `isHashPlaceholder` 判定为 jitter 占位 → `inferTownshipAnchor` 回退到乡镇中心 → **4 道路 + 14 站点 + 3 公园 全部消失，塌成 56 个乡镇点**；
3. 因被识别为占位，连 ±800m 抖动都不渲染，全部堆在乡镇中心点。

即：208/209 辛苦做出的"道路 / 站点 / 公园 / 乡镇"四级可视化，**一跑回填即归零**，且静默无报错。

### 9.4 缓解建议

- **【强烈建议】保持现状**：当前 56 条坐标维持 null，**永远不要对该表执行 `backfill --execute`**。map.vue 的宽松正则分级**只有在 null 坐标下才生效**——一旦被回填写入坐标，反而触发 `isHashPlaceholder` 把它当占位、回退到乡镇。
- **如确须回填**（例如大批量导入真实 GPS 坐标），应先改造脚本对齐前端：① 加 `is_deleted=false` 过滤；② 增加道路级（`G\d{3}`/`S\d{3}` 正则）与宽松正则站点/公园级；③ 保留"已含精确坐标则不覆盖"的防护。
- **两份 `TOWNSHIP_CENTERS` 手工同步无断言**：`map.vue` 与 `backfill` 各硬编码一份 12 乡镇数组（经核顺序、坐标逐一一致），但**无任何单测/断言守卫**。任一处重排或增删会**静默错配** `id % 12` 映射且零报错。建议抽成共享模块或加一致性断言。

### 9.5 结论

报告 §八 所述"回填兼容、无需修改"仅在"不报错"层面成立；在"保留业务分级"层面，回填与前端机制不兼容，属**高危陷阱**。当前最安全状态：**保持 null 坐标、不跑回填**，让 `map.vue` 的宽松正则分级继续生效。
