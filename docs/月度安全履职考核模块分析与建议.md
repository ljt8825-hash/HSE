## 一、问题一：考核周期管理「新增→创建」无法创建

### 1.1 现象
在「目标职责 → 月度安全履职考核 → 考核周期」页面点击「新增」，填写年份/月份后点「创建」，提示失败，周期列表无新增。

### 1.2 复现
以 admin 角色直连后端接口复现：

- `POST /api/hse/assessment-monthly/cycles`（`{"assessment_year":2026,"assessment_month":8}`）
- 响应：`HTTP 200, {"code":500,"message":"创建考核周期失败"}`

后端日志（server/logs/combined-*.log）对应错误：

```
[assessment-cycle] 创建失败: 插入或更新表 "hse_assessment_cycle" 违反外键约束 "fk_assessment_cycle_created_by"
```

### 1.3 根因
2026-07-30 外键治理脚本 `server/sql/hse_fk_phase2_assessment_events.sql` 在补全约束时，将
`hse_assessment_cycle.created_by / frozen_by` 两个外键指向 **`employee(id)`**（员工花名册）。

但模块代码 `server/routes/hse-assessment-monthly.js` 创建周期时写入的是 **`users.id`**（系统登录账号 ID，见 `getUserInfo()` 返回 `req.user.id`）：

```js
const user = getUserInfo(req); // req.user.id 为 users 表主键
// INSERT ... created_by = user.id
```

`users` 与 `employee` 是两套互相独立的 ID 序列（实库验证：employee 中不存在 id=1，而 admin 在 users 中 id=1），
任何非空写入都会违反外键 → 500。这是「外键补全脚本的语义假设错误 vs 业务代码长期语义（created_by=系统用户）」冲突的典型回归：
- 代码（所有模块约定）：`created_by` = 操作的系统账号（users.id）
- 治理脚本：错误假设 created_by 是员工档案 ID（employee.id）
- 同理影响冻结周期（`fk_assessment_cycle_frozen_by`）：冻结也会 500

### 1.4 修复（已执行）
数据库迁移，将两处外键改指 `users(id)`（与全系统 `created_by` 语义一致）：

```sql
BEGIN;
UPDATE hse_assessment_cycle SET created_by = NULL WHERE created_by IS NOT NULL AND created_by NOT IN (SELECT id FROM users);
UPDATE hse_assessment_cycle SET frozen_by = NULL WHERE frozen_by IS NOT NULL AND frozen_by NOT IN (SELECT id FROM users);
ALTER TABLE hse_assessment_cycle DROP CONSTRAINT IF EXISTS fk_assessment_cycle_created_by;
ALTER TABLE hse_assessment_cycle DROP CONSTRAINT IF EXISTS fk_assessment_cycle_frozen_by;
ALTER TABLE hse_assessment_cycle ADD CONSTRAINT fk_assessment_cycle_created_by FOREIGN KEY (created_by) REFERENCES users(id) ON DELETE SET NULL;
ALTER TABLE hse_assessment_cycle ADD CONSTRAINT fk_assessment_cycle_frozen_by FOREIGN KEY (frozen_by) REFERENCES users(id) ON DELETE SET NULL;
COMMIT;
```

可执行脚本已归档：`server/sql/hse_fix_cycle_fk_to_users.sql`（幂等，可重复执行）。

### 1.5 验证（已测）

|---|---|---|
| 创建周期 2026-08 | 500 创建失败 | 200 创建成功（id=15, HSE-CYCLE-202608） |

### 2.3 核心表（sprint10d2_assessment_init.sql）
hse_assessment_cycle（周期）→ hse_assessment_target（对象）→ hse_assessment_score（评分明细）→
hse_assessment_deduction（扣分明细）→ hse_deduction_adjustment（调整历史）→ hse_responsibility_chain（责任链）→
hse_assessment_audit_log（审计）＋ hse_assessment_metric（指标）。

### 2.4 周期状态机
```
not_started --启动(start)--> in_progress --评分(execute)--> pending_review --冻结(freeze)--> frozen
                                 ^                                              |
                                 └-----------解冻(unfreeze)----(frozen→reviewed)--┘
```
注：`reviewed` 正常流程中除了解冻外没有任何入口写入（见 §5.4）。

## 三、核心业务流程

1. **建周期**：选择年份/月份（留空名称则自动生成 `{年}年{月}月月度考核`，编码 `HSE-CYCLE-YYYYMM`）；同年月唯一（唯一索引 + 409 提示）。
2. **启动/同步对象**：从 `v_employee_org_full` 视图取「岗位 ∈ (乡镇作业中心经理, 管理员)」的在职员工写入 target，更新 target_count。
3. **自动评分**：按 metric 逐指标统计（三违次数、隐患整改率、培训完成率；风险预警/责任书为待接入占位）算扣分，写 score（版本号 score_version+1），对象 status→scored，周期→pending_review。
4. **扣分审核/调整**：待审核扣分单条/批量通过或驳回（驳回需原因）；调整生成新版本并保留历史。
5. **冻结**：先计算乡镇/全员排名 → 对象/周期置 frozen → 冻结后不可改。
6. **Excel**：导出为本地 JSON 文件、按 JSON 文本导入扣分（模板字段 employee_code/deduction_item/deduction_type/score/evidence/remark）。

## 五、发现的其他问题（按影响排序）

### P1（高）冻结/审核权限码 `hse:training:audit` 未配置给任何角色
- 后端冻结、扣分审核通过/驳回/批量、调整接口均要求 `requirePermission('hse:training:audit')`。
- 但 `server/middleware/auth.js` 的 `ROLE_PERMISSIONS_MAP` 中没有任何角色配置该权限码（仅 system_admin 走 `'*'`）。
- 实测：admin 调 `POST /freeze/cycle/:id` → `403 权限不足，缺少权限: hse:training:audit`。
- 影响：admin/safety_manager/hse_manager 均无法冻结，也无法审核扣分 → 「评分→审核→冻结」主流程断裂。
- 建议：在 `HSE_MANAGER_PERMISSIONS` 补充 `'hse:training:audit'`（与扣分调整/冻结接口对齐），并同步前端权限码声明。

### P2（高）扣分审核「通过/批量通过」接口前后端不匹配
- 前端 `reviewDeduction()` 调 `POST /deductions/review`；后端只存在 `/deductions/review/approve` 与 `/deductions/review/reject`。
- web-naive 与 web-antd 两个前端版本一致（`apps/web-antd/src/api/hse/assessment-monthly.ts` 同样是 `/deductions/review`），与后端不匹配 → 审核通过必然 404；驳回路径匹配可用。
- 建议：将前端 API 端点改为 `/deductions/review/approve`（或后端补兼容路由），并做一条链路回归。

### P3（中）考核对象筛选选项硬编码，与实际数据不一致
- targets.vue 乡镇选项硬编码「乡镇1/2/3」，岗位硬编码「安全员/负责人」；而启动时同步的岗位取值是「乡镇作业中心经理/管理员」，乡镇取自组织路径第二段（真实乡镇名）。
- 影响：下拉选不到真实候选值，乡镇/岗位筛选形同虚设；keyword 搜索正常。
- 建议：乡镇改为后端 `DISTINCT township` 枚举接口，岗位与同步规则（position_name）对齐。

### P4（低）周期状态机 `reviewed` 无正常入口；`reviewed_count` 无更新点
- `reviewed` 仅出现在解冻写库；`reviewed_count` 仅在重算清零，其余写库点未更新（审核通过扣分时不累加）。
- 影响：冻结前置判断（freeze.vue 允许 pending_review/reviewed 冻结）实际走 pending_review；已审核人数统计恒为 0。
- 建议：明确「reviewed」语义（或审核完成置周期 reviewed），并在审核通过时维护 reviewed_count。

### P5（低）Excel 导入导出名不副实（JSON 伪装）
- 导出实际 `JSON.stringify` 下载 `.json`；导入把文件按文本 `JSON.parse`，但 file input `accept=".xlsx,.xls"`，真实 Excel 会被解析失败；模板下载同样是 JSON。
- 建议：要么引入 exceljs 真做 .xlsx 导入/导出，要么将页面文案/accept 改为 JSON，避免误导用户。

### P6（低）责任传导（chain/generate）无前端入口
- 后端实现了三违责任传导生成，但 8 个页面均未调用 `chain/generate`，功能为空转。
- 建议：确认需求中责任传导是否需要在 PC 端露出；若需要，补「责任传导」页+按钮；若不需要，保留后端但标注未启用。

### P7（低）代码细节
- `getUserInfo()` 兜底 `req.user?.id || 1`：无 token 直连时静默用 id=1，与审计语义可能跑偏（authMiddleware 已拦截，风险低）。
- 启动与同步对象为两段重复 SQL，建议收敛为同一函数。
- `startAssessmentCycle` 若视图数据为空，targetCount=0 仍置 in_progress（业务上建议告警）。
