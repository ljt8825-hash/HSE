## 一、优先级校准结论（四维矩阵）

> 严重度=综合业务连续性/开发效率/安全/新人上手四维后的结论。

### 🔴 校准后 P0（最优先，未来 3–6 个月内必然出事）

| 问题 | 业务连续性 | 开发效率 | 安全 | 新人上手 | 综合 |
|---|---|---|---|---|---|
| **P0-A 源码未入版本控制（F1）** | **致命**：一次错误 deploy / 误编辑 / 磁盘故障 = 数周成果或整套代码/表结构丢失，无法回滚追责 | 无法 diff/回退/分支协作 | 密钥与代码无法审计追溯 | 无历史可溯源 | **第一优先** |
| P0-B 分层缺失、业务逻辑内联在巨无霸 route（F3） | 中：改动高风险 | **高**：合并冲突、回归难测、评审失效 | 低中 | **高**：万行文件无法上手 | 高 |
| P0-C 领域按 Sprint 命名碎片化（assessment×6/risk×6） | 中：口径重复易打架 | **高**：新功能不知归哪、重复造轮子 | 低中 | **高** | 高 |

> ⚠️ 修正上版报告：原先的 **P0-3"版本库污染"** 判定不成立 —— 一次性脚本是**未跟踪**的工作区堆积，不会进 git 历史。真正的隐患换成：**首次 `git add .` 时可能误夹带 `.env`/临时脚本/上传文件**进首个提交。因此"补 `.gitignore` → 谨慎做首次提交"成为 P0-A 的配套动作。

### 🟡 校准后 P1（1–3 个月会拖慢交付，不致命）

| 问题 | 说明 |
|---|---|
| P1-1 平行子项目并存 | `rule-engine-design/comparison`、`assessment-rule-library`、`assessment-score-design`、`open-assessment-system` 等同一主题多个口径 → 考核打分"两套实现打架"事故概率上升 |
| P1-2 API 命名空间混乱 | `/api/risk-control` 与 `/api/hse/*` 并存；`vben-compat` 契约垫层双份维护 |
| P1-3 前端 monorepo 膨胀 | 只用 `web-naive`，却保留 5 个闲置 app + mock |
| P1-4 安全复核项 | `CORS_ALLOW_ALL=true` 是否生产误开；通用 `/uploads` 匿名静态目录下是否有敏感文件；`requireRole` 覆盖抽查；`F5` 开发态内存降级静默 |
| P1-5 依赖重复/陈旧 | 同时 `bcrypt`+`bcryptjs`；`multer ^1.4.5-lts.1` 偏旧；无 pnpm `overrides` |

### 🟢 P2（可顺手清，不阻塞）
- 前端根目录 `_shot_*.cjs` 截图脚本 / `*.log` / 复制报告 md 与源码混放。
- `schemas/`(zod) 是否被所有 route 复用存疑；`metrics`/`requestLogger` 与 `morgan` 日志链路重复。

### ⏱ 3–6 个月若不处理的必然后果
- **无版本控制**：一次事故即不可逆，属于"不是会不会出事、是何时出事"级别；
- **在巨无霸 route 上继续加功能**：开发速度随文件行数线性下滑，评审形同虚设；
- **平行子项目继续并存**：考核规则双重维护 → 数据口径打架的生产事故；
- **新人**：目录 80% 是临时文件 + 无提交历史 → 上手成本极高，且无法安全尝试。

## 三、中期重构路线图（2–4 周）

### Phase A — 拆分巨无霸 route（以 `hse-employee.js` 为样板）

**目标结构（domain-first 边界定义）：**
```
server/
  routes/<domain>/          # 纯绑定：path + method + middleware → controller
    index.js                # 聚合 router，对外挂载点不变
    employee.js             # employee CRUD
    org-tree.js             # department 五级组织树
    position.js             # 岗位管理
    assignment.js           # 员工调配/调岗流转
    history.js              # 人事变更记录(operator_id)
    import.js               # JSON/Excel 导入
  controllers/<domain>/     # 薄 handler：仅 req 解析 + 调 service + res 包装
  services/<domain>/        # 业务规则 + SQL（复用 config/db.js 的注入 pool）
  (可选) repos/<domain>/    # 数据访问层（现阶段可直接 service 内 SQL）
```
> 说明：优先用"文件大小/子域"切分而非先造 DDD 抽象。controllers 薄一层、services 收逻辑，route 只剩绑定，是 ROI 最高的一步。

**保持行为不变的迁移步骤（可回滚）：**
1. `server/routes/hse-employee/` 建目录，把 6 大子域的导出按子域拆到子文件（子文件 `module.exports = (deps)=>router`，`deps` 注入 `pool`/`services`，消解对 `require` 顶部状态的依赖）。
2. 保留 `hse-employee.js` 作**聚合入口**：`const r = require('./hse-employee'); router.use(r)` 或内部 `router.use('/', sub)` → **`app.js` 挂载点 `/api/hse/employee` 与对外契约零变化**。
3. **每迁一个子域提交一次**（小步、可 `git revert` 单个 commit）。
4. 每步迁移后用现有 `jest + supertest` 跑该子域回归 + 全量主流程 smoke。
5. 全部完成后，把 `hse-employee.js` 改为纯 re-export，后续新功能直接落子文件。

**阶段节奏：** Week1 拆 hse-employee + insurance；Week2 拆 import/training；Week3 处理 assessment 系列合并（业务逻辑层合并更谨慎，先路由归组）。

### Phase B — 领域边界收敛（Sprint 命名 → 领域命名）

**领域地图（以 F4 前端 `api/hse/*` 为镜像锚点，一一对应）：**

| 领域 | 现散落模块（Sprint 命名） | 收敛目标 |
|---|---|---|
| `employee` 人员 | hse-employee / employee-import-v2 / employee-profile / over-age-personnel / personnel | `routes/employee/`，API `/api/hse/employee/...` |
| `assessment` 考核 | assessment / assessment-monthly / assessment-analysis / assessment-rule / assessment-category / violation-assessment / sanwei-analysis / safety-culture / meeting-records / responsibility-forms | `routes/assessment/`，收敛规则库到 `hse_assessment_rule` 单一口径 |
| `risk` 风险 | risk-control / risk-profile / risk-score / risk-profile-detail / driver-risk-center / hazard-rectification / hazard-baseline | `routes/risk/`，统一 `/api/hse/risk/...` |
| `training` 培训 | training / training-ocr / training-assessment | `routes/training/` |
| `accident` 事故应急 | accidents / accident-analysis / emergency | `routes/accident/` |
| `standard` 标准化 | standard / standard-relation / standard-evaluation / documents | `routes/standard/` |
| `insight` 分析驾驶舱 | statistics / dashboard / report / executive-cockpit / warning-center / analysis-center | `routes/insight/` |
| `system` 系统 | system-mgmt / audit / audit-records / roles / menus / users / workflow / notifications / todos | `routes/system/` |

**命名规范建议：**
- 文件：`hse-<领域>-<子业务>.js`（如 `hse-assessment-rule.js` → `assessment/rule.js`）。
- API 前缀：统一 `/api/hse/<领域>/...`；历史混乱前缀（如 `/api/risk-control`）在**兼容期用 route 别名/重定向**双注册，随后废弃。
- 前端同步：后端领域目录与前端 `api/hse/<领域>.ts` 互为主契约表——改后端必改前端对应文件，保证契约不 double 维护。

### Phase C — 基建收敛（可延后）
- 前端 monorepo 只保留 `web-naive` + 所需 `packages/*`，删闲置 app；
- 消除 `src/` TS 僵尸代码与 `legacy:*` 脚本（确认 `app.js` 唯一真源后迁 `_archive/`）；
- 用 OpenAPI/swagger 把 `vben-compat` 契约并入正式文档。
