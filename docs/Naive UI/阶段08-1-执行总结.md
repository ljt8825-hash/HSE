## 一、Part 1 — 附条件① N1 复测（结论 a · 均正常渲染 · 闭环）

### 1.1 结论
**N1 判定：基线同源·均正常渲染**（推翻了阶段 07 的「测试 token 缺 accessCodes」归因；真实根因为阶段 07 的登录检测器缺陷导致的假阳性）。
**附条件① 闭环**：N1 升级为「阶段 07 复测工件瑕疵，非路由/权限回归」。

### 1.2 关键证据（超越原假设）
阶段 07 的 `n1-retest` JSON（`docs/Naive UI/_verify/07/report.json`）三路由原始记录如下：

| 路由 | mounted | hasAppLayout | breadcrumb | finalUrl | is404 | failResolve | **redirectedToLogin** |
|---|---|---|---|---|---|---|---|
| /system（redirect→users） | true | **true** | 系统管理 / 用户管理 | `…/system/users`（≠ /login） | false | false | true |
| /system/users | true | **true** | 系统管理 / 用户管理 | `…/system/users` | false | false | true |
| /system/roles（对照组） | true | **true** | 系统管理 / 角色管理 | `…/system/roles` | false | false | false |
| /system/audit | true | **true** | 系统管理 / 审计日志 | `…/system/audit` | false | false | true |

> 关键观察：所有被标 LOGIN 的路由**实际上都挂载了完整 app 布局、渲染了正确面包屑、finalUrl 停留在路由自身而非 /login**。

### 1.3 根因：阶段 07 检测器缺陷（已修正）
原检测器 (`07_regression.cjs:239`)：
```js
const redirectedLogin = await evaluate(
  "(document.body && (document.body.innerText||'').match(/登录|账号|密码|Sign in|Login/i) && !document.querySelector('.vben-layout')) ? true : false"
);
```
两处缺陷（互相叠加）：
1. **`.vben-layout` 类在 web-naive 中不存在**（`rg -n "vben-layout" apps/web-naive/src` → 0 命中）。该 `!document.querySelector('.vben-layout')` 恒为 true，检测器退化为「页面正文含登录/账号/密码/Sign in/Login」单一判据。
2. **「登录」是页面正常数据**：
   - `views/security/audit/index.vue` 的 `ACTION_LABEL.login = '登录'`，表格中 actionType='login' 的行渲染为「登录」标签（**截图 `n1-route-system-audit.png` 可见三行「登录」action tag**）。
   - `views/system/users/index.vue` 的用户数据可能含「最后登录时间/IP」类字段。
   - 「角色管理」页面数据不出现「登录」字样 → 未误报。
3. 守卫 `guard.ts:66` 的实际行为：`accessToken` 为空才重定向到 `/login`。阶段 07 注入了有效 token（且 `/api/user/info` 在当时有效），auth 守卫放行，路由**没有发生真实重定向**——`finalUrl` 等于路由路径即为铁证。

### 1.4 复测：fresh admin token + 修正检测器（CDP 实机）
执行：`08_1_n1_retest.cjs`（使用 `_06e2_dev.cjs` / `_06e1_cdp_verify.cjs` 的 CDP 模板：PUT `/json/new`、Node22 全局 WebSocket、`evaluate` 读 `r.result.result.value`、异步重试 8×1.2s）。
- **token 来源**：重新自签 `_06d2_admin_token.txt`（payload `{id:1, username:'admin', role:'admin', realName:'管理员', type:'access', jti, iat, exp}`，expiresIn 2h）。后端 `/api/user/info` 实测 200，响应 `{roles:['admin'], homePath:'/hse/todos'}`（无 accessCodes——admin 即超级用户）。
- **注入策略**：仅 `accessToken`，**不强制 `accessCodes=[]`、不预置 `isAccessChecked=true`**，让 SPA 走真实登录后流程（guard `fetchUserInfo` → `generateAccess({roles:['admin']})` → 生成可访问路由）。
- **修正检测器**：以 `location.pathname ∈ ['/login','/auth/login']` 为唯一权威判据；layout 判定改用实际存在的宽选择器（`aside,[class*=sider],[class*=breadcrumb],.vben-header,[class*=layout]`）。

复测结果（`docs/Naive UI/_verify/08-1/n1-retest.json`）：

| 路由 | pathname | finalUrl | layoutOk | mounted | is404 | failResolve | **isLoginPath** | bodyLen | consoleErrors | 截图 |
|---|---|---|---|---|---|---|---|---|---|---|
| /system（redirect→users） | /system/users | `…/system/users` | true | true | false | false | **false** | 192 | 0 | — |
| /system/users | /system/users | `…/system/users` | true | true | false | false | **false** | 192 | 0 | —（含手机号列，不截） |
| /system/roles（对照组） | /system/roles | `…/system/roles` | true | true | false | false | **false** | 302 | 0 | `n1-route-system-roles.png` ✅ |
| /system/audit | /system/audit | `…/system/audit` | true | true | false | false | **false** | 587 | 0 | `n1-route-system-audit.png` ✅ |

视觉证据：
- `n1-route-system-roles.png` — 角色管理页：布局完整、面包屑正确、数据表加载 3 行（admin/manager/viewer）。
- `n1-route-system-audit.png` — 审计日志页：布局完整、面包屑正确、数据表含 actionType「登录」标签（**与检测器误报源一致**）。

> 四路由全部 `reachable=true`，零控制台错误，无重定向，无组件解析失败。**结论 a 闭环**。

### 1.5 重新审视原附条件①
原条件：「N1 复测需携带正确权限码」。本批证实：阶段 07 使用的 token（角色 admin、accessCodes=[]、payload 过期约 9.8h 前）**实际上仍是有效 token 的「假象错位」**——token 有效期内后端 `/api/user/info` 能返回 200 即证明 SPA 处于已认证会话。本批用全新 2h token + 修正检测器确认三路由全部正常渲染，因此 **N1 闭环的放行依据不是「权限码补齐」而是「检测器误报」**，附条件①在更严格的实际证据下亦获闭环。

## 四、Part 4 — 决策项 #7：风险地图风险集 `pageSize:500` 截断确认（无需改动）

### 4.1 现状
`apps/web-naive/src/views/risk-control/map.vue:754`
```js
const { list } = await getRiskList({ page: 1, pageSize: 500 });
```

### 4.2 生产风险总数确认（只读探针）
- **接口**：`GET http://127.0.0.1:5800/api/risk-control?page=1&pageSize=1`（admin token，后端 `server/routes/risk-control.js`）
- **响应**（HTTP 200）：`{ code:0, success:true, message:'ok', data:{ list:[…1 条], total: 56 } }`
- **结论**：**生产可观测到的风险总数 = 56，远低于 500 阈值**。

### 4.3 处置
`total ≤ 500` ⇒ 现状不截断，**无需改动**。
- 无需前端调大 pageSize。
- 无需循环拉取合并。
- 无需改后端/分页契约（红线约束亦未触发）。
- 如未来风险数逼近 500，可优先前端方案：`getRiskList` 自动累加多页直到 `list.length >= total` 或直接调大到后端单页上限（待后端授权窗口处理）。

> 标注：本确认仅基于本环境后端即时数据，**未经生产正式复核**；若上线后生产风险总数 > 500 需重议方案（届时优先前端方案，并就分页契约咨询后端授权）。
