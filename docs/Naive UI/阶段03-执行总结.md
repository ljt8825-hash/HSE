## 四、排序事件协议（服务端三态）

- 组件 `sortConfig.remote = true` + `orders: ['asc','desc',null]`：VXE 仅维护排序状态（表头箭头），**绝不在本地重排数据行**；组件也不对 `data` 做任何排序。
- `gridEvents.sortChange({ field, order })` → 标准化为 `sort-change` 事件，载荷 `{ sortBy: field, sortOrder: order==='asc'||'desc' ? order : undefined }`。**取消排序时 `sortOrder` 为 `undefined`**（不发送 `null`）。
- 调用方（如演示页 `onSortChange`）收到事件后，自行按 `sortBy/sortOrder` 请求服务端（演示页用本地全量数据排序代替），再把结果通过 `:data` 回灌。网格本身不重排——满足「服务端 `sortBy/sortOrder` 承载、不把服务端分页误当前端全量排序」的约束。
- 仅 `columns` 中 `sortable: true` 的列可排序（白名单），其余列点击不触发排序。

## 五、行编辑状态设计

- `editable` 为 `true` 时启用 `editConfig`（manual/row/showStatus），并 `keepSource: true` 以支持校验失败回滚原始值。
- 进入编辑：`beginEdit(row)` → `gridApi.grid.setEditRow(row)`，行进入可编辑（单元格出现 `input`）。
- 保存：`saveEdit(row)` → `gridApi.grid.validate(row)`（VXE 校验）。**复审修复校验判断**：`vxe-table@4.19.25` 的 `validate()` 成功返回 `true / undefined / void`，失败返回错误映射（truthy 对象）。故「成功」容纳 `true` 与 `undefined`，仅当结果为错误映射才视为失败，避免把「无规则/校验通过」的行误判为失败而回滚+发 `edit-cancel`。成功则 `clearEdit` + emit `edit-save {row}`；失败则 `revertData(row)`（回滚原始值）+ `clearEdit` + emit `edit-cancel {row}`。
- 取消：`cancelEdit(row)` → `revertData` + `clearEdit` + emit `edit-cancel {row}`；`revertRow(row)` 仅回滚不改状态。
- 保存/取消动作通过事件交给调用方，组件内不写业务 API。

## 六、导入状态设计

流程状态机：`下载模板 → 上传文件 → 解析/校验预览 → 确认导入 → 导入结果`。
- **下载模板 / 上传 / 确认 / 关闭** 全部以事件交给调用方（`download-template` / `upload(file)` / `confirm` / `close`）。
- **复审修复上传通道**：`NUpload`（`default-upload:false`）+ `NUploadDragger` 双重入口，`:accept="accept"` 动态绑定；点击与拖拽各精确触发一次 `upload(file)`；文件类型不匹配时本地提示 `typeError` 且**不向任何未知地址自传、不发出 `upload` 事件**；隐藏 input 与内置 input 不重复触发。
- 组件仅承载 UI 状态：`previewData`（预览数据）、`previewError`（校验失败，非空即红色告警且不显示预览）、`confirming`（确认中禁用+加载）、`result`（最终结果成功/失败展示）。
- 预览表格复用 `HseDataGrid`（同列契约），保证表格观感一致。
- 文案固定「下载模板」「导入」，不出现「导入数据」。
- 实测弹窗内容含「下载模板」按钮与「确认/导入」操作，状态切换无横向溢出。

## 十、Codex 复审整改：排序三态根因与修复（核心）

### 现象
真实鼠标点击「编号」可排序列头，**排序指示（箭头 / `column.order`）始终不生效**：点击后 `getSortColumns()` 为空、`aria-sort` 为空、数据看似不重排；而程序化 `api.sort('code','asc')` 却能让 `getSortColumns` 返回 `asc`。每次点击列对象 `id` 会从 `col_24` 递增到 `col_34 / col_44 / col_54` —— 证明点击触发了**列重建**，把 VXE 刚设置的排序态一并清掉。

### 根因定位（过程化证据）
1. 在 Vben 包装层 `packages/effects/plugins/src/vxe-table/use-vxe-grid.vue` 的 `options` computed 与 `use-vxe-grid.ts` 外层 `Grid` 的 `setState` 注入 `[DIAG]` 日志，真实点击一次后捕获：
   - 外层 `Grid` 的 `setState`（每次渲染都会跑）**未**重跑；
   - `options` computed **恰好重算一次**。
   → 触发源是 `options` 的某个响应式依赖变化，而非父级整体重渲染。
2. `options` 的依赖为 `gridOptions / toolbarOptions / tableData / viewedRowOptions`。结合数据流：点击 → VXE 设置列 `order` 并发 `sort-change` → 父级 `onSortChange` 重排并 `gridData.value = [...].sort(...)` → `HseDataGrid` 的 `watch(props.data)` 触发 `gridApi.setState({ tableData: val })` → store 的 `tableData` 变化 → 内层 `options` 重算 → `cloneDeep(mergeWithArrayOverride(...))` 生成**全新 gridOptions** → VXE 重建所有列（新 `id`、新 `order=null`），刚设置的排序态被抹除。
3. 若演示数据本就升序，`onSortChange` 升序重排后视觉顺序不变，进一步掩盖了「数据其实已重排」的事实（用 `A-0005..A-0001` 降序实证可排除）。

### 修复
`HseDataGrid.vue` 的数据同步改为 `syncTableData(val)`：
- **优先** `gridApi.grid.loadData(val)`：VXE 实例方法，**只更新行数据、不重建列、不清排序态**（已用 `inst.sort('code','asc')` 后 `inst.loadData(sameData)` 实证 `getSortColumns` 仍为 `asc`，证明 `loadData` 保留排序态）。
- 仅当 VXE 实例尚未挂载（`immediate` 首次）时，回退 `setState({ tableData: val })`（仅一次，不干扰排序）。
- `reload(data?)` 同样走 `syncTableData`。
- 顺带 `loadData / reloadData / setData` 多级兜底，确保方法缺省时仍可渲染。

### 修复后实证（dev 8091）
- 列 `id` 三次点击恒为 `col_24`（无重建）。
- `column.order`：`null → asc → desc → null`；箭头 `.vxe-sort--*-btn.sort--active` 三态循环正确。
- 数据行随 `sort-change` 正确重排（desc → `A-0005..A-0001`；取消 → 恢复默认）。
- 三态排序端到端通过，符合「服务端排序、组件不本地重排、只上报事件」的协议。
