# HSE 安全环保管理系统 · 组织关系与逻辑关系分析报告

> 面向读者：**不懂编程的业务人员**。本报告尽量使用汉字和业务语言，少讲代码，重点讲清楚"系统里有哪些东西、它们之间怎么连、数据怎么流动"。遇到绕不开的技术名词会顺手解释。

---

## 一、这个项目到底是个什么东西

一句话概括：**这是一套环卫（保洁）公司的"安全环保管理系统"，用来管人、管车、管三违、管培训、管考核、管风险的电脑端 + 手机端系统。**

这里的"三违"是指作业中的"违章操作、违章行为、违章指挥"之类的不安全行为（比如保洁人员作业时不按要求操作）。整条业务主线是：

> **保洁员 / 网格长在手机上报现场不安全行为 → 数据暂存在飞书 → 后台定时拉进公司自己的数据库 → 电脑端安全看板给管理员查看、统计、考核。**

它其实由好几套"程序"拼在一起，就像一个团队里有分工不同的成员。下面把每个成员分别介绍。

---

## 二、总体组织架构：系统一共有哪几块

整个项目（`G:\hse-dashboard` 目录）里虽然文件很多很杂，但真正"干活"的核心就这几大块：

| 板块 | 目录（存放位置） | 它是干嘛的 | 通俗理解 |
|------|------------------|-------------|----------|
| **电脑端网页** | `安全看板vben` | 给管理员、经理在电脑上用的管理后台 | 等于公司的"办公室"，看报表、管人员、配考核规则都在这里 |
| **后端服务** | `server` | 电脑端网页"背后"的大脑，负责存数据、算数据 | 等于"账房先生"，办公室点一下按钮，账房先生去算并回结果 |
| **手机端网页 H5** | `grid-mobile-cloudflare` | 给保洁员 / 网格长 / 乡镇经理在手机上用的填报入口 | 等于"外勤手机"，在外面拍现场照片、上报违纪 |
| **飞书多维表格** | 放在飞书云上（不在这台电脑） | 手机端先把手上的记录写进飞书表格 | 等于"临时登记本"，先在外面记一笔 |
| **公司数据库 PostgreSQL** | 存在数据库服务器上 | 系统的正式"账本"，所有电脑端看到的数据都来自这里 | 等于"大账房" |

**建议先记住这个核心关系：**

```
手机端H5 → 飞书多维表格（临时登记本） → 后端自动拉取 → 公司数据库（正式账本） → 电脑端网页（展示和统计）
```

这是一条**只看一遍就会明白的流水线**，数据从手机一路流向电脑，中间飞书是"中转站"，数据库是"仓库"，电脑页面是"橱窗"。下面分章节把每一块拆开讲。

## 三、电脑端网页：安全看板（面向前端界面讲）

电脑端网页的名字叫"安全看板"，整体是一个管理后台。登录进去后，左侧会有一列**菜单**，点开某个菜单就进入对应的页面。这些页面就是给用户看的"界面"，按业务分成 14 组，我按你能看到的界面菜单逐个列出来。

| 菜单（你在界面上看到的文字） | 这个页面主要让用户干什么 |
|------|--------------------------|
| **安全总览** | 一进来先看的"首页驾驶舱"，汇总员工数、风险等级、风险趋势等总览指标；下方还有 BI 数据看板、驾驶员风险中心、事故分析中心、考核分析中心、报表中心、预警与整改中心等分析子页 |
| **AI 智能分析** | 系统用 AI 帮忙做统计分析、生成管理建议，并支持人工审核把关（这是这个项目的一个亮点模块） |
| **目标职责** | 管"目标责任书"，配安全人员和安委会、安全费用预算与支出、安全文化建设、月度安全履职考核（很多考核规则的入口都在这）、扣分规则库 |
| **制度标准** | 管理规章制度、法律法规文档，以及标准条款库 |
| **风险管控** | 查看风险清单（风险点台账）和风险地图 |
| **事故管理** | 录入和管理事故记录 |
| **隐患排查** | 录入和跟踪隐患整改记录 |
| **待办事项** | 我的待办工作台、考核计划 |
| **现场管理** | 这是核心业务区：**三违管理**（三违候选、记录、分析、台账、三违考核）、消防设施、转运站、**网格管理**（网格区域、网格长巡查台账）、**驾驶员管理**（安全档案、违章记录、月度考核） |
| **人员管理** | 员工列表（员工主数据）、组织管理（部门树）、岗位管理、员工档案、花名册批量导入、超龄人员 |
| **培训考核** | 培训计划、培训记录台账、证书管理（培训记录可支持 AI 识图自动识别） |
| **应急管理** | 应急预案、应急演练、应急物资、应急队伍 |
| **保险管理** | 人员保险、车辆保险、其他保险 |
| **系统管理** | 用户管理、角色管理、审计日志（谁操作了什么） |

电脑端主要负责的是"**管理、统计、考核、配置**"这类办公室工作，跟手机端（负责现场填报）正好互补。

## 四、手机端网页 H5（面向前端逻辑讲）

手机端网页是一套独立的、部署在云上的小网页，给基层作业人员用。它在手机上能看到的主要页面：

- **登录页**：用手机号 + 密码登录（密码规则是"姓名拼音首字母 + 手机号后4位"，由系统根据飞书身份表派生出）。能登录的人来自飞书里的"网格长信息台账"，目前有 68 人。
- **三种角色（分级）**：登录后分"公司管理 / 乡镇作业中心经理 / 管理员"三种权限，权限不同能做的事不同（比如经理可以"两步选人"、可以把整改转给乡镇）。
- **现场巡查页（核心）**：拍现场照片 → 判断是否"三违" → 若是三违，从系统下发的三违行为列表里选一条 → 选择违章人员 → 提交。
- **整改流转页**：公司管理可见"自己处理"或"转给责任乡镇"，乡镇经理可指派整改接收人。
- **记录与台账页**："我的记录""待整改""已闭环"、个人资料。
- **微信推送**：整改任务可通过微信（WxPusher）推送到个人微信提醒。

> 顺带说明：目录里还有一个 `safety-check-h5`，那是**旧版/试用版**（写法上还在用老的做法），当前真正常用的是 `grid-mobile-cloudflare`。

## 五、手机端 → 手机端填报的数据落到了哪（飞书多维表格）

手机上的操作员提交后，记录**不是**直接进自己公司的数据库，而是先写进**飞书的多维表格**（相当于公司的云上电子表格，放在飞书里）。具体写到飞书里的哪张表：

- **登录身份表**：`网格长信息台账` —— 存谁能登录、什么角色（68 人）。
- **巡查主台账**：`H5员工日常不安全行为台账` —— 手机端填写的每一条现场巡查/三违记录的"家"。

主台账里登记了这些信息（用你能看懂的说法）：

| 主台账里的栏目 | 含义 |
|----------------|------|
| 片区 / 班组 | 现场属于哪个片区、哪个班组 |
| 网格等级 | 这个网格是几级网格 |
| 日期 | 提交时间（自动记录） |
| 违章人员姓名 | 违反安全规定的当事人是谁 |
| 性别 / 年龄 / 司龄 | 当事人的基本信息 |
| 违章行为 | 具体是什么三违行为（不是三违的填"无三违行为"） |
| 项目采取措施 | 当时怎么处理的 |
| 整改后照片 | 事后补拍并上传的整改证据照片 |
| 违章照片 | 提交时拍的现场照片 |
| 检查人姓名 | 提交这条记录的人是谁 |
| 车辆类型 / 保洁员 | 当事人属于车辆岗还是保洁岗 |
| 描述 / 备注 | 问题描述，备注里会记下巡查人手机号、巡查时间等备用信息 |
| 惩罚数额 | 罚款相关的金额 |

**关键点：手机端只是"在飞书表格里登记"，并不会直接改公司数据库。** 照片会先传到飞书云空间，再把标记存进负责的附件栏里。

## 六、飞书 → 公司数据库：后台自动拉数据（面向逻辑讲）

飞书表格只是"登记本"，真正要被电脑端查询的是**公司自己的数据库（正式账本，PostgreSQL）**。中间靠"后台的大脑"（后端服务 `server`）来做"搬运工"。

这个搬运工作的规矩（非常重要，也是系统设计上特意锁死的一条铁律）：

1. **方向只能从飞书往数据库搬**：飞书 → 数据库。**反向（数据库改回飞书）是禁止的**，系统会拒绝，这是为了不让数据乱套、保证飞书是"第一手记录"。
2. **按规则搬运**：后台有一个"字段对照表"，把飞书表格里的栏目，对应翻译成数据库里的正式栏目，再写入数据库。例如飞书的"检查人姓名"会对应到数据库里的"巡查人员"概念。
3. **记录进正式的数据库表**：写入 `网格巡查记录`（grid_inspection_records，正式台账）和一张"同步映射表"（记录哪条飞书记录对上了哪条数据库记录）。
4. **不重复、不丢、不误删**：
   - 以"飞书记录编号 + 飞书文件编号"当唯一指纹，同一笔不会重复搬。
   - 飞书端删掉的记录，数据库端**不会删**（只是统计标记），保证正式账本安全。
   - 有几类特殊记录（比如 BT/EA 标记的）会被排除，不搬进数据库。
5. **两个"权威字段"不许动**：巡查人对应关系、网格归属这两个关键字段，由数据库自己说了算，搬运时**绝不覆盖**，因为它们关系到"谁负责、归哪个网格"，一旦被乱改整个考核就乱了。

**通俗总结这一段：** 飞书是"外面的登记本"，数据库是"家里的正账"，后台定时去抄一遍本子，抄的时候不能抄错、不能漏、更不能把家账改乱。

## 七、数据库 → 电脑端页面：管理端怎么看到数据（前后端怎么连）

这是从"幕后"到"幕前"的一段。数据库里存好了正式数据后，电脑端页面上要看到它、或要操作它，靠的是"前端"和"后端"之间的对话。

**用一个生活化的比喻：**

- **前端（电脑网页/手机页面）** 就像**餐厅的前台服务员**——只管顾客看到什么菜单、点哪个菜、上什么菜。
- **后端（server）** 就像**厨房**——顾客（页面）要菜品时，前台端点个单（发起请求），把订单从"前台"递到"厨房"（前端 → 后端），厨房按方子买菜、下锅、算账（写数据库、算统计），再把做好的菜端回前台（后端 → 前端），前台摆上桌给顾客看（页面展示）。

**"菜单"就是"接口"**：前端每个页面背后，都对应后端一串"点菜的入口"，形式上是一串网址（像 `/api/hse/xxx`）。前端页面里写好了它该去访问哪些入口，后端收到就对号入座去处理，然后返回结果。我在排查时发现，电脑端的安全看板页面和它对应的后端入口基本是"一对一"接好的，例如：

| 你在电脑网页上点的页面 | 它背后主要连着的后端入口（接口）业务 |
|----------------------|--------------------------------------|
| AI 智能分析 | AI 分析任务、健康检查、模型服务等 |
| 安全总览 / 驾驶舱 | 综合统计、仪表盘 |
| 驾驶员风险中心 | 驾驶员风险统计 |
| 考核分析中心 / 扣分规则库 | 考核分析、考核规则 |
| 人员管理 / 员工列表 | 员工数据 |
| 三违管理 / 三违分析 | 三违记录、三违分析统计 |
| 网格管理 / 巡查台账 | 网格内巡查记录（**这部分数据就来自前面飞书搬过来的**） |
| 培训考核 | 培训计划、培训记录、证书 |
| 应急 / 保险 / 规章制度等 | 各自的台账接口 |
| 系统管理 | 用户、角色、审计日志 |

**开发还有一个快捷说法**：前端调用后端时统一带一个共同的"接头暗号"（接口前缀），方便同一套后台服务既服务电脑网页、又服务其他入口，不至于走错门。

**登录这块再补一句**（两种登录，容易混）：
- **电脑端安全看板登录**：用账号密码登录，通过"身份令牌"确认你是谁、有什么权限，才能进对应菜单。
- **手机端 H5 登录**：用手机号+派生密码，身份来源读的是**飞书身份表**，登录后按"公司管理 / 乡镇经理 / 管理员"分级分配手机端权限。

它们各自管各自的入口，不冲突。

## 八、后端内部是怎么分工的（面向逻辑讲）

把后端（那个"厨房"）再拆细一层，它有比较标准的三层分工，用大白话说：

1. **提问层（路由 routes）**：负责"接单"。前端一开口，它判断这个要求该找哪个部门，并把参数检查一遍。
2. **传达层（控制器 controllers）**：负责"转单"。把前端的要求梳理整理好，交给真正的师傅。
3. **实质层（服务 services）**：负责"干活的师傅"。真正去查数据库、算统计数据、或者去调飞书/外部服务，把结果算出来后一层层传回前端。

后端按业务分成很多"域"，每个域管一类事，比如：登录与账号、人员与花名册、三违管理、网格长巡查、风险画像/风险评分、考核管理、培训、隐患事件、AI 智能分析、飞书同步、组织岗位、系统管理……电脑端那个 14 组菜单，正好和这些域基本对得上。

## 九、AI 智能分析模块（单独提一下）

这是这个项目里比较特别、也比较"聪明"的一块，放在电脑端"安全总览 → AI 智能分析"里：

- 它能**调用后端的 AI 服务**（可以用本地离线大模型，比如 Ollama 上的开源模型）去做统计分析和生成管理建议。
- 设置了一条"**人机边界**"：AI 只负责出**建议**，不能替人类做"定责任、扣分罚款、处罚处分、改考核结果"这类决定——这些必须由**人工审核**拍板。系统会先展示确定性的统计结果，再展示 AI 的分析说明和建议，两者不会混淆。
- 为了保证可靠，AI 不可用时页面会**自动降级**为只显示统计结果，不会整页报错。

这块的逻辑比较复杂，但对业务人员来说，理解"AI 是参谋、人做决定"这一句就够了。

## 十、整条链路一张图 + 一次完整故事

把上面所有串起来，画成一张"数据怎么走"的示意图（*为便于阅读，用箭头表示方向*）：

```
【手机端 H5】安全看板 by 网格长/保洁员/经理
    （拍照→判断是否三违→选违章行为→选人→提交）
            │
            ▼
【飞书多维表格】 H5员工日常不安全行为台账 / 网格长信息台账
    （临时登记本：谁、何时、什么行为、照片、措施）
            │  后台定时/手动拉取（单向，只搬不反向）
            ▼
【公司数据库 PostgreSQL】 网格巡查记录 + 同步映射表
    （正式账本：数据写进这里才供查询统计；关键字段不许被覆盖，删记录只标记不误删）
            │
            ▼
【电脑端网页】安全看板（安全总览/三违分析/网格台账/考核…）
    （前台点单→后端厨房算账→回传页面展示）
```

**用一个完整的小故事把这条链路讲清楚：**

1. **今天**，乡镇作业中心经理小张在保洁现场巡逻，发现保洁员老李工作时没戴防护、属于"三违"。
2. 小张用**手机端 H5**拍下现场照片，勾选"三违"，从行为列表里选"作业不规范"，选了违章人老李，点了提交。
3. 这条记录连同照片，**先存进飞书的"H5员工日常不安全行为台账"**（临时登记本记录在案，照片传到云空间）。
4. **后台的搬运工（后端服务）定时/手动地从飞书把这条抄回公司数据库**，翻译成正式字段，写进"网格巡查记录"，还登记对应关系；关键字段（巡查人归属、网格归属）不许被动。
5. 安全管理人员在**电脑端安全看板**打开"现场管理 → 三违管理 / 网格长巡查台账"，就能看到这条正式记录，进行统计分析、扣分考核、整改跟进。
6. 需要整改的，系统还能通过**微信推送**提醒责任乡镇/接收人去处理，处理完补传整改后照片，形成闭环。

## 十一、常见疑问速答（业务视角）

- **为什么手机端不直接写进公司数据库，非要先存飞书？**
  因为基层人员都在外面，飞书是他们熟悉、易用的"登记处"；先记在飞书，再由后台统一、规范地搬运进正式库，这样既能保证手机端随时能用，又能保证正式账本整齐、不脏、不乱。

- **电脑端和手机端是不是同一个系统？**
  不是同一套代码，但属于同一套业务体系：**电脑端管"管理、统计、考核"，手机端管"现场填报"**，两者通过"飞书 → 数据库"这条链路衔接起来。

- **为什么有的飞书表在文档里写的编号和实际对不上？**
  项目里飞书表格编号历史上换过/旧记录过时，排查时以实际飞书为准（例如当前主台账是 `H5员工日常不安全行为台账`）。对业务人员只需认"表名字面含义"即可，编号是程序内部用的，不用纠结。

- **数据会被误删吗？**
  设计上做了多重保护：删除只在飞书端统计、不进普通账本删除流程；关键关联字段不许被覆盖；搬运有唯一指纹防重复。正式账本比较安全。

- **AI 会替人做决定吗？**
  不会，AI 只出建议，任何定责、扣分、处罚都要人工审核确认，这是系统特意做死的边界。
