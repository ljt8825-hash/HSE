## A. 身份链冻结

### A.1 冻结的正式身份链（唯一权威路径）

```
登录账号（username + password）
  ↓  POST /api/auth/login，bcrypt 校验
JWT payload { id, username, role, realName }
  ↓  authMiddleware 校验签名 + 黑名单 + 回库 checkUser
req.user { id, username, role, realName, jti }
  ↓
public.users.id           ← req.user.id 即 users 主键
  ↓
public.users.employee_id  ← 【待新增】账号↔人员唯一绑定
  ↓
employee.id               ← 稳定人员身份
  ↓  校验 employee 存在且当前有效任职
成功 → 得到 inspector_employee_id
```

### A.2 正式解析规则（fail-closed）

```
resolveCurrentEmployee(req.user):
  1. 读 public.users.employee_id（WHERE id = req.user.id）
  2. employee_id 为空            → FAIL-CLOSED（拒绝创建巡查记录）
  3. 校验 employee 存在且未删除    → 否则 FAIL-CLOSED
  4. 校验当前有效任职（v_employee_current 命中） → 否则 FAIL-CLOSED
  5. 返回 employee.id 作为 inspector_employee_id
```

### A.3 明确禁止（新链）

新的「当前登录用户 → 巡查人员」身份链 **禁止**使用：

- `realName → employee.name` 姓名匹配
- 任何模糊姓名匹配 / 同名任选其一

**证据（为何必须禁姓名兜底）**：花名册同名 85 组、182 人（含郭秀梅、赵书坤——正是 WPS-03-B 暂缓那两人）。按姓名解析对这些员工结构性失效；按 `employee_id` 直连零歧义。

### A.4 现有代码待改点（本轮只标注，不修改）

| 位置 | 现状 | 冻结后要求 |
|---|---|---|
| `server/services/employeeResolver.js` `resolveEmployeeByName` | 姓名唯一匹配兜底 | **保留**给旧业务兼容；**禁**用于新巡查身份链 |
| `server/services/currentEmployeeContext.js` | 当前经 `real_name → resolveEmployeeByName` | 新增 `users.employee_id` 优先分支；无则 fail-closed，不回落姓名 |
| `server/routes/site-mgmt.js` POST `/grid-records`（PG 分支，~L1633） | 纯白名单插入，无身份 | INSERT 前调用身份解析，写 `inspector_employee_id`；失败整单拒绝 |
| `server/routes/site-mgmt.js` POST `/grid-records`（WPS 分支，~L1629） | 已 `gridWps.create({ user: req.user })` fail-closed | 维持；身份源统一切到 `users.employee_id` |

**A 结论：身份链可冻结。**

## B. `public.users.employee_id` 方案冻结

### B.1 登录实际表已确认

- **登录/注册/改密全部走无前缀 `users` → 解析到 `public.users`**（`search_path="$user",public`）。
- `public.users`：15 列，**无 metadata、无 employee_id**（→ 方案 A 不可行）。
- `webapp.users`：另一套（有 metadata），**非登录生效表**；本轮不使用、不迁移、不删除。
- 无任何 `user ↔ employee` 中间映射表（→ 方案 C 不存在）。

### B.2 推荐字段（唯一推荐：方案 B）

```sql
-- 本轮只评估，不执行
ALTER TABLE public.users
  ADD COLUMN employee_id bigint NULL UNIQUE;
-- 可选（软引用转正式外键，需先确认 employee 表已就绪）：
--   REFERENCES employee(id)
```

### B.3 对现有登录/JWT/auth 的影响评估（关键：零影响证据）

本轮**实读**登录相关 SQL，全部为**显式列清单**，不含 `SELECT *`：

| 位置 | SQL（节选） | 加列影响 |
|---|---|---|
| `auth.js:205` 登录 | `SELECT id, username, password_hash, real_name, role, department, phone, email, avatar, is_active, last_login_at FROM users WHERE username=$1` | **无**（未 SELECT 新列） |
| `auth.js:494` 注册 | `INSERT INTO users (username, password_hash, real_name, role, department, phone, email, is_active) ...` | **无**（显式列，新列走默认/NULL） |
| `auth.js:537/707` 当前用户 | 显式列清单 | **无** |

- JWT payload `{ id, username, role, realName }` **无需改动**——`employee_id` 在需要时由后端按 `req.user.id` 回库读取，不入 token。
- auth middleware **无需改动**。
- 用户管理 `routes/users.js`：当前 CRUD **完全没有** `employee_id` 处理（实测 grep 零命中）→ 绑定维护属净新增功能（管理端批量初始化页），不影响既有 CRUD。

**B 结论：`public.users.employee_id` 可实施，不改 JWT、不改 auth、不影响 admin 登录。**

## C. `must_change_password` 设计冻结

### C.1 最终默认值

```sql
-- 本轮只评估，不执行
ALTER TABLE public.users
  ADD COLUMN must_change_password boolean NOT NULL DEFAULT false;
```

**必须 `DEFAULT false`，禁止 `DEFAULT true`**——理由：现有正式管理员 `admin`（全库唯一账号）若 `DEFAULT true` 会在下次登录被强制改密，改变既有登录行为。`DEFAULT false` 保证 admin 及所有存量账号零影响；仅「新建的网格负责人账号」在 INSERT 时**显式**置 `must_change_password = true`。

### C.2 逐条核验

| 审计项 | 结论 |
|---|---|
| 1. 登录 SQL 是否受影响 | **否**（`auth.js:205` 显式列，未读该列；bcrypt 校验逻辑不变） |
| 2. admin 是否受影响 | **否**（`DEFAULT false`，admin 行 must_change_password=false） |
| 3. 强制改密在哪层实现 | 登录成功响应体加 `mustChangePassword` 标志 + 前端路由守卫拦截到改密页；后端改密接口 `PUT /api/auth/password` 已存在（`auth.js:622` `UPDATE users SET password_hash=...`） |
| 4. 改密后状态清除 | 改密成功后 `UPDATE users SET must_change_password=false`（在既有改密接口内追加一句，不改核心流程） |
| 5. 是否改 JWT 结构 | **否** |
| 6. 是否改核心认证流程 | **否**（仅在登录响应附加只读标志 + 改密成功附加清零） |

**C 结论：`must_change_password boolean NOT NULL DEFAULT false` 冻结，admin 零影响。**

## D. `inspector_employee_id` 设计冻结

### D.1 字段定义

```sql
-- 本轮只评估，不执行
ALTER TABLE grid_inspection_records
  ADD COLUMN inspector_employee_id bigint NULL;   -- → employee.id
```

> 类型 **bigint**（对齐 `employee.id`，非早期误记的 varchar）。当前 `grid_inspection_records` 实查 27 列**无任何**身份/创建人字段（`inspector_employee_id`/`violator_employee_id`/`created_by`/`creator_*` 全无），`grid_id` 是 `grid_areas.id` 完成度统计外键（禁挪用），`personnel_name` 是前端自填的非唯一姓名快照。故新增列是最小且必要。

### D.2 写入规则

```
创建巡查记录：
  req.user.id → public.users.employee_id → employee.id → inspector_employee_id（后端自动写入）

前端：不得传入、不得覆盖该值（POST body 中的 inspector* 一律忽略）。
```

### D.3 更新/历史不可变规则

- 普通巡查接口 **不允许**修改 `inspector_employee_id`（更新白名单不收该字段）。
- 身份字段保持历史事实：**网格负责人变更不得自动回写历史巡查记录的 inspector**。

**D 结论：`inspector_employee_id bigint NULL` 可实施。**

## E. 代巡查关系冻结（只冻结数据模型）

- 数据模型保持两个**独立**概念，严禁合并为一个字段：
  - `grid_areas.personnel_id` = 网格**责任人**
  - `grid_inspection_records.inspector_employee_id` = 本次**实际巡查登录员工**
- **本轮不硬编码**「`当前 employee_id == grid_areas.personnel_id`」为唯一规则。
- 数据模型天然支持「责任人 ≠ 巡查人」，故未来无论选择哪种业务规则都**无需再改表**：
  - 仅负责人巡查（校验 `inspector == personnel_id`）；
  - 允许代巡查（不校验或按授权范围校验）；
  - 指定岗位代巡查（按岗位/组织授权）。
- 现状核验：`personnel_name` 与网格负责人**无强绑定**，PG 创建分支无任何巡查资格校验 → 现有代码不阻碍上述任一规则后续以「权限/配置」方式实现。

**E 结论：数据模型分离已冻结；具体巡查资格规则留待实施阶段以配置/权限实现，不改身份模型。**

## F. 网格负责人账号权限矩阵（本轮新增审计重点）

### F.1 现有 RBAC 实际能力（真机核验）

存在**两套并行**的角色面，务必分清哪套在运行时生效：

| 面 | 位置 | 运行时是否生效 | 说明 |
|---|---|---|---|
| 静态权限映射 | `middleware/auth.js` `ROLE_PERMISSIONS_MAP` | **✅ 权威运行时门** | `requirePermission(code)` 按 `req.user.role` 字符串取权限码集判定 |
| DB 角色表 | `roles` 表 + `/api/core/roles` | ⚠️ 管理面 | 供角色管理 UI 用；运行时权限判定不读它 |
| 菜单可见性 | `/api/core/menus` + 前端 `router/access.ts`（`getAllMenusApi`） | ✅ 后端驱动 | 菜单/路由可见性由服务端下发 |

- **全局认证门**：`app.js:246 app.use('/api', authMiddleware)` → 所有 `/api/*` 必须登录。
- 现有角色（静态映射）7 个：`system_admin`(`*`)、`admin`/`safety_manager`/`hse_manager`（全量 `HSE_MANAGER_PERMISSIONS`）、`township_manager`（乡镇级：含 `hse:site:grid:view` + `hse:site:create/update/delete`）、`manager`、`viewer`。
- 权限码粒度 = **模块:子模块:动作**（如 `hse:site:grid:view`、`hse:site:create`），**无任何行级数据作用域**。

### F.2 关键缺口（两处，均非阻断）

1. **grid 路由当前未挂权限门**：`site-mgmt.js` 的 `/grid-areas`、`/grid-records` GET/POST/PUT/DELETE **只有全局 authMiddleware，没有 `requirePermission`/`requireRole`**（对比 `app.js:390` 的 `wps/dbsheet` 显式 `requireRole('system_admin','admin')`）。→ 现状任何已登录角色都能读写全部网格。
2. **无「只能操作自己负责网格」的行级作用域**：整个代码库不存在按 `当前用户 employee_id / personnel_id` 过滤 grid_records 的逻辑（GET 列表仅按 keyword/片区/等级/月份过滤）。

### F.3 网格负责人账号权限矩阵（建议）

> 原则：**不新建 role**，复用现有角色承载「模块级可见/可操作」；「仅自己网格」这层由**查询层行级过滤**补齐，不做复杂 per-grid ACL。

| 权限 | 网格负责人 | 承载方式 |
|---|---|---|
| 登录系统 | ✅ | 全局 authMiddleware |
| 安全总览 | 只读（可选） | 复用角色的 `hse:overview:view` |
| 网格巡查（菜单） | ✅ | `hse:site:view` + `hse:site:grid:view` |
| 查看自己负责网格 | ✅ | **缺口→行级过滤（新增）** |
| 查看其他网格 | ❌ | **缺口→行级过滤（新增）** |
| 新增巡查 | ✅（仅自己网格） | `hse:site:create` + 行级校验 |
| 修改巡查 | 受限（不含 inspector 字段） | `hse:site:update` + 白名单排除身份字段 |
| 删除巡查 | ❌（建议禁） | 不授予 `hse:site:delete` |
| 查看历史巡查 | ✅（仅自己网格） | 行级过滤 |
| 隐患整改 | ❌（本期不授予） | 不授予 `hse:hazard:*` |
| 人员中心 | ❌ | 不授予 `hse:personnel:*` |
| 系统管理 | ❌ | 不授予 `hse:system:*` |

### F.4 最小方案（本轮不实现，仅提出）

1. **复用现有角色**：给网格负责人账号赋一个**已存在**的窄角色（如基于 `viewer` 语义或新增一个**仅权限码组合、不引入行级逻辑**的静态映射项 `grid_inspector`——若判定为「组合现有权限码」而非「新建复杂 role 体系」，可在 `ROLE_PERMISSIONS_MAP` 增一项；是否新增由实施阶段决策，本轮不改）。
2. **补 grid 路由权限门**：给 `/grid-records`、`/grid-areas` 挂 `requirePermission('hse:site:grid:view' / 'hse:site:create' ...)`。
3. **补行级作用域**：在 grid_records 查询/创建服务层，按当前登录者 `employee_id` 关联 `grid_areas.personnel_id` 过滤——这是「只能操作自己网格」的**唯一**正确落点，不需要新的复杂权限引擎。

**F 结论：现有 RBAC 可表达模块级权限但无行级作用域；缺口明确、最小方案清晰，属实施阶段正常工作项，不构成阻断。**

## G. 网格负责人账号生成规则冻结（62 人 DRY RUN）

### G.1 数据来源（禁反向）

```
grid_areas.personnel_id → employee.id → employee.name / employee.phone
```

**禁止**经 `grid_areas.name` 反向查员工（姓名非身份键）。

### G.2 规则与保护

```
username         = 姓氏首字母 + 手机号后4位
initial password = 姓氏首字母 + 手机号后4位
```

保护条款（全部纳入设计冻结）：手机号来自 `employee.phone`（AES 加密，仅初始化服务在必要时解密）；日志禁打印完整手机号/初始密码；库中只存 `password_hash`（bcrypt）、不存明文；首次登录强制改密（`must_change_password=true`）；username 冲突 **FAIL-CLOSED**（禁自动加随机后缀掩盖）；`employee_id` UNIQUE，一员工仅一账号。

### G.3 62 人 DRY RUN 预期（真机核验数据）

| 指标 | 结果 |
|---|---|
| 有效网格负责人 | 62（personnel_id 非空 62/62） |
| 唯一员工 | 62（一人多网格 = 0，1:1） |
| 手机号可用（解密后合法 11 位） | **62/62** |
| 手机号缺失 | 0 |
| 手机后 4 位冲突 | 0 |
| (姓首字母 + 后4位) username 冲突 | **0** |
| employee_id 已绑定其他账号 | 0（当前仅 admin，无绑定） |

> 花名册整体 3025 人、1388 有手机（全 `ENC:` 加密，解密后 1388/1388 合法）——「11 位校验=0」是密文假象，已澄清。

### G.4 唯一缺口：拼音首字母零依赖字典

后端 `package.json` 与 `node_modules` **均无拼音依赖**。按纪律**禁新增 npm 依赖**，方案为**自建零依赖姓氏→首字母静态字典**：仅覆盖当前 62 名负责人姓氏；**未命中必须报错 FAIL-CLOSED**（禁算法猜测、禁生成错误账号）；支持复姓/特殊姓氏显式登记。该字典属「技术字典」，非业务规则硬编码。

**G 结论：账号规则数据可行；本轮仅出 DRY RUN 规则与预期，不创建任何账号。**
