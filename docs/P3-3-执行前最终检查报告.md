### ⚠️ 一致性观察（建议执行时注意，非文档缺陷）

1. **只读保护存在「双机制」表述**：P3-2 速查卡 + `hse_employee_org_ReadOnly_Change.sql` 采用**触发器**方案（3 个 BEFORE 触发器）；Runbook-Final §十（L1132「旧模型冻结方案」）采用 **REVOKE INSERT/UPDATE/DELETE**（L1162）+ migration_log 标记方案。两者均实现只读，但机制不同。执行时须明确采用其一或二者互补，避免重复/遗漏。建议以触发器 SQL 为防御主手段、Runbook REVOKE 为权限兜底，并确认不冲突。

2. **SQL 内置自检含「误通过」陷阱**：`hse_employee_org_ReadOnly_Change.sql` Step 3.3（L153）与 3.4（L165）的阻断验证使用 `WHERE id = 0`。若生产库不存在 `id=0` 行，UPDATE/DELETE 影响 0 行，**BEFORE ROW 触发器不触发**，测试会落入外层 EXCEPTION 误报「被正确阻止」（即 P1-4 §五 警告的陷阱）。执行时**必须用真实存在的行 ID** 验证（P3-2 速查卡已提醒）。该 SQL 自检脚本的 `WHERE id=0` 属已知隐患，建议执行时临时改用真实 ID，但不在此审计内修改。

**结论**：T-0 速查卡与 Runbook/SQL 引用**主体一致 ✅**；2 项观察项已记录供执行参考，不阻塞。
