# 待办事项模块 · 方案设计（v1 讨论稿）

> 目标：在 HSE 看板中新增一个统一入口，把各业务模块里"还没做完 / 该跟进"的事项（如目标责任书未签订人员）按「每天 / 每周 / 每月 / 每年」聚合展示，每行可一键导出明细、可跳转到来源模块处理。
> 状态：方案草稿，待与用户商议后定稿再开发。

---

## 0. 一个前提：系统里已有「通知中心」

现有 `通知中心`（`/hse/notifications`，路由当前 `hideInMenu: true`、仅 admin）是**事件驱动的消息流**：某件事发生 → 推一条消息（临期 / 紧急 / 系统 / 任务），有已读未读、详情抽屉、CSV 导出。

新模块不是再做一个消息箱，而是**数据缺口的主动聚合**：实时扫描各模块当前状态，把"还缺什么 / 谁没做"直接列出来，直到缺口关闭才消失。

| 维度 | 通知中心（已有） | 待办事项（新增） |
|------|----------------|----------------|
| 驱动方式 | 被动推送（事件触发） | 主动拉取（实时扫描数据） |
| 内容性质 | 已发生的消息 | 待处理的缺口 / 待跟进事项 |
| 生命周期 | 可已读、可清空 | 随数据缺口存在，缺口关闭即消失 |
| 核心动作 | 查看 / 标记已读 | 导出明细 / 前往处理 |
| 典型例子 | "责任书将于 7 天后到期" | "目标职责·责任书管理：23 人未签订" |

两者互补：通知中心负责"提醒你某件事发生了"，待办事项负责"把各处的待办摊开给你跟"。

---

## 1. 命名建议：待办事项 vs 计划事项

**结论：推荐用「待办事项」。** 理由：

1. **语义更准**：你描述的都是"数据里发现的缺口，需要人去跟"（未签订人员、逾期未整改…），这是 *pending / to-be-done*，不是 *planned / scheduled*。「计划事项」会让人误以为是"预先排好的日程"。
2. **与通知中心区分清晰**：通知=消息，待办=动作项，两个词不重叠，用户一眼能分。
3. **周期维度是"查看节奏"而非"事项性质"**：每天 / 每周 / 每月 / 每年 指的是"在哪些视图里能看到这条待办"，一条待办可以同时在多个周期出现（见 §2）。用"待办"作事项名、"周期"作视图维度，概念最干净。

**备选（供商议）：**
- `待办提醒` —— 强调"提醒"语义，和周期提醒更贴，但略啰嗦。
- `任务中心` / `待办中心` —— 更"平台感"，适合未来做成工作台。
- `周期事项` —— 强调每天/每周维度，但弱化了"待跟进"的动作感。

> 无论叫哪个，建议**不要把"每天/每周/每月/每年"做成模块名**，而是做成模块内的一组 Tab（视图维度）。模块名 = 事项类型，Tab = 时间维度。

---

## 2. 模块定位与边界

- **解决什么**：跨模块"待跟进事项"的统一入口，避免用户每天挨个模块翻"谁还没做"。
- **周期语义（重要）**：每天 / 每周 / 每月 / 每年 = 这条待办**在哪些视图里出现**。一个数据源可打多个周期标签。
  - 例：目标责任书未签订人员 → 是一个持续缺口，**每天、每周、每月**都该看到（直到签完）。
  - 例：年度责任书到期 / 年度演练未完成 → 主要归在**每年**，临期前也可在每月冒头。
- **"每年"里放什么**：年度性、跨年才闭环的事项——年度责任书到期、年度培训计划未完成、年度应急演练未完成、年度考核未提交等。

---

## 3. 整体架构：数据源注册 + 聚合器模式

核心思想：**每个业务模块只声明"我的缺口怎么查"，聚合器统一编排、前端统一展示**。新增一个模块的待办 = 注册一条配置，不改聚合器、不改前端。

```
各业务模块 ──暴露──> 缺口查询(gap query) 返回 {count, items[]}
                              │
                     hse_todo_sources 注册表（配置）
                              │
                 待办聚合器 GET /hse/todos?cadence=daily
                              │
              前端 待办事项页（每天/每周/每月/每年 Tab）
                              │
              导出明细 GET /hse/todos/export?sourceCode=xxx
```

### 3.1 数据源注册表 `hse_todo_sources`（配置表 / JSON）

| 字段 | 说明 |
|------|------|
| `source_code` | 唯一标识，如 `target_responsibility_unsigned` |
| `module` / `sub_board` | 来源模块 / 子板块，如 `目标职责` / `目标责任书管理` |
| `title` | 事项名称，如"目标责任书未签订人员" |
| `cadence` | 周期标签数组：`[daily, weekly, monthly]` |
| `query_type` | `sql` 或 `service`（指向一个返回 `{count, items}` 的函数） |
| `detail_api` | 取明细的接口，如 `/objectives/employees/responsibility-status?signStatus=unsigned` |
| `export_columns` | 导出列定义（字段→中文表头），如 工号/姓名/部门/岗位/分管 |
| `link` | 前往处理的路由，如 `/objectives/target-contract` |
| `enabled` | 是否启用 |

### 3.2 聚合器 `GET /hse/todos?cadence=daily`

- 读取 `hse_todo_sources` 中 `cadence` 含该周期且 `enabled` 的源；
- 逐个调用其 `detail_api`（或 SQL/service），取 `count` 与（按需）`items`；
- 返回统一结构：`[{ sourceCode, module, subBoard, title, count, link, updatedAt }]`；
- 为控负载加短期缓存（如 5 分钟 TTL）；明细仅在"导出"或"展开"时拉取。

## 4. 你的例子如何落地（目标职责 → 目标责任书管理）

**无需新写查询**，直接复用现有接口：

- `GET /objectives/employees/responsibility-status?signStatus=unsigned`
  返回未签订人员明细：`employeeId, employeeCode, name, department, team, position, supervisor, contractStatus …`
- `GET /objectives/employees/responsibility-stats` 返回 `{ total, signed, unsigned, signRate }`

**注册一条 source 即可：**

```json
{
  "source_code": "target_responsibility_unsigned",
  "module": "目标职责",
  "sub_board": "目标责任书管理",
  "title": "目标责任书未签订人员",
  "cadence": ["daily", "weekly", "monthly"],
  "detail_api": "/objectives/employees/responsibility-status?signStatus=unsigned",
  "export_columns": [
    {"key": "employeeCode", "label": "工号"},
    {"key": "name", "label": "姓名"},
    {"key": "department", "label": "部门"},
    {"key": "position", "label": "岗位"},
    {"key": "supervisor", "label": "分管"}
  ],
  "link": "/objectives/target-contract",
  "enabled": true
}
```

**页面上呈现为一行：**

> 目标职责 · 目标责任书管理 ｜ 目标责任书未签订人员 ｜ **23 人** ｜ [导出明细] [前往处理]

点击「导出明细」→ 调 `GET /hse/todos/export?sourceCode=target_responsibility_unsigned` → 下载该 23 人的 CSV（复用 `notifications.js` 的 CSV 导出实现，UTF-8 BOM）。
点击「前往处理」→ 跳 `/objectives/target-contract` 责任书管理页。

## 5. 前端页面设计

### 5.1 菜单位置（建议，待定）
- 方案 A：与「通知中心」同属一个分组（如"消息与待办"），二者并列；
- 方案 B：作为独立一级菜单（更显眼，适合日常高频使用）。
- 鉴于它面向日常跟进、使用频率高，**倾向方案 B（独立一级菜单）**，但需你拍板。

### 5.2 页面结构
- 顶部汇总条：当前周期「共 N 项待处理 / 涉及 M 个模块」，带角标。
- 四个 Tab：**每天 ｜ 每周 ｜ 每月 ｜ 每年**。
- 待办表格列：**来源模块 ｜ 子板块 ｜ 事项 ｜ 待处理数量 ｜ 更新时间 ｜ 操作（导出明细 / 前往处理）**。
- 待处理数量用颜色分档（如 ≥20 红、5–19 橙、<5 绿），一眼看出轻重。
- 操作列：每行都有「导出明细」；「前往处理」跳来源页。

> 表格形式的具体排版见随附的页面布局图。

## 6. 导出机制

- 复用 `server/routes/notifications.js` 的 `/export` CSV 实现（UTF-8 BOM、中文表头、引号转义）。
- 新增 `GET /hse/todos/export?sourceCode=xxx`：按 source 的 `export_columns` 跑明细查询，流式输出 CSV。
- **Excel 备选**：`server/node_modules` 已含 `xlsx`，如需 `.xlsx` 可直接生成（建议作为二期，首期先 CSV）。

## 7. 扩展性：其他模块如何接入（核心卖点）

把"某模块的缺口"接进待办事项，只需三步，聚合器与前端零改动：

1. **确认缺口查询**：该模块是否已有"列出未完成项"的接口？没有就补一个返回 `{count, items}` 的查询（如保险未参保、培训待培训）。
2. **注册 source 行**：往 `hse_todo_sources` 插一条配置（周期 + 明细接口 + 导出列 + 跳转链接）。
3. **完成**：前端自动出现该行，自动可导出。

**候选首批接入源（举例，待你选定）：**
- 保险管理：未参保 / 脱敏异常人员
- 培训管理：应培未培人员、逾期未复训
- 隐患治理：超期未整改隐患
- 应急管理：临期未演练预案
- 目标职责：责任书未签订人员（首期必做，作范式）

> 约定（可选优化）：让每个路由模块 `export` 一个 `todoSource` 描述符，聚合器启动时自动 `require` 发现，连"插表"都省了。

## 8. 分阶段落地路线

- **P1（核心 + 范式）**：聚合器 + `待办事项` 页（4 周期 Tab + 汇总 + 表格 + 导出）+ 接入目标职责例子。跑通"注册即出现"模式。
- **P2（扩源）**：接入 2–3 个高价值缺口源（保险 / 培训 / 隐患），验证扩展成本。
- **P3（增强，可选）**：顶栏角标总待办数；与通知中心 `task` 类型双向跳转；定时快照（每日生成待办快照供"每年"回看）。

## 9. 待商议的关键决策点（请你拍板）

1. **命名**：`待办事项`（推荐） / `待办提醒` / `任务中心` / 其他？
2. **菜单位置**：独立一级菜单（推荐） / 与通知中心同组？
3. **周期语义**：每天=实时缺口常驻？还是每日生成一次快照？"每年"具体承载哪些事项？
4. **首批接入**：除目标职责外，P2 先接哪几个模块？
5. **导出格式**：CSV（首期，复用现有） / 直接上 Excel？
6. **与通知中心关系**：是否打通（通知的 `task` 类型 ↔ 待办行互跳）？还是两库并行？
