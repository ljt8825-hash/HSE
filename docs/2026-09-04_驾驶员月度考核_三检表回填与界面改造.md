## 三、口径决策（用户 2026-09-04 拍板，本文为唯一权威口径）

### 3.1 √ 的取值映射

| 三检表 E 列 | 语义 | 写入 `three_check_management` |
|---|---|---|
| `√` / `✔` / `☑` / `✓` / `✅` | 已执行三检 | **1** |
| 空白 | 缺检 | **0** |
| `×` / `✗` / `✘` | 未执行 | **0** |
| 其它 | — | **0** |

> 说明：该列**不是**「扣分次数」口径，而是「已完成次数」口径。与同一行的 灯牌污损 / 灯具失效 / 安全监控 / 消防管理（问题计数口径）语义相反，需特别注意，勿在后续开发中混用。

### 3.2 多来源合并规则

同一 `(月份, 姓名)` 在多个文件中出现时（仅 2026-04 出现），**任一来源为 √ 即记 1**（`OR` 合并）。
→ 2026-04 因 `综管` 副本全 √，最终全员记 1。

### 3.3 姓名匹配规则

1. `v_employee_current` 中 `position_name LIKE '%驾驶员%'` 为花名册驾驶员全集（当前 **43 人**）；
2. 依次尝试：精确同名 → 去空格后同名 → 唯一包含匹配（模糊）→ 无法匹配；
3. 花名册中查无此人 → **跳过并记录，视为已离职**，不写入；
4. 写入的 `personnel_id` = `employee_id`，`department` = **`org_name`**（作业中心，如「津城街道作业中心」），与既有 2026-09 数据的口径一致（注意：不是 `unit_name` 的「xx镇收运车组」）。

### 3.4 入库范围

- **9 个自然月（2025-11 ~ 2026-07）× 40 人 = 360 条，全部新建**；
- 不新建 2026-09 的记录，既有 74 条数据保持原样（三检表管理全为 0）；
- 其余 4 个计数列（灯牌污损 / 灯具失效 / 安全监控 / 消防管理）本次**一律写 0**，待后续数据源补齐。

## 九、追加诊断：2026-09 存在 30 条重复记录（回填后交叉校验发现）

### 9.1 现象

回填后做交叉校验时发现：`driver_monthly` 的 **2026-09 有 74 行，但只有 44 个不同的人**，30 人被重复建了 2 条。

| 指标 | 值 |
|---|---|
| 2026-09 总行数 | 74 |
| 去重姓名 | 44 |
| 去重 `personnel_id` | 44 |
| **重复组** | **30 组（每组 ×2）** |

### 9.2 根因（已实锤）

1. 74 行**全部**创建于 `09:52:30 ~ 09:52:43` 这 13 秒内，重复对的 id 呈交错分布（16/24、17/27、19/30…），说明是**两个执行流并发写入**，而非两次先后独立的同步；
2. `syncFromRoster()` 依赖组件内 `allRows` 快照判断"某人是否已存在"，**两次并发执行各自持有过期快照**，于是给同一个人各 INSERT 一条；
3. 循环内新建的行**不回写** `byPersonnelId` / `byName` 索引（同一轮内的兜底缺失）；
4. 表上**没有 `(month, personnel_id)` 唯一约束**，数据库层面无法兜底。

排除项：花名册接口**不是**元凶 —— 实测 `/hse/employee/employees` 拉全 1312 行、驾驶员 44 条去重 44 人、**零重复**。
（顺带发现该接口分页有 8 名**保洁员**跨页重复，属 `LIMIT/OFFSET` + 排序键不唯一的漂移，与本次事故无因果，但已作为防御点处理。）

CREATE UNIQUE INDEX uq_driver_monthly_month_pid
  ON driver_monthly (month, personnel_id) WHERE is_deleted = false;
