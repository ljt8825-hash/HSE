## 1. 执行摘要

**核心结论：在不购买云服务器的前提下，「手机 → WPS 官方表单入口 → 现有 Pull → PG」的架构（方案 C）技术可行**。关键依据全部来自 WPS 官方文档/官方社区，非推测：

1. **WPS 多维表格「表单视图」是官方内置能力**：把数据表字段自动转为手机适配的填写页，提交即实时写入多维表记录；链接权限分「互联网获得链接的人 / 仅企业内获得链接的人」两档；支持附件字段传图片（JPG/PNG 等，暂不支持视频）；填写者背对背互不可见、不能修改/撤回已提交内容。
2. **存在系统级可信身份机制**：「登录后填写」是官方开关（关闭即匿名）；开启「收集填写者信息」可自动记录填写者 WPS 账号；多维表格存在**「创建人」高级字段（系统按实名的 WPS 账号自动填充，填写者零输入、无法伪造）**。
3. **图片可以从 WPS 拿回可访问地址**：官方 DBT API 提供「获取文档内附件的下载地址」（`POST /api/v1/openapi/dbt/:file_token/attachment/urls`，按遍历记录返回的 `uploadId + source` 换取 `download_url`，明确支持图片附件；正式应用限频 1000 万次/天）。
4. **手机全程不接触 `WPS_APP_SECRET`**：表单链接是公开入口，Secret 仍只存在本机后端 `.env`。
5. **现有 Pull 体系零改动即可承接**：表单提交的记录就是普通多维表记录，`list_by_page` 全量可读；逐条「INSERT 记录 + INSERT sync_map」单事务、失败回滚、下轮重拉（幂等），断电不丢不重。
6. **WPS 侧新增字段不触碰 05-H-0 冻结**：冻结清单是代码组件层（wpsClient/FieldMap/Pull/Scheduler/Facade/Resolver/gridScope/生产生命周期）；FIELD_MAP 未映射的新列被 Pull 静默忽略、不入 sync_hash。

**但方案 C 有两个必须正视的弱项**（不得粉饰）：

- **身份桥接缺口**：WPS 表单身份 =「WPS 账号身份」（可信但**与 employee 体系无既有映射**），users/employee 表没有 WPS 账号字段；按姓名映射存在重名风险，必须 fail-closed。提交者信息的确切字段内容（昵称/姓名/手机号？）需外部确认。
- **图片与现有 Pull 投影的错位**：表单写入的是**原生 Attachment 字段**，而现有 Pull 的 `rectified_photo` 只从「整改后照片链接」**链接镜像列**（MultiLineText）取值 → Pull 拿不到表单图片。需要一个桥（AirScript 自动化回写链接列，或归属组件经 attachment-urls 端点换 URL），二者均有外部确认项。

**终态：`PHASE_HSE_MOBILE_GRID_ARCH_03_COMPLETED_WITH_EXTERNAL_DEPENDENCIES`**（能力官方文档确证，4 项外部确认项 + 3 项人工决策，见 §19/§20/§21）。

**推荐：方案 C**（详见 §13/§14）。03-B 全部保留（§16）。05-H-0 保持冻结（§17）。

## 6. 身份机制（Q3）

### 6.1 七种方案逐项判定

| 方案 | 判定 | 说明 |
|---|---|---|
| 1. WPS 登录用户身份 | **可行（推荐基础）** | 开启「登录后填写」→ 提交者必须以 WPS 实名账号登录；系统「创建人」高级字段自动填充，**填写者无法伪造他人**。这是表单路径下唯一的系统级可信身份 |
| 2. WPS 表单提交者身份 | 可行 | 「收集填写者信息」自动记录；官方社区确认「提交者」可作为视图筛选/权限维度 |
| 3. 表单预填员工信息 | **NEEDS_EXTERNAL_CONFIRMATION** | 表单支持「字段默认值」但是**静态**配置；按 URL 参数动态预填未见官方文档 |
| 4. 每人专属入口 | 理论可实现（不推荐） | 每人生成专属链接可定位身份，但链接转发即失效其约束（R3-03），62 个网格长维护成本高 |
| 5. 每网格专属入口 | 理论可实现（不推荐） | 同上；且「链接定网格」≠「链接定人」 |
| 6. 匿名提交 + PG 侧归属 | 可行但最弱 | 匿名时官方明确「创建者也看不到身份」→ 只能靠内容字段自报姓名 → **等同用户自填，禁止认定为可信身份**（任务红线） |
| 7. 其他官方机制 | Webhook/自动化存在 | 官方支持 Webhook 实时推送、AirScript 自动化、高级权限（视图级，2026Q1 企业版新增）——可作辅助，不是身份源 |

### 6.2 关键结论

1. **可信的是「WPS 账号身份」**（登录后填写 + 创建人/提交者字段），**不是「手机提交的 employeeId/姓名」**——后者任何时候都必须视为用户自填。
2. **桥接缺口（本架构最大弱点）**：users/employee 表**没有 WPS 账号字段**，WPS 身份 → employee.id 没有现成映射。可行桥只有两种：
   - **姓名对照**：创建人字段值 = WPS 实名姓名 → 与 employee.name 匹配；**重名必须 fail-closed（拒绝归属、转人工）**。employee 表存在重名吗？——生产 employee=3417 条，大概率存在，fail-closed 是硬要求；
   - **人工维护映射**：WPS 账号 ↔ employee 对照表（WPS 侧列或本地维护），62 名网格长规模可人工维护。
3. 提交者信息的确切内容（昵称？实名？手机号？）**NEEDS_EXTERNAL_CONFIRMATION**——官方只说「WPS 账号信息」，具体字段决定姓名对照是否可行。

## 7. grid_id 归属（Q4）

1. **必须在 WPS 中保存 employeeId 吗？——不必须。** WPS 侧保存的是「WPS 账号身份快照」（创建人/提交者 + 可选的姓名快照列）。employeeId 是 PG 概念，它的产生地永远在 PG 侧（resolver/归属逻辑）。
2. **可以在 PG Pull 后通过身份推导 grid_id 吗？——可以，且这是唯一不破坏冻结的路径。** PROTECTED_COLUMNS = ['grid_id','inspector_employee_id'] 不在 SYNC_PROJECTION，Pull 恒写 NULL → 归属必须在 Pull 之后由独立逻辑完成。
3. **可复用现有函数吗？——可以。** `deriveGridIdForEmployee(employeeId)`（gridScope.js）+ resolver 的身份语义 + own_grid 的判定标准全部复用；归属组件只做「employeeId → grid_id（唯一才写）」。
4. **会出现多网格吗？——会。** 一个网格长可兼任多格（`deriveGridIdForEmployee` 返回 multiple/no_grid 两类失败态）。
5. **多网格必须 fail-closed 吗？——必须。** multiple/无网格 → 不回填、登记待人工。宁可 NULL（PC 可见、手机 own_grid 暂看不到）也不可错绑。
6. **只在 inspector_employee_id IS NULL 时首次写入？——是。** `WHERE id=$ AND inspector_employee_id IS NULL`（07 数据基线中 NULL 是历史集合，更不可回填——只处理本轮 Pull 产生的新行）。
7. **永不覆盖？——是。** NULL→值单向，永不 UPDATE 已有值。
8. **与 05-H-0 冲突？——无。** 不改 SYNC_PROJECTION/PROTECTED_COLUMNS/Pull 引擎/sync_map；只读消费 `grid_record_sync_map`（UNIQUE(wps_record_id,wps_file_id) 恰好是「哪些 PG 行来自 WPS」的现成索引）。

### 「独立归属组件」是否真的必要 → 必要，定性 B

- **A（WPS-PG-SYNC 的修改）？否**：它不触碰 Pull 引擎、FieldMap、Scheduler、sync_map 的任何写入路径；只是在 Pull 产物之上运行的**下游业务步骤**。
- **B（PG 正式业务层的独立业务组件）？是**：其职责（身份解析、网格归属、fail-closed）与 `authenticatedEmployeeResolver`/`gridScope` 同属正式业务层的身份语义；它消费 sync_map 只读、写 gir 仅 NULL→值。
- 判定依据：05-H-0 冻结清单是同步链路组件本身；「Pull 之后谁补业务字段」从来不是同步引擎的职责（同步引擎连 identity 都不信任 WPS，见「WPS ≠ 正式身份源」语义边界）。

## 8. 幂等能力（Q5 场景 + Q6）

### 8.1 六场景

| 场景 | 结果 |
|---|---|
| 1. 电脑正常，手机提交 | 表单提交 → WPS 记录（≤秒级）→ 下一个 15 分钟周期 Pull → PG → HSE 可见。**全程无损** |
| 2. 电脑完全关机 → 开机 | 提交瞬间即存 WPS 云端（**A 阶段完成**）；关机期间 B/C/D 全部暂停；开机后 Task Scheduler（AtStartup+每分钟）自动拉起后端 → Scheduler 15 分钟周期 Pull → `list_by_page` 全量分页 + hash 比对，**追赶式补齐**（无论欠多少轮都只补增量）。B/C/D 依次完成 |
| 3. 关机 1 天、20 条 | 20 条全在 WPS；开机后**一次 Pull 批量入库**（每条独立事务）。无丢失 |
| 4. 开机后 Pull 未跑、手机继续提交 | WPS 继续累积；Pull 下轮统一拉取。缓冲与入库解耦，不存在竞态 |
| 5. Pull 中途断电 | 引擎逐条处理：「INSERT gir + INSERT sync_map」**单事务**，失败整体 ROLLBACK（wpsGridPullEngine.js:247-272/290-303）；断电时至多丢「当前正在写的一条」，该行 sync_map 未落 → 重启后重拉重写（幂等 upsert）。**不丢、不重** |
| 6. 同一手机重复提交 | 表单官方明确「重新提交 = 新增一条记录」「无次数限制」→ WPS 产生记录 A、B → **PG 会出现两条**。这是方案 C 唯一真实的数据质量缺口，防线见 8.2 |

### 8.2 幂等与 client_token（Q6）

- **WPS 自生成 Record ID 是否足够？——对「Pull 不重复」足够**（sync_map UNIQUE(wps_record_id,wps_file_id) 已真机冻结验证）；**对「同一次业务提交被填两次」不够**——A/B 是两条合法记录，sync_map 各自映射，天然无唯一业务键。
- **能否提交前查重？——不能。** `list_by_page` 无字段值筛选（官方参数表 + 本地真机双确证）；官方能力清单的「查询记录」专用端点是否支持条件筛选仍 **NEEDS_EXTERNAL_CONFIRMATION**；表单填写者侧更不可能调 API。
- **增加 WPS 字段 `client_token` 是否违反 05-H-0？——分别判定（按任务要求）：**
  - **WPS 表结构加一个业务缓冲字段：不违反 05-H-0 字面**。冻结清单为代码组件（wpsClient/Adapter/FieldMap/Pull/Scheduler/Facade/Resolver/身份链/生产生命周期）+ 语义边界；新列不在 FIELD_MAP 中 → Pull 静默忽略、不入 SYNC_PROJECTION、不入 18 列 sync_hash → 三个冻结物全都不动。**但**它属于「冻结层外的数据源结构变更」，必须：①人工在 WPS 界面执行（本任务禁止，列 P0 决策）；②变更后跑一次 Pull 幂等回归（预期零 DML）证明零扰动。
  - **修改 PG 表结构（为 token 加列）：违反冻结原则，禁止。** 05-H-0 基线 + 本系列「不新增 PG 字段」的一贯约束。
  - **零 DDL 替代**：归属/去重组件复用 gir 现有冗余文本列（如 `marker`）存放 client_token 快照——只写测试曾用过的既有列，不加字段。此为可选设计，需人工决策。
- **现实防线分级**：①表单内加「提交时间」自动字段 + 创建人，便于人工识别重复；②（若加 client_token 列）PG 侧去重逻辑按 token 合并；③兜底：重复记录在 PC 台账人工清理（与现状 PC 侧手工纠错一致）。

## 9. WPS 行级权限（Q7）

| 网格长能做什么 | 判定（表单路径，网格长**不是**多维表格协作者） |
|---|---|
| 1. 只提交 | **PASS** —— 表单即只新增入口 |
| 2. 查看自己提交 | **NEEDS_EXTERNAL_CONFIRMATION** —— 需「登录后填写」+ 分享「仅自己创建记录」的筛选视图（官方社区确认可行）；该能力依赖企业版高级权限（2026Q1 新增视图权限）是否对本组织开放待确认 |
| 3. 修改自己的 | **FAIL（被官方禁止）** —— 表单不支持撤回/修改（对缓冲层是**优点**：提交即固化） |
| 4. 删除自己的 | **FAIL（被官方禁止）** —— 同上 |
| 5-7. 查看/修改/删除**其他人**的 | **FAIL（被官方禁止）** —— 「每个填写者只能看到自己的填写页面，无法查看他人的提交数据；数据汇总只有创建者和管理员可以查看」 |

**目标原则达成判定**：「手机端只允许提交，不获得整表管理权限」——**成立**，前提是运营纪律：**网格长绝不能被添加为该多维表格的协作者**（协作者才有记录编辑权）。APP_SECRET 始终只在本机后端。

优先评价：**「仅企业内可填写」+ 登录后填写 + 收集填写者信息 + 字段隐藏内部列 = 高安全方案**（Q7 官方标准下的最优档）。

