## 0. 背景

审计报告（§2.8）标明考核模块当前状态：

| 维度 | 状态 |
|------|------|
| 数据库 | 🟢 `hse_responsibility_assessment.employee_id` 列存在（但前端从未写入，恒为 NULL） |
| 后端 formatRow | 🔴 动态 keys 返回，未暴露 `employeeId` |
| 后端 INSERT/UPDATE | 🟡 列存在可写，但前端不传 |
| 前端 API 类型 | 🔴 `assessment.ts` 无 `employeeId` 字段 |
| 前端表单 | 🔴 `person` 文本 Input |
| 前端详情/列表 | 🔴 `person` 文本 |

**核心问题**：数据库列存在但全链路未启用。审计报告明确标注"需先确认'考核对象'应为个人还是组织/岗位，再决定修复方案"。

**目标**：通过代码审查 + 数据探查，确认考核模块的语义，输出明确结论和修复方案（如有）。

## 1. 审计方法

### 1.1 前端代码审查

```bash
# 1. 定位考核模块的活动文件
grep -n "assessment" src/router/routes/index.ts

# 2. 审查考核对象字段的上下文

grep -n "部门\|岗位\|组织\|dept\|org\|position" src/views/assessment*/index.vue
```

### 1.2 后端代码审查

```bash
# 4. 确认后端动态 keys 是否可传 employee_id
grep -n "employee_id\|employeeId" server/routes/objectives.js
grep -n "b\[k\]\|dynamic.*keys\|formatRow" server/routes/objectives.js

# 5. 确认考核表结构
grep -rn "employee_id" server/sql/ | grep -i assessment
```

### 1.3 数据库探查

```sql
-- 6. 确认 employee_id 列的实际数据
SELECT 
  COUNT(*) AS total,
  COUNT(employee_id) AS has_employee_id,
  COUNT(*) - COUNT(employee_id) AS null_employee_id
FROM hse_responsibility_assessment;

-- 7. 查看考核对象文本的实际内容（判断是人名还是组织名）
SELECT DISTINCT person, COUNT(*) AS cnt
FROM hse_responsibility_assessment
WHERE person IS NOT NULL AND person != ''
GROUP BY person
ORDER BY cnt DESC
LIMIT 20;

-- 8. 查看同表是否有部门/组织字段
SELECT column_name, data_type
FROM information_schema.columns
WHERE table_name = 'hse_responsibility_assessment'
ORDER BY ordinal_position;
```

## 2. 判定标准

| 证据 | 指向"个人" | 指向"组织/岗位" |
|------|-----------|---------------|
| 表单同页有部门选择器 | 可能是个人（部门作为从属信息） | 可能是组织（考核对象 = 部门） |
| 表单同页无部门选择器 | 可能是组织（考核对象本身就是部门） | — |
| `person` 字段实际数据为姓名 | ✅ 个人 | ❌ |
| `person` 字段实际数据为部门名 | ❌ | ✅ 组织 |
| `employee_id` 列已有非 NULL 数据 | ✅ 个人（已有映射） | — |
| 提交时是否需要选部门 | 个人（额外选部门） | 组织（考核对象即为部门） |


### 3.2 若为"个人"的修复方案（方案 A）

| 层次 | 改动 |
|------|------|
| 前端 API 类型 | `assessment.ts` 补 `employeeId?: number` |
| 前端表单 | `person` Input → `EmployeeSelector`（`@change` 同步 `person` 文本） |
| 前端详情/列表 | `person` 文本 → `<EmployeeName>` + 文本兜底 |
| 后端 | 确认动态 keys 可透传 `employee_id`（若 `b[k]` 模式自动支持则零改动） |

### 3.3 若为"组织/岗位"的结论（方案 B）

输出明确结论：考核模块不适用 EmployeeName 统一模式，保持现状，列入"已评估-不适用"。
