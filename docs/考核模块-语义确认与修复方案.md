## 1. 审计结论

### 考核模块语义结论

**结论：考核对象为「个人（员工）」，适用 EmployeeName 统一模式。**

**依据：**

1. **前端（活动文件 `views/objectives/assessment/index.vue`）**
   - 表单同时含 `部门` 选择器（`<Select>` 绑 `department`，作为从属信息）与 `考核对象` 文本输入框（`<Input v-model="assessmentForm.person">`）。
   - 按判定标准：「表单同页有部门选择器 → 部门作为从属信息 → 指向个人」。此处「考核对象」为被考核的**具名个人**，部门是其所属单位，并非考核对象本身。
   - 列表/详情均以 `person`（考核对象）为主展示字段，语义即「某人被考核」。

2. **数据库（`hse_responsibility_assessment`）**
   - 列结构明确为个人维度：`employee_id BIGINT`、`employee_no VARCHAR(50)`、`employee_name VARCHAR(100) NOT NULL`、`position VARCHAR(100)`、`department VARCHAR(100)`、`org_unit_id BIGINT`、`period_year`、`period_quarter`、`score_total`、`grade` 等。
   - `employee_name NOT NULL` + `employee_id` + `employee_no` + `position` 组合，是不折不扣的「按员工逐人考核」建模，不存在「组织/部门作为考核对象」的设计（若有，应无 `employee_*` 列而仅 `org_unit_id`）。
   - **当前表为空（0 行）**：无任何生产数据可采样。但表结构已足以判定语义。

3. **后端（`server/routes/objectives.js`）**
   - 列表/详情为 `SELECT * FROM hse_responsibility_assessment`，**响应中已包含 `employee_id`**（提示词-46 所述「formatRow 未暴露 employeeId」不准确，实际已暴露，只是前端从未使用）。
   - 写入为动态 `b[k]` 模式（`INSERT` L461、`UPDATE` L472），**若前端传入 `employee_id` 即可透传落库，后端零改动即可支持**（与提示词假设一致）。

**结论指向：个人（员工）。** → 适用 **方案 A**。

## 2. 实勘对提示词占位假设的纠正（重要）

提示词-46 §0 审计表的若干结论为「印象/占位」，经实勘需修订：

| 提示词假设 | 实勘结果 | 影响 |
|-----------|---------|------|
| 前端 API 类型 `assessment.ts` 无 `employeeId` | **错误模块**。`assessment.ts` 是「考核分析」系统（`BASE /hse/assessment` ↔ `server/routes/hse-assessment.js`），与责任考核无关。本模块真实 API 在 `src/api/hse/goals.ts` 的 `AssessmentApi` 命名空间（`AssessmentItem.person: string`、`createAssessment`→`/objectives/responsibility`）。 | 修复应改 `goals.ts`，非 `assessment.ts` |
| 后端 formatRow 动态 keys 未暴露 `employeeId` | **不准确**。后端 `SELECT *` 已返回 `employee_id`。真实缺口在前端（类型/表单/详情从未使用 `employeeId`/`employee_name`）。 | 后端链表无需改 |
| 数据库 `employee_id` 恒为 NULL（前端从未写入） | **部分准确但根因更深**。表实际 **0 行**（完全空），并非「有数据但 employee_id 为 NULL」。整条写入链路当前是坏的（见 §3），故无任何行。 | 修复范围比「补 employeeId」更大 |
| 路由 `/objectives/responsibility` vs 后端 `/responsibilities` 不一致 | **已核实为别名，非 bug**。后端 L1042-1046 将 `/responsibility*` 转发至 `/responsibilities*`，前端路径可正常命中。 | 无需改路由 |

## 3. 关键伴生缺陷（写入链路当前失效，超出原语义确认范围，但为修复前置）

实勘发现本模块写入路径**整体不可用**，根因是「前端字段名 ↔ 后端列名」未做映射：

- 前端提交（L571-580）字段为 camelCase：`person / year / quarter / score / level / status / remark / department`。
- 后端表列为 snake_case：`employee_name / period_year / period_quarter / score_total / grade / status / remark / department`。
- 后端 `responsibilities` 的 `POST/PUT` 处理（L461-485）是**纯动态 `b[k]` 透传**，**没有任何 camelCase→snake_case 映射层**；而同文件的 `goals` 处理（L939-981）却显式做了 `responsiblePerson→responsible_person`、`responsiblePersonId→responsible_person_id` 映射。
- 结果：提交 `person` 等列时，动态 SQL 尝试 `INSERT INTO ...(person, year, quarter, score, level)`，而表无这些列 → SQL 报错 → 创建失败 → **表恒为空**。

**含义**：即便仅按「方案 A 补 employeeId」实施，若不补字段名映射，数据仍写不进库。因此方案 A 必须包含「字段名映射补全」这一步（详见 §5）。

## 5. 修复方案（方案 A — 增强版，适用「个人」语义）

> 说明：本提示词为**纯审计**，不执行修复。以下为确认后的修复蓝图，供后续独立任务（提示词-46 范围外 #5）实施。

### 5.1 后端（基本零改动，仅需补映射）

| 层次 | 改动 |
|------|------|
| `objectives.js` responsibilities 写入 | 在 `POST/PUT` 的 `b[k]` 透传前，增加 camelCase→snake_case 映射（参照 goals 处理 L939-981）：`person→employee_name`、`year→period_year`、`quarter→period_quarter`、`score→score_total`、`level→grade`，并**新增 `employeeId→employee_id`**（`employee_no/position/department` 可选由前端随选人回填或后端查表派生）。 |
| 列表/详情 | 已 `SELECT *` 含 `employee_id`，**零改动**。建议显式 `employee_id` 以确保稳定。 |
| FK（可选，P2） | 当前 `employee_id` 无 FK；可后续补 `REFERENCES employee(id) ON DELETE SET NULL`（范围外 #2）。 |

### 5.2 前端 API 类型（`src/api/hse/goals.ts`）

| 改动 | 说明 |
|------|------|
| `AssessmentItem` | 增 `employeeId?: number \| null`、`employeeNo?`、`position?`；保留 `person`（作为 `employee_name` 文本兜底）。 |
| `AssessmentListParams` | 可增 `employeeId` 过滤（可选）。 |

### 5.3 前端表单（`views/objectives/assessment/index.vue`）

| 改动 | 说明 |
|------|------|
| `考核对象` 字段 | `<Input v-model="person">` → `<EmployeeSelector v-model:employeeId @change="onPersonChange">`；`@change` 回填 `person = item.name`、`employeeNo`、`position`、`department`（选人即带出所属部门/岗位）。 |
| 提交载荷 | `data` 增 `employeeId: assessmentForm.employeeId`（经映射层落 `employee_id`）；保留 `person` 文本兜底。 |
| 重置/回填 | `assessmentForm` 增 `employeeId`，`handleEdit`/`handleCreate` 同步。 |

### 5.4 前端详情/列表

| 改动 | 说明 |
|------|------|
| 列表 `考核对象` 列 | `bodyCell` 改为 `<EmployeeName v-if="record.employeeId" :employee-id="record.employeeId" /><span v-else>{{ record.person }}</span>`。 |
| 详情 `考核对象` 行 | 同上模式（L231-232）。 |

### 5.5 统一度收口

实施完成后，人员 ID + EmployeeName 统一覆盖模块将由 **6/8** 提升至 **7/8**（事故/隐患/应急/三违/目标/培训/考核）；仅剩 **保险超龄 personnel 域**、**考核 FK 补全** 为后续 P2。

## 6. 结论一句话

考核模块的「考核对象」是**个人（员工）**，数据库以 `employee_*` 列建模、表当前为空（写入链路因字段名未映射而失效）；语义确认适用 EmployeeName 统一模式（方案 A），且修复必须**同时补全字段名映射层**，否则数据仍无法落库。本提示词未改动任何文件。
