## 2. 编码根因分析（⚠️ 关键偏离项）

### 2.1 假设与实测结论
提示词-04 调研基于"同日网格/三违导入中文正常、培训 82 行乱码"推断**培训导入链路存在编码 bug**。本轮 **A1 端到端实测推翻该假设**：

```
实测链路：构造含中文姓名/合格-不合格/培训日期的样例文件
  → upload（multipart）→ parseExcelNative → confirmImportNative → 查 DB
结果：name / result / content 中文完全正常落库 ✅
```

→ **当前导入解析链路无编码缺陷**。

### 2.2 82 行乱码真因（取证）
- 存活 82 行 `id` 连续 907–988，`created_at` **全部** `2026-08-29 14:39:01`（同一批次）。
- `name` = U+01E9「ǩ」(GBK `c7a9`=「签」)，`result` = U+03F8「ϸ」(GBK `cfb8`)；用 `iconv-lite` 按 GBK 回解 `c7a9`=签、`cab1 d0a7 d7b4 ccac`=时效状态 → **单元格内容本身是 GBK 字节被按 UTF-8 解读**，生成的是"合法但语义错"的 UTF-8 字符。
- 反证链（非导入 API 产生）：
  - `file_records` 08-29 全为 `grid` 模块；`import_logs` 无 `training_records` 写入记录；
  - 仓库无针对 `training_records` 的 INSERT 脚本；
  - 既有守卫（`import.js` 旧逻辑仅在首行含 U+FFFD 替换符时拦截）漏过此类"合法但乱码"字符。
- 结论：疑为**手工 SQL / 临时脚本批量插入**了一批已损坏源数据，与导入 API 无关。

### 2.3 对策（不修解析、加防御守卫）
既非解析 bug，则**不动 xlsx/CSV 读取逻辑**，仅在导入入口加防御：
- `looksLikeMojibake()`：检测"GBK 字节序列被当 UTF-8 解读"产生的特征字符（U+01E9/U+03F8 等合法 UTF-8 码位）；
- `mojibakeCheck` 字段清单（两培训模块共 8 个业务文本字段：name/dept/position/content/result/trainer/remark/training_type）；
- 命中即**整文件拒绝导入**并提示"请另存为 UTF-8 编码后重试"，避免部分乱码数据静默入库。

## 3. 人员落键口径

对齐三违导入 `resolveViolatorId` 口径，三级优先级（显式 > 证件 > 姓名）：

```
1. 显式 employeeId / personnelId（前端选择器传来）→ 直接落键
2. 身份证号 → hashSensitive(id_card) 命中 employee.id_card_hash → 落 personnel_id/employee_id
3. 姓名经 v_employee_org_full（is_current=true, is_deleted=false）批量唯一匹配
   → 唯一存活匹配落键并写回标准 name；重名/未匹配保留原文、不落键、不报错
```

- 落键后 `conflictKey` 优先用人员 id（避免同名文本冲突）；无键行回退原 name 文本键。
- 响应与日志输出 `trainingResolveStats`：`resolved / resolvedByIdCard / ambiguous / unmatched / unmatchedSamples`。
