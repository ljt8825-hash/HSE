## 0. 已核验事实（直接采信）

* 缺陷位置：`server/services/assessmentScheduler.js` 的 `cycleBoundary(year, month)`（约 69-73 行）用 `new Date(Date.UTC(year, month-1, 1, 0,0,0))` 与 `new Date(Date.UTC(year, month, 1, 0,0,-1))` 构造窗口 → 落库为 UTC 0 点 = **北京时间 08:00**。

* 库内实证：cycle43（自动建）窗口 = 2026-09-01 08:00 CST \~ 2026-10-01 07:59 CST；cycle24（手工建）= 2026-08-01 00:00 \~ 2026-08-31 23:59 CST。DB 会话时区 Asia/Shanghai；服务器本地时区即北京时。

* 后果：①9/1 01:00 网格校验 `start_time <= NOW()` 不成立 → 9 月周期当天选不中，首次累计推迟到 9/2（应巡按天累计、数字自愈，无永久损失）；②月末边界跨入下月 1 号早 8 点；③未来每月自动周期均偏移 8 小时。

* cycle43 当前 0 扣分、0 得分、62 targets（修正窗口安全）。

* 旧评分路在 `server/services/assessmentScoringEngine.js`：`FILL_SOURCES`（约 523-590 行）——training（training\_records.employee\_id，result='不合格'，3 分/次，HSE-KPI-TRN-002）与 accident（accidents.personnel\_id，一票否决 suggestedScore=100，按事故类型映射 HSE-KPI-NEG-001/002/003）。两路当前均为死路（关联键全空），但**未来事故/培训录入落键后会静默激活**，且无测试覆盖、业务口径未拍板。

* 基线：cycle24 网格 54 行/103.00/全 pending；三违来源 0 行；ruleEngine 95/95 + scheduler 10/10 = 105/105（8 套件）；全量 jest 失败 7 基线；typecheck 51 基线。

* 部署：后端进程在运行、WorkBuddy 无权限重启；数据修复即时生效，代码修复待重启。

* `cycleBoundary(year, month)` 改为**服务器本地时区午夜**构造：`new Date(year, month-1, 1, 0,0,0,0)` 与 `new Date(year, month, 1, 0,0,0,0) - 1ms`（或 `new Date(year, month, 0, 23,59,59,999)`），与手工建周期路径落库口径一致（本地 00:00:00 \~ 23:59:59）。

* 注释写明：服务器时区固定 Asia/Shanghai，禁止再用 Date.UTC 构造业务日边界。

* 排查其它使用 Date.UTC 构造业务日期/月份边界的位置（grep `Date.UTC`），同口径修复；与业务日边界无关的（如纯时间戳）不动。
