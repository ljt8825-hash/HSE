## 一、背景与现象

提示词-97 已修复清空按钮的「401 跳登录」与「FK 错误友好提示」问题，但**清空操作本身在现网仍不可达**：

| 阻塞层 | 状态 |
|--------|------|
| 401 Token 过期（access 12h + body 刷新） | ✅ 已修复 |
| 6 个 `NO ACTION` 外键硬引用 `employee.id` | ❌ 仍阻塞物理删除 |
| 约 5,412 条活跃业务引用 | ❌ 仍阻塞 |

原 `POST /clear-all` 的删除顺序为 `employee_assignment → employee → pending → batch`，但 `employee` 被 6 个 `NO ACTION` 外键引用，`DELETE FROM employee` 被 PostgreSQL 以 `23503` 拦截，整个事务 `ROLLBACK`，数据零变动（属**安全拦截**，非 bug）。

## 二、FK 审计（实测）

- 引用 `employee.id` 的外键共 **40 条**（`pg_constraint` 行）
- 去重后涉及 **30 张不同子表**（`employee_assignment` 有两个指向 `employee` 的外键）
- **6 张 `NO ACTION` 表**（拦截物理删除）
- **24 张 `SET NULL` 表**（不拦截，删除时置 NULL）

## 三、关键发现：双重计数 Bug（已修复）

`employee_assignment` 对 `employee` 存在**两个外键**：

- `employee_id` → 删除规则 **NO ACTION**
- `supervisor_id` → 删除规则 **SET NULL**

若按「每条 FK 单独计数 / 单独删除」，会将该表 **5,234 行重复计入两次**，并在级联中**重复 DELETE** 一次（虽幂等无害，但统计与展示会翻倍误报）。

**修复方式**：后端在 `preview` 与 `cascade` 中均以**表名去重**（`Map<tbl, rule>`），当同一表同时存在两种规则时，**归为 NO ACTION 一类**（因其必须在删 employee 前清空），每个表只计一次、只删一次。审计落地后 `employee_assignment` 仅计入 NO ACTION 桶、`supervisor_id` 那条 SET NULL 不再单独成表。

## 四、备份状态（执行前置条件）

级联路由内置**备份闸门**：若不存在 `backup_97_*` 或 `backup_98_*` 逻辑备份表，直接拒绝执行。

## 六、结论

| 层面 | 诊断 | 处置 |
|------|------|------|
| 清空不可达 | 6 个 NO ACTION FK + 5,412 引用 → 物理删 employee 被整体回滚 | 实现级联清空：先解 FK 再删核心表 |
| 双重计数 | employee_assignment 双 FK → 重复计/删 | 按表名去重，NO ACTION 优先 |
| 硬编码风险 | 提示词清单含 5 张不存在表 | 改为动态 FK 发现 |
| 安全 | 生产库真实引用，破坏性清空需授权 | 备份闸门 + admin-only + 事务回滚 |
| 防改触发器 | `hse_deduction_adjustment` / `hse_assessment_audit_log` 有 BEFORE DELETE 触发器 | 级联中 `DISABLE/ENABLE TRIGGER USER` |

> 说明：本生产库存在真实业务引用，**级联物理清空属于不可逆破坏性操作**。诊断与验证仅通过「只读预检查」+「事务 ROLLBACK 干跑」确认机制正确、数据零变动，**未**做真实提交（符合「禁止破坏性生产数据操作」原则）。
