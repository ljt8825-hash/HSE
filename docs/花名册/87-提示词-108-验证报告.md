## 1. Task 1：部门员工子列表 SQL 关联修复（P1）

### 1.1 根因确认

`GET /departments/:id/employees` 原实现：

```js
conditions.push(`ou.id = $${paramIdx}`);   // ← hse_org_unit.id 与 department.id 跨 ID 空间比较
params.push(deptId);
```

实测两表 ID 空间完全不相交：`department.id` 从 **4056** 起，`hse_org_unit.id` 仅 **1–20** → 条件恒不成立 → 员工子列表恒为空。根因与提示词-107 §5 记录一致。

### 1.2 ⚠️ 提示词方案 A 的前提不成立（重要修正）

提示词建议直接改为 `WHERE ou.org_name = (SELECT name FROM department WHERE id = $1)`。**实测该写法改完仍然全空**：

```sql
SELECT COUNT(*) AS dept_total,
       COUNT(*) FILTER (WHERE EXISTS (
         SELECT 1 FROM hse_org_unit ou WHERE ou.org_name = d.name AND ou.is_deleted = false)) AS matched
FROM department d WHERE d.is_deleted = false;
-- dept_total = 77 | matched = 0     ← 精确等值命中 0 行
```

原因是**两张表的组织粒度与命名口径不同**：

| 表 | 行数 | 粒度 | 命名样例 |
|---|---|---|---|
| `department` | 77 | 细到**班组** | `宁城街道`、`宁城街道一班`、`杜集镇三四班`、`转运车辆`、`生产运营部` |
| `hse_org_unit` | 20 | 只到**作业中心** | `宁城街道作业中心`、`刘营伍乡作业中心`、`环卫作业中心`、`财务部` |

同时验证了其他候选关联键，均不可用：

- `employee_assignment` 无 `dept_id` 列（列为 `employee_id / org_unit_id / operation_unit_id / position_id / supervisor_id / …`）→ 员工与部门树之间**只能经 `hse_org_unit` 绕行**；
- `department.township` 77 行中 76 行为 NULL、1 行为空串 → 不可用；
- `department` 表也没有 `org_unit_id` 之类的外键列。

### 1.3 实际采用方案：精确优先 + 前缀兜底

```sql
-- 前缀规则命中情况（已验证 1:1，无一对多）
SELECT d.id, d.name, ou.id, ou.org_name
FROM department d
JOIN hse_org_unit ou ON ou.org_name LIKE d.name || '%' AND ou.is_deleted = false
WHERE d.is_deleted = false;
-- 24 行；GROUP BY d.id HAVING COUNT(ou.id) > 1 → 0 行（无歧义）
```

命中样例（含一个只有前缀才能救回的边界）：

| department | → hse_org_unit | 在岗人数 |
|---|---|---|
| 宁城街道 (4056) | 宁城街道作业中心 (9) | 49 |
| 柴胡店镇 (4067) | 柴胡店镇作业中心 (12) | 167 |
| **刘营伍 (4104)** | **刘营伍乡作业中心 (8)** | 66 |
| 长官镇 (4087) | 长官镇作业中心 (10) | 155 |
| …共 12 个乡镇 × 2（L5 父 + L6 同名子）= 24 个部门 | | 合计 1287 |

> 注：`刘营伍 → 刘营伍乡作业中心` 中间多一个「乡」字，`d.name || '作业中心'` 的拼接式规则会漏掉它，前缀规则则能正确命中——这是选前缀而非拼接的原因。

### 1.4 代码改动（`server/routes/hse-employee.js`）

**改动 1 —— `GET /departments/:id/employees`（约 1280 行）**

```js
// 提示词-108 T1：修复跨 ID 空间比较 bug（P1）… （完整注释见源码）
const deptRow = await pool.query(
  `SELECT name FROM department WHERE id = $1 AND is_deleted = false`, [deptId]
);
if (deptRow.rows.length === 0) return res.json(error(-2, '部门不存在'));
const deptName = deptRow.rows[0].name;

const ouRows = await pool.query(
  `SELECT id, (org_name = $1) AS exact_hit FROM hse_org_unit
    WHERE is_deleted = false AND (org_name = $1 OR org_name LIKE $1 || '%')`,
  [deptName]
);
const exactIds = ouRows.rows.filter((r) => r.exact_hit).map((r) => r.id);
const orgUnitIds = exactIds.length > 0 ? exactIds : ouRows.rows.map((r) => r.id);

// 班组级部门在 hse_org_unit 中无对应节点，返回空列表而非报错
if (orgUnitIds.length === 0) {
  return buildListResponse(res, [], 0, pageNum, limitNum, '查询成功', { camelCase: false });
}
conditions.push(`ou.id = ANY($${paramIdx})`);
params.push(orgUnitIds);
```

设计要点：**精确匹配优先**（若某天两表命名对齐，精确结果直接生效，前缀不参与）；用 `ANY(array)` 而非单值，即便未来出现一对多也不会报错；未命中返回空列表而非 500；部门本身不存在才返回 `-2`。

**改动 2 —— `GET /departments/tree` 的 `employee_count`（约 1198 行，连带修复）**

原统计同样用精确 `ou.org_name = d.name` → **全部 77 个节点人数恒为 0**。前端 `departments.vue` 第 142/162 行读 `actual_headcount ?? employee_count ?? deptEmployeesTotal`（`??` 只对 null/undefined 兜底，`0` 会被原样显示），若只改子列表不改统计，会出现「树上写 0 人、点开却有 49 人」的新矛盾。故同步统一口径，并补 `ea.is_primary = true` 使两处数字完全一致：

```sql
LEFT JOIN hse_org_unit ou ON (ou.org_name = d.name OR ou.org_name LIKE d.name || '%')
  AND ou.is_deleted = false
LEFT JOIN employee_assignment ea ON ea.org_unit_id = ou.id
  AND ea.is_current = true AND ea.is_primary = true AND ea.is_deleted = false
```

### 2.3 ❗E3 附带发现并修复：统计卡片 camelKeys（与 101/102/107 同类）

`GET /employees/stats` 原实现对整个返回对象套了 `camelKeys(...)`，它会**递归改写数组元素内的键**：

```json
// 修复前
"byPersonType":[{"personType":"生产人员","count":1219}, …],
"byPersonCategory":[{"personCategory":"适龄人员","count":1311}],
"byOrgStatus":[{"status":"在职","count":1311}]
```

而 `index.vue` 读的是 snake_case：

```js
stats.value.byPersonType.find((s) => s.person_type === '生产人员')       // → undefined
stats.value.byPersonCategory.find((s) => s.person_category === '超龄人员') // → undefined
stats.value.byOrgStatus.find((s) => s.status === '在职')                  // → 正常（status 无下划线）
```

**后果**：4 张统计卡中「生产人员」「超龄人员」两张**恒显示 0**，而「员工总数」「在职人数」正常——只坏一半，极易被误认为是数据问题而漏看。前端类型契约 `EmployeeApi.EmployeeStats`（`api/hse/employee.ts:105-107`）本就声明为 `person_type` / `person_category`，说明后端的 camelKeys 才是偏离项。

**影响面**：`getEmployeeStats` 全仓仅 `views/hse/employee/index.vue:330` 一处消费，改动安全。

**修复**：去掉 `camelKeys` 包装（外层 `byPersonType` 等本身就是 camelCase 字面量键，不受影响）。


### 3.3 附带记录：班组级部门无员工（设计限制，非缺陷）

`employee_assignment.org_unit_id` 只指向 `hse_org_unit`（20 个节点，最细到「作业中心」），全库实际使用 18 个。因此 `department` 树中的班组级节点（`宁城街道一班`、`杜集镇三四班` 等 53 个）在任何关联方案下都无法挂到员工，点击后显示「该部门暂无员工」属**数据模型的固有限制**。若业务确需班组级人员归属，需要为 `employee_assignment` 增加班组维度（`dept_id` 或扩展 `hse_org_unit` 到班组粒度），属独立需求。

另记：`department` 树中 12 个乡镇存在「L5 父节点 + 同名 L6 子节点」的重复结构（如 4056 宁城街道 / 4057 宁城街道），两者会映射到同一个作业中心并显示相同人数（各 49），属部门树自身的数据结构问题，不在本次范围。
