## 1. 问题描述

在「员工列表」页面导入花名册（`员工信息维护_20260730090323.xlsx`）后，人员 **孙佳敏**（员工编码 `00271497`）在系统中显示的职位为 **管理员**，而花名册中其职位为 **行政综合主管**，两者不一致。

## 2. 根因分析

### 2.1 花名册格式

本次导入的花名册表头为：

```
序号 | 员工编码 | 姓名 | 所属部门 | 职位 | 入职日期 | 身份证号码 | 性别 | 出生日期 | 年龄 | 直接上级 | 手机号码 | 入司日期 | 完整度百分比
```

即采用 **「所属部门 + 职位」** 格式，**不包含「组织路径」列**。

孙佳敏所在行：
- 所属部门：`人力综合部`
- 职位：`行政综合主管`

### 2.2 旧导入逻辑缺陷

`server/routes/hse-employee.js` 中 Excel 导入的组织/岗位关联逻辑为：

```javascript
if (normalized.org_path) {
  // 仅当存在「组织路径」时才解析组织并关联岗位
  ...
} else if (normalized.position_name) {
  // 无组织路径时仅提示，不关联岗位
  warnings.push({ index: rowIndex, message: `岗位"${normalized.position_name}"因未指定组织路径已跳过` });
}
```

**缺陷**：系统只识别「组织路径」列，对「所属部门 + 职位」格式的花名册，岗位（职位）关联被直接跳过。因此孙佳敏导入后没有关联到「行政综合主管」岗位，其 `employee_assignment` 仍保留旧的默认任职记录「管理员」，导致列表显示为「管理员」。

### 2.3 关联字段缺失

`EXCEL_HEADER_MAP` 中缺少以下表头映射：
- `所属部门` → `dept_name`（未映射，部门无法解析）
- `职位` → `position_name`（未映射，职位无法解析）
- `身份证号码` → `id_card`（未映射，身份证无法解析）

## 3. 修复方案

### 3.1 表头映射补齐

在 `EXCEL_HEADER_MAP` 中新增：

```javascript
'身份证号码': 'id_card',
'所属部门': 'dept_name',
'职位': 'position_name',
```

（`岗位`、`岗位名称` 原有映射保留，三者均映射到 `position_name`）

### 3.2 新增部门解析函数

新增 `resolveOrgUnitByDeptName(client, deptName)`，支持无「组织路径」列时按「所属部门」名称解析组织单位（`hse_org_unit`）：

```javascript
async function resolveOrgUnitByDeptName(client, deptName) {
  if (!deptName) return null;
  // 1. 精确匹配 org_name
  const exact = await client.query(
    `SELECT id FROM hse_org_unit WHERE org_name = $1 AND is_deleted = false LIMIT 1`,
    [deptName]
  );
  if (exact.rows.length > 0) return exact.rows[0].id;
  // 2. 模糊匹配：去掉「片区/作业中心/中心」或「X班」后缀后按前缀匹配
  const base = String(deptName)
    .replace(/(片区|作业中心|中心)$/, '')
    .replace(/[一二三四五六七八九十]+班$/, '')
    .trim();
  if (base && base !== String(deptName).trim()) {
    const fuzzy = await client.query(
      `SELECT id FROM hse_org_unit WHERE org_name LIKE $1 AND is_deleted = false LIMIT 1`,
      [`${base}%`]
    );
    if (fuzzy.rows.length > 0) return fuzzy.rows[0].id;
  }
  return null;
}
```

匹配策略示例：
- `人力综合部` → 精确匹配 `人力综合部`
- `宁城街道片区` → 去后缀 `宁城街道` → 前缀匹配 `宁城街道作业中心`
- `宁城街道一班` → 去后缀 `宁城街道` → 前缀匹配 `宁城街道作业中心`

### 3.3 导入逻辑重构

组织/岗位关联逻辑改为 **优先按组织路径，其次按「所属部门 + 职位」**：

```javascript
if (normalized.org_path) {
  // 原有逻辑：组织路径解析 + 岗位关联（不变）
  ...
} else if (normalized.dept_name || normalized.position_name) {
  // 新增：无组织路径的花名册格式
  orgAssigned = true;
  if (normalized.dept_name) {
    orgUnitId = await resolveOrgUnitByDeptName(client, normalized.dept_name);
  }
  if (!orgUnitId && existingEmployee) {
    // 回退：沿用现有组织关系
    ...
  }
  if (normalized.position_name) {
    positionId = await matchPositionByName(client, normalized.position_name, null);
    if (!positionId) {
      warnings.push({ index: rowIndex, message: `岗位"${normalized.position_name}"未找到，已跳过岗位关联` });
    }
  }
}
```

`matchPositionByName` 在岗位不存在时自动创建新岗位（`position` 表），确保花名册中的职位名称可正确关联。

## 6. 影响范围与风险

- **影响范围**：仅影响花名册 Excel 导入的岗位/部门关联逻辑；对已有数据的读取、展示无影响。
- **兼容性**：原有「组织路径」格式导入路径完全保留，回归测试通过。
- **风险**：部门模糊匹配可能将花名册中的班组（如「宁城街道一班」）归并到父级作业中心（组织树无班组层级，属预期行为）。
- **数据修正**：已通过重导整份花名册修正存量数据（详见数据库迁移说明）。
