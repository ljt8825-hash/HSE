## 一、任务1：clear-all 物理删除改造（P1）

### 1.1 代码改造内容

文件：`server/routes/hse-employee-import-v2.js` → `clearAllEmployees` 路由

- 原逻辑：4 条 `UPDATE ... SET is_deleted = true`（软删）
- 新逻辑：4 条物理 `DELETE`（FK 安全顺序 + 事务包裹 + 警告日志）
  ```sql
  BEGIN;
  -- 警告日志：[ImportV2][clear-all] 执行物理清空
  DELETE FROM employee_import_pending;   -- 无外键依赖，先清
  DELETE FROM employee_import_batch;     -- 无外键依赖
  DELETE FROM employee_assignment;       -- employee_id FK（NO ACTION）
  DELETE FROM employee;                  -- 主表
  COMMIT;
  ```
- 返回信息已更新为"人员信息已物理清空（如被外键拦截请先清理业务表引用）"。

### 1.2 FK 审计（关键发现：前提与事实不符）

提示词假设 `employee_assignment.employee_id` 为 `ON DELETE CASCADE`，据此设计 `DELETE FROM employee` 单语句级联。实测全库 **40 个外键指向 `employee.id`**，删除规则分布如下：

| 删除规则 | 数量 | 对 `DELETE FROM employee` 的影响 |
|----------|------|-------------------------------|
| `SET NULL` | 34 | 不阻断删除，但会把业务记录中的员工引用置空（破坏关联） |
| **`NO ACTION`** | **6** | **直接阻断删除**（报错 23503） |
| `CASCADE` | **0** | —（提示词假设不成立） |

6 个 `NO ACTION` 外键（均为子表 `employee_id` 列）：

| 子表 | 外键列 | 规则 |
|------|--------|------|
| employee_assignment | employee_id | NO ACTION |
| hse_grid_inspection_records | employee_id | NO ACTION |
| hse_responsibility | employee_id | NO ACTION |
| risk_level_records | employee_id | NO ACTION |
| risk_score_history | employee_id | NO ACTION |
| risk_score_records | employee_id | NO ACTION |

**阻断证据（当前库实有引用行数）**：

| 子表 | employee_id 非空的子行数 |
|------|------------------------|
| employee_assignment | 3923 |
| hse_responsibility | 129 |
| risk_level_records | 22 |
| risk_score_history | 5 |
| risk_score_records | 22 |
| hse_grid_inspection_records | 0 |
| **合计** | **4101** |

即：在本库直接 `DELETE FROM employee` 会立即被 4101 条 `NO ACTION` 子引用阻断（报错 `foreign_key_violation / 23503`），即使在代码里把 4 张表按顺序物理删，也因 `employee_assignment` 自身持有 3923 条对 `employee.id` 的 `NO ACTION` 引用而无法清空主表。

### 1.3 安全决策：不在线上执行物理清空

经评估，**本次未对线上数据执行 clear-all 物理删除**，理由：

1. **结构层面**：40 个 FK 无一为 CASCADE，6 个为 NO ACTION，物理删除主表会被外键拦截，无法达到"employee=0"。
2. **数据保护层面**：当前库含 **1361 名真实在职员工**，且被 4101+ 条业务记录引用（含 `employee_assignment` 任职关系、`hse_responsibility` 责任书、`risk_score_*` 风险评分等）。物理清空将不可逆地销毁生产数据，超出本提示词"收尾"的授权范围。
3. **提示词边界**：提示词"禁止修改"清单明确含"数据库表结构（外键）"，因此**不能通过改 FK 为 CASCADE 来强行满足验收**——这既违反边界，也在生产库上极其危险。

**代码的真实价值**：改造后的 `clearAllEmployees` 在**干净的测试/ staging 库（无业务引用或已按依赖清理）**上可正确、事务安全地完成物理清空；在本生产-like 库上会安全失败（COMMIT 前被 FK 拦截回滚），不会造成脏数据。

> ⚠️ **如需在本库真正执行"清空并重导"**：必须先按依赖顺序清理/归档上述 4101+ 条业务引用（或明确业务归档策略），这属于独立的、需单独审批的数据销毁任务，**不在提示词-94 授权范围内**，请勿直接点 clear-all。
