## 0. 背景

用户导入花名册时，员工"刘金涛"的岗位"安环管理部副经理"被标记为**未知岗位**。经根因分析，`matchPosition()` 函数采用三级匹配策略：

| 层级 | 匹配方式 | 数据源 |
|:--:|------|------|
| L1 | 条件精确匹配（source_position + condition_dept） | `employee_position_mapping_rule` |
| L2 | 无条件精确匹配 | `employee_position_mapping_rule` |
| L3 | 模糊匹配兜底 | `position` 表 name 字段 |

L3 的 SQL 逻辑：
```sql
SELECT id, name FROM position WHERE is_deleted = false
  AND (name = $1 OR name LIKE $2 OR $1 LIKE '%' || name || '%')
ORDER BY CASE WHEN name = $1 THEN 3 WHEN name LIKE $2 THEN 2 ELSE 1 END DESC
LIMIT 1
```

**关键条件**：`$1 LIKE '%' || name || '%'` — 即原始岗位名包含 position 表的岗位名作为子串。

**"安环管理部副经理"失败原因**：`position` 表中没有"副经理"这个岗位名，导致 `'安环管理部副经理' LIKE '%副经理%'` 无法匹配。

**用户需求**：希望一劳永逸，让"XX部副经理"、"XX部经理"、"XX部安全员"等模式自动匹配，不再每次手动添加映射规则。

## 3. 设计原理

**为什么加 position 表而不是 mapping_rule 表？**

- `mapping_rule` 是精确匹配（L1/L2），每次新岗位变体都要手动加一条规则
- `position` 表是 L3 的子串匹配，加一个"副经理"词条后，所有含"副经理"的原始岗位名（"安环管理部副经理"、"财务部副经理"等）全自动匹配
- 这是一种**以数据驱动匹配**的方案，零代码改动，维护成本为零

**为什么不需要改代码？**

L3 已经具备 `$1 LIKE '%' || name || '%'` 子串匹配能力，只是 position 表中缺少细粒度词条。补全词条后 L3 自然生效。

## 5. 风险提示

- **position_code 唯一性**：INSERT 前需确认 `position_code` 是否有 UNIQUE 约束，若有冲突需调整 code
- **name 唯一性**：确认 name 是否有 UNIQUE 约束，若有冲突需跳过
- **后端重启**：`node app.js` 无热加载，INSERT 后需重启后端使新岗位名在后续导入中生效
- **已有的映射规则优先**：L1/L2 优先于 L3，若某岗位名已在 mapping_rule 中有精确匹配，不会走到 L3
