# 提示词-97：清空人员信息按钮报错修复 — 诊断报告

> 创建日期：2026-08-01
> 执行人：WorkBuddy
> 关联提示词：76-提示词-97-清空人员信息按钮报错修复.md

## 一、现象回顾

用户进入「人员管理 → 花名册导入」，点击「更多操作 → 清空人员信息」后：
- 控制台出现 3 个 401 Unauthorized + "Access token or refresh token is invalid or expired"
- 员工列表未变动
- 页面跳转至登录页 `/auth/login`

## 二、调用链路还原

```
点击「清空人员信息」
  → openClearAllConfirm() → Modal.confirm 弹窗（文案误写"软删除"）
  → 确认 → handleClearAll()
  → clearAllEmployees() → POST /api/hse/employee-import/v2/clear-all
  → requireRole('admin') 中间件
  → 事务：物理 DELETE employee_assignment → employee → employee_import_pending → employee_import_batch
  → 成功 → loadList() 刷新；失败 → catch(message.error)
```

注意：提示词假设路径为 `/api/hse/employee/clear-all`，实测挂载点为
`/api/hse/employee-import/v2/clear-all`（app.js:401），与提示词不符。

## 三、根因诊断（已实测）

### 3.1 表层根因：401 = Token 过期（高概率）

本库 PostgreSQL 返回中文错误消息，且后端 `/api/*` 统一挂 JWT 鉴权（app.js）。
当用户会话中 access token 过期（此前 access token 仅 30 分钟，刷新依赖跨端口
cookie 易失败）时，包括 clear-all 在内的所有 `/api` 请求均返回 401，401 拦截器
触发 `doReAuthenticate() → logout() → 跳登录`，故用户看到"401 + 跳登录"。

**该根因已在同会话的「Token 有效期延长 + 自动刷新优化」任务中修复**：
access token 改为 12h（可配置 `JWT_ACCESS_EXPIRES_IN`），刷新请求改用 body
携带 refreshToken，不再依赖跨源 cookie。重新登录后基本不会再因 token 过期而 401。

### 3.2 深层根因：物理删除被外键整体回滚（安全拦截）

经 FK 审计（任务1 SQL 实测）：

- 全库 **40 个外键**引用 `employee.id`
- 其中 **6 个为 `NO ACTION`**（会拦截物理 DELETE）：
  `employee_assignment`、`hse_grid_inspection_records`、`hse_responsibility`、
  `risk_level_records`、`risk_score_history`、`risk_score_records`
- 其余 34 个为 `SET NULL`（不拦截）
- 当前存在 **5,412 条**活跃员工引用（主要来自 `employee_assignment` 5234 条、
  `hse_responsibility` 129、`risk_level_records` 22、`risk_score_history` 5、
  `risk_score_records` 22）

因此，即便 token 有效，物理 `DELETE FROM employee` 也会被 `risk_level_records`
等 NO ACTION 外键拦截（23503），事务整体 `ROLLBACK`，数据不被破坏（安全）。
此时前端收到业务错误，但原 `handleClearAll` 仅 `message.error(e.message)`，
且原提示词描述的 401 拦截器会跳登录，用户难以理解失败原因。

### 3.3 表结构 / 角色问题排除

- `requireRole('admin')`：admin 用户调用返回业务错误码 `-1`（非 403），角色拦截非主因。
- 表结构无变更需求，红线未触碰。

## 五、结论

| 层面 | 根因 | 处置 |
|------|------|------|
| 表层（用户可见 401） | access token 过期 + 刷新不可靠 | **已修复**（同会话 token 优化：12h + body 刷新） |
| 深层（清空不可达） | 6 个 NO ACTION FK + 5412 条引用 → 物理删除被整体回滚 | 属**安全拦截**，非 bug；通过任务3 返回友好提示，且不脏写 |
| 文案误导 | 弹窗写"软删除"（实际物理删除） | 任务4 修正为"物理删除" |
| 错误处理 | catch 无场景区分 | 任务2 区分 401/403/外键 |

> 说明：本生产库存在真实业务引用，物理清空**不应**在此库执行（会触发 FK 回滚，
> 与「禁止破坏性生产数据操作」原则一致）。任务验证仅确认"FK 拦截 → 友好提示 →
> 数据零变动"，未做真实清空（合理且安全）。
