## 二、任务1：v_employee_current 视图加固

### 根因（关键发现）

线上视图在 `server/routes/hse-employee-import-v2.js` 的 `ensureViewFields()` 中于每次 `/upload` 时通过 `CREATE OR REPLACE VIEW` 重建，但该重建定义**缺少 `DISTINCT ON (e.id)`**，且列顺序与规范源（`sprint5_6_employee_master_migration.sql`）不一致。这导致视图按任职行展开（历史曾膨胀到 3913 行）。`CREATE OR REPLACE` 因列名/顺序冲突无法覆盖，故必须改用 `DROP + CREATE`。

### 修复

- 修改 `ensureViewFields()`：将 `CREATE OR REPLACE VIEW` 改为 `DROP VIEW IF EXISTS v_employee_current; CREATE VIEW ...`，并对 SELECT 增加 `DISTINCT ON (e.id)` 与 `ORDER BY e.id, a.start_date DESC NULLS LAST`（保留原列集，仅加固语义，零列移除风险）。
- 同步更新规范源 `sprint5_6_employee_master_migration.sql`（视图定义加 `DISTINCT ON`）。

## 三、任务2：导入链路任职去重

### 修复

在 `executeImport` 插入新任职前，将原「仅置 `is_current=false`」升级为显式降级旧主职：

```js
await client.query(
  `UPDATE employee_assignment
   SET is_primary = false, is_current = false, end_date = CURRENT_DATE, updated_at = CURRENT_TIMESTAMP
   WHERE employee_id = $1 AND is_current = true AND is_primary = true AND is_deleted = false`,
  [employeeId]
);
```

配合既有部分唯一索引 `uk_emp_assign_primary`（`UNIQUE(employee_id) WHERE is_primary=true AND is_current=true AND is_deleted=false`），保证每位员工至多 1 条主职任职。

## 四、任务3：导入链路上级兜底写入

### 修复

- `executeImport` 的待入库查询新增 `raw_supervisor` 列。
- 在写入 `employee_assignment` 前增加兜底：若 `p.supervisor_id` 为空且存在 `raw_supervisor`，再次调用 `matchSupervisor(client, p.raw_supervisor)` 按姓名匹配；命中则回填 `supervisor_id` 并回写 pending 记录。

```js
let finalSupervisorId = p.supervisor_id || null;
if (!finalSupervisorId && p.raw_supervisor) {
  const fbMatch = await matchSupervisor(client, p.raw_supervisor);
  if (fbMatch && fbMatch.supervisor_id) {
    finalSupervisorId = fbMatch.supervisor_id;
    await client.query(`UPDATE employee_import_pending SET supervisor_id = $1 WHERE id = $2`, [finalSupervisorId, p.id]);
  }
}
```

### 端到端探针（真实 API）

批次1 设计两名员工：

- 行1「测试主管93A」：批次内新建，**无上级**。
- 行2「测试下属93B」：直接上级填「测试主管93A」。

上传时行2 的 `matchSupervisor("测试主管93A")` 返回 **null**（主管尚未入库）→ pending `supervisor_id` 为空。入库时按行序先建「测试主管93A」，行2 触发兜底匹配命中刚创建的员工，写入 `supervisor_id`：

| employee_code | 名称      | 主职数 | supervisor_id | 上级姓名      |
| ------------- | ------- | --- | ------------- | --------- |
| TEST93A001    | 测试主管93A | 1   | （空）           | —         |
| TEST93B001    | 测试下属93B | 1   | **6686**      | 测试主管93A ✅ |

→ 批次内新建的上级被成功兜底匹配并写入 `supervisor_id` ✅。系统外上级（如区域层领导）仍保持 NULL，不报错。
