## 二、Part B 保险管理模块五维诊断

> 诊断对象：前端 3 子页 `views/insurance/{personnel,vehicle,other}/index.vue` + API 模块 `src/api/hse/insurance.ts`；后端 `server/routes/insurance.js`（挂载于 `/api/insurance`，全局 `authMiddleware` 已作用于 `/api`）。
> 说明：本模块为**只读诊断**，未做任何修改。

### 维度一：前端质量

- **【P0】`other/index.vue` 数据解包与 `responseReturn:'data'` 契约冲突**
  `request.ts` 中 `requestClient = createRequestClient(apiURL, { responseReturn: 'data' })`，响应拦截器已剥离 `{code,data,message}` 外层，直接返回 `data` 内容（`{list,total,page,pageSize}`）。但 `other/index.vue` 的 `fetchData` 仍按旧契约写：
  ```ts
  const r = await request.get('/insurance/other', { params: {...} });
  if (r.code === 0) {                 // r.code 永远 undefined → 条件恒 false
    dataList.value = r.data.list;     // r.data 永远 undefined
  }
  ```
  结论：**列表与统计（`fetchStats` 同病）永远为空**，子页面功能完全失效。正确写法应取 `r.list` / `r.total`（与 `personnel`/`vehicle` 通过 `insurance.ts` 的 `res.list`/`res.total` 一致）。**后端 `/insurance/other` 正常（探针返回 200、total=0），问题纯在前端。**

- **【P1】`personnel/index.vue` 身份证号明文展示，未脱敏**
  - 表格列 `身份证号`：`L615 { title: '身份证号', dataIndex: 'idCard' ... }` 直接渲染 `idCard`。
  - 详情抽屉：`L379 <DescriptionsItem label="身份证号">{{ currentDetail.idCard || '-' }}</DescriptionsItem>`。
  - 与 `overage` 模块的展示脱敏（`maskIdCard` 前4+**********+后4）不一致，PII 在前端暴露。

- **【P1】`personnel/index.vue` catch 块误报成功（掩盖失败）**
  - `handleSavePerson` 的 catch：`L903–L905` → `message.success('保存成功')`
  - `handleDelete` 的 catch：`L918–L920` → `message.success('删除成功')`
  - `handleRenewalConfirm` 的 catch：`L975–L978` → `message.success(\`成功续保 ${count} 人\`)`
  - 真实请求失败时反而提示成功，用户误以为操作生效，属于严重逻辑错误。`vehicle/index.vue` 的同类 catch（L739-741）正确用 `message.error`，二者不一致。

- **【P2/P3】三子页未使用 `useDataTable`/`useSearchForm` 组合式**
  `emergency` 模块已重构为由 `#/composables/hse` 的 `useDataTable`/`useSearchForm` 托管分页/筛选/加载态；而 `personnel`/`vehicle`/`other` 仍手写 `ref` + 重复分页逻辑，维护成本高且与 emergency 风格割裂。

- **【P2】`other/index.vue` 导出为桩**
  `handleExport` 仅 `message.info('导出功能开发中')`；后端 `/other` 亦无 export 端点 → 功能缺口（按钮应隐藏或补齐）。

- **【P3】三子页 UI 模式不统一**：筛选栏、分页、统计卡片实现各异，无统一封装。

### 维度二：后端质量

- **【P1】`/personnel/export` 明文导出身份证号 + 无 `requireRole`**
  `insurance.js:808` `router.get('/personnel/export', async ...)` **未加 `requireRole`**，且 `L823` 直接写 `(r.idCard || '').replace(...)`（明文）。对比：
  - `vehicle/export`（`L345`）加了 `requireRole('admin','safety_manager')`；
  - `overage/export`（`L1068`）加了 `requireRole` + `maskIdCard(r.id_card)`。
  → 任何持有效 token 的非管理员均可导出含明文身份证号的 CSV，**PII 泄露 + 角色缺口**。

- **【P1】授权策略不统一**
  `/overage/*` 全部端点均 `requireRole('admin','safety_manager')`；`/vehicle/export` 有；但 **`/personnel/*`（GET/POST/PUT/DELETE/export/import/batch-renewal/batch-delete/job-type-stats/expiring-soon）与 `/vehicle`（GET/stats）与 `/other/*` 全部未加 `requireRole`**。含 PII 的 personnel 读取/写入/导出对仅持有效 token 的普通角色开放。

- **【P3】insurance 四个 `formatXxxRow` 的 `id` 返回 string（BIGINT 类）**
  `insurance.js:162/517/1003/1364` 均为 `id: row.id`（pg BIGINT → string）。emergency 模块本次已统一改为 `Number(row.id)`，**跨模块类型不一致**；前端 API 类型标注 `id: number` 但运行时为 string，存在隐性不匹配（vue-tsc 不报错，运行时才暴露）。

### 维度三：数据流一致性

- **【P0】同维度一 P0**：`other/index.vue` 与 `responseReturn:'data'` 契约冲突，是该维度最严重的一致性问题。
- **【P2】同一模块内两种解包约定并存**：`insurance.ts` 的 `getPersonnelList/getVehicleList/getOverAgeList` 正确返回 `{list,total}`（对齐契约），而 `other/index.vue` 绕过 `insurance.ts` 直接用 `request` 且用错解包方式（`r.code`/`r.data.list`），导致 `other` 子页失效、与另两个子页行为不一致。
- **【P3】身份证号前后端处理不一致**：`/personnel` 返回明文（前端明文展示）；`/overage` 经 `decryptMiddleware` 返回明文供前端、前端再脱敏展示。同系统两套口径。

### 维度四：边界 / 异常处理

- **【P1】personnel 前端 catch 误报成功**（维度一已述）—— 失败被静默掩盖。
- **【P1】`/personnel/export` 明文 + 无鉴权**（维度二已述）—— PII 边界失守。
- **【P2】`other/index.vue` `fetchData` 无 catch**：仅 `try/finally`，请求异常会未捕获 reject（finally 关 loading 但错误冒泡，依赖全局 `errorMessageResponseInterceptor` 兜底，健壮性弱于另两个子页）。
- **【P2】personnel 写入缺身份证号格式校验**：与 `overage` 的校验/脱敏策略不一致。
- **【P3】空数据表现**：各列表空表时 `total=0`（探针验证 `other` 空表正常），前端均做了 `|| []` 兜底，OK。

### 维度五：回归

- **R1–R4 已实施并验证**：探针 11/11 通过，未引入新运行时错误（详见 §1.2）。
- **风险点**：emergency 现已返回 `number` id，若其它前端代码假设 string 可能错位；但类型层面 `id: number` 已在 `emergency.ts` 标注，vue-tsc 通过即证明无类型错位（见 §5）。
- **`other/index.vue` 的 P0 属历史遗留（非本次 Part A 引入）**，但属本模块功能性回归隐患，建议随本报告一并修复（不在本次红线禁止范围内，因红线仅约束"不修改保险模块"——本项为诊断建议，待后续独立提示词执行）。
