# 提示词-85：考核模块数据补录策略说明

> 制定日期：2026-07-31
> 结论：**策略 A —— 直接插入 `assessment_records`**

---

## 一、策略选择矩阵回顾

| 策略 | 适用场景 | 本任务适配度 |
|------|----------|:----:|
| A. 直接插入 assessment_records | 表结构简单、无前置依赖 | ✅ **采用** |
| B. 先建目标再生成记录 | 有 target→record FK 依赖 | ❌ 不适用（`assessment_records` 无强制 FK） |
| C. 仅建上游，记录由流程自动产生 | 记录由前端表单提交时自动生成 | ⚠️ 部分适用但无法演示空表 |
| D. 跳过，标记"需业务流程驱动" | 数据依赖复杂、无法合理模拟 | ❌ 过度保守（本表结构简单） |

---

## 二、选择策略 A 的理由

1. **结构宽松**：`assessment_records` 仅 `id`、`assessment_title` 为 NOT NULL，无强制外键（`employee_id` 为业务约定引用），可直接 INSERT。
2. **无硬依赖链**：与月度履职考核（`cycle→target→score→deduction` 的多级 FK 链路）不同，本表是独立的"培训/考试考核记录"表，不依赖任何父表先存在。
3. **真实业务映射**：考核记录本就是"某次考核产生一条记录"，直接插 5 条代表性记录（覆盖理论/实操、合格/不合格）即可让「考核记录」视图（`views/objectives/assessment/index.vue`）正常展示与筛选。
4. **不触碰已 populated 模块**：调研发现 `hse_assessment_*` 族（110/880/4/9 行）已自带数据，**不重复补录**，避免数据冲突。
5. **符合红线**：直接 SQL 插入，未改任何代码/表结构/匹配规则/应急种子数据。

---

## 三、为什么不选 B / C / D

- **B 不适用**：`assessment_records` 与 `hse_assessment_target` 之间**没有外键链路**（分属"考核记录"与"月度履职"两个独立业务域），强制走 target→record 流程是误读。
- **C 部分适用但不足**：若只建上游（如 `hse_assessment_target`），前端「考核记录」视图仍读 `assessment_records`（0 行），模块依旧空白；而该视图的记录本就由 `training-assessment` 业务流生成，纯 SQL 模拟反而更可控。
- **D 过度保守**：本表无复杂依赖，模拟 5 条记录完全合理，无理由跳过。

---

## 四、补录方案要点

| 项 | 内容 |
|----|------|
| 目标表 | `assessment_records`（仅此一张） |
| 条数 | 5 条代表性记录 |
| 引用真实性 | `employee_id` 引用真实在册员工（宁城街道作业中心 org_unit_id=9：张万恒3866/马金华3867/武志刚3868/曹鹏3869/杨占刚3870），姓名/工号/部门/岗位均取自真实主数据 |
| 覆盖维度 | 理论×3、实操×2；合格×4、不合格×1（演示补考筛选）；优秀/良好/合格/不合格 四档 grade |
| 幂等 | `assessment_no = 'SEED-ASR-2026-00X'` 作种子标记，`WHERE NOT EXISTS` + 首行 `DELETE` 清理标记行，可重复执行 |
| 红线校验 | 未改表结构/代码/规则；`is_deleted=false`；employee_id 全部指向真实存在的主键（FK 孤儿=0） |
