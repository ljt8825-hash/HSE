## 1. 模块概述

员工档案模块位于「人员管理 → 员工档案」页面，是花名册体系的核心查询与详情模块，功能范围如下：

| 功能域 | 能力 |
|--------|------|
| **列表页** | 11 列展示（员工编号、姓名、性别、年龄、所属组织、作业单元、岗位、入职日期、是否驾驶员、状态、人员类型等）；支持关键词搜索（姓名/员工编号）、驾驶员筛选、分页与每页条数切换、重置 |
| **详情页（Drawer）** | 基础信息区 12 字段（员工编号、姓名、性别、年龄、出生日期、手机号、身份证号、人员类型、人员分类、是否公益岗、状态、创建时间）+ 组织信息区 11 字段（所属组织、组织编码、作业单元、岗位、岗位编码、风险等级、主管、入职日期、状态等）+ 任职历史 Tab + 驾驶员信息 |
| **搜索 / 筛选 / 分页** | 关键词搜索、驾驶员筛选（是/否）、搜索+筛选联动、重置、分页状态保持 |
| **任职历史** | 抽屉内 Tab 展示组织/作业单元/岗位/开始结束日期/状态，标记当前任职 |
| **导入** | 花名册 Excel 导入，作业单元班组匹配（支持中文/中文数字/阿拉伯数字班组名，getOrCreate 防重复） |

## 2. 修复历史（提示词-101 ~ 提示词-104）

### 提示词-101：员工档案字段映射修复（列表页）
- **根因**：后端 `/employees/profile/list` 对结果调用 `camelKeys()`，将 snake_case 键转为 camelCase，与前端 `dataIndex`（全为 snake_case）不匹配 → 整列空字段；且 5 个列被硬编码为 `NULL`（`org_code / operation_unit_id / unit_name / unit_type / position_code`）。
- **修复**：移除 `camelKeys()` 直接返回 `snake_case`；5 个 `NULL` 改为 `v_employee_current` 视图真实列；更新过时注释。
- **附带环境修复**：后端端口 5666 被 Windows 系统保留区间（5595–5694）拦截（`EACCES`），迁移至 **5800**，同步更新 `server/.env` 与 `vite.config.ts` 代理目标。
- **验证**：列表返回 snake_case、`is_driver=43`（基于岗位名）、字段填充率 `org_code 1311/1311`、`position_code 1308/1311`、`hire_date 1311/1311`、`status 1311/1311`、`unit_name 59/1311`（真实数据），构建通过。

### 提示词-102：员工档案详情页字段映射验证与修复
- **根因**：`/employees/profile/:id` 同样 `camelKeys()` → Drawer 内 `basic.*` / `currentOrg.*` 全部空列（与列表页同类问题）。
- **修复**：移除详情 handler 的 `camelKeys()`，直接返回 snake_case（与前端/类型定义对齐）。前端与 API 类型定义未改动。
- **验证**：修复后返回 `employee_code / org_name / start_date ...` 全部 snake_case，抽样值填充正常；`/assignments`、`/driver-info` 子接口 200；列表回归正常；构建通过。

### 提示词-103：员工档案模块交互功能完整性验证（22 项）
- **范围**：搜索、筛选、分页、详情 Drawer、任职历史 Tab、边缘情况（空数据/单条/特殊字符/无任职关系）的交互完整性验证。
- **结果**：全部通过，无需修改代码（验证清单 V1.1~V6.3 全 PASS）。为提示词-104 的 22 项断言基线。

### 提示词-104：详情页加密字段解密 + 作业单元班组匹配修复
- **问题1（P0）加密字段未解密**：`decryptMiddleware` 仅处理 `data.data` 顶层/扁平结构，详情接口返回嵌套 `{ basic: { id_card, phone } }` → 中间件命中失败 → 前端收到 `ENC:` 密文。
  - **修复**：详情 handler 手动 `decryptFields(emp, ['id_card','phone'])`；前端 `maskIdCard`/`maskPhone` 增加 `ENC:` 前缀兜底（防御性）。
  - **验证**：`id_card=371481197610084528`（18 位）、`phone=13953422830`（11 位），脱敏为 `371481********4528` / `139****2830`。
- **问题2（P1）作业单元班组匹配增强**：`matchOperationUnit` 原仅匹配含数字班组（"一班"→"第1保洁组"），纯中文/中文数字班组返回 null。
  - **修复**：新增 `cnNumeralToDigit`；支持阿拉伯数字、中文数字、纯中文班组（getOrCreate 防重复）。
  - **验证**：`"保洁组"`→`柴胡店镇保洁组`、`"一班"`→`柴胡店镇第1保洁组`（隔离单元测试 PASS）；实时样本 `unit_name=大柳镇收运车组` 已填充。
- **问题3（合并 103 验证，22 项全 PASS）**：含搜索/筛选/分页/详情/边缘情况；并**附加修复**「驾驶员筛选否退回全量」既有缺陷——`is_driver='false'` 分支补 `OR ev.position_name IS NULL`，使"否"正确返回 1268 名非驾驶员（零泄漏），列表端点(6048)与同名过滤端点(6254)一致。

### 构建环境修复详情（提示词-105 核心交付）
- **根因**：rolldown-vite **v8.1.4 默认内置压缩器**在本机产物写出/优化（emit）阶段发生死锁，非代码缺陷（全部 8277 个模块转换成功，含本次修改的 `employee-profile/index.vue`）。
- **修复（已固化）**：`apps/web-antd/vite.config.ts` 的 `build` 增加 `minify: 'esbuild'`，替代默认混淆器。
  ```ts
  build: {
    // [构建环境修复-提示词105] rolldown-vite 8.1.4 默认内置压缩器在本机 emit 阶段死锁，
    // 改用 esbuild 压缩器可正常产出压缩版生产构建并 exit 0（已验证）。
    minify: 'esbuild',
    rollupOptions: { /* ... 既有 manualChunks ... */ },
  }
  ```
- **验证矩阵**：
  | 方案 | 命令 | 结果 |
  |------|------|------|
  | A | `pnpm vite build --mode production --minify false` | exit 0（无压缩，仅验证产物生成） |
  | B | `pnpm vite build --mode production --minify esbuild` | exit 0（**压缩版生产构建**） |
  | 规范 | `pnpm run build:antd`（配置固化后） | **exit 0**（turbo 11/11 成功，5m23s） |
- **说明**：`--minify false` 可绕过但产出未压缩；`--minify esbuild` 保留压缩且绕开死锁，为生产推荐方案，已写入 `vite.config.ts`，使规范命令 `pnpm run build:antd` 开箱可用。

## 4. 已知限制

1. **`unit_name` 仅 59/1311 有值**：多数员工无运营单元归属，属真实数据，非映射缺陷。
2. **`is_driver` 基于 `position_name` 启发式**（非 `remark`）：经实测全库 `remark` 为 NULL，提示词原 `remark` 方案会把 43 名驾驶员误判为 0，故保留岗位名启发式；与现有驾驶员/司机筛选、`/driver-info` 解析逻辑一致。
3. **加密中间件不处理嵌套结构**：详情接口的 `id_card`/`phone` 解密需在 handler 内手动 `decryptFields`；前端 `ENC:` 兜底为防御性，正常流程不应触发。
4. **构建死锁（历史）**：rolldown-vite 默认压缩器死锁已于本提示词修复（`minify: 'esbuild'`）；若后续升级 vite/rolldown 可重评是否移除该覆盖。
