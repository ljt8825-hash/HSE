## 二、缺陷详情

### 问题1：clear-all 根因治理 —— 软删 vs 物理删除

**现状**（`server/routes/hse-employee-import-v2.js` 的 `clearAllEmployees` 路由）：

当前 clear-all 执行：
```sql
UPDATE employee SET is_deleted = true WHERE is_deleted = false;
UPDATE employee_assignment SET is_deleted = true WHERE is_deleted = false;
```

**问题**：软删导致 `employee` 和 `employee_assignment` 表数据持续累积，虽然提示词-91 的部分唯一索引修复已消除「同号无法重导」问题，但软删数据的长期累积会：
- 增加存储空间浪费
- 增加查询性能开销（需额外 `is_deleted=false` 过滤）
- 增加维护复杂度

**修复方案**：将 clear-all 改为物理删除（CASCADE），利用 `employee_assignment` 的 FK 自动级联：

```sql
-- 物理删除（利用 FK ON DELETE CASCADE）
DELETE FROM employee WHERE is_deleted = false OR is_deleted = true;
-- employee_assignment 等关联表通过 FK CASCADE 自动清理
```

**风险评估**：
- `employee_assignment` 的 FK 为 `FOREIGN KEY (employee_id) REFERENCES employee(id) ON DELETE CASCADE`，确认后可直接 DELETE
- 需要确认其他关联表（`employee_import_pending`、`employee_import_batch` 等）的 FK 约束，确保不会因 CASCADE 导致意外数据丢失
- 如非 CASCADE 约束，需按顺序 DELETE：`employee_import_pending` → `employee_import_batch` → `employee_assignment` → `employee`

**注意**：clear-all 属于管理操作，物理删除的语义更清晰（"清空所有人员"）。建议在 clear-all 前自动执行全量备份。

**验收标准**：
- clear-all 后 `employee` 表行数 = 0
- clear-all 后 `employee_assignment` 表行数 = 0
- clear-all 后重新导入不受影响
- clear-all 前自动备份（或至少输出警告提示）

### 问题2：视图列集统一 —— ensureViewFields vs 迁移 SQL

**现状**：
- `ensureViewFields()`（`server/routes/hse-employee-import-v2.js`）生成 38 列视图
- 规范迁移 SQL（`server/sql/sprint5_6_employee_master_migration.sql`）定义 35 列

差异的 3 列为：`id_card`、`is_public_welfare`、`id_address`（由 `ensureViewFields` 补充）。

**问题**：运行时视图以 `ensureViewFields()` 为准（每次 `/upload` 重建），规范源与实际运行不一致，造成维护困惑。

**修复方案**：以 `ensureViewFields()` 的 38 列为准，同步更新迁移 SQL 的视图定义：

1. 比对两处视图定义的列差异
2. 将迁移 SQL 的视图定义补全至 38 列（与 `ensureViewFields()` 一致）
3. 确保两处 `DISTINCT ON` + `ORDER BY` 逻辑一致

**验收标准**：
- `ensureViewFields()` 和迁移 SQL 的视图定义列集一致
- 视图重建后 `/employees` 接口正常返回
- 无前端/后端报错
