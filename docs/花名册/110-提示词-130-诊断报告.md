## 3. 维度二：后端代码质量

### 3.1 路由注册（无字面冲突，有逻辑重复）
- 三套路由挂载前缀不同，无 Express 路由碰撞：
  - `/api/hse/employee/over-age/auto-*` ← hse-employee.js（子系统A，读 employee 表）
  - `/api/insurance/overage*` + `/api/insurance/:bizType/:id/attachments|versions` ← insurance.js（子系统B，读写 over_age_personnel）
  - `/api/over-age-personnel/*` ← over-age-personnel.js（独立 CRUD，读写 over_age_personnel）
- **逻辑重复**：insurance.js 与 over-age-personnel.js **都操作同一张 `over_age_personnel` 表**，但行为不一致（见 3.5）。

### 3.2 权限控制（**F6**）
- hse-employee.js 绝大多数端点均声明 `requireRole('admin', 'safety_manager', ...)`，但 **3 个超龄 auto 端点均未声明 `requireRole`**：
  - `GET /over-age/auto-list`（hse-employee.js:6683）
  - `GET /over-age/auto-stats`（hse-employee.js:6763）
  - `GET /over-age/auto/:id`（hse-employee.js:6823）
- insurance.js `/overage*` 与 over-age-personnel.js 全部端点同样**未声明 `requireRole`**。
- 三者仅依赖 `app.js:232` 的全局 `authMiddleware`（登录校验），**无角色授权**。而前端路由 `authority:['admin']`，前后端权限不一致：任何已登录用户均可直接调用这些 API。

### 3.3 年龄计算规则（正确）
- 阈值从 `employee-age-rule.json` 经 `getOverAgeThresholds()` 集中读取（hse-employee.js:6639-6644），无硬编码散落 —— 合规。
- SQL：`EXTRACT(YEAR FROM age(birth_date))::INT`，与规则文件 `ageCalculation.sql` 完全一致。
- 判定逻辑 `> ` 严格大于（buildOverAgeCondition，hse-employee.js:6654-6656），与"超过该年龄则识别"语义一致。
- 实时查询（realtime_query），无需手动同步 —— 与规则文件 `autoIdentification` 一致。

### 3.4 错误处理（基本完善）
- auto-list/auto-stats/auto/:id 均使用统一 `success/error` 响应。
- 数据库连接检查完整（`isConnected()`）。
- `:id` 做了数值解析（`req.params.id` 直接用于参数化查询，无 SQL 注入风险；但 `auto/:id` 未做 `parseInt` 校验——非法 id 会触发 PG 类型错误被 catch 转为 `error(-1)`，不影响安全，仅提示不友好，归 P3）。

### 3.5 加密字段（**F1 / P0 核心**）
- `ENCRYPT_FIELDS = ['id_card','phone']`（hse-employee.js:68）。
- **子系统A**：`auto-list` / `auto/:id` 使用 `decryptMiddleware(...ENCRYPT_FIELDS)` → 解密后以**明文**返回 `id_card`/`phone`（实测返回 18 位完整身份证号）。
- **over-age-personnel.js**：`POST/PUT` 用 `encryptMiddleware`，`GET/GET/:id` 用 `decryptMiddleware` —— 加密写、解密读。
- **insurance.js `/overage`**：`POST/PUT/GET` **均未使用加解密中间件** → 写入明文、读取明文。
- 后果：
  1. 经 insurance.js 写入的 `id_card` 为明文；经 over-age-personnel.js 读取时会尝试"解密明文"→ 得到乱码。
  2. 经 over-age-personnel.js 写入的 `id_card` 为密文；经 insurance.js 读取时返回密文 → 泄露密文。
  → **同一字段在不同路由间读写互相破坏**，属数据完整性与安全双重风险（**P0**）。
- 另：子系统A把解密后的明文身份证/手机号直接回传前端并在界面完整展示（**F2**），未脱敏。

## 4. 维度三：数据流一致性

### 4.1 字段命名一致性
- 子系统A auto-list 返回 snake_case（`dept_name`/`position_name`/`over_age_years`/`employee_code`），与前端 `dataIndex` 完全一致；`buildListResponse` 未启用 camelCase（hse-employee.js:6756）—— 命名一致 ✅。
- 子系统B `formatOverage` 同样输出 snake_case，与自身前端 API 契约一致 ✅。

### 4.2 双系统数据一致性（**F3 / F4**）
- 子系统A 数据来源：`employee` 表实时计算（主键 `employee.id`）。
- 子系统B 数据来源：`over_age_personnel` 表（主键自增 `id`，`personnel_id` 关联）。
- 页面把 A 的列表行 `record.id`（= employee.id）直接喂给 B 的附件/版本/上传接口（`bizId=employee.id`），但 B 体系以 `over_age_personnel.id` 为 biz_id 键。两者**无可靠映射**：
  - 详情抽屉「附件列表 / 历史版本」恒为空（**F3**）。
  - 「导出」导出的是 B 表全量，而非页面所见的 A 列表（**F4**）—— 导出内容与屏幕不一致。

### 4.3 分页一致性 ✅
- `buildListResponse` 输出 `{ list, total, page, pageSize }`，与 `useDataTable` 期望一致；实测 `auto-list` 返回 `total=1092, page=1, pageSize=3`，字段名匹配。

### 4.4 统计卡片数据口径
- 总数：auto-stats `total=1092` 与 auto-list `total=1092` 一致 ✅。
- 男/女：byGender `{男:439, 女:653}` 合计 1092，与总数一致 ✅。
- 70岁以上：byAgeGroup 仅返回有数据的桶（`51-55/56-60/61-65/66-70`），当前无 `>70` 记录，故不含 `70岁以上` 键；前端用 `byAgeGroup['70岁以上'] || 0` 兜底显示 0 —— 口径一致，缺键已优雅处理 ✅。
- 统计阈值 `thresholds={男:60,女:50}` 与规则文件一致 ✅。

## 5. 维度四：边界与异常

### 5.1 空状态处理 ✅
- 无超龄人员：表格默认空态、统计卡显示 0、附件/版本 Table 空态 —— 均有兜底。
- 附件/版本空：因 F3 恒为空，空态即其常态表现。

### 5.2 年龄边界（**F7 同源，非 bug**）
- 判定 `> ` 严格大于：男恰好 60、女恰好 50 **不**计入超龄，与"超过"语义及规则描述一致 —— 非缺陷，仅记录。
- 无出生日期：`auto-list`/`auto-stats` 均有 `birth_date IS NOT NULL` 过滤，自动排除 —— 处理正确 ✅。
- 年龄为 NULL：同上被排除，不会出现在列表/统计中 ✅。

### 5.3 数据安全（**F2 / F1**）
- 身份证号：子系统A 明文返回并完整展示（表格"身份证号"列 170px、详情抽屉、CSV 导出均含完整 18 位）—— **PII 暴露，建议脱敏**（如 `3724**********1234`）。
- 导出 CSV（insurance.js:1079-1093）：`id_card` 明文写入，无掩码 —— 与 F2 同源。
- 手机号：子系统A 同样明文返回并展示 —— 建议一并脱敏。

### 5.4 规则配置变更（**F7 / F9**）
- 阈值变更后：后端需**重启**才生效（模块加载时读取，无热加载）；前端阈值因硬编码常量（F7）亦需重新构建。
- 关键信息：`getOverAgeThresholds()` 后端兜底 `female:55` 与 JSON `female:50` 不一致（**F10**），JSON 缺失时静默回退到 55，属隐患。

## 7. 修复优先级建议

### 立即修复（P0）
1. **F1 — 统一 `id_card` 加解密策略**：
   - 方案 A（推荐）：让 insurance.js `/overage` 的 `POST/PUT` 加 `encryptMiddleware`、`GET` 加 `decryptMiddleware`，与 over-age-personnel.js 对齐；
   - 或方案 B：合并两套路由，仅保留 over-age-personnel.js 作为 `over_age_personnel` 的唯一写入方，insurance.js 仅保留附件/版本/导出。
   - 上线前需对存量数据做一次 `id_card` 加密态普查与修复脚本。

### 高优先级（P1）
2. **F2 — 身份证/手机号脱敏**：前端展示与 CSV 导出均做掩码（如 `****` 中段）；后端返回可保留明文但前端不展示完整号。
3. **F3 — 修复详情抽屉附件/版本主键**：建立 `employee.id ↔ over_age_personnel.personnel_id` 映射，或在附件/版本接口中以 `personnel_id` 维度查询，避免用 employee.id 直接当 bizId。
4. **F4 — 导出数据一致性**：导出按钮改为导出当前所见（子系统A 列表），或明确切换为"导出保险管控台账"并在 UI 标注来源，避免误导。
5. **F5 — 新增/编辑可用化**：将演示弹窗接入真实持久化端点（over-age-personnel.js `POST/PUT`），或移除"新增人员"入口（因自动识别为只读）。

### 中优先级（P2）
6. **F6 — 补齐 `requireRole`**：三套超龄路由按需加 `requireRole('admin'[, 'safety_manager'])`，与前端 `authority` 对齐。
7. **F7 — 前端阈值去硬编码**：从规则接口/配置读取阈值，删除 `MALE_THRESHOLD/FEMALE_THRESHOLD` 常量。
8. **F8 — 导出 blob 错误校验**：下载前判断 `Content-Type`，非 CSV 时解析 JSON 报错提示。
9. **F9 — 规则热加载（可选）**：改为运行时读取或提供刷新接口，避免改阈值必须重启。

### 低优先级（P3）
10. **F10** 修正 `getOverAgeThresholds` 兜底为 `female:50`。
11. **F11/F12** 收敛 `as any`、表单可选字段用 `undefined`。
12. **F13** 移除未渲染的 `topDepartments` 或补充展示。
13. **F14** 在 UI/文档中明确两套"超龄"页面的职责边界。
