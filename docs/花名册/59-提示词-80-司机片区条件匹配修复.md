## 一、背景

提示词-78 修复了99.4%的"未知部门"问题，提示词-79修复了21条"未知岗位"（公司职能岗位）。但提示词-79的端到端验证中，用1311行乡镇花名册上传后，仍有**约35条 `unknown_position`** 残留，全部为 `司机 + XX街道/镇片区` 组合。

提示词-79的验证报告中已标注此问题并给出修复建议，本次正式立项修复。

## 二、根因分析

### 2.1 现有「司机」规则

`employee_position_mapping_rule` 表中有两条司机规则：

| id | source_position | condition_dept | target_position_name |
|----|----------------|---------------|---------------------|
| 16 | 司机 | 车队 | 驾驶员 |
| 29 | 司机 | 片区 | 驾驶员 |

### 2.2 匹配逻辑缺陷

`matchPosition()` 函数中，L1条件匹配前的处理逻辑：

```javascript
let cond = rawDept;
if (rawDept && rawDept.includes('片区')) cond = '*片区';
```

当Excel中 `raw_dept = "宁城街道片区"` 时：
1. `rawDept.includes('片区')` → true → `cond = '*片区'`
2. L1查询 `condition_dept = '*片区'` → 与规则中 `condition_dept = '片区'` **不匹配**
3. L2无条件匹配（`condition_dept IS NULL`）→ 无兜底规则
4. 结果：`unknown_position`

**根因**：代码将 `cond` 改写为 `'*片区'`，但规则表中存的是 `'片区'`（不带星号），两者不匹配。

### 2.3 影响范围

| 指标 | 数值 |
|------|------|
| 受影响行数 | ~35行（1311行花名册中） |
| 触发条件 | `raw_position = '司机'` 且 `raw_dept` 包含 "片区" |
| 涉及部门 | 宁城街道片区、津城街道片区、各镇片区等 |

---

## 三、修复方案

**推荐方案**：新增一条 `condition_dept IS NULL` 的司机兜底规则（极低风险，一行SQL）。

选择此方案而非修改 id=29 的 `condition_dept`，原因：
- 不修改现有规则数据，避免影响其他可能依赖 `condition_dept='片区'` 的逻辑
- 兜底规则作为L2无条件匹配的补充，只在L1全部未命中时生效
- 既修复"片区"问题，也覆盖未来任何新出现的司机部门

### 执行步骤

**步骤1：新增司机兜底规则**

```sql
INSERT INTO employee_position_mapping_rule
  (source_position, condition_dept, target_position_id, target_position_name,
   rule_version, match_priority, status, created_by, remark)
SELECT '司机', NULL, id, name, 'v1.0', 50, 'active', 'system', '提示词-80：司机无条件兜底规则'
FROM position WHERE name = '驾驶员' AND is_deleted = false
  AND NOT EXISTS (
    SELECT 1 FROM employee_position_mapping_rule
    WHERE source_position = '司机' AND condition_dept IS NULL
      AND is_deleted = false
  );
```

**步骤2：端到端验证**

用1311行乡镇花名册重新上传，确认：
- `unknown_position` 中不再有 "司机+片区" 组合
- 司机行全部自动匹配到"驾驶员"
- `unknown_dept` 仍为0（78修复不退化）
