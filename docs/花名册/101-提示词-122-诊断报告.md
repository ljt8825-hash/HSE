## 2. 问题诊断

### P1 — 岗位删除无友好提示（确认存在，已修复）
- **现象**：DELETE `/positions/:id` 直接软删，未检查员工关联。实际为软删除（UPDATE is_deleted=true），本身不会触发 FK 报错；但若有员工关联，用户无从知晓，且语义上产生"幽灵岗位"。
- **影响**：删除有关联员工的岗位后，花名册侧仍引用该岗位 → 数据不一致。
- **修复**：删除前查 `employee_assignment WHERE position_id=? AND is_current=true AND is_deleted=false`，>0 返回 `-5` 友好错误（含 N 名在职员工）。

### P2 — 筛选/分页为纯前端（确认存在，已修复）
- **3.2 筛选**：`jobCategory` / `specialPost` 在前端 `filteredList` computed 二次过滤，每次切换全量重拉。
- **3.3 分页**：`:pagination` 仅 `pageSize:20` 无 `current`/`total`，走 Ant Design 前端切片。
- **修复**：后端 GET `/positions` 增加 `jobCategory` / `isSpecialPost` 服务端筛选 + `page`/`pageSize` 分页（返回 `{list,total,page,pageSize}`）；前端移除 `filteredList`，直接绑定 `list` + 服务端分页。

### P3 — dept_id 非必填（确认存在，已修复）
- `formRules` 仅校验 `position_code` / `name`，`dept_id` 未 `required` → 可创建无归属部门岗位。
- **修复**：`formRules` 增加 `dept_id: [{ required: true, message: '请选择所属部门' }]`。

### P5 — 代码规范偏离 useDataTable（确认存在，本轮未改）
- `positions.vue` 手写 `loading`/`list`/`searchForm`/`handleSearch`，未用 `useDataTable` + `useSearchForm`。
- **判定**：不影响功能，属技术债。**本轮按提示词"可选"标记为后续债务**，不改造（避免大改引入回归，且红线仅允许改 positions.vue/employee.ts，改造需连带 hook 适配，风险偏高）。

## 3. 关键兼容性约束（影响修复方案）

`getPositionList` 被 **3 处**调用：
1. `positions.vue`（本任务改造，传 page 触发分页）
2. `OrgTransferModal.vue`：`getPositionList({ deptId })` 后 `positionList.value = data || []` — **不传 page，依赖数组返回**
3. `index.vue`：仅 import，未实际调用

**约束推导**：若后端在「无 page 参数」时也返回分页对象，则 `OrgTransferModal.vue`（禁止修改）会因 `data || []` 拿到对象而崩溃。**因此后端设计为：仅当传入 page/pageSize 时返回 `{list,total,page,pageSize}`，否则返回数组（保持旧行为）**。`getPositionList` 返回类型声明维持 `PositionItem[]`（不破坏 OrgTransferModal 类型），positions.vue 内以 `as any` 读取分页字段。
