## 缺陷1（P0）：驾驶员风险中心列表 500

**文件**: `server/routes/hse-driver-risk-center.js`
**位置**: `router.get('/drivers', ...)` 内的 `listResult` 查询（约第 208–246 行）

### 根因
PostgreSQL 在 `SELECT DISTINCT ... ORDER BY` 严格模式下，要求 `ORDER BY` 中的表达式必须出现在 `SELECT` 列表中（或为其列别名）。原代码对 `snap.total_score` 做 `COALESCE(snap.total_score, 100)` 排序，但该表达式未出现在 `SELECT` 列表中，触发报错：

```
ERROR: 在 SELECT DISTINCT 查询中，ORDER BY 表达式必须出现在查询列表中
```

### Before（修复前）
```sql
SELECT DISTINCT
    e.id as employee_id, e.employee_code, e.name, e.gender,
    o.org_name, ou.unit_name, ou.unit_type,
    p.name as position_name,
    snap.total_score, snap.risk_level,
    rlc.level_name as risk_level_name, rlc.color_code,
    lr_d.total_demerit_points,
    lr_d.demerit_count,
    a_c.accident_count
  FROM employee e
  -- ... 其余 JOIN / WHERE ...
  ORDER BY COALESCE(snap.total_score, 100) ASC, e.id
  LIMIT $n OFFSET $m
```

### After（修复后）
```sql
SELECT DISTINCT
    e.id as employee_id, e.employee_code, e.name, e.gender,
    o.org_name, ou.unit_name, ou.unit_type,
    p.name as position_name,
    snap.total_score, snap.risk_level,
    rlc.level_name as risk_level_name, rlc.color_code,
    lr_d.total_demerit_points,
    lr_d.demerit_count,
    a_c.accident_count,
    COALESCE(snap.total_score, 100) as sort_score   -- ✅ 新增：将排序表达式纳入 SELECT 列表
  FROM employee e
  -- ... 其余 JOIN / WHERE 保持不变 ...
  ORDER BY sort_score ASC, employee_id               -- ✅ 改为引用别名
  LIMIT $n OFFSET $m
```

### 关键改动点
1. `SELECT` 列表末尾新增 `COALESCE(snap.total_score, 100) as sort_score`。
2. `ORDER BY` 由 `COALESCE(snap.total_score, 100) ASC, e.id` 改为 `sort_score ASC, employee_id`（别名引用，满足 PG 严格模式）。

> **注意**：修复后该接口返回 `total=0` 是数据条件——`position` 表中驾驶员岗位行（30 行）均为 `is_deleted=true` 但业务上活跃（已知红线保护项），而该查询的 `driverCondition` 为 `p.name ILIKE '%驾驶员%' OR p.name ILIKE '%司机%'` 且 JOIN 时限定 `p.is_deleted = false`，因此命中 0 行。这是历史数据状态，非本次回归或修复引入的问题，接口本身已恢复正常（HTTP 200 / code=0）。

## 缺陷2（P1）：matchPosition 哨兵不一致

**文件**: `server/routes/hse-employee-import-v2.js`
**位置**: `async function matchPosition(client, rawPosition, rawDept, ruleVersion)` 内（约第 353–358 行）

### 根因
提示词-80 引入的哨兵值 `*片区` 与 `employee_position_mapping_rule.condition_dept` 实际存储值 `片区`（无星号）不一致，导致条件分支永远不命中，回退到 `condition_dept IS NULL` 的兜底规则。当前 `司机` 在两种条件下均映射到 `position_id=1398`（结果一致，无功能影响），但属于隐性不一致，未来新增仅在 `片区` 条件下生效的规则时会失效。

### Before（修复前）
```js
async function matchPosition(client, rawPosition, rawDept, ruleVersion) {
  if (!rawPosition) return null;

  // 1. 条件匹配（精确：source_position + condition_dept）
  let cond = rawDept;
  if (rawDept && rawDept.includes('片区')) cond = '*片区';   // ❌ 哨兵带星号，与 DB 实际值 '片区' 不一致
  // ...
}
```

### After（修复后）
```js
async function matchPosition(client, rawPosition, rawDept, ruleVersion) {
  if (!rawPosition) return null;

  // 1. 条件匹配（精确：source_position + condition_dept）
  let cond = rawDept;
  if (rawDept && rawDept.includes('片区')) cond = '片区';     // ✅ 与 DB 实际值一致
  // ...
}
```

### 关键改动点
- 第 358 行 `cond = '*片区'` → `cond = '片区'`，使条件规则 `source_position='司机' AND condition_dept='片区' → target_position_id=1398` 能够真正命中，而非回退 NULL 规则。
