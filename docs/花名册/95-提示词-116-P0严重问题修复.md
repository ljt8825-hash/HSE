## P0-1: level 枚举前后端不一致，level=6 写入必失败

### 根因分析

**数据库**（`hse_employee_master_v59_migration.sql:42`）：
```sql
level SMALLINT NOT NULL CHECK (level BETWEEN 1 AND 5)
```

**前端 Select**（`departments.vue:234-239`）：
```html
<Select.Option :value="1">公司</Select.Option>
<Select.Option :value="2">部门中心</Select.Option>
<Select.Option :value="3">乡镇作业中心</Select.Option>
<Select.Option :value="4">部门</Select.Option>
<Select.Option :value="5">乡镇</Select.Option>
<Select.Option :value="6">班组</Select.Option>
```

当用户选择 `level=6 (班组)` 时，后端 `INSERT INTO department` 直接触发 `CHECK (level BETWEEN 1 AND 5)` 约束错误，用户看到的是拦截器的通用错误提示而非明确的业务提示。

**此外**，level 语义在数据库注释和前端不一致：
- 数据库注释：1=集团 2=区域公司 3=企业 4=项目 5=班组
- 前端 `levelText`：1=公司 2=部门中心 3=乡镇作业中心 4=部门 5=乡镇 6=班组

### 修复方案

**方案：对齐数据库 CHECK 约束到 1-6，同时统一前后端 level 语义**

#### 步骤 1：数据库迁移（需生成 migration SQL）

创建新的 migration 文件 `hse_department_level_6_migration.sql`：

```sql
-- 移除旧约束
ALTER TABLE department DROP CONSTRAINT IF EXISTS department_level_check;
-- 添加新约束（1-6）
ALTER TABLE department ADD CONSTRAINT department_level_check CHECK (level BETWEEN 1 AND 6);
```

#### 步骤 2：前端 level 语义对齐

将 `departments.vue` 中的 `levelText()` 和 Select 选项对齐为数据库实际语义（环卫项目的实际业务层级）：

```typescript
function levelText(level?: number) {
  const map: Record<number, string> = {
    1: '公司',
    2: '部门中心',
    3: '乡镇作业中心',
    4: '部门',
    5: '乡镇',
    6: '班组',
  };
  return level ? map[level] || '-' : '-';
}
```

Select 选项保持不变（已经是 1-6）。

#### 步骤 3：后端 level 校验增强

在 `hse-employee.js` 的 `POST /departments` 和 `PUT /departments/:id` 中，增加 level 值校验：

```javascript
// POST /departments 中，在参数校验后增加
if (level !== undefined && (level < 1 || level > 6)) {
  return res.json(error(-3, '层级必须在 1-6 之间'));
}
```

### 影响范围
- 数据库：新增 migration SQL 文件
- 前端：`departments.vue` levelText 注释对齐（仅注释，实际值不变）
- 后端：`hse-employee.js` POST/PUT 增加 level 校验

## P0-2: 删除提示与实际行为完全相反

### 根因分析

**前端 Popconfirm**（`departments.vue:96-98`）：
```html
<a-popconfirm
  title="确定删除该部门吗？删除后子部门将一并删除。"
  @confirm="handleDelete(currentDept)"
>
```

**后端删除逻辑**（`hse-employee.js:1498-1500`）：
```javascript
const childResult = await pool.query(
  `SELECT id FROM department WHERE parent_id = $1 AND is_deleted = false`, [req.params.id]
);
if (childResult.rows.length > 0) return res.json(error(-5, '存在子部门，无法删除'));
```

前端提示"子部门将一并删除"，但后端硬拒绝有子部门的删除操作。用户点击确认后看到"存在子部门，无法删除"的错误提示，体验极差。

### 修复方案

**方案 A（推荐）：修正前端 Popconfirm 文案，保持后端行为不变**

将 Popconfirm 文案改为：
```
确定删除该部门吗？存在子部门时无法删除，请先删除所有子部门。
```

**方案 B：实现真正的级联删除（不推荐，风险高）**

级联删除涉及软删除所有子孙部门，需要事务 + 审计日志，且可能影响员工归属数据。建议暂不采用此方案。

### 修复内容

修改 `departments.vue:97` 的 `title` 属性：

```html
<a-popconfirm
  title="确定删除该部门吗？若存在子部门将无法删除，请先移除所有子部门后再操作。"
  @confirm="handleDelete(currentDept)"
>
```

同时增强 `handleDelete` 的错误处理，区分"有子部门"和"其他错误"：

```typescript
async function handleDelete(record: EmployeeApi.DeptNode) {
  try {
    await deleteDept(record.id);
    message.success('删除成功');
    currentDept.value = null;
    selectedKeys.value = [];
    await loadTree();
  } catch (err: any) {
    // 错误提示已由拦截器处理，但可以在此处增强提示
  }
}
```

> 后端错误码 `-5` 的提示已经是"存在子部门，无法删除"，前端无误额外处理。

### 影响范围
- 仅修改 `departments.vue` 第 97 行 Popconfirm 的 title 文案

## P0-3: level 递增溢出风险

### 根因分析

`handleAdd` 函数（`departments.vue:487`）：

```typescript
level: parent ? (parent.level || 3) + 1 : 1,
```

当 `parent.level = 5` 时，子级 `level = 6`。如果 P0-1 的数据库约束仍为 1-5，则会触发约束错误。即使 P0-1 修复为 1-6，也缺少上限保护——当 `parent.level = 6` 时，子级 `level = 7` 仍会失败。

### 修复方案

在 `handleAdd` 中增加 level 上限保护：

```typescript
function handleAdd(parent: EmployeeApi.DeptNode | null) {
  editMode.value = 'create';
  parentDeptName.value = parent?.name || '';
  
  // 计算子级 level，上限为 6
  let childLevel = 1;
  if (parent) {
    childLevel = Math.min((parent.level || 3) + 1, 6);
  }
  
  Object.assign(formData, {
    dept_code: '',
    name: '',
    short_name: '',
    parent_id: parent?.id || null,
    level: childLevel,
    township: parent?.township || '',
    headcount: 0,
    sort_order: 0,
    status: 'active',
    description: '',
  });
  editModalOpen.value = true;
}
```

同时在 Select 中：当 `parent.level === 6` 时，理论上不应该再允许新增子部门（班组是最底层）。可以在 UI 上隐藏"新增子部门"按钮：

```html
<a-button
  v-if="currentDept && canEdit && (currentDept as any).level !== 6"
  type="primary"
  size="small"
  @click="handleAdd(currentDept)"
>
```

### 影响范围
- `departments.vue` 第 479-495 行：`handleAdd` 函数 level 计算逻辑
- `departments.vue` 第 83-89 行：条件渲染"新增子部门"按钮

## P0-4: 两套组织体系双轨运行（架构级问题）

### 根因分析

这是本次检查中发现的最核心的架构问题。系统存在两套完全独立的组织数据模型：

| 维度 | `department` 表 | `hse_org_unit` 表 |
|------|-----------------|-------------------|
| 行数 | 77 行 | 20 行 |
| 粒度 | 公司→部门中心→乡镇作业中心→部门→乡镇→班组（6 级） | 公司→职能部门→作业中心→乡镇作业中心（4 级） |
| 管理页面 | ✅ "组织管理"页面 CRUD 操作 | ❌ 无前端管理页面 |
| 员工归属 | ❌ 不参与 | ✅ `employee_assignment.org_unit_id` → `hse_org_unit.id` |
| 外键关联 | 无 | 无 |

**核心矛盾**：用户在"组织管理"页面增删改部门，操作的是 `department` 表，但员工归属绑定的是 `hse_org_unit`。两者的唯一关联是通过 `department.name` 与 `hse_org_unit.org_name` 的字符串前缀匹配（如"宁城街道" → "宁城街道作业中心"），**精确等值匹配命中率为 0/77**。

**已完成的修复**（v110 migration）：
- `department` 表新增 `org_unit_id` 列，建立 ID 级映射
- 初始填充：精确匹配 0 行，前缀匹配 24 行，53 个班组级部门无对应 org_unit 可映射
- 新建/改名部门时自动检测并更新 `org_unit_id` 映射

**当前残留问题**：
1. `hse_org_unit` 的管理页面缺失——后端有完整 CRUD API（`hse-org-center.js`），前端无任何页面
2. 班组级部门（53/77=69%）无法映射到 `hse_org_unit`，因为 org_unit 粒度只到"作业中心"
3. 组织架构变更（department CRUD）需要同步更新 `hse_org_unit` 才能影响员工归属，但当前无此同步机制
4. 调岗弹窗（OrgTransferModal）选择的是 `department` 树节点，但调岗 API 最终写入 `hse_org_unit.id`，依赖 `resolveOrgUnitId` 的字符串匹配兜底

### 修复方向

此为架构级问题，不宜在当前提示词中一次性修复，建议作为**独立专项**处理。此处列出修复方向供后续规划：

**短期（本提示词范围）**：无需修改代码，仅生成诊断报告文档。

**中期（独立专项）**：
- 方案 A：建立 `department` ↔ `hse_org_unit` 主数据映射表，实现双向同步触发器
- 方案 B：统一为单棵组织树，将 `hse_org_unit` 合并到 `department` 或反之
- 方案 C：在"组织管理"页面中同时展示 `hse_org_unit` 树，提供映射管理 UI
