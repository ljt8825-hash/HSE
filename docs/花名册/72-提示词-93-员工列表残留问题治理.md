## 二、缺陷详情

### 问题1：`v_employee_current` 视图语义 —— 任职行 vs 员工行

**现状**（`server/sql/sprint5_6_employee_master_migration.sql` 第 262-309 行）：

```sql
CREATE OR REPLACE VIEW v_employee_current AS
SELECT ... FROM employee e
LEFT JOIN employee_assignment a
  ON a.employee_id = e.id
  AND a.is_current = true AND a.is_primary = true AND a.is_deleted = false
WHERE e.is_deleted = false;
```

当前视图 1:1 LEFT JOIN `employee_assignment`，本应一行一员工。但提示词-91 发现 1299名员工存在多条 `is_primary=true AND is_current=true` 的任职行，导致视图膨胀为 3913 行。

**提示词-91 已降级重复任职**（2552行 → `is_primary=false`），当前视图应已恢复正常。但需要验证 + 加固。

**修复方案**：

1. **验证当前视图行数**：确认降级后 `v_employee_current` 是否 = 1361
2. **视图加固**：加 `DISTINCT ON (e.id)` 确保每人一行，防止未来重复数据再次导致膨胀：

```sql
CREATE OR REPLACE VIEW v_employee_current AS
SELECT DISTINCT ON (e.id)
  e.id AS employee_id,
  e.employee_code,
  e.name,
  ...
  a.supervisor_id,
  sup.name AS supervisor_name,
  ...
FROM employee e
LEFT JOIN employee_assignment a
  ON a.employee_id = e.id
  AND a.is_current = true AND a.is_primary = true AND a.is_deleted = false
LEFT JOIN employee sup ON sup.id = a.supervisor_id AND sup.is_deleted = false
WHERE e.is_deleted = false
ORDER BY e.id, a.start_date DESC NULLS LAST;
```

**验收标准**：
- `SELECT COUNT(*) FROM v_employee_current` = 1361
- `GET /hse/employee/employees` → total = 1361
- 前端分页正常（页数从 ~196 页降低到 ~69 页，每页20条）

### 问题2：任职去重 —— 导入链路加固

**根因**：花名册导入时 `INSERT INTO employee_assignment` 未做「每员工仅一条 `is_primary=true AND is_current=true`」的写入约束，导致重复导入同一员工时不断追加新任职行而非更新旧行。

**提示词-91 处理**：激活任职时触发 `uk_emp_assign_primary` 冲突，已降级 2552 行。但此为**被动防御**，根因在导入链路。

**修复方案**：在导入入库阶段（`server/routes/hse-employee-import-v2.js` 的 `executeImport`），插入新任职前先清理旧主职：

```js
// 插入新任职关系前，先将该员工旧主职降级
await client.query(`
  UPDATE employee_assignment
  SET is_primary = false, updated_at = NOW()
  WHERE employee_id = $1
    AND is_primary = true
    AND is_current = true
    AND is_deleted = false
`, [employeeId]);

// 然后插入新任职（is_primary=true, is_current=true）
```

**验收标准**：
- 重复导入同一员工后，`employee_assignment` 中仅 1 条 `is_primary=true AND is_current=true`
- 旧主职被标记为 `is_primary=false`
- 视图行数不再膨胀

---

### 问题3：导入链路 supervisor 写入加固

**根因**：花名册导入时 `matchSupervisor` 按姓名精确匹配，但**导入当时**区域层领导（如马鑫、刘晓光）尚未作为员工入库，导致匹配失败 → `supervisor_id` 写入 NULL。

提示词-92 通过数据回填（`employee_import_pending.raw_supervisor` 反向匹配）修复了历史数据，但**未来导入**仍可能产生相同问题。

**修复方案**：在导入入库阶段，增加「兜底匹配」逻辑：

```js
// 在 executeImport 中，插入 employee_assignment 时：
// 如果 matchSupervisor 返回 null（导入时匹配失败），
// 从 employee_import_pending 中读取 raw_supervisor 再做一次兜底匹配
const supervisorMatch = await matchSupervisor(client, row.raw_supervisor);
let supervisorId = supervisorMatch?.supervisor_id || null;

// 兜底：如果导入时匹配失败，尝试从当前已入库的员工中再次匹配
if (!supervisorId && row.raw_supervisor) {
  const fallback = await matchSupervisor(client, row.raw_supervisor);
  supervisorId = fallback?.supervisor_id || null;
}
```

**注意**：提示词-92 禁止修改 `hse-employee-import-v2.js`，但提示词-93 是独立提示词，且该修复属于导入链路加固，授权修改。

**验收标准**：
- 新导入员工（含系统内上级）后，`employee_assignment.supervisor_id` 不为 NULL
- 系统外上级（如区域层领导）保持 NULL，不报错
- 花名册导入流程不受影响
