### #7 详细验证（clear-all 重导不重复键）

采用**原子事务**（单条 `-c` 命令，确保回滚可靠）模拟 clear-all→重导：
```sql
BEGIN;
  UPDATE employee SET is_deleted = true WHERE employee_code = '00347342';   -- 模拟 clear-all 软删
  UPDATE employee SET employee_code = '00347342' WHERE employee_code = '00360023'; -- 模拟重导复用同号
  SELECT 'probe_executed' AS r;
ROLLBACK;
```
回滚后立即核对：`employee` 总数 = **1361**、distinct code = **1361**、重复 code = **0**。
→ 软删后的工号不再占用部分唯一索引，重导复用同号**不触发 duplicate key**，根因消除，且数据零副作用。

## 六、事故记录（必须上报）

**在执行 #7 验证探针时，首次采用 `psql -f` 事务文件（`BEGIN; …; ROLLBACK;`）模拟重导，事务未回滚，导致 `employee` 表被污染**：
- 表现：`employee` 由 1361 行变为 **2672 行**（新增 1361 条幻影行 id 5227–7996），出现重复 `employee_code`，`is_deleted` 分布变为 f=1311 / t=1361。
- 根因：`psql -f` 在本环境的脚本事务未可靠回滚（疑似连接/事务边界处理差异），2 条 UPDATE 被提交。
- **恢复**：利用任务0全量备份，以 `postgres` 超级用户 `DROP DATABASE` + `CREATE DATABASE OWNER hse_app` + `pg_restore` 整体恢复至执行前干净基线（已先对污染态做保险备份 `hse_bk_91_corrupted_*.dump`，恢复验证成功后已清理以保 `backups/` 整洁），随后重新执行 `fix_91_index_and_position.sql`，结果干净（index 部分化、position=33、employee=1361、assignment=3920、0 冲突）。
- 加固：#7 改用**单条 `-c` 原子事务**重试，回滚可靠、数据零副作用（见第三节 #7）。
- 当前数据库状态已完全正确，无任何残留污染。

**教训**：验证探针严禁使用 `psql -f` 多语句事务做写操作；须用单条 `-c` 原子事务或应用层导入接口，且任何写前必做全量备份。
