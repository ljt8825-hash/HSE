## 一、问题描述

用户操作路径：人员管理 → 花名册导入 → 上传Excel → 点击"详情" → 点击"刷新" → 查看"匹配状态"

**现象**：花名册导入后，大量记录显示"匹配状态 = 未知部门"（红色error标签），导致无法自动入库。用户期望花名册作为数据基础，导入后应全部匹配，供其他板块使用。

### 2.4 四级匹配全部失败的原因

以"时集镇四班"为例，模拟 `matchOrgUnit()` 四级匹配结果：

| 级别 | 策略 | 结果 | 原因 |
|------|------|------|------|
| L1 | 映射规则精确匹配 | ❌ MISS | `employee_import_mapping_rule` 表中无任何乡镇部门的映射规则 |
| L2 | 组织表精确匹配 | ❌ MISS | "时集镇四班" ≠ "时集镇作业中心" |
| L3 | 模糊包含匹配 | ❌ MISS | "时集镇四班" 不包含 "时集镇作业中心"，反之也不包含 |
| L4 | 关键字匹配 | ❌ MISS | 剥离"部中心室办组"后 → "时集镇四班" vs 剥离后"时集镇作业" — "作业"不包含"四班" |

**关键发现**：L4关键字匹配的剥离正则 `/[部中心室办组]/g` 不包含"班"字，且"XX镇X班"中的"X班"不是"XX镇作业中心"的字串。简单前缀匹配（提取"时集镇" → 匹配"时集镇作业中心"）即可解决，但当前算法缺少这一级。

`employee_import_mapping_rule` 中仅9条规则，全部针对顶层部门：

## 三、三方意见辩论

### 3.1 反对意见（辩驳用户"花名册应全部匹配"的假设）

**你的假设存在三个逻辑漏洞：**

1. **命名粒度不匹配是业务现实，不是代码bug**。Excel用"时集镇四班"（班组级别），系统用"时集镇作业中心"（中心级别）。这是两个不同粒度的组织层级，代码无法凭空推断"四班"属于"时集镇作业中心"。如果强制全部匹配，反而会掩盖真实的组织层级差异——比如"杜集镇三四班"到底对应"杜集镇作业中心"还是其他？这需要业务确认。

2. **"花名册作为基础"与"花名册导入全部匹配"是两回事**。花名册作为数据基础意味着其数据质量决定下游质量，这恰恰要求导入阶段必须严格校验，而非盲目放行。如果花名册中出现了系统不存在的部门（如"宁津街道二班"但系统只有"宁城街道作业中心"），强行匹配反而会制造脏数据。

3. **当前系统的设计哲学是正确的**：导入分两阶段（自动匹配 → 人工审核），异常数据进入pending表等待人工确认。这不是缺陷，而是数据治理的护栏。问题在于自动匹配的覆盖率太低（99.4%失败），而非"不应该有pending"。

### 3.2 主流意见（大多数开发者会如何看）

**核心观点：这是映射规则缺失 + 匹配算法覆盖不足的组合问题，修复优先级P0。**

主流做法分两步：
1. **补全映射规则**：为所有乡镇→作业中心建立映射规则（30+条），这是最直接、最安全的方案
2. **增强匹配算法**：在L4之后增加L5"乡镇前缀匹配"——提取"XX镇/XX乡/XX街道"前缀，匹配包含该前缀的org_unit

选择方案1（补规则）优于方案2（改算法），因为：
- 规则是显式的、可审计的、可维护的
- 算法改动有引入过度匹配（false positive）的风险
- "杜集镇三四班"到底是"杜集镇作业中心"还是别的？这需要业务确认，规则表可以精确控制

### 3.3 专业性意见（技术深度分析）

**根因分类**：这是一个**数据建模层面的设计缺陷**，而非单纯的代码bug。

**三层问题**：

1. **Schema层**：`employee_import_mapping_rule` 表设计是正确的（source_value → target_id映射），但初始化数据不完整。Sprint6.0只创建了9条规则，遗漏了15个乡镇作业中心的映射。这是典型的"初始化数据不完整"问题。

2. **Algorithm层**：`matchOrgUnit()` 的四级匹配策略设计合理，但L4关键字匹配的正则 `/[部中心室办组]/g` 是针对"职能部门"命名习惯设计的（如"安环管理部"→"安环品质部"），对"乡镇班组"命名模式（"XX镇X班"→"XX镇作业中心"）完全不适用。需要增加L5"乡镇前缀匹配"作为兜底。

3. **Process层**：当前导入流程是"上传→自动匹配→pending→人工审核→入库"，设计上允许pending存在。但99.4%的pending率说明自动匹配阶段形同虚设，失去了"减少人工审核工作量"的设计初衷。

**推荐修复方案（按优先级排序）**：

| 方案 | 描述 | 工作量 | 风险 | 推荐度 |
|------|------|--------|------|--------|
| **A. 补全映射规则** | 为所有乡镇班组→作业中心创建mapping_rule | 中（30+条SQL） | 低 | ⭐⭐⭐⭐⭐ |
| **B. 增加L5乡镇前缀匹配** | 在matchOrgUnit()中增加镇/乡/街道前缀提取+LIKE匹配 | 小（~15行代码） | 中（可能误匹配） | ⭐⭐⭐⭐ |
| **C. 方案A+B组合** | 先补规则，再加算法兜底 | 中 | 低 | ⭐⭐⭐⭐⭐ |
| **D. 全自动创建org_unit** | 遇到未知部门时自动创建org_unit | 大 | 高（可能创建重复/错误组织） | ⭐⭐ |

**推荐方案C**：先补全所有乡镇映射规则（确保已知映射100%覆盖），再增加L5乡镇前缀匹配（兜底未知情况），形成"规则优先 + 算法兜底"的双保险。

## 四、执行任务（WorkBuddy 执行清单）

### 任务1：补全乡镇映射规则（主方案）

**目标**：在 `employee_import_mapping_rule` 表中为所有乡镇班组→作业中心创建映射规则。

**执行步骤**：

1. 查询数据库，获取所有 `unknown_dept` 的 `raw_dept` 去重列表
2. 对每个 `raw_dept`（如"时集镇四班"），提取乡镇前缀（如"时集镇"），匹配 `hse_org_unit` 中对应的作业中心（如"时集镇作业中心"）
3. 生成 INSERT 语句，写入 `employee_import_mapping_rule` 表：
   - `source_type = 'excel_department'`
   - `target_type = 'org_unit'`
   - `rule_version = 'v1.0'`（当前生效版本）
   - `match_priority = 70`（低于精确匹配的90，高于默认的50）
   - `status = 'active'`
4. 特别处理边界情况：
   - "杜集镇三四班" → 合并班组（三班+四班），映射到"杜集镇作业中心"
   - "杜集镇六七班" → 同理
   - "宁城街道二班" → 映射到"宁城街道作业中心"（注意Excel可能是"宁城"也可能是"宁津"）
5. 验证：重新上传花名册，确认 `unknown_dept` 数量降至0

### 任务2：增强匹配算法（兜底方案）

**目标**：在 `matchOrgUnit()` 函数中增加L5"乡镇前缀匹配"。

**修改文件**：`server/routes/hse-employee-import-v2.js`

**修改位置**：在L4关键字匹配（第226-238行）之后、`return null`（第240行）之前，增加L5：

```javascript
// 5. 乡镇前缀匹配（处理"XX镇X班"→"XX镇作业中心"模式）
const townshipPrefix = dept.match(/^(.+?[镇乡街道])/);
if (townshipPrefix) {
  const prefix = townshipPrefix[1];
  const townshipMatch = await client.query(
    `SELECT id AS target_id, org_name AS target_name
     FROM hse_org_unit WHERE is_deleted = false
       AND org_name LIKE $1 || '%'
     ORDER BY id LIMIT 1`,
    [prefix]
  );
  if (townshipMatch.rows.length > 0) {
    return { target_id: townshipMatch.rows[0].target_id, target_name: townshipMatch.rows[0].target_name };
  }
}
```

**注意**：L5应作为兜底策略，不替代L1-L4。如果L1-L4中任一命中，不会进入L5。

## 六、附加说明

### 6.1 关于"未知岗位"（unknown_position，21条）

这是独立问题，不在本次修复范围内。`unknown_position` 的根因是 `employee_position_mapping_rule` 表缺少对应岗位的映射规则，需要另案处理（建议创建提示词-79）。

### 6.2 关于"花名册作为基础"的架构含义

当前架构中，`hse_org_unit` 是组织数据的主表，花名册导入时要求部门必须能映射到已有org_unit。如果业务上确实需要"花名册定义组织架构"（即反向写回org_unit），则需要在导入流程中增加"自动创建org_unit"的逻辑，但这涉及：
- 防止重复创建（同名检查）
- org_type自动推断（town_center / department）
- org_path自动生成
- 与现有组织架构的冲突处理

建议在后续迭代中单独评估，不作为本次修复范围。
