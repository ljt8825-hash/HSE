## 二、缺陷详情

### 缺陷1：uk_employee_code 部分索引条件缺失（根因）

**根因**：迁移脚本 `hse_employee_master_v59_migration.sql` 定义的索引为：

```sql
-- 设计意图（v59迁移脚本）
CREATE UNIQUE INDEX IF NOT EXISTS uk_employee_code
    ON employee (employee_code) WHERE employee_code IS NOT NULL AND is_deleted = false;
```

但实际数据库中的索引缺少 `is_deleted = false` 条件：

```sql
-- 实际数据库现状
CREATE UNIQUE INDEX uk_employee_code ON employee
    USING btree (employee_code) WHERE (employee_code IS NOT NULL);
```

**后果**：`clear-all` 执行 `UPDATE employee SET is_deleted=true` 后，被软删员工的 `employee_code` 仍然占用唯一索引，导致：
- 重新导入同一工号时触发 `duplicate key value violates unique constraint "uk_employee_code"`
- 这是提示词-81、90 中反复遇到的"clear-all 软删缺陷"的根因

**修复方案**：重建索引，补回 `is_deleted = false` 条件：

```sql
DROP INDEX IF EXISTS uk_employee_code;
CREATE UNIQUE INDEX uk_employee_code
    ON employee (employee_code) WHERE employee_code IS NOT NULL AND is_deleted = false;
```

**注意**：`uk_employee_idcard` 同样缺少 `is_deleted = false` 条件（实际为 `WHERE id_card IS NOT NULL`），建议一并修复。

### 缺陷2：position 表30行软删标记（数据一致性问题）

**现状**：`position` 表共30行，全部 `is_deleted=true`。但这些岗位是系统核心业务岗位（如 垃圾收运车驾驶员 1398、管理员 1395 等），被 `employee_assignment` 和 `employee_position_mapping_rule` 活跃引用，业务上实际活跃。

**影响**：`driver-risk-center/drivers` 查询中 JOIN `position p` 时条件 `p.is_deleted = false` 导致命中0行，即使提示词-89已修复SQL，接口仍返回 TOTAL=0。

**修复方案**：将所有30行岗位的 `is_deleted` 改为 `false`：

```sql
UPDATE position SET is_deleted = false, updated_at = NOW()
WHERE is_deleted = true;
```

**安全性确认**：`position` 表仅 `position_code` 有唯一约束（非部分索引），不存在 `is_deleted=false` 后与已有记录冲突的风险。
