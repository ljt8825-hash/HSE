# 提示词-116 双轨制诊断报告：两套组织体系并行运行

> 日期：2026-08-01
> 专家：Senior Developer（高级开发工程师）吴八哥
> 范围：仅分析，不改动任何代码/表（对应提示词-116 P0-4）

## 一、核心结论

系统存在两套完全独立的组织数据模型：`department`（组织管理 UI 维护）与 `hse_org_unit`（员工归属基准）。两者从数据模型上就不是同一棵树，唯一的"关联"是查询期的字符串前缀匹配。这是"员工花名册与组织管理无数据交互"的根因（详见 `90-花名册组织管理无数据交互-根因诊断.md`）。

> 进展：提示词-112 方案A 已在 `department` 新增 `org_unit_id` 外键，建立 **ID 级主数据映射**（初始 24 映射 / 53 班组级未映射），缓解但**未彻底消除**双轨——`hse_org_unit` 仍无前端管理页、班组级部门(53/77=69%)因粒度差异无法映射。

## 二、表结构对比

| 维度 | `department` | `hse_org_unit` |
|------|--------------|----------------|
| 行数 | 78（77 活跃 + 1 软删） | 20 |
| 层级 | 4/5/6（乡镇/班组为主；无 1-3） | 1-4（公司/职能部门/作业中心/乡镇作业中心） |
| 粒度 | 细到班组 | 粗到作业中心 |
| 前端管理页 | ✅ 组织管理 CRUD | ❌ 无（后端 `hse-org-center.js` 有完整 CRUD API） |
| 员工归属 | ❌ 不参与 | ✅ `employee_assignment.org_unit_id` → `hse_org_unit.id` |
| 外键 | 仅 FK→`hse_org_unit`(org_unit_id, 方案A 新增) | 被 `employee_assignment` 等 10 个 FK 引用 |
| 同步触发器 | 0 | 0 |

## 三、关联链路

1. **组织管理写路径**：`POST/PUT/DELETE /departments` 只写 `department` 表（方案A 后新建/改名会自动维护 `org_unit_id` 映射）。
2. **花名册读路径**：`GET /employees/profile/list` → `v_employee_current` → `employee_assignment.org_unit_id` → `hse_org_unit`，**不经过 `department`**。
3. **唯一桥梁**：`department.name` ↔ `hse_org_unit.org_name` 的字符串匹配（精确 0/77 命中，前缀兜底 24 命中）。方案A 的 `org_unit_id` 外键已将该桥梁固化为 ID 引用。
4. **调岗弹窗**（`OrgTransferModal`）：选 `department` 树节点，但最终写入 `hse_org_unit.id`，依赖 `resolveOrgUnitId` 字符串兜底。

## 四、影响范围

- 用户在"组织管理"增删改部门，操作的是 `department`；员工归属绑定的是 `hse_org_unit`。一侧变更因无双向同步机制而不传播到另一侧。
- 53 个班组级部门无法映射到 `hse_org_unit`（org_unit 粒度只到作业中心），其下员工在组织管理中"无归口"。
- `hse_org_unit` 缺前端页，管理员无法在前端维护作业中心/乡镇作业中心，依赖导入或 DB 直改。

## 五、推荐修复方案（供后续专项规划）

- **方案 A（主数据映射 + 双向同步）**：在方案A 的 `org_unit_id` 基础上，增加双向同步——组织管理变更 `department` 时联动 `hse_org_unit`（或反之），并补 `hse_org_unit` 前端管理页。最贴合现有架构，但需处理粒度不对等（班组无法落 org_unit）。
- **方案 B（单树合并）**：将 `hse_org_unit` 合并进 `department`（或反之），统一为单棵组织树，员工归属直接引用该树节点。最彻底，但迁移成本与业务中断风险最高。
- **方案 C（映射管理 UI）**：在"组织管理"页并列展示 `hse_org_unit` 树，提供 `department ↔ hse_org_unit` 映射管理界面，人工维护 53 个班组级缺失映射。侵入最小，可先行。
