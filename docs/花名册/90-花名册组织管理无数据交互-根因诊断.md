# 花名册 ↔ 组织管理「无数据交互」根因诊断报告

> 类型：纯诊断（未改动任何代码 / 表结构 / 数据）
> 方法：源码审查 + 数据库探针（`_109_diag.sql` 实跑）
> 日期：2026-08-01

## 一、问题概述

用户报告：人员管理模块中，"员工花名册 / 员工档案"与"组织管理"两个模块之间**未进行数据交互**。要求排查三点：

1. 花名册与组织管理之间的**数据接口**是否存在、是否正常调用；
2. 组织架构变更时，花名册中的**员工归属信息是否同步更新**；
3. 两个模块之间的**数据绑定关系是否正确建立**。

本报告给出根因与具体证据。

## 二、两个模块各自的「组织数据」来源

| 维度 | 组织管理模块 | 花名册 / 员工档案 / 导入模块 |
|---|---|---|
| 维护表 | `department`（77 行，level 4/5/6，细到「班组」级） | `hse_org_unit`（20 行，company / center / department / town_center，到「作业中心」级）+ `employee_assignment` |
| 前端 | `apps/web-antd/src/views/hse/employee/departments.vue` | `apps/web-antd/src/views/hse/employee-profile/index.vue`（路由 `/personnel/profile`） |
| 后端接口 | `POST / PUT / DELETE / GET /departments*` | `GET /employees/profile/list` → 视图 `v_employee_current` |
| 员工归属字段 | **无**（部门表本身不持有员工） | `employee_assignment.org_unit_id` → `hse_org_unit.id` |

**关键事实**：员工归属（谁属于哪个组织 / 班组）**只**存在于 `employee_assignment.org_unit_id` → `hse_org_unit`，与 `department` 表**毫无关系**。

## 三、数据库硬证据（`_109_diag.sql` 实跑）

1. **行数**：`department` = 77（活跃）；`hse_org_unit` = 20（活跃）。
2. **外键**：引用 `department` 的外键 **0 条**；引用 `hse_org_unit` 的外键 10 条（含 `fk_employee_assignment_org_unit` → `employee_assignment`）。
3. **触发器**：`department`、`hse_org_unit` 上同步触发器 **0 个**。
4. **字段**：`employee_assignment` **没有 `department_id` 列**（探针 `WHERE department_id IS NOT NULL` 直接报 `字段 "department_id" 不存在`），只有 `org_unit_id`。
5. **名称精确匹配**：77 个 `department` 中，名称与任一 `hse_org_unit.org_name` 完全相等的 **0 个** —— 两表层级粒度不同（部门树到「班组」，组织单元只到「作业中心」），精确等值根本不可能命中。

## 四、三检查点逐一结论

### 1) 数据接口是否存在 / 是否正常调用？
- **不存在真正的数据接口**。两模块走的是两套独立的表与接口：
  - 花名册侧：`GET /employees/profile/list`（及员工列表 `GET /employees`）读取 `v_employee_current` → `employee_assignment.org_unit_id` → `hse_org_unit`，**完全不经过 `department`**。
  - 组织管理侧：`/departments/tree`、`/departments/:id/employees` 读 `department`，**仅在查询期**用字符串匹配 `department.name = hse_org_unit.org_name OR ou.org_name LIKE d.name || '%'`，把 `hse_org_unit` 关联的员工数「投影」到部门树节点上。
- 这种投影是**单向只读**的：组织管理页面能看到某部门（按名字匹配到的作业中心）下有多少员工，但这是临时计算的，不是两个模块之间的数据接口。

### 2) 组织架构变更时，花名册是否同步更新？
- **不会同步**。组织管理的写接口（`POST/PUT/DELETE /departments`，`hse-employee.js` ~1363 / 1412 / 1453）的 SQL **全部只操作 `department` 表**：
  - `INSERT INTO department …`
  - `UPDATE department SET … WHERE id = $N`
  - `UPDATE department SET is_deleted = true …`
- 它们**从不**触碰 `hse_org_unit` 或 `employee_assignment`。因此：
  - 在「组织管理」里新增 / 改名 / 删除一个部门（即使改了部门名称），花名册里员工的 `org_unit_id` 指向的 `hse_org_unit` 节点纹丝不动 → **员工归属信息不更新**。
  - 反之，花名册导入 / 调整 `hse_org_unit`、改 `employee_assignment`，也不会回写到 `department`。
- 唯一可能的「联动」只是查询时的名字前缀匹配，且由于**精确匹配 0/77 命中**，完全依赖模糊前缀，极易因改名 / 新增而失效。

### 3) 两个模块的数据绑定关系是否正确建立？
- **没有正确建立**，只存在脆弱的字符串前缀匹配：
  - 关联键是**名字字符串**，不是 ID / 外键；
  - 精确等值匹配 **0/77 命中**，100% 依赖 `LIKE d.name || '%'` 前缀兜底；
  - 粒度不对等：`department` 到「班组」级（如「宁城街道一班」），`hse_org_unit` 只到「作业中心」级（如「宁城街道作业中心」）。**班组级部门在 `hse_org_unit` 中没有对应节点** → 点开该部门员工子列表时 `orgUnitIds.length === 0` → **恒返回空列表**（代码 `hse-employee.js` ~1319 直接返回空）。
  - 前缀匹配还存在语义错位 / 一对多风险（代码注释称已验证 1:1，但建立在现有命名约定上，命名一旦变动即崩）。

## 五、根因总结

> **根因：系统存在两套并行的「组织」数据模型，却缺乏主数据（MDM）治理；二者之间没有外键、触发器或共享关联列，仅在查询期靠字符串模糊匹配临时拼接。**

具体原因链：

- **数据库层**：`department` 不被任何表外键引用；`employee_assignment` 只关联 `hse_org_unit`（且无 `department_id` 字段）；两表无任何同步触发器。
- **应用层**：组织管理写接口只写 `department`；花名册读接口只依赖 `hse_org_unit` + `employee_assignment`。两条数据流在代码里不交汇。
- **关联逻辑层**：唯一桥梁是 `department.name ↔ hse_org_unit.org_name` 的「精确 + 前缀」匹配，但精确命中 0/77，且双方层级粒度不对等，关联既不可靠也不可维护。

于是从用户视角看：在「组织管理」里调整组织架构，花名册（员工归属）毫无反应 —— 这就是「两个模块未进行数据交互」的真实原因。它们**从数据模型上根本不是同一棵组织树**，只是界面上借名字拼出了一个交叉视图。

## 六、影响面

- 「组织管理」部门树上的「员工人数」（`employee_count`）与「部门员工子列表」依赖前缀匹配：班组级部门恒为空，且改名即失准。
- 花名册 / 员工档案 / 风险画像 / 驾驶员风险中心等所有员工归属维度，完全绑定 `hse_org_unit`，与「组织管理」的部门调整脱钩。
- 前序（提示词-108）已记录：53 个班组级部门因 `employee_assignment` 仅引用 `hse_org_unit` 而永无员工。

## 七、可选修复方向（本次未实施，供决策）

1. **建立主数据映射（推荐）**：在 `department` 与 `hse_org_unit` 之间增加映射表或 `department.org_unit_id` 外键列；组织管理增改时同步维护关联；花名册统一以 `employee_assignment.org_unit_id` 为唯一归属源，通过映射反查部门。
2. **收敛为单一组织树**：将 `department`（可编辑、细粒度）作为唯一可维护树，`hse_org_unit` 仅作业务快照 / 导入映射基准，变更时由触发器或应用层同步。
3. **至少修复查询关联（治标）**：将前缀匹配改为基于映射 ID 的关联，消除 0/77 精确命中和班组级子列表恒空问题。
