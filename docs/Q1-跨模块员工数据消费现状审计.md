## 一、审计方法

### 1.1 审计范围
按 Q1 提示词枚举的 **18 个业务模块**全覆盖（含子模块文件），对每个模块审计以下 4 个维度：

| 维度 | 含义 |
|------|------|
| 维度1 使用方式 | 是否用 `EmployeeSelector`、是否调 `api/hse/employee.ts`、是否硬编码姓名/工号搜索、是否用员工统计 |
| 维度2 数据一致性 | 员工标识符字段命名、姓名来源（API vs 手填）、调岗/离职后陈旧数据风险 |
| 维度3 模块联动 | 员工变更（调岗/离职/状态）是否影响本模块、是否有「点击姓名→档案」跳转、是否需要其他模块员工数据 |
| 维度4 API 模式 | 员工函数是否统一从 `employee.ts` 导入、请求/响应格式一致性、是否存在 N+1 循环查询 |

### 1.2 评分标准
- ✅ 规范：符合统一消费主数据约定
- ⚠️ 有瑕疵：可用但有不一致或可优化点
- ❌ 严重问题：功能缺陷或数据正确性风险
- — 不涉及：模块不消费员工/花名册数据

### 1.3 已确认的基础事实（贯穿全仓）
- 规范主数据 API：`src/api/hse/employee.ts`，`EmployeeItem` 主键字段名 `id`（数字），字段含 `name`/`dept_name`/`position_name`/`employee_code`/`org_status` 等；导出 `getEmployeeList`/`getEmployeeDetail(id)`/`getEmployeeStats`/`getDeptEmployees`。
- 选择器 API：`src/components/hse/EmployeeSelector.vue`，内部值绑定 `employee-selector.ts` 的 `SelectorItem.employee_id`（snake_case），走 `getEmployeeSelectorList` + `getEmployeeSelectorBatch` 批量回显。
- **`employee.ts` 的 `getEmployeeDetail` 全仓零调用（死代码）**；**不存在 `getEmployeesByIds` 批量端点**。
- 员工主数据详情页在 UI 层**无入口**（仅有列表/部门/岗位/超龄/导入页）；所有「点击→档案」跳转均指向 `risk-profile`（风险画像），非主档案 `/hse/employee`。

### 2.1 关键模块的实质发现（按行号引用）

**① 人员管理（hse/employee）**
- 删除员工无引用校验：`index.vue:382-391` `handleDelete` 直接 `deleteEmployee(record.id)`，下游 violations/hazards/training 存储的 `employee_id` 外键将悬空。
- `OrgTransferModal.vue:211-219` 调岗经 `assignOrg({employee_id: props.employeeId, ...})`，`employee_id` 实为 `EmployeeItem.id` —— 字段命名不统一（见 P0-2）。

**② 三违管理（violations）**
- `EmployeeSelector` 用法正确：`violatorId`/`inspectorId`/`handlerId`/`punisherId`（`:255/:269/:274/:279`、整改 `:336`）。
- 但 `violatorIdCard` 为手填身份证文本框（`:259-265`），与所选 `violatorId` 并存，存在手填与选择不一致风险。
- 姓名反规范化快照（`violatorName` 等）来自记录自身，员工离职/改名后历史记录姓名不过期刷新。

**③ 隐患治理（hazards）— ❌ 最严重**
- 混合使用：`EmployeeSelector`（`finderId`/`responsibleId`/`correctorId`/`reviewerId`，`:239-254`、整改 `:303`、复查 `:332`）与纯文本 `Input`（`checker` `:263`、`fixer` `:268`）——同一隐患内数据模型不一致。
- **致命缺陷**：`getEmployeeName(id)` 根本不解析姓名，仅返回 `员工${id}`（`index.vue:1402-1405`），详情抽屉调用 4 次（`:394/:398/:402/:406`），真实姓名从未显示。根因：hazards 从不调用任何员工查询 API。

**④ 培训考核（training）— 子模块间不一致**
- `ledger`/`execute` 的 `EmployeeSelector` 用法正确（`employeeId`/`trainerId`，`:143/:148`、`execute:57`+`mode="multiple"`）。
- `requirements`/`:98-100` 与 `plans`/`:161-162` **误用组件不支持的 `v-model:employee-id`/`v-model:employee-name`/`mode="position"`** → `positionId`/`trainerId` 恒为 `0`，关联未落库（功能级 bug）。
- `training/index.vue` 培训师为纯 `Input`（`trainer`，`:198/:532`），不与主数据关联。

**⑤ 事故管理（accidents）— ❌**
- 唯一人员字段 `handler` 为自由文本字符串（`index.vue:428-429`），无 `employeeId`、不调员工 API。员工调岗/离职后文本永久陈旧且无法回源。

**⑥ 应急管理（emergency）— ❌**
- 负责人/队长全为自由文本 `Input`（`responsiblePerson` `index.vue:346`、teams `leader_name:140`）。
- `teams/index.vue:239-240` 队员经 `request.get('/system/employees', {pageSize:999})` 拉取，该接口**非 HSE 主数据**，id 空间与主数据不可考证。

**⑦ 目标职责（objectives / goals）**
- `objectives/committee`：`personnelForm.name` 自由文本（`:125`），独立「安全人员」台账，与主数据完全重复脱钩。
- `goals`：`EmployeeSelector` 用法规范（`:212-216`），但 `@change` 把 `name` 反规范化存入 `responsiblePerson`（`:508-511`），快照陈旧。

**⑧ 月度考核（assessment-monthly）— ⚠️**
- **未用 `EmployeeSelector`**，考核对象靠手填 id 文本框（`addForm.employeeIds`，`targets.vue:130-134`），`split` 解析后批量提交（`:329-339`）——易错、无校验。
- 唯一亮点：提供 `handleSync`→`syncAssessmentTargets`（`:298-313`）手动对齐主数据，但仍需手触发。

**⑨ 保险管理（insurance）**
- `over-age` 唯一规范消费主数据（导入 `getOverAgeAutoList/Stats/Detail` from `employee.ts`，`:311-316`），基于 `birth_date` 实时查询。
- `personnel` 为独立人员台账（`name`+`idCard`），与主数据重复。

**⑬ 安全驾驶舱（cockpit）— ❌**
- `index.vue:211/223` 绕过 `cockpit.ts` 改用裸 `requestClient.get('/overview/stats')`/`'/overview/cards'`（前缀不一致，`cockpit.ts` 用 `/hse/dashboard/...`），**`cockpit.ts` 全部导出函数死代码**。
- 员工 TOP10 组件 `RiskTop.vue` 为孤儿组件（未被任何父组件 import），`emit('employeeClick')` 无人监听 → 「点击员工→画像」联动断链。

**⑭ 风险画像（risk-profile-detail）— 联动汇聚点**
- 正确读取 `route.params.employeeId`（`index.vue:110`），`watch` 重载；字段 `BasicInfo`（`risk-profile-detail.ts:14-30`）与 `employee.ts` 部分一致（`id`/`name`/`phone`）、部分不一致（`employeeCode`/`status`/`department`/`position`）。

**⑰ 预警整改中心（warning-center）**
- 人员以 `targetName`/`responsibleName` 后端预 join 字符串展示（`:683/:825`），无 EmployeeSelector、`targetId` 非 `employeeId`。
- 有 `goToSourceSystem`→`/hse-advanced/risk-profile/:targetId` 跳转（`:783-804`），但姓名本身不可点。

**⑱ 工作流引擎（workflow）— ❌**
- `assignee` 纯文本（`:273/:289`），零员工主数据关联，无跳转。

### 2.2 全局模式扫描结论
- **EmployeeSelector 采用地图**：goals、hazards、violations、training（ledger/execute/requirements/plans）共 7 个模块文件引用；warning-center / workflow / accidents / emergency / objectives / assessment-monthly 均未采用。
- **N+1 查询**：全 src **无**逐行循环调员工接口（正面项）；但缺少 `getEmployeesByIds` 批量端点，列表展示关联姓名时只能依赖后端 join 或各模块自行实现（hazards 实现坏掉）。
- **标识符命名分裂**：`employeeId`（前端主流）/ `employee_id`（选择器值·后端契约）/ `EmployeeItem.id` / 各业务表 `violatorId`/`finderId`/`employeeId`/`trainerId`/`responsiblePersonId` —— 同一数字主键多种命名。
- **点击姓名→档案**：除 risk-profile 系（driver-risk-center/executive-cockpit/warning-center）、accident-analysis 外，多数模块姓名不可点；且均跳「画像」而非「主档案」。

## 三、关键缺口分类（P0 / P1 / P2）

### P0 — 数据不一致，影响业务正确性

**P0-1 隐患模块姓名显示完全失效（❌）**
- 位置：`views/hazards/index.vue:1402-1405`（`getEmployeeName` 返回 `员工${id}`），调用点 `:394/:398/:402/:406`。
- 影响：隐患详情「发现人/责任人/整改人/复查人」全部显示为「员工123」，真实姓名从未获取；根因是模块从不调员工查询 API。
- 修复方向：复用 `EmployeeSelector` 的 `getEmployeeSelectorBatch` 做只读回显。

**P0-2 员工标识符字段命名不统一**
- 位置：`EmployeeItem.id`（employee.ts:23）/ `SelectorItem.employee_id`（employee-selector.ts:14）/ 前端 `employeeId` 主流 / 业务表 `violatorId`/`finderId`/`employeeId`/`trainerId`/`responsiblePersonId`（violations/hazards/training/goals 等）。
- 影响：同一数字主键多种命名；跨模块提交时字段名不一致（如 `finderId` vs `employeeId`），影响数据正确性与自动化解析。
- 修复方向：以 `employee_id`（数字）为唯一规范键，全模块收敛。

**P0-3 自由文本/独立源替代主数据，形成重复且陈旧台账**
- 位置：`accidents/index.vue:428-429`（`handler` 文本）、`emergency/*`（responsiblePerson/leader_name 文本 + teams 用 `/system/employees`）、`objectives/committee`（独立安全人员台账）、`insurance/personnel`（独立人员台账）。
- 影响：与主数据脱钩，员工离职/调岗后文本永久陈旧且无法回源；`/system/employees` 与主数据 id 空间不可考证。

**P0-4 安全驾驶舱 API 端点分叉 + 死代码 + 联动断链（❌）**
- 位置：`views/hse/cockpit/index.vue:211/223` 裸调 `/overview/stats`/`/overview/cards`；`cockpit.ts` 全部函数无调用方；`RiskTop.vue` 孤儿组件。
- 影响：员工 TOP10 榜单不挂载，「点击员工→画像」彻底断链；API 层与视图层端点分叉。

**P0-5 删除员工无引用校验（⚠️→P0 风险）**
- 位置：`views/hse/employee/index.vue:382-391`。
- 影响：删除员工后，violations/hazards/training 的外键悬空，形成脏数据。

**P0-6 状态枚举语义不一致**
- 位置：`employee-profile` 用 `active`/`inactive`（`index.vue:235/:372/:398`），`employee.ts` 用 `在职/离职/待岗/退休/返聘`。
- 影响：同一「在职/离职」语义两模块枚举不同，跨模块比对易错。

### P1 — 交互缺失，影响用户体验

**P1-1 点击姓名→档案联动缺失**
- 位置：violations（`:427/:440` 原始 id 无链接）、training（姓名快照）、accidents/emergency/objectives/insurance-personnel（纯文本姓名）、assessment-monthly、warning-center（`targetName`/`responsibleName` 不可点 `:683/:825`）、workflow（`assignee` 不可点 `:273/:289`）。
- 影响：员工不可追溯，审计/追责困难。

**P1-2 员工调岗/离职无前端联动刷新**
- 位置：violations/training/hazards/goals 的姓名反规范化快照；仅 assessment-monthly 有手动 `syncAssessmentTargets`（`:298-313`）。
- 影响：在职期间改名/调岗后，历史记录姓名/部门陈旧。

**P1-3 离职/调岗人员在风险看板前端未过滤**
- 位置：`driver-risk-center`/`executive-cockpit` 高风险/TOP 名单为服务端一次性聚合，前端无 `org_status` 过滤；`risk-profile-detail/BasicInfo.vue:33` 展示 `status` 但无「已离职」强提示。
- 影响：离职/调岗人员可能继续出现在风险看板。

### P2 — 代码重复，影响可维护性

**P2-1 `EmployeeSelector` 误用（功能 bug）**
- 位置：`training/requirements/index.vue:98-100`、`training/plans/index.vue:161-162` 误用 `v-model:employee-id`/`v-model:employee-name`/`mode="position"`（组件无这些 props）→ `positionId`/`trainerId` 恒为 0。
- 影响：岗位/培训师关联未落库。

**P2-2 姓名字段反规范化快照普遍**
- 位置：violations（`violatorName` 等）、training（ledger `name/department/position` `:421-425` 选人后无 `@change` 回填）、goals（`responsiblePerson`）、assessment-monthly（`employee_name/code`）、accidents（`handler`）、emergency、objectives、insurance-personnel。
- 影响：需明确「快照为有意设计」或「展示时回查主数据」的规范。

**P2-3 重复人员台账**
- 位置：objectives/committee、insurance/personnel、emergency/teams（`/system/employees`）——与主数据重复建人员库。

**P2-4 死代码**
- 位置：`employee.ts:268` `getEmployeeDetail` 全仓零调用；`employee-selector.ts:48` `getEmployeeSelectorById` 零调用；`cockpit.ts` 全部导出函数零调用。

## 五、消费层设计建议（优先级排序）

1. **统一标识符为 `employee_id`（数字）**：全模块收敛 `EmployeeItem.id`/`employee_id`/`employeeId`/业务字段名，作为跨模块唯一键（对应 P0-2）。
2. **建设 `getEmployeesByIds(ids)` 批量端点 + 前端内存缓存**：消除「只存 id 要显示姓名时各模块各自实现」的混乱（hazards 因此坏掉），替代后端 join 或死代码 `getEmployeeDetail`（对应 P2-4 / N+1 隐患）。
3. **公共 Composable**：`useEmployeeData` / `useEmployeeEvent` / `useEmployeeLink` / `useEmployeeSearch` —— 封装统一取数、事件订阅、姓名跳转、搜索（对应 P1-1 / P2-2）。
4. **EmployeeSelector 增强**：统一 props、修复误用（`training/requirements`/`plans`）、向后兼容（opt-in），引导脱钩模块（accidents/emergency/objectives/assessment-monthly）迁移（对应 P0-3 / P2-1）。
5. **统一 API 规范**：查询/批量/统计接口请求响应格式标准化，`EmployeeInfo` 类型统一（对应 P0-2 / P2-3）。
6. **模块间数据依赖声明**：`employee-deps.json` 声明 `dependsOn`/`provides`，支撑影响分析与回归测试（对应 P0-2 / P2-3）。
