# 指标取数配置化改造 —— 设计与实施（第一步）

> 对应主线：把「评分需要从各业务模块取数」的硬编码耦合，抽成「插一行配置」的声明式取数。
> 本次只做**第一步**（指标取数配置化 + 引擎配置驱动），不动业务口径、不动三违活源聚合。

## 0. 口径变更记录（2026-10-13 · A 方案口径清理）

> ⚠️ 本改造首版（2026-10-13 早）曾把 `accident` 否决源 seed 进配置表（NEG-001/002/003），
> 但该口径已被淘汰，生产实际由规则引擎 `accidentVetoAdapter`（**NEG-004**）独家承担。
> 经核实生产数据后，当日即做 A 方案清理：事故否决**彻底移出**配置表 / legacy 路径。

**核实结论（生产 `safety_dashboard` 只读 SELECT）**：
- `HSE-KPI-NEG-004`（规则引擎现行口径）：**18 行**（active 13 + 已删 5），横跨 7 个考核周期（2025-09 ~ 2026-03），真实投产。
- `HSE-KPI-NEG-001/002/003`（首版 config 声称口径）：**0 行**，phantom code，从未产生。

**清理动作（已落地代码 + SQL）**：
1. 引擎 `getMetricSources` 对 `source_name='accident'` **硬排除**（即便 DB 行被重新启用或误翻 env，也绝不走 config 路径生成 NEG-001/002/003）。

5. 单测同步修订（accident 不再走 config/legacy 路径）。

**唯一遗留风险已消除**：旧「误翻 `LEGACY_ACCIDENT_VETO=true` 会让 config 的 NEG-001/002/003 与规则引擎 NEG-004 并存 → 同事故双扣」的陷阱被根除。

## 1. 痛点与诊断（源码级，已核查）

`server/services/assessmentScoringEngine.js` 的「跨模块取数」真实只有 3 个来源，耦合方式各异：

| 来源 | 代码位置 | 取数方式 | 耦合点 |
|---|---|---|---|
| 培训不合格 | `FILL_SOURCES.training`（原第 624 行） | 直查 `training_records` 表（硬编码 SQL） | 引擎直接写死业务表 + 字段 |
| 事故否决 | `FILL_SOURCES.accident`（原第 629 行） | 直查 `accidents` 表，带 `accident_type → 指标` 映射 | 引擎直接写死业务表 + 映射分支 |
| 三违扣减 | `computeCategoryCappedScore` 调 `getEmployeeSanweiTotal`（原第 369 行） | 调 `violationAssessmentService`（service 接口） | 已通过 service 解耦，**本次不动** |

**根因**：评分引擎把「取数来源（哪个业务表、什么条件、扣几分、是否否决）」写死在代码里。
新增一个评分数据源（保险 / 转运站 / 隐患 …）就要改引擎代码、加 `FILL_SOURCES` 条目、加映射分支。

---

## 2. 设计目标

1. **取数与引擎解耦**：新增评分数据源 = 往配置表插一行，引擎零改动。
2. **语义零漂移**：配置表的 seed 值 = 原 `FILL_SOURCES` 逐字节口径；配置表未 seed 时自动回退原硬编码逻辑。
3. **保留现有开关**：`LEGACY_TRAINING_FILL` 环境变量仍控制 training 源（设 `false` 即停用）。事故否决已移出配置表 / legacy 路径（归规则引擎 NEG-004），`LEGACY_ACCIDENT_VETO` 已无作用（见 §0）。
4. **保留三违活源**：`getEmployeeSanweiTotal` 已走 service 接口，本次不触碰。

## 3. 方案概览

- **新建表** `hse_assessment_metric_source`：声明每个评分数据源（`source_table` / `filter_expr` / `agg_type` / `fixed_score` / `is_veto` / `veto_metric_map` / `item_template` / `enabled`）。
- **引擎改造**：`assessmentScoringEngine.js` 新增 `getMetricSources()` / `fetchSourceRows()` / `renderItem()` / `resolveVetoMetric()`，把 `fillMissingDeductionsForTarget` 改为配置驱动；原硬编码逻辑原样保留为 `fillMissingDeductionsLegacy()` 作回退。
- **交付物**：
  - `server/sql/assessment_metric_source_config.sql`（建表 + 幂等 seed）
  - `server/services/assessmentScoringEngine.js`（已改，语法校验通过）

## 4. 配置表结构（`hse_assessment_metric_source`）

| 列 | 类型 | 含义 |
|---|---|---|
| `metric_code` | varchar(64) | 兜底/默认关联指标（关联 `hse_assessment_metric.metric_code`） |
| `source_name` | varchar(64) UNIQUE | 唯一键，如 `training` / `accident` |
| `source_type` | varchar(16) | `sql`（直查业务表，本期支持）/ `service`（调 service 函数，预留） |
| `source_table` | varchar(64) | 业务表名 |
| `filter_expr` | text | WHERE 片段，占位 `$1=employeeId` `$2=start` `$3=end` |
| `agg_type` | varchar(16) | `row`（逐行生成明细，本期）/ `count` / `sum`（预留） |
| `fixed_score` | numeric(10,2) | `row` 类型时每行固定扣分 |
| `is_veto` | bool | 是否否决项（命中总分归 0） |
| `map_column` | varchar(64) | 否决项：按该列值映射到指标 |
| `veto_metric_map` | jsonb | `{ 列值: metric_code, "default": metric_code }` |
| `item_template` | varchar(128) | 扣分明细文案，支持 `{列名}` 占位 |
| `enabled` | bool | 开关（env 可最终覆盖） |

## 5. FILL_SOURCES → 配置表 映射清单（seed 值 = 原口径）

| 原 `FILL_SOURCES` 键 | source_name | source_table | filter_expr（节选） | fixed_score | is_veto | 映射 |
|---|---|---|---|---|---|---|
| `training` | `training` | `training_records` | `employee_id=$1 AND result='不合格' AND training_date>=$2 AND training_date<=$3 AND is_deleted=FALSE` | 3 | 否 | — |
| `accident` | `accident` | `accidents` | `personnel_id=$1 AND accident_date>=$2 AND accident_date<=$3 AND is_deleted=FALSE` | 100 | 是 | `交通事故→HSE-KPI-NEG-002`；`环境污染事故→HSE-KPI-NEG-003`；其它→`HSE-KPI-NEG-001` |

原 `makeItem()`：`training` → `'培训不合格1次'`；`accident` → `` `${accident_type}（否决项）` `` → 现用 `item_template`（`{accident_type}（否决项）`）实现，等价。

## 6. 引擎改造要点（语义零漂移保证）

1. **回退链路**：`fillMissingDeductionsForTarget`（新）先 `getMetricSources()`；若配置表无 `enabled` 数据，直接 `return fillMissingDeductionsLegacy(...)`，走原硬编码逻辑，**未 seed 时行为完全一致**。
2. **幂等不变**：生成明细仍走 `addAutoDeduction()`，其内置 `findAutoDeduction()` 按 `source_table + source_id + metric_code` 去重，与原 `hasKey` 优化互不冲突。
3. **env 开关保留**：`getMetricSources()` 对 `training` 应用 `LEGACY_FILL_ENABLED` 覆盖，`LEGACY_TRAINING_FILL=false` 等同原「停用培训补扣」；`accident` 源已被硬排除（见 §0）。
4. ~~**否决映射等价**：`resolveVetoMetric()` 实现原 `accident_type → HSE-KPI-NEG-00x` 三元映射。~~（A 方案口径清理后，事故否决不再走配置表路径，该映射已废止；规则引擎 `accidentVetoAdapter` 按事故类别/性质判定 NEG-004。）

**验证方法（受控注入，类比项目 WPS-PG-SYNC-05-C 的受控变更纪律）：**
- dev 克隆库所有周期对考核对象均**无任何**「不合格培训 / 事故」记录，故回填逻辑无数据可跑、空比对无意义。

**零漂移比对结果：PASS ✅**
- 配置驱动版 `fillMissingDeductionsForTarget` 与原硬编码版 `fillMissingDeductionsLegacy` 对同一样本各生成 4 行，逐字段（`source_table / source_id / metric_code / suggested_score / deduction_item`）完全一致。
- 事故类型→否决指标映射正确：`交通事故→HSE-KPI-NEG-002`、`环境污染事故→HSE-KPI-NEG-003`、其它→`HSE-KPI-NEG-001`。
- 培训：`HSE-KPI-TRN-002` / 扣 3 分 / 文案「培训不合格1次」。
- dev 已还原：backfill 明细 0 行、注入业务行 0 行。

**⚠️ 验证中发现并修复的 latent bug（重要）：**
- `addAutoDeduction()` 的参数名是 `deductionItem`，但 legacy 两处（培训 / 事故）与本次新增的 config 路径都把参数写成了 `item:` → 落入 `deduction_item` 列时恒为 `NULL`，触发 `NOT NULL` 约束报错。
- 后果：legacy 培训/事故回填**一直是"死路"**——只要出现一条不合格培训或事故就会崩溃（与项目自述"无测试覆盖、业务口径未拍板"一致，此前因数据为零一直没暴露）。
- 本次把 3 处统一改为 `deductionItem:`，既修好配置驱动路径，也修好 legacy 回退路径（使回退口径正确，A/B 才有意义）。`assessmentEventService.js` 的调用方本就用 `deductionItem: item`，无需改。
- 该 bug 属**预先存在**于 shipped legacy 代码，非本次引入；修复是验证顺带暴露并消除的真实隐患。

**生产生效：** 用户已授权对生产库跑 DDL（建表 + seed，仅 training）。事故否决归规则引擎 NEG-004，配置表不再含 accident 源，**不存在重复扣分风险**。若生产既有库已存在 accident 源，另跑 `assessment_metric_source_remove_accident.sql` 将其 `is_deleted=TRUE`（幂等、纯 UPDATE）。

```sql
INSERT INTO hse_assessment_metric_source
  (metric_code, source_name, source_type, source_table, filter_expr, agg_type, fixed_score, item_template, enabled, sort_order)
VALUES
  ('HSE-KPI-INS-001','insurance_uninsured','sql','insurance_records',
   'employee_id = $1 AND insured = FALSE AND insured_date >= $2 AND insured_date <= $3 AND is_deleted = FALSE',
   'row', 2, '保险未投保1次', TRUE, 30);
```
**引擎无需改动**。
