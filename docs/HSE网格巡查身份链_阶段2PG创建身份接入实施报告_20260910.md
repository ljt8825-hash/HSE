## 三、POST 创建链路改造前后

### 改造前（PG 分支）

```text
POST /api/site-mgmt/grid-records
  → gridDataSourceMode() === 'wps' ? WPS 分支 : PG 分支
  → PG: 遍历 GRID_RECORD_CREATE_CAMELS 白名单取 body 字段
  → INSERT INTO grid_inspection_records (...)   ← 无任何身份字段
```

### 改造后（PG 分支）

```text
POST /api/site-mgmt/grid-records
  → gridDataSourceMode() === 'wps' ? WPS 分支（未改动）: PG 分支
  → 【新增】剥离 body.inspectorEmployeeId / body.inspector_employee_id
  → 【新增】resolveAuthenticatedEmployeeFromRequest(req)
        ├─ 失败 → res.status(httpStatus).json(error(...)); return   ← fail-closed，不 INSERT
        └─ 成功 → identity.employeeId
  → 遍历白名单取 body 字段（身份不来自 body）
  → 【新增】cols.push('inspector_employee_id'); params.push(identity.employeeId)
  → INSERT
```

WPS 分支（`gridWps.create({ user: req.user, ... })`）**保持原样**，仍用旧 `currentEmployeeContext` 姓名兜底链路——按阶段2 边界要求，WPS 旧链迁移不属于本阶段。

## 五、inspector_employee_id 写入机制

```js
// 后端派生身份：DB.inspector_employee_id 恒等于 resolver.employeeId
cols.push('inspector_employee_id');
params.push(identity.employeeId);
```

保证：

- 值**只**来自 `identity.employeeId`，不来自 body / query / header / realName；
- 代码中**不存在** `body.inspectorEmployeeId || employeeId` 或 `?? employeeId` 形式的回退；
- 位置在 `if (!cols.length)` 校验之后，保证身份列一定随业务字段一起入库。

## 六、request body 身份字段防覆盖验证

三重防护：

1. **显式剥离**（新增）：
   ```js
   delete body.inspectorEmployeeId;
   delete body.inspector_employee_id;
   ```
   客户端无论以 camelCase 还是 snake_case 提交，都被直接丢弃，绝不作为可信来源。
2. **白名单不含身份列**：`GRID_RECORD_CREATE_CAMELS`（22 字段）中本就没有 `inspectorEmployeeId` → 映射循环不会产出该列。
3. **身份列由后端追加**：唯一写入点是 `params.push(identity.employeeId)`。

**实测（绑定 A=6692，伪造 B=6693）**：

| 用例 | 请求体 | HTTP | DB 实际值 |
|---|---|---|---|
| Case4 | `inspectorEmployeeId: 6693` | 200 | **6692（=A）** |
| Case5 | `inspector_employee_id: 6693` | 200 | **6692（=A）** |

## 十六、已知观察项（仅记录，未修改）

1. **【重要·生效前提】** 账号未绑定 `employee_id` 时，PG 新建巡查将**一律 403 拒绝**。当前唯一账号 `admin` 的 `employee_id` 为 NULL → **阶段4 完成账号绑定前，PG 分支的新建功能对 admin 不可用**。这与 fail-closed 设计一致，但上线/联调时必须先完成绑定，或明确接受该行为。
2. **【生产配置】** 当前 `WPS_GRID_DATA_SOURCE=true`，实际流量走 WPS 分支，**PG 分支的本次改造在生产上暂不会被触发**；其价值在数据源切回 PG 或 WPS 链路迁移后生效。
3. **【口径不一致】** POST 白名单用 camelCase、PUT 白名单用 snake_case（见 §七）。
4. **【遗留】** `site-mgmt.js:1534` GET 列表仍为 `SELECT *`，响应会多带 `inspector_employee_id`（阶段0 已记录，良性）。
5. **【事务边界】** PG 创建为单条 INSERT、无事务。当前「身份解析 → INSERT」两步间无并发风险（解析只读、INSERT 单条）；若未来创建流程扩展为多步写入，需届时补事务。
6. **【对阶段1报告的订正】** 阶段1 报告中以 `git diff` 为空作为「未修改」的证据，实际上 `server/` 在本仓库为 untracked 状态，`git diff` 对其不适用。本阶段已改用文件修改时间（mtime）作为客观证据。结论本身不受影响（阶段1 确实未改既有文件），仅证据方式需订正。
