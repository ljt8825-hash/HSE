## 三、RBAC 运行时权威模型（回答问题 1）

### 3.1 权威链路实证

```text
Authorization: Bearer <JWT>
      ↓
app.use('/api', authMiddleware)                 ← app.js:246 全局唯一认证挂载
      ↓
resolveAuthentication(authHeader, {checkUser:true})   ← middleware/auth.js:221
      ↓
SELECT id, username, role, real_name, is_active FROM users WHERE id = $1   ← auth.js:170-173
      ↓
req.user = { id, username, role: row.role, realName, jti }   ← auth.js:181-187
      ↓
requirePermission(code) → getPermissionsForRole(req.user.role)   ← auth.js:459
      ↓
ROLE_PERMISSIONS_MAP[role]（代码内静态对象）   ← auth.js:371-431
```

### 3.2 结论：谁是权威

| 候选 | 是否运行时权威 | 证据 |
|---|---|---|
| `ROLE_PERMISSIONS_MAP`（代码静态） | ✅ **权限码权威** | `auth.js:439-441` 直接查该对象，不查任何表 |
| `public.users.role` 列 | ✅ **角色权威** | `auth.js:184` 用库中角色**覆盖** JWT 里的 role，防令牌内角色漂移 |
| `public.roles` 表 | ❌ 非权威 | 全库检索：`requirePermission`/`getPermissionsForRole` 从未 JOIN 该表 |
| `public.user_role` 表 | ❌ 非权威 | 仅 1 行（admin→role 1），无代码读取其做鉴权 |
| `public.role_menu` 表 | ❌ 非权威 | 98 行，仅驱动菜单可见性 |
| JWT payload 内的 role | ❌ 非权威 | 被 `checkUser:true` 的库查询覆盖 |

**唯一权威模型**：

```text
功能权限 = ROLE_PERMISSIONS_MAP[ users.role ]
数据范围 = 不存在（全系统零实现，见第九节）
```

### 3.3 `users.role` 的约束状态（影响方案可行性）

```sql
-- 实测
SELECT conname FROM pg_constraint WHERE conrelid='public.users'::regclass
  AND (contype='f' OR contype='c');
-- 结果：[]（空）
```

- `users.role` 为 `character varying`，**无外键、无 CHECK 约束**
- 含义：可直接写入 `hse_manager` / `safety_manager` / `township_manager` / `system_admin` 等代码 MAP 支持的角色，即使 `roles` 表中不存在对应行
- 风险：写入 `roles` 表不存在的角色时，**角色管理界面与菜单配置（`role_menu`）将缺失该角色**，形成"后端有权限、前端看不到菜单"的半残状态
- 阶段3-A 仅记录，不修改

## 五、现有权限码体系（回答问题 3）

### 5.1 命名体系（两套并存）

| 体系 | 形态 | 使用者 | 示例 |
|---|---|---|---|
| **后端接口权限码** | `hse:<模块>:<动作>` | `requirePermission()` | `hse:site:create`、`hse:site:grid:view` |
| **菜单权限码** | `hse:<模块>:<页面>` | `menus.permission` 字段 | `hse:site-mgmt:grid`、`hse:site-mgmt:view` |

两者**命名不互通**：`hse:site:grid:view`（后端） vs `hse:site-mgmt:grid`（菜单）。实测 `menus` 表含 55 个不同 permission 值，全部为菜单口径。

### 5.2 现场管理（`hse:site:*`）权限码全表

**查看类**

| 权限码 | 授予角色 |
|---|---|
| `hse:site:view` | hse_manager / safety_manager / admin / township_manager / manager |
| `hse:site:violations:view` | 同上（viewer 无） |
| `hse:site:grid:view` | 同上 |
| `hse:site:fire:view` | 同上（manager 无） |
| `hse:site:vehicles:view` | 仅 HSE_MANAGER 组 |
| `hse:site:inspection:view` | 同上 |

**操作类**

| 权限码 | 授予角色 |
|---|---|
| `hse:site:create` | hse_manager / safety_manager / admin / township_manager / manager |
| `hse:site:update` | 同上 |
| `hse:site:delete` | 同上 |
| `hse:site:export` | 仅 HSE_MANAGER 组 |
| `hse:site:import` | 仅 HSE_MANAGER 组 |
| `hse:site:freeze` | 仅 HSE_MANAGER 组 |

### 5.3 关键缺陷：网格无专用操作码

现场管理下挂 4 个子业务（三违 `violations` / 网格 `grid` / 消防 `fire` / 车辆 `vehicles`），但**操作类权限码只有模块级的 `hse:site:create/update/delete`**。

后果：持有 `hse:site:delete` 的人，等价于同时拥有"删三违 + 删网格 + 删消防"的权限，无法做子业务隔离。

| `routes/hse-employee.js` | 71 |
| `routes/hse-assessment-monthly.js` | 25 |
| `routes/hazards.js` | 9 |
| `routes/hse-risk-profile.js` | 2 |
| **`routes/site-mgmt.js`** | **0** |

→ 现场管理模块是权限覆盖的"洼地"。

## 八、网格负责人 vs 实际巡查人员（回答问题 9、10）

### 8.1 字段名修正（**用户预设与实际的差异**）

用户任务书假设的关系链为：

```text
users.employee_id → employee.id → grid_areas.personnel_id → grid_inspection_records.grid_area_id
```

**实测结果**：`grid_inspection_records` **不存在 `grid_area_id` 列**。实际列为 **`grid_id`**，且存在正式外键约束：

```sql
-- information_schema 实测
from_table=grid_inspection_records, from_col=grid_id
  → to_table=grid_areas, to_col=id      ✅ 正式 FOREIGN KEY
```

**修正后的权威链路**：

```text
users.employee_id
   ↓
employee.id
   ↓
grid_areas.personnel_id        （网格负责人）
   ↓
grid_areas.id
   ↓
grid_inspection_records.grid_id  （非 grid_area_id）
```

### 8.2 链路可用性实测

| 指标 | 值 | 说明 |
|---|---|---|
| `grid_areas` 总数 | 62 | — |
| `personnel_id` 非空 | **62 / 62** | 无空缺 |
| `personnel_id` 去重数 | **62** | **一人一网格，无重复** |
| JOIN `employee` 命中 | **62 / 62** | 无孤儿 |
| 负责人 `is_deleted=true` | **0** | 全部在册有效 |
| 一人多网格 | **0 组** | `multiGridOwners` 为空 |

→ **scope 判定唯一且可靠**：一个 `employee_id` 最多映射到一个网格。

### 8.3 记录归属覆盖率（决定性数据）

| 指标 | 值 | 占比 |
|---|---|---|
| 记录总数 | 2051 | 100% |
| `grid_id` 非空 | **1724** | 84.1% |
| `grid_id` IS NULL | **327** | 15.9% |
| 可归属到负责人 | **1724** | 100%（在有 grid_id 的记录中） |

327 条无归属记录的时间分布：

```text
2026-09 → 327 条（全部）
```

→ 与 WPS-03-B EXECUTE 迁入批次吻合（2026-09-09 迁入 327 条）。**WPS 数据源不携带网格外键**，故迁入时 `grid_id` 为空。

### 8.4 网格层级分布（影响角色设计）

| grid_level | 数量 |
|---|---|
| 三级网格长 | 45 |
| 二级网格长 | 11 |
| 一级网格长 | 5 |
| 总网格长 | 1 |

→ 金字塔结构。`township` 字段 61/62 为 NULL，说明网格体系与乡镇行政维度**不是同一套划分**。

### 8.5 两个概念的关系裁定（回答问题 10）

| 维度 | 字段 | 语义 | 是否可作 scope |
|---|---|---|---|
| 网格负责人 | `grid_areas.personnel_id` | 该网格的责任人 | ✅ **推荐** |
| 实际巡查人 | `grid_inspection_records.inspector_employee_id` | 当次巡查的执行人 | ❌ 现阶段不可用（0 条填充） |

**明确规则**：

1. **不要求** `inspector_employee_id = grid_areas.personnel_id`。允许"负责人 A、巡查人 B"。
2. **scope 以网格负责人为准**：用户能看的记录 = 其负责网格下的全部记录（无论谁巡查）。
3. **理由**：`inspector_employee_id` 当前 0 条填充（实测 `filled=0`），历史 2051 条全部为 NULL，若以巡查人为 scope，则全部历史记录对所有人不可见。
4. 姓名匹配**禁止**作为 scope 依据 —— 实测 `personnel_name` 与负责人姓名匹配 1722/1724，**存在 2 条不一致的反例**，与阶段0「新链禁姓名兜底」决策一致。

### 8.6 ⚠ 关键阻断项：新建记录无网格归属

```js
// routes/site-mgmt.js:255-278
const GRID_RECORD_CREATE_CAMELS = {
  areaTeam, inspectionDate, personnelName, gridLevel, position,
  violatorName, violatorGender, violatorAge, vehicleType, reportStatus,
  imageContent, violationBehavior, violationTypeResult, needRectification,
  rectifier, rectifiedPhoto, schematic, nickname, signupToday,
  marker, isResubmit, serialNo,
};
// ❌ 不含 gridId / grid_id
```

**后果**：阶段2 之后通过 PG 新建的每一条记录，`grid_id` 恒为 NULL。若直接启用 grid scope，网格负责人将**看不到自己刚创建的记录**。

**同时 `GRID_RECORD_EDITABLE`（L247-252）也不含 `grid_id`** → 事后无法补全。

**三种解法（阶段3-B 决策用）**：

| 方案 | 做法 | 优劣 |
|---|---|---|
| **A（推荐）** | POST 时后端派生：按 `inspector_employee_id` 反查 `grid_areas.personnel_id = 本人` 取 `grid_id` 写入 | 与阶段2 身份派生同思路，客户端不可伪造；一人一网格保证唯一；非网格负责人账号需定义降级策略 |
| B | 客户端传 `gridId`，后端校验其 `personnel_id` 等于当前用户 | 需新增白名单字段，引入伪造面 |
| C | scope 改用 `inspector_employee_id` | 历史 2051 条全 NULL，不可行 |

## 九、行级数据范围现状（回答问题 8、11）

### 9.1 现状：全系统零数据范围机制

| 检索项 | 结果 |
|---|---|
| 表名含 `scope` / `data_range` / `owner` / `filter_rule` | **0 张** |
| `users` / `roles` 表含 scope 列 | **无** |
| 代码中 `dataScope` / `rowScope` / `organization scope` | **0 处命中** |
| `getGridDataSourceMode()` | 仅判定 WPS/PG 数据源，**与权限无关** |

→ 项目当前**只有功能权限，没有任何数据范围概念**。这是全新能力，不是改造。

### 9.2 GET / POST / PUT / DELETE 是否应统一（回答问题 11）

**是，必须统一**。依据：

| 端点 | 若不统一的后果 |
|---|---|
| GET 做了 / PUT 没做 | 看不到但能改 → 越权修改 |
| GET 做了 / DELETE 没做 | 看不到但能删 → 越权删除 |
| PUT 做了 / DELETE ALL 没做 | 行级限制被批量接口绕过 |

**统一原则**：同一个 `scope` 条件，列表/详情/修改/删除四处复用同一段 SQL 片段。

### 9.3 建议的三维数据范围

| 范围码 | 含义 | 判定条件 | 建议授予 |
|---|---|---|---|
| `all_grid` | 全部网格 | 无附加条件 | `system_admin` / `admin` / `hse_manager` / `safety_manager` |
| `org_grid` | 本组织网格 | 预留（当前 `township` 字段 61/62 为空，**暂不可实现**） | 暂不启用 |
| `own_grid` | 本人负责网格 | `grid_areas.personnel_id = :employeeId` | 62 位网格负责人 |

### 9.4 `grid_id IS NULL` 记录的处理（必须裁定）

327 条无归属 + 未来新建记录（若不解 8.6 阻断项）。建议：

```text
own_grid 可见集合 = (grid_id ∈ 本人负责网格)
                 ∪ (grid_id IS NULL AND 记录创建者 = 本人)   ← 可选放宽，见下
```

| 策略 | 做法 | 影响 |
|---|---|---|
| 严格（推荐先采用） | `grid_id IS NULL` 的记录仅 `all_grid` 可见 | 327 条历史对网格长不可见；新建记录若未派生 grid_id 也对创建者不可见 |
| 放宽 | 追加 `OR (grid_id IS NULL AND inspector_employee_id = :employeeId)` | 需先解决 8.6 派生问题，且历史 327 条因 `inspector_employee_id` 为 NULL 仍不可见 |

→ **8.6 的后端派生 `grid_id` 是行级 scope 的必要前置**。

## 十、角色方案比较（回答问题 6）

### 10.1 62 位网格负责人画像

### 10.2 方案 A：复用现有角色

**候选**：`township_manager`（乡镇/单位负责人）

| 维度 | 分析 |
|---|---|
| 已有权限 | `hse:site:grid:view` ✅ + `hse:site:create/update/delete` ✅ |

### 10.3 方案 B：新增最小权限角色

**候选命名**（遵循现有 snake_case 体系）：`grid_inspector` 或 `grid_manager`

| 维度 | 分析 |
|---|---|
| 命名合规性 | ✅ 符合 `system_admin`/`safety_manager`/`township_manager` 的 snake_case 体系 |
| 最小权限设计 | 仅授予 `hse:site:grid:view/create/update/delete` + `hse:overview:view`，其余一律不给 |
| 优点 1 | 精确表达"网格巡查人员"，不与乡镇负责人混淆 |
| 优点 2 | 可为该角色单独配置 `own_grid` 数据范围，不影响其他角色的 `all_grid` |
| 优点 3 | 层级可通过"附加 `all_grid` 范围"单独授予（如总网格长） |
| 缺点 1 | 需同步 3 处：`roles` 表新增行、`ROLE_PERMISSIONS_MAP` 新增键、`role_menu` 配置 |
| 缺点 2 | 前端 `authority:['admin']` 需追加该角色（本阶段不做） |

### 10.4 推荐：**方案 B —— 新增 `grid_inspector`**

**理由**：

1. 62 位网格长是一线操作岗，不是乡镇管理岗。给 `township_manager` 等于把"隐患全量删除、风险创建"等管理权限发给 62 个一线人员，风险显著大于收益。

3. 网格长存在 4 级层级（1/5/11/45），需要一个专属角色承载"按层级授予不同数据范围"的能力。
4. 方案 B 可增量启用：先建角色不分配，待阶段4 账号初始化时批量绑定，对现有 admin 零影响。

**裁定**：

## 十二、行级权限落点设计（回答问题 11 续）

### 12.1 现有架构事实

`routes/site-mgmt.js`（83KB）为**路由直写 SQL** 模式：

- 无 service 层（除 WPS 的 `gridInspectionRepository`）
- 无 repository 层（PG 分支直接 `pool.query`）
- SELECT/INSERT/UPDATE/DELETE 各写各的 WHERE

→ 强行引入三层架构 = 大规模重构，**违反阶段3「最小修改」纪律**。

### 12.2 三个候选落点比较

| 落点 | 可行性 | 能否覆盖全部 6 端点 | 改动量 |
|---|---|---|---|
| **route middleware** | 中间件无法改写 SQL；DELETE ALL 无 WHERE 可注入 | ❌ 只能做功能权限 | 小但不够 |
| **service 层** | 当前无 service 层，需新建 | ✅ | 中（需抽 6 处逻辑） |
| **repository SQL** | 当前无 repository 层 | ✅ | 大 |
| **`buildGridScope` 工具函数 + 端点内调用**（推荐） | 不改架构，复用现有拼接点 | ✅ | **最小** |

### 12.3 推荐落点：单一 scope 构造函数

```text
新增：server/services/gridScope.js（纯函数，无副作用）
  ├─ resolveGridScope(identity) → { mode: 'all_grid'|'own_grid', sql, params }
  └─ 返回可直接拼进 WHERE 的片段

调用方（routes/site-mgmt.js 6 处）：
  GET 列表   → WHERE <filters> AND <scope>
  PUT        → UPDATE ... WHERE id=$n AND <scope>       ← 防越权改
  DELETE     → DELETE ... WHERE id IN (...) AND <scope> ← 防越权删
  DELETE ALL → 拒绝 own_grid（仅 all_grid + purge 权限）
  POST       → 后端派生 grid_id（8.6 方案 A）
```

**关键防护**：PUT/DELETE 把 scope 条件**拼进同一条 SQL 的 WHERE**，而非"先查后判"。这样天然避免"GET 做了 scope、PUT 没做"的漏洞，也避免 404 信息泄露（越权表现为 0 行影响，而非"无权限"提示）。

### 12.4 一致性保证

```text
同一段 scope SQL 片段 → 列表/修改/删除三处复用同一函数调用
```

任何新增端点若忘记调用，将**查全量**（fail-open）。因此建议阶段3-B 配套一个回归测试：对每个端点用 `own_grid` 账号越权访问他人网格记录，断言影响行数为 0。

## 十四、阶段4 依赖与上线顺序（回答问题 14、15）

### 14.1 admin 当前状态实证

```sql
SELECT id, username, role, employee_id, is_active FROM public.users;
-- → id=1, username=admin, role='admin', employee_id=NULL, is_active=true
```

### 14.2 admin.employee_id=NULL 的三重影响

| 影响面 | 说明 |
|---|---|
| **阶段2 fail-closed** | PG 新建时对 admin 返回 **403 EMPLOYEE_NOT_BOUND**。当前生产 `WPS_GRID_DATA_SOURCE=true` 走 WPS 分支，故暂不触发；一旦切 PG 或 admin 手动新建 → 直接失败 |
| **行级 scope** | 若 admin 无 `employee_id`，`own_grid` 无法判定；但 admin 属 `all_grid`，可绕过 scope，故不阻断 |
| **阶段4 账号初始化** | 62 位网格长账号必须先有 `employee_id` 绑定，否则全部 403 |

### 14.3 上线顺序裁定（回答问题 14）

```text
阶段4（账号初始化 + employee_id 绑定）
   ↓ 必须先于
阶段3-B 的 scope 上线 + PG 数据源切换
```

**理由**：

1. 阶段2 已使 PG 创建链 fail-closed。若先上 scope / 先切 PG，而 62 个账号尚未绑定 `employee_id`，将出现"所有人无法新建 + 看不到任何记录"的全面瘫痪。
2. admin 自身 `employee_id` 也需在阶段4 一并处理，否则 admin 在 PG 分支同样 403。

### 14.4 建议发布批次

| 批次 | 内容 | 前置 |
|---|---|---|
| 批次 1 | B-1/B-2/B-3（功能权限 + DELETE ALL 收紧） | 无。可独立上线，对 admin 无影响（admin 有 `*`） |
| 批次 2 | 阶段4：62 账号创建 + `employee_id` 绑定（含 admin） | 需用户确认花名册映射 |
| 批次 3 | B-4/B-5/B-6（scope）+ 新增 `grid_inspector` 角色 | 批次 2 完成 |
| 批次 4 | PG 数据源切换（`WPS_GRID_DATA_SOURCE=false`） | 批次 2、3 完成 + WPS 身份链迁移评估 |

→ **批次 1 可提前独立上线**，因为它只收紧不放松，且 admin 走 `['*']` 通配符不受影响。这是风险最低的先行项。
