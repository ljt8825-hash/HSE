## 端点覆盖（12 条，挂载 `/api/hse/tasks`）
> 本域注册在 `/api` 全局 `authMiddleware` 之后，**原文件无 requireRole / requirePermission 写保护**，故不追加鉴权，忠实复刻（已认证角色即可读写）。端点按原文件注册顺序列出。
| 端点 | 说明 |
|------|------|
| `GET /` | 任务列表（task_type/status/responsible_person/department 过滤 + 分页） |

## ⚠️ 既有缺陷点：单段 GET 被 `/:taskId` 遮蔽（原文件即有，予以保留）
原文件路由顺序为 `GET /` → `GET /:taskId` → … → `GET /inspection|pending|overdue`。因后三条为**单段路径**，在 Express 中会被先注册的 `/:taskId` 命中，命中后**原文件详情 handler 的 catch 引用了 try 块内块作用域变量 `taskId` → `ReferenceError: taskId is not defined` → async handler 未处理拒绝 → 无响应（请求挂起）**。
- 三层化**严格保留原注册顺序**，三条单段 GET 仍被遮蔽（不提前注册、不改变既有路由语义），与 `position-responsibility` 等已拆域「保序保遮蔽」一致。
- **行为差异（如实点出）**：原文件此处为「崩溃/挂起（无任何响应）」；拆分版由 controller `run()` 归一返回**干净 HTTP 500**（`code=无效的类型 bigint 输入语法: "inspection"`）。即拆分把「进程内未处理拒绝」收敛为「可观测 500」，属**修良性收敛而非功能回归**——三条端点在原记录与拆分版中 **均不可达其各自预期 handler**（列表语义从无有效工作路径）。是否后续单独修复（把静态路径前置）不在本轮范围，需另行决策。
- 相关风险已按自动归档规则沉淀（见 `④风险待办`/`③决策结论` 对应条目）。
