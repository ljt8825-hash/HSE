# 热更新失效实锤与自动强更（2026-10-20，CF-WPS-108j，版本 .122）

> 类别：②交付报告。第二段 69 秒录屏逐帧分析 + 旧版留档文案比对，锁定「所有修复到不了手机」的终极原因。

## 一、决定性证据链

- **f020 toast**「隐患已登记（编号 YH202610200250087388）」——与 `_releases\2026-10-19.110` 留档的旧文案 `"隐患已登记（编号 "` **精确吻合**；.119+ 的文案必带「已登记并闭环销号（…整改后照片 N 张）」或「…，未附整改后照片」后缀——**用户手机主脚本 = .118 或更早**；
- **生产表裁决**：YH202610200250087388（10:50）rectCNT=0+待整改+sceneCNT=1——与旧版行为一致；
- **代码矛盾排除**：本地 frontend L5014-5054 同一 rectTokens 数组既判 toast 又发 body（`if(rectTokens.length) body.rectify_photo_tokens=rectTokens`），逻辑上不可能「toast 无后缀 + 服务端没收到」并存；Worker L3321 `处理状态: rectTokens.length ? CLOSED : PENDING` 自 .109 未变——**唯一自洽解释 = 手机跑旧版主脚本**；
- **f017 缩略图（反光背心男）在「提交中」时显示但落表 rectCNT=0** = 旧版幽灵照片（用户没拿到 .118 的幽灵修复）；
- **线上验证**：.119/.120/.121 部署后 verify 全过——**服务端发布无误，问题全在客户端滞留**；
- **热更机制缺陷**：banner 需用户手动点「立即升级」，且热更检测只在页面加载时跑一次——长驻页面进程永远停在旧版。

## 二、修复（.122，deployment 2d455c6c）

1. **自动强更**：热更检测发现 remote>here 时，不再只弹 banner——**直接 `location.replace` 自动刷新**（check.html 响应 no-cache，reload 必拿最新 HTML+新 ?v= 脚本）；
2. **防死循环**：sessionStorage 计数 `hseAutoUp`，同一会话最多自动 reload 2 次，仍旧则退回手动 banner；
3. 注意：自动强更对「已在 .118 的页面」无效（.118 没有这段代码）——**当前用户需彻底重启一次页面**，之后 .122 的自动强更永久兜底；
4. 线上实测：build=2026-10-20.122、autoForceUpdate=true、version.json 一致。

## 三、冻结口径（增补）

- **前端发布后必须验证「用户实际拿到」而非「服务端已发布」**：toast 文案等带版本指纹的行为特征可作客户端版本裁决（与 `_releases` 留档比对）；
- **热更新必须自动**：任何依赖用户点击的升级提示都不可靠；自动 reload 必须配防死循环计数；
- `_releases` 留档除回滚外还是**旧版行为指纹库**（文案/特征比对定位客户端实际版本）。

## 四、用户验证
