# 压缩时序竞争修复二期——状态可视化 + 30 秒等待（2026-10-20，CF-WPS-108h 二期，版本 .120）

> 类别：②交付报告。.119 的 8 秒等待被真机实测突破（.119 下 08:57 登记 YH202610200057202687 仍 rect 列 null），二期修复。

## 一、.119 失效原因（实测+代码定位）

- 用户确认手机版本号已是 .119 后测试仍复现（08:57 记录：待整改+rect null+scene 1 张）。
- **scene COUNT=1 排除「误传到现场照片区」**（若误传会是 2 张）。
- **compressImage 实现审查**（L1890+）：三段异步 = probeImageWidth（读文件头）→ createImageBitmap（**大图解码+降采样**）→ canvas drawImage + toDataURL（**JPEG 编码**）——**手机 1200 万像素照片全程可达十几秒**（低端机更久），.119 的 8 秒等待上限不够，超时后照常提交 → 丢照片。

## 二、修复（.120，deployment 472084ae）

1. **等待上限 8s→30s**：提交前 while 轮询 hzPhotoBusy 归零，按钮实时显示「照片处理中…（已等 N 秒）」；
2. **超时不静默**：30 秒仍未压完 → toast 明确警告「照片处理超时，本次提交未包含整改后照片；可稍后在详情页补传」（6000ms）；
3. **压缩状态可视化（hzRectBusy 专用计数）**：选图后整改照片区立即显示黄色占位条「⏳ 正在处理整改后照片（大图压缩需数秒到十几秒），处理完成前请勿提交…」，压缩完成自动消失；
4. **完成按钮实时计数**：`完成（含整改后照片 N 张，提交即闭环）`——**用户点完成前就能确认照片是否就绪**；N=0 时只显示「完成」；
5. 自测：SYNTAX OK、rectBusy inc/dec 配对、4 内联块 ALL OK、3 文件同步 MD5 一致、线上 appfix/build=2026-10-20.120 全过。

## 三、冻结口径（增补）

- **压缩耗时不可假设**：手机大图压缩「数秒到十几秒」，任何基于固定秒数的等待都可能不够——**等待必须以计数器归零为准 + 超时明确告知用户**（绝不静默降级）。
- **状态可视化原则**：异步准备的数据，其就绪状态必须对用户可见（占位条/按钮计数），不能只靠系统内部等待。
- 指纹补充：scene COUNT 检查可排除「照片传错区」假设（误传=现场 2 张）。

## 四、验证

用户热更 .120 后：传整改后照片 → 照片区显示黄色「正在处理」占位 → 处理完成后占位消失、完成按钮变为「完成（含整改后照片 1 张，提交即闭环）」→ 点完成 → 提示「已登记并闭环销号（…整改后照片 1 张）」→ 台账已闭环+有整改后照片。
