# 登记丢整改照片真根因——压缩异步时序竞争修复（2026-10-20，CF-WPS-108h，版本 .119）

> 类别：②交付报告。**本报告修正 .118 归档结论**：「幽灵照片」只是次生 bug；真根因是 compressImage 异步压缩与提交的时序竞争。

## 一、新证据与再排查

- 用户新登记 **YH202610200029485187**（孟祥宇 08:29，三违=是）：生产表实测 处理状态=待整改、整改后照片列缺失、现场照片=hazard.jpg、**无任何整改流程痕迹**（排除「详情页整改」路径）。
- 全链路代码逐段复核：前端绑定（L4557-4560 静态 input+onchange）、pickHazardRectPhoto、renderHzRectPhotos、submitHazard body 构造、Worker rectTokens 校验（失败 400 不静默）/CLOSED 分支（L3321/3328）——**全部正确**；Worker 部署历史确认活跃版本 8afe5c3c（.109 部署后无人覆盖）。
- **唯一剩余解释：提交那一刻 hazardForm.rectPhotos 就是空的。**

## 二、真根因（定谳）

`pickHazardRectPhoto` 选照片后经 **compressImage 异步压缩（1~3 秒）**才 push 进 rectPhotos。**用户 AI 识别后快速连续操作：传整改照片→立刻点「完成」**——提交时压缩未完成、push 未发生 → rectTokens=[] → body 不带 rectify_photo_tokens → Worker 走待整改分支落表；**压缩完成后缩略图才显示**，用户看到「照片在了」，无从察觉丢失。现场照片在第①步拍摄、到提交早已压缩完，故每次都在——完美吻合两起案例（YH202610191503255813 / YH202610200029485187）与「时好时坏」特征。

**.118「幽灵照片」（草稿恢复漏渲染）是另一个真 bug 但非本案主因**（干净流程同样丢照片）。

## 三、修复（.119，deployment 86d03377）

1. **hzPhotoBusy 在途压缩计数器**（现场+整改共用）：pickHazardPhoto / pickHazardRectPhoto 的 compressImage 回调首行 `hzPhotoBusy--`（成功/失败路径都必减）；
2. **submitHazard 提交前等待**：`while(hzPhotoBusy>0 && <8s)` 轮询 150ms，等待期间按钮显示「照片处理中…」——压缩完成才继续上传提交（8 秒上限防卡死）；
3. **成功 toast 自证**：闭环时「已登记并闭环销号（编号 xxx，**整改后照片 N 张**）」；非闭环时附「，未附整改后照片」——用户每次提交都能自查照片带没带上；
4. 自测：SYNTAX OK、busy inc2/dec2 配对、4 内联块 ALL OK、3 文件同步 MD5 一致、线上 appfix/build=2026-10-20.119/version.json 全过。

## 四、冻结口径（修正 .118）

- **压缩异步纪律**：凡「选图→compressImage 异步回调→push 表单数组」模式，提交动作**必须等待在途压缩归零**再读数组；用户感知的「照片显示了」≠「数据已就绪」。
- **诊断方法论**：代码逐段全对时，转向**时序/并发**假设——「数据显示在 UI」的时刻 ≠「数据进入模型」的时刻（异步回调延迟）。
- 生产 Worker 活跃版本查询：`npx wrangler deployments list`（输出 oldest→newest，看末尾）。
