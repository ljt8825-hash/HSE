# H5 弱网落表提示与自动补传强化 交付报告（CF-WPS-103）

> 日期：2026-10-16　类别：②交付报告　归属对话：H5 上传是否落飞书多维表格提示 + 弱网自动补传
> 改动文件：`grid-mobile-cloudflare/frontend/app.js`（1 处）、`check.html`（6 处）、`patrol/records/login/detail.html`（仅 `?v=` bump）；零后端、零 Worker、零生产数据、零 WPS

## 一、背景与根因

用户原话：「是否可以增加上传是否落到飞书多维表格的提示？现在很多在乡镇上巡查，信号不好，没有上传成功，等到晚上到了家里，再次打开后，才上传成功。」

调研结论：离线队列/补传机制本已存在（本地暂存 + client_request_id 幂等 + 单飞锁 + 6 个补传触发点 + 台账页待补传条），「晚上打开自动补传成功」正是 boot 兜底在工作。真正缺陷有三：

1. **提交终屏误导（最直接）**：提交是后台异步的，`showDone` 渲染瞬间 `syncState` 还是 `pending`，CF-WPS-84 的静态 ⚠ 行把 pending 也写成「⚠ 记录未上报：未知原因，请到巡查台账重试」，**且终屏此后永不更新**——用户每次提交都看到「未上报」，无法判断是否落表。
2. **照片上传无超时**：`app.js mobileUpload` 用裸 `fetch`，乡镇弱网下悬挂数分钟，把补传队列整个堵死（`syncInFlight` 单飞锁在途、40s 兜底轮询进不来）。
3. **补传成功无反馈**：夜里打开页面自动补传成功，界面毫无提示。

Worker 端已确认无需改动：`/api/mobile/patrol/submit` 幂等（client_request_id 先查后写 + deduplicated 返回），重复补传不会产生重复行。

## 二、改动清单（每项独立段落）

### 1. B1：照片上传加 60s 超时（关键修复）

`app.js mobileUpload`：裸 `fetch` → `fetchWithTimeout(…, H5_UPLOAD_TIMEOUT_MS=60000)`；超时/断网返回 `{status:0, timeout:true}`（与 `mobileApi` 同口径），异常绝不外溢（patrol.html 等直接调用方也不再被 abort 异常打断）。

### 2. A1：终屏落表状态行实时化

- 新增 `doneSyncLineHtml(rec)` + `attachDoneSyncLine(rec, el)`（check.html，CF-WPS-103 注释）：
  - `pending` → 「正在上报到飞书多维表格…（弱网时较慢，可先返回，记录已存本机不会丢）」
  - `synced` → 「✓ 已落到飞书多维表格（HH:MM）」
  - `failed` → 「⚠ 暂未上报：{真实原因}」+「记录已保存在本机，网络恢复后自动补传（下次打开也会自动上传），无需重复填写」
- `showDone` 内替换 CF-WPS-84 静态 ⚠ 行（保留其「硬失败如实显示原因」的意图，但 pending 不再误报「未上报」）；未定态时挂 `syncRecord` 完成回调原地刷新（`el.isConnected` 守卫；单飞锁保证只是复用在途请求，绝不重复提交）。
- 「稍后整改」自定义终屏卡同口径补挂该状态行。

### 3. A2：落表时间 syncedAt

`syncRecordOnce` 成功分支写入 `rec.syncedAt = Date.now()`，为「落表时间」唯一来源；终屏「✓ 已落（HH:MM）」与徽标 title 据此显示。

### 4. A3：上报徽标文案对齐「落表」语义

`syncChip`：synced=「已落台账」（title=已写入飞书多维表格 · syncedAt）；failed=「待补传」（title=原因+已存本机自动补传）；pending=「上报中」→「待上报」（title=已保存在本机，等待网络可用后自动上报）。详情页「换一张现场照片」右上角小字「已上报/未上报」→「已落台账/待上报」。

### 5. A4：补传成功轻提示

新增 `syncToast(msg)`（顶部固定胶囊条，3s 自动消失，幂等创建）；`retryPendingSyncOnce` 末尾统计本轮 `landed`（pending→synced 条数），>0 时提示「✓ 已补传 N 条记录到飞书台账」——覆盖夜里打开 boot 补传成功的场景。

### 6. B2：切回页面立即补传

`DOMContentLoaded` 补传注册区新增 `visibilitychange` 监听：`!document.hidden` 时立即 `tryAutoSync()`。补传触发点由 6 个增至 7 个（enterHome / 台账入口 / online / 40s 轮询 / 完成页按钮 / boot / **visibilitychange**）。

### 7. 版本号 bump → 2026-10-16.104

`check.html`（hse-build meta + config.js/app.js `?v=` 三处）与 **全部引用 app.js 的页面**（patrol/records/login/detail，自 .95 一并 bump 至 .104）。`sw.js` 纯透传无版本号，不 bump。

- 未触 5876 生产后端、生产计划任务、生产 `.env`、生产表、WPS 写入、身份链/JWT——纯前端静态文件改动。

- **使用环境口径（用户纠正）**：一线实际使用**本机浏览器 / Chrome / Firefox**，非微信内置浏览器（纯标准 H5，无微信 JS-SDK；转派「微信通知」为 Worker 服务端推送，与打开方式无关）。本次全部改动（fetchWithTimeout/终屏状态行/徽标/syncToast/visibilitychange）均为标准 Web 能力，各浏览器通用。
- **弱网补传 Web 边界（对用户解释口径）**：页面关闭后无法后台补传——Firefox 与 iOS 均不支持 Background Sync；仅 Chrome 安卓（sw.js 已注册 + PWA 安装流程）理论上可用，覆盖不全故未实施；「下次打开自动补传」是现行兜底机制并保留。可选增强：若用户收敛到 Chrome/PWA 安装，可评估 Background Sync。
