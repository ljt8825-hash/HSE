# 整改后照片台账漏挂死锁修复（2026-10-19）

> 类别：②交付报告。触发：用户报告「手机端已上传整改后照片，但飞书台账『整改后照片』列为空」。

## 现象与定性

- 截图：SW20261019005（孟祥宇查、违章人刘玉花、骑车不戴头盔、已闭环），页面显示整改后照片，台账列空。
- 只读实测主台账（tbl5QiCv5Qbal044，2026-10-19）：当日 8 条三违中 **7 条整改后照片正常**（14:51=2张、16:15=1、16:17=1、16:40=2），**仅 15:35:53 这单为 0（hasKey=false）**。
- 结论：**链路整体通畅，仅单条漏挂**，非系统性故障。漏挂单特征 = 检查人**自建记录 + 秒闭环**（建单 15:35:53 与整改时间同刻）。

## 根因（前端死锁，check.html）

整改完成即时补挂分支（本人自建记录路径）：

```
上传 token 成功 → attachPhotoToRecord 失败（瞬时网络/限频）
→ token 已存、未设 rectifyPhotoPending
→ retryPendingSyncOnce 补挂循环条件 `afterPhoto && !rectifyPhotoToken` 恒 false
→ 永不重试 attach ⇒ 台账列永远空，页面显示本机照片（用户误以为已上传）
```

同一死锁模式 3 处：①补偿循环主路径（原 L4383）②syncRecordOnce 补传后补偿（原 L4107）③整改完成即时补挂分支失败不落 pending（原 L5568）。待办派发路径（retryRectifyLocal，按 `!uploaded` 判断）无此问题。

## 修复（frontend/check.html，bump 2026-10-19.107）

统一改为 **pending 驱动 + token 复用**：

- 补挂循环与 syncRecordOnce 补偿条件：`(rectifyPhotoPending || !rectifyPhotoToken)`；有 token 直接重试 attach，无 token 先补传；attach 成功才摘 pending。
- 整改完成即时补挂分支：进入即落 `rectifyPhotoPending = true`，attach 成功才摘 —— 失败必被补偿循环接管。
- photoPending 探测条件同步扩展，保证此类记录能触发 retryPendingSyncOnce。

部署：`wrangler pages deploy _pages_deploy`（含 Functions）。线上实测：build=2026-10-19.107、死锁修复代码已上、同源登录链路 401 正常。Worker 未动。

## 存量数据修复路径（不人工补写台账）

15:35 那单的照片仍在孟祥宇手机本机。**他下次打开 H5**，新版补偿逻辑会自动补挂（本机记录 synced+serverRecordId+afterPhoto，pending 或 token 缺失均会重试）。若本机缓存已清，则由其在详情页手动重传（attach 权限：本人/待办接收人）。

## 风险提示

- 手机端「显示照片」≠「已落台账」：本机 blob 渲染与台账附件列写入是两条链路，中间任何一环失败都靠补偿循环兜底 —— 此前的静默失败即证明 UI 反馈不足（CF-WPS-103 落表反馈只覆盖整条记录，不含照片补挂结果）。
- 后续可考虑：详情页整改照片区域加「已落台账/待补传」状态角标（未实施，待用户决策）。
