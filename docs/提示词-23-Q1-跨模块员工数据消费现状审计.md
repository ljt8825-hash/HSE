## 任务：审计跨模块员工数据消费现状

### 背景

花名册数据模型已统一（employee_assignment），API 已收敛，旧表已只读保护。但目前各模块对员工数据的使用方式零散、无统一标准、无事件联动——距"花名册作为基石打通各模块"的愿景还有最后一公里。

本次任务是消费层的起点：全面审计各模块对员工数据的消费现状，识别缺口和不一致，生成消费层设计基线。

纯审计，不修改任何代码。

#### 2. 对每个模块审计以下维度

**维度 1：员工数据使用方式**
- 是否使用 EmployeeSelector 组件？用于什么字段？
- 是否直接调用 employee API（getEmployeeList / getEmployeeById 等）？
- 是否在页面中硬编码员工姓名/工号搜索？
- 是否使用员工统计数据（人数、完成率等）？

**维度 2：数据一致性**
- 同一员工在不同模块中的字段名是否一致（employeeId / employee_id / empId / userId）？
- 员工姓名是否从 API 获取还是用户手动输入？
- 是否存在"员工已调岗/离职，但关联数据未更新"的风险？

**维度 3：模块间联动**
- 当员工信息变更（调岗、离职、状态变更）时，是否会影响该模块的数据？
- 该模块是否有"点击员工姓名跳转到员工档案"的交互？
- 该模块是否需要知道"其他模块中该员工的数据"？

**维度 4：API 调用模式**
- 该模块的 API 文件中，员工相关接口是否从 `employee.ts` 导入？还是自行定义？
- 员工相关接口的请求参数和响应格式是否统一？
- 是否存在 N+1 查询问题（如循环调用 getEmployeeById）？

#### 4. 识别关键缺口

按严重程度列出：

**P0 级缺口**（数据不一致，影响业务正确性）：
- 示例：同一员工在不同模块使用不同标识符
- 示例：员工姓名手动输入导致数据孤立

**P1 级缺口**（交互缺失，影响用户体验）：
- 示例：点击员工姓名无法跳转到员工档案
- 示例：员工调岗后关联模块数据未联动

**P2 级缺口**（代码重复，影响可维护性）：
- 示例：多个模块重复实现员工搜索逻辑
- 示例：N+1 查询问题
