## 六、修复方案详情

### 6.1 修复项 1：确认/创建 `uk_emp_assign_primary`

**原方案**: 使用 `ON CONFLICT ON CONSTRAINT uk_emp_assign_primary`，假设约束已存在。
**修改内容**: 增加前置检查和创建步骤。
**修改原因**: 设计文档中未明确此约束，存在生产环境不存在的风险。
**影响范围**: B-2 迁移 SQL、Step 0 检查流程。

**修复步骤**:
1. 在 Step 0 阶段，执行检查 SQL。
2. 如果不存在，执行创建 SQL。
3. 验证约束创建成功。

### 6.2 修复项 2：增加 `baseline_count` NULL 判断

**原方案**: `IF rec_count < baseline_count * 0.98 OR rec_count > baseline_count * 1.02 THEN`
**修改内容**: 增加 `baseline_count IS NULL` 的判断分支。
**修改原因**: 当 `migration_baseline` 表中无对应记录时，`baseline_count` 为 NULL，导致比较逻辑失效。
**影响范围**: B-0 Step 3 和 B-2 Step 2 的 `DO $$` 块。

**修复后 SQL 片段**:
```sql
    -- 动态校验
    IF baseline_count IS NULL THEN
        RAISE NOTICE '基线不存在，跳过动态校验';
    ELSIF rec_count < baseline_count * 0.98 OR rec_count > baseline_count * 1.02 THEN
        RAISE EXCEPTION '恢复行数异常: %, 预期范围 [%, %]',
            rec_count, FLOOR(baseline_count * 0.98), CEIL(baseline_count * 1.02);
    END IF;
```

### 6.3 修复项 3：增加脏数据检查步骤

**原方案**: B-2 迁移直接执行，无前置数据清洗。
**修改内容**: 在 B-2 执行前，增加重复数据检查。
**修改原因**: 如果存在违反唯一约束的脏数据，迁移 SQL 会因 `ON CONFLICT` 行为不确定而可能导致数据丢失。
**影响范围**: B-2 执行流程。

**修复步骤**:
1. 在 B-2 Step 1（备份）之后，增加脏数据检查步骤。
2. 如果发现重复数据，人工处理（保留 `is_current=true` 且 `start_date` 最新的一条）。
3. 处理完成后，再执行 B-2 Step 2。

### 6.4 修复项 4：统计 `status` 枚举值

**原方案**: `CASE WHEN her.status = 'active' THEN 'active' WHEN 'pending' THEN 'pending' WHEN 'inactive' THEN 'inactive' ELSE 'active'`
**修改内容**: 在迁移前统计所有 `status` 值，并确认映射关系。
**修改原因**: ELSE 分支强制将未知状态转为 `'active'`，可能导致数据错误。
**影响范围**: B-2 Step 2 的 `DO $$` 块。

**修复步骤**:
1. 执行 `SELECT DISTINCT status FROM hse_employee_relation`。
2. 将所有枚举值列在迁移日志中。
3. 如果存在非预期值，决定正确的映射关系。
4. 更新 SQL 中的 CASE WHEN 分支。
