### 1.3 本轮最重要的三个发现

**发现一：退休编码不是「撤回已批准规则」，而是「未经上位裁决即已落地的实现选择」。**

A-02e.2 将 D1 表述为「撤回 A-02d §二.4（已发出的业务规则）」。本轮核对 DEC-01 后认为该表述**不完整**：

- DEC-01 `A-05 :602` 明文：「A-05a 定后并入 TECH-INPUT-02，**但必须早于 A-02d**，否则 `status` 合法值集合无法冻结」；
- 而 A-05 在 §11.1 `:1834` 的状态是「**待裁决**」，裁决人与日期全空；
- ⇒ **A-02d 的 `退休→inactive` 是在其上位裁决 A-05 未签署的情况下实施的。**

因此退休编码的裁决归属**不是**「A-02d 规则发布者」，而是 **A-05 的裁决人（人事负责人，DEC-01 §11.2 `:1854` 第 2 轮）**。这一点直接改变了签署页该由谁签（§5.4）。

**发现二：DEC-01 `:562` 与代码的矛盾是「事实栏漂移」，不是「裁决冲突」。**

`:562` 位于「④ 已确认事实 [FACT]」栏，记录的是 2026-10-28 的 HEAD 代码（当时 `退休→retired` 正确）。它是**事实记录**，不是裁决。DEC-01 全文**从未裁决过退休应存哪个编码**。⇒ 不存在「DEC-01 批准 retired、A-02d 违反 DEC-01」这种情形；只存在「A-02d 改变了事实，DEC-01 未同步事实栏」。

**发现三：两份 DDL 的差异比 A-02e.2 记录的更多一项。**

除 `status` 长度/可空性与 `start_date` 默认值外，**`is_primary` 的默认值也正好相反**（DDL-1 `NOT NULL DEFAULT true`，DDL-2 `NOT NULL DEFAULT FALSE`）。本轮新增记录（§9.1）。

## 6 返聘业务规则签署页（C2）

### 6.1 前提：返聘在当前系统里完全不可达

任务书要求「把问题拆开，不得只决定新建段就宣告闭环」。本轮实测重新确认三层不可达：

| 层 | 证据（本轮实测） |
|---|---|
| **前端 API** | web-naive **无** `updateOrgStatus` 定义（`api/hse/employee.ts` 全文件无 `/org/.../status`） |
| **前端调用** | web-antd 有定义，但**全仓无任何 UI 调用点** |
| **后端可达性** | 即便手工调用，`changeAssignmentStatus:507` 按 `WHERE ea.id = $1 AND ea.is_current = true` 定位；终态段的 `is_current` 已是 `false` ⇒ `:510-513` 直接返回 `{error:-2, message:'组织关系不存在或非当前记录'}` |

**⇒ 返聘不是「修改现有行为」，而是「新建一个从未存在的业务动作」。** 它属新功能定义，不属状态编码修复。这一点必须写在签署页上，否则决策人会误以为是在修 bug。

**叠加数据事实**：`status='reinstated'` 0 行、`history` 中「返聘」事件 0 条（`DEC-01:565`、`:577`）⇒ 无任何业务先例可参照。

### 6.2 E-01 / E-02｜业务定义与关系层表达

**签署问题 1（E-01）：谁是「返聘」？**

| 选项 | 定义 | 影响 / 风险 |
|---|---|---|
| A | 曾**离职**（辞职）的人员重新入职 | 与「重新招聘」重叠，需区分「返聘」与「新入职」的边界 |
| B | 仅**退休**人员返聘（退休返聘） | 范围最窄，与「退休返聘」这一常见人事用语一致；但排除了辞职后回流 |
| C | 含内部退养、停薪留职期满复岗 | **与现有「复岗」实现重叠**（`employeeAssignmentService.js:542-543` 已有 `在职 ∧ beforeStatus='待岗' → 复岗`）⇒ 会产生两套语义并存的复岗 |

> **陷阱排除（写在此处以防误用）**：`server/sql/alter_employee_relation_status.sql:16` 的注释含「退休返聘」四字，但该注释属于**死列 `employee_relationship_status`**（`VARCHAR(50)`，全表 3,401 行全 NULL，代码与前端零使用）。**「字符串含这四个字」不等于「枚举值」**，不得作为「返聘是正式关系取值」的依据。

**签署问题 2（E-02）：返聘后 `employment_relation` 写什么？**

| 选项 | 做法 | 对 A-02 的影响 | 风险 |
|---|---|---|---|
| A | 关系改回 `正式员工` | 符合「关系=当前事实」的解释 | **丢失"此人曾返聘"的当前态事实**，只能靠 `employee_history` 追溯 |
| B | 新增「返聘」为第 5 个正式关系值 | 需改 `RELATION_VALUES`(`:113-115`)、`validateRelationInput`(`:255`)、前端硬编码下拉（`web-naive/.../employee/index.vue:796-802` 硬编码 5 项，**不读字典，必改**） | 关系字段同时承载「是否在职」（正式员工）与「怎么来的」（返聘）⇒ 语义混杂 |
| C | 新增「退休返聘」复合值 | 同 B，且更窄 | 复合值会与 B 的选项冲突，需先定 E-01 |

**铁律**：`reinstated` **不得**未经依据加入 `employment_relation` 的正式取值。本轮实测确认 `RELATION_VALUES` 仅 4 值（正式员工/辞职/死亡/退休），`validateRelationInput('reinstated')` 会返回 `{ok:false}`。

### 6.3 E-03｜任职段规则

**签署问题 3：旧段如何处理？**

| 选项 | 做法 | 风险 |
|---|---|---|
| A | **保持原样**（`is_current=false`、原 `status`、原 `end_date` 均不动） | 最安全；但「曾退休」只能从旧段 `status` 读出 |
| B | 归档软删（`is_deleted=true`） | 打破「历史不可变」，影响 `v_employee_current` 口径与所有带 `is_deleted = false` 的查询 |
| C | 补写 `remark` 标注 | 不影响逻辑，仅加文本 |

**签署问题 4：新段四字段怎么定？**

| 字段 | 候选 | 现状行为 / 约束 |
|---|---|---|
| `status` | ①`reinstated`（保持返聘态）②`active`（直接在职）③`reinstated` 后续可转 `active` | 若选①，必须定义「何时转 `active`」，否则永久停在返聘态；`WRITABLE_STATUS_CODES:71-73` 已含 `reinstated` |
| `is_current` | 必须 `true` | `:527-533` 非终态分支**不动** `is_current` |
| `is_primary` | 需明确 | **现状缺陷**：`changeAssignmentStatus:521-526` 终态分支只写 `status`/`is_current`/`end_date`，**从不处理 `is_primary`** ⇒ 存在 `is_current=false ∧ is_primary=true` 的残留 |
| `start_date` | 返聘生效日（业务日） | 现状无可复用路径（返聘不可达）；`OrgTransferModal` 是唯一形态参考，但预填系统日（Q3-4） |
| `end_date` | 新段应为 `NULL` | — |

**约束交互（必须同时告知决策人）**：`uk_emp_assign_primary`（`sprint5_6...sql:62-64`）是条件唯一索引 `WHERE is_primary = true AND is_current = true AND is_deleted = false`。若旧段的 `is_primary` 仍为 `true`（因为终态分支不清它）而 `is_current` 已 `false`，则**不冲突**；但若返聘新段同时设 `is_primary=true` 且旧段仍有其他 current 主岗，则 INSERT 会抛唯一约束错误。

**签署问题 5：已存在多条 `current` 段时怎么办？**

| 选项 | 做法 | 风险 |
|---|---|---|
| A | 阻断报错，要求人工整理 | 最安全，但返聘操作成功率取决于存量数据质量 |
| B | 自动关闭除主岗外全部 current | 会做「未授权的数据变更」 |
| C | 只关 `is_primary=true` 的那条 | 与 `assignEmployee:386-393` 现状一致（无 `ORDER`/`LIMIT`，取 `rows[0]`）⇒ **可能残留第二条 current** |

### 6.4 E-04｜显示逻辑的结构性冲突（本轮最关键约束）

`displayStatusSql:282-290` 是**关系优先**：

```
CASE WHEN relation = '退休' THEN 'retired'
     WHEN relation IN ('辞职','死亡') THEN 'left'
     ELSE assignment.status END
```

**⇒ 若只建新段、不改关系，结果必然是：**

```
employee.employment_relation = '退休'          ← 没改
employee_assignment(新段) status='active', is_current=true
        ↓ displayStatusSql 先判关系
org_status = 'retired'                          ← 列表仍显示「退休」
```

**新段建成了、`is_current=true` 了，但列表/档案仍显示「退休」，统计仍把他算作「已离开」。**

这不是 bug，是「关系优先」设计的必然结果。**因此「返聘的关系表达」（E-02）与「返聘建段」（E-03）必须同时决定，单独决定任何一个方案都不成立。**

**签署问题 6：`displayStatusSql` 是否要为返聘加分支？**

| 选项 | 做法 | 风险 |
|---|---|---|
| A | 不改，要求 E-02 必须改关系为 `正式员工` | 逻辑最简单；但关系字段会丢失「曾退休」 |

### 7.3 三处待整改缺陷（Q3 已认定，修法待裁）

**缺陷 ①：V2 导入「新旧段时间轴倒挂」（最严重，与 Q3-1 同源）**

```
:1025  旧段 end_date   = CURRENT_DATE          ← 系统执行日
:1052  新段 start_date = COALESCE(hire_date, CURRENT_DATE)   ← 历史入职日
```

若 `hire_date = 2020-03-01`、本次导入在 2026-10-29 执行：
- 旧段结束于 `2026-10-29`
- 新段开始于 `2020-03-01`
- ⇒ **两段重叠 6 年 7 个月**，且新段的开始时间早于旧段的结束时间

**一次导入同时制造「复活」（Q3-1）与「倒挂」（Q3-2）两类问题，两者在同一个代码块内。**

**缺陷 ②：`updateAssignmentStatus` 的 `endDate` 默认为 `null`**

终态时若调用方不传 `endDate`，`end_date` 写 `null` ⇒ 该段变成「已关闭但无结束日」。
**当前属死代码**（A-02e.1 已证：4 个封装 `createAssignment`/`updateAssignmentStatus`/`endCurrentAssignment`/`findCurrentAssignment` 仅导出零调用），实际生效的是 `assignEmployee`/`changeAssignmentStatus` 的内联 SQL。
⇒ **不构成现实风险，但构成「若被启用即违规」的隐患**，须在 C-02 中明确「是否保留该封装」。

**缺陷 ③：`employee_history.event_date` 的系统日期兜底**

旧链在缺业务日时用系统日期写入 `event_date`，使该列**同时承载业务时间与系统时间**（违反 D-6 的「必须分离」）。

## 8 V2 导入 P0 风险与 5-A～5-D 比较

### 8.1 触发条件与执行顺序（本轮重新实测，不引用旧报告）

`employeeImportV2Service.js` 在 `performBatchImport` 的逐人循环内，按固定顺序执行三步：

| 步 | 行号 | SQL 动作 | 条件 |
|---|---|---|---|
| 1 | `:1023-1028` | `UPDATE employee_assignment SET is_primary=false, is_current=false, end_date=CURRENT_DATE WHERE employee_id=$1 AND is_current=true AND is_primary=true AND is_deleted=false` | **仅命中「当前 + 主岗 + 未删」的段** |
| 2 | `:1030-1041` | 上级兜底匹配（与时间无关） | 可选 |
| 3 | `:1049-1055` | `INSERT INTO employee_assignment (..., is_primary, is_current, status, start_date, ...) VALUES (..., true, true, 'active', COALESCE($10,CURRENT_DATE), ...)` | **无任何前置条件** |

### 8.2 关键推论：复活不依赖第一步是否命中

**情形 A：正常在职人员**（存在 `is_current=true ∧ is_primary=true` 的段）
- 步骤 1 命中 1 行 ⇒ 旧段被置 `is_current=false`
- 步骤 3 插入新段 ⇒ 无唯一约束冲突（旧段已非 current）
- 结果：正常调岗，**但制造倒挂**（旧段结束于系统日、新段始于 `hire_date`）

**情形 B：终态人员**（段已 `is_current=false`）
- 步骤 1 **命中 0 行**（条件含 `is_current = true`）
- 步骤 3 **照常 INSERT** `status='active'、is_current=true、is_primary=true`
- 结果：**该人员被「复活」**——重新出现在当前视图、重新计入在岗统计、重新进入培训/考核名单

**⇒ 结论（本轮实测确认，与 A-02e.2 一致）**：**「终态标准形态」反而是最无防护的形态**。因为终态段天然不满足步骤 1 的 `is_current = true`，防护逻辑对它完全失效。

### 8.3 数据库层为何没有兜底

| 潜在兜底 | 实测 | 结论 |
|---|---|---|
| `uk_emp_assign_primary`（`sprint5_6...sql:62-64`） | `UNIQUE ... WHERE is_primary=true AND is_current=true AND is_deleted=false` | 情形 A：旧段已 false ⇒ 不冲突；情形 B：终态段已 false ⇒ 不冲突。**两种情况都不触发** |
| `employee.employment_relation` 校验 | 导入**不读关系**（`ROSTER_HEADER_MAP:45-61` 15 列无关系列） | 无从判断 |
| 触发器 / 应用层校验 | 无 | — |

**⇒ 数据库与应用层均无「拒绝复活」的能力。这是结构性的，不是配置问题。**

### 9.1 两份建表 DDL 的完整差异（本轮实测，含新增发现）

| 情形 | 结果 |
|---|---|

### 9.3 对裁决的直接影响（必须告知决策人）

| 受影响裁决 | 影响方式 |
|---|---|
| **R-04 / A-01b（NULL 处理）** | 若 `status` 不可为 NULL ⇒ 「`status IS NULL`」不是合法状态，152 人的问题只能落在 `relation IS NULL`；若可为 NULL ⇒ 存在第三种退化形态 |

| **C-01（`start_date` 语义）** | 若 `NOT NULL DEFAULT CURRENT_DATE` ⇒ 省略即系统日，与 D-6 冲突且**不可识别**（无法区分「业务日恰好是今天」与「用了默认值」） |
| **C-03（时间字段性质）** | 带不带时区决定「系统时间」的定义边界（本地时 vs UTC） |
