## 1. 决策 1–4 的落地映射

### 1.1 核心障碍：`指派人ID` 会被转派覆盖

| 位置 | 代码 | 行为 |
|---|---|---|
| 建单即指派 | `worker/index.js:2149` | `指派人ID = 指派人姓名 = 调用者本人` |
| 转派 | `worker/index.js:2494` | `指派人ID = 当前调用者`（**覆盖写入**） |

⇒ 公司管理派给经理、经理转派给管理员后，`指派人ID` 从"公司管理"变成"经理"再变成"经理"（第二次转派后仍是经理），**公司管理这条链的归属信息被销毁**。这是决策 1 无法直接实现的唯一原因。

### 1.2 落地方式：新增一列 `原始指派人ID`（链的 owner，永不变更）

| 环节 | 写入规则 |
|---|---|
| `patrol/submit` 带 `assign_to` | `原始指派人ID = 指派人ID = 调用者` |
| `handleAssign` 首次转派 | 若 `原始指派人ID` 为空 → 先用**旧**的 `指派人ID` 补写（兼容存量），再写新的 `指派人ID` |
| `handleAssign` 后续转派 | **只改 `指派人ID`，`原始指派人ID` 永不动** |
| 存量数据 | 一次性回填脚本：`原始指派人ID ← 指派人ID`（存量记录均未被转派过，此回填无信息损失） |

### 1.3 接口按角色分流（决策 1 与 4 的分叉点）

`GET /api/mobile/dispatched` 的过滤键按 `payload.role` 分流：

| 角色 | 过滤键 | 语义 | 对应决策 |
|---|---|---|---|
| 公司管理 | `原始指派人ID == 我` | **我发起的整条链**（无论被转派几手、当前在谁手上） | 决策 1 |
| 乡镇作业中心经理 | `指派人ID == 我` | **当前在我手上派出的**（转出去后不再占我的列表） | 决策 4 |
| 管理员 | 无此页签 | — | 现状保持 |

> ⚠️ **必须讲清的一个边界**：这一版「整条链」能给出的是 **「我发起的所有任务 + 当前责任人 + 当前状态」**。
> 「谁在什么时候转给了谁」这种**流转历史**，写在一列里装不下，需要 P2 的事件表。
> 若把两者混为一谈，验收时会出现"我说要看链、你只给了当前状态"的落差。

### 1.4 「已完成」分组（决策 2）

现状：`dispatched` 只返回未完成列表 + `done_count` 一个数字（`worker/index.js:2660` 附近）。
目标：新增 `done_records` 数组（限量 `PATROL_LIST_LIMIT`，超出给 `done_more: true`），前端按 `待整改 / 已完成` 两组渲染。

**注意**：`dispatched` 的 `records` 语义（= 仅未完成）**保持不变**，避免打断既有 25 条离线断言 + 54 条 E2E 断言；已完成走新字段。

### 1.5 组织树 scope（决策 3）

现状：`handlePatrolRecords` 硬编码 `patrolIsMine(r.fields, payload.sub)`（`worker/index.js:2352`）—— 只能看**自己巡查**的。

目标：按角色放开。

| 角色 | scope | 过滤方式 |
|---|---|---|
| 公司管理 | `ALL` | 不过滤（全公司台账） |
| 乡镇作业中心经理 | `DEPT` | 台账 `巡查人ID`（备注里的手机号）∈ **我的直接/间接下级手机号集合** |
| 管理员 | `SELF` | `巡查人ID == 我`（现状） |

⚠️ **组织关系不在主台账里**。主台账实际列只有 `检查人姓名 / 网格等级 / 片区\|班组 / 违章行为 / 违章人员姓名 / 描述 / 备注 / 违章照片 / 整改后照片 / 日期`（`worker/index.js:2268` 注释即实测结论），**没有「所属单位」列**。所以 DEPT 过滤必须靠**花名册 `tbl2ZHdXX5d8R12a`（1291 人，含手机号与直接上级）**反查下级 → 得到手机号集合 → 再过滤台账。

性能：花名册全量 1291 行 + 台账全表扫描不能每请求都做 ⇒ 需要 **Worker 侧缓存**（模块级 TTL 缓存或 `caches.default`），TTL 建议 5–10 分钟。

⚠️ **这是放开读权限**。巡查记录含 **违章人姓名 + 现场照片**（PII）。放开范围必须配：
1. 组织树收敛（只给"我管的人"，不给全公司，除公司管理）；
2. 服务端审计日志（谁在什么时候拉了谁的记录）；
3. **业务书面授权**（需你或安环管理部确认"经理可看下属全部巡查记录"是制度允许的）。

### 2.2 好消息：后端字段基本已就绪

| 后端能力 | 现状 | 结论 |
|---|---|---|
| `todoView(rec, full)` | `full=true` 时**多下发** `description` + `rectify_photo_count` | `dispatched` 现在传的是 `false` ⇒ **改一个参数**即可补全派发详情 |
| `inbox` 返回体 | **已经包含已完成记录**（`worker/index.js:2592` 把未完成与已完成拼进 `todos`），且 `monthly_done_count` 为全量计算 | 「已整改」下钻**零新增接口**，前端筛 `todoStatus==='已完成'` 即可 |
| 单条详情接口 | `GET /api/mobile/patrol/records?id=` **已存在**，返回 `patrolRecordView(hit, true)` | 台账详情**已有后端支撑** |
| 照片 | ⚠️ 只下发**数量**（`photo_count` / `rectify_photo_count`），**不下发 URL** | 服务端记录的详情**显示不了图**（见 §2.4） |

### 2.3 设计：统一「记录视图」协议

引入统一前端模型，三类来源归一化后再渲染：

```
Card = {
  kind: 'local' | 'server' | 'todo',      // 数据来源
  key : 唯一键,                            // local: rec.id / 其它: record_id
  title, sub, time, chips[], raw
}
```

**渲染分派**（`renderDetail(card)` 按 `kind` 走三条分支）：

| kind | 详情内容 | 照片 |
|---|---|---|
| `local` | 现有渲染：检查人 / 时间 / 定位 / 违章人（含电话）/ 整改信息 | ✅ 本机 blob 可见 |
| `server` | 检查人姓名 / 巡查时间 / 网格 / 违章人员 / 描述 / 照片数 / 整改状态与责任人 | ⚠️ 仅数量 |
| `todo` | 派发链摘要（谁派给谁 / 派发时间 / 完成时间）/ 整改说明 / 整改后照片数 | ⚠️ 仅数量 |

同时：`view-detail` 的 `nav-title` **动态化**（三违详情 / 巡查详情 / 派发详情）。

### 2.4 硬约束：服务端照片在详情里显示不了图

飞书附件不会下发可访问 URL（既有结论：`normalizeAttachments` 只能拿到**短时效**对象链接，且未落地字节）。因此：

- 本机记录（刚拍的照片）→ 详情里**有图** ✅
- 服务端记录（历史台账）→ 详情里**只有「N 张照片」**⚠️

要显示服务端图片，必须**新增 Worker 附件代理接口**（转发飞书 drive media 下载）⇒ 计入 P2，且需评估飞书附件下载配额与缓存。

**这一条必须提前跟你对齐**，否则"点卡片看详情"做出来发现看不到照片，会认为是没做完。

### 2.5 设计：首页统计卡下钻

新增视图 `view-stat-detail`（复用现有 view 切换机制，非新页面）：

```
navbar : [返回]  动态标题（如「本月派发」）  [计数]
page   : 统一卡片列表 → 点卡片 → 统一详情
```

统计卡加 `data-drill`，四类下钻：

| 统计卡 | drill | 下钻数据源 | 口径 |
|---|---|---|---|
| 本月派发 / 本月上报 | `month` | 公司管理/经理 → `dispatched`；管理员 → `patrol/records?month=` | **服务端** |
| 已整改 | `rectified` | `inbox` 筛 `已完成`（本月，按 `done_at`） | 服务端 |
| 待整改 | `pending` | `inbox` 筛 `待整改` + 本机未同步 | 服务端 + 本机 |
| 已闭环 | `done` | 本机 `status ∈ {done, reviewed}` | **本机** |

### 2.6 ⚠️ 一实现就暴露的真实缺陷：首页统计与明细不同源

现状（`check.html:1772-1784`）：

- `本月派发/本月上报` 数字 = `db.records.filter(checkerId === 我 && 本月)` ⇒ **纯本机口径**
- 而「派发记录」页签 = `dispatched` 接口 ⇒ **服务端口径**

两者**必然不一致**：换手机、清缓存、或派发动作发生在别人手机上时，本机口径归零而服务端口径正常。

决策 5 要求「点数字出卡片」，等于**强制两者同源** —— 否则就是"卡上写 3，点进去 0 条"这类一眼可见的 bug，而且是**统计口径信任度**的崩塌（用户会开始不信首页任何数字）。

**根治方案：新增 `GET /api/mobile/summary`**，把首页 4~5 个数字统一由服务端计算并返回：

```json
{ "role":"经理",
  "month_post": 12, "month_dispatch": 3, "rectified": 5, "pending": 7, "done": 4,
  "scopes": { "month":"dispatched", "rectified":"inbox", "pending":"inbox", "done":"local" } }
```

前端只渲染不计算 ⇒ **数字与下钻明细同源，不可能不一致**。本机未同步的记录作为 `+N 待上报` 的**独立提示**呈现，不再混进主数字。

> 顺带修掉一个已有问题：`check.html:1774` 只统计 `localStorage`，「本月派发」换手机即归零；`renderMyRectify` 的本机分支仍按**姓名**匹配（`check.html:2861` `transferAdminName === session.name`），而花名册有 24 组重名 ⇒ 重名会串号。统一由服务端按 ID 出数后，这两个问题一并消失。
