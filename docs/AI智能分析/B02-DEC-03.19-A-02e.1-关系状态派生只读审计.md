## 六、派生触发边界与副作用（任务书 §五 十问逐条回答）

### Q1. 关系从「正式员工」变为「辞职」，当前代码是否自动派生任职段状态？

**否。零派生。**

逐入口核对：

| 入口 | 是否监听关系变化 | 证据 |
|---|---|---|
| W-01 `updateEmployee` | **否**。UPDATE 只拼 `employment_relation`/`leave_date`/主档字段，无任何 `employee_assignment` 语句 | `employeeService.js:487-528` |
| W-02 `createEmployee` | 不涉及 | `:453-458` |
| 事件 | **不触发**。`changedFields` 白名单（`:534`）不含关系字段 | 同上 |
| 定时任务 / 触发器 | 全仓检索 `employment_relation` 无任何 `CREATE TRIGGER` 或 cron 引用 | `grep employment_relation` 结果全部为 SQL 读条件 |
| 数据库触发器 | 无法从代码确证 | **DB-INT-05** |

**⇒ 结论：`employment_relation` 与 `assignment.status` 之间当前**不存在任何联动**，两侧完全独立。**这正是 A-02e 要建立的东西，也是本轮**不能**声称已完成的东西。

### Q2. 关系变为「死亡」或「退休」，是否存在不同分支？

**在写关系时：没有。** W-01 对三个终态原因走完全相同的代码路径，只把字符串存进 `employment_relation`。

**在写任职段时（W-04）：**
- 「辞职」「死亡」→ 都归一为 `inactive`，发 `EMPLOYEE_RESIGNED`
- 「退休」→ 也归一为 `inactive`，但发 `EMPLOYEE_STATUS_CHANGED`（`resignedLabels:564` 不含退休）

**⇒ 差异只存在于事件类型，不存在于存储状态。** 三种原因在 `assignment.status` 上完全不可区分，唯一区分载体是 `employee.employment_relation` 与 `employee_history.after_status`（D2 修正后保留原因原样）。

### Q3. 关系变为待岗/借调/停薪留职，是否有可验证的中间态转换逻辑？

**没有自动转换。** 中间态只能通过 W-04 手工触发（且前端无入口，见 Q6）。`INTERMEDIATE_STATUS_CODES:85` 定义了"不得自动关闭段"的行为约束，但没有任何"关系→中间态"的映射。

另：关系字段里**根本不存在**「借调」「停薪留职」取值（`RELATION_VALUES` 只有 4 项 + 兼容 `待岗`）。⇒ 这两个中间态**在关系字段层无表达载体**，只能存在于 `assignment.status`。

### Q4. 关系变为 NULL，是否会触发错误的默认状态？

**不会触发状态变化**（无联动）。但存在两处读取侧陷阱：

1. `listEmployees` 默认分支 `= '正式员工'` ⇒ NULL 的人默认不在列表里（`:119-122`）。
2. `v_employee_current.assignment_status` 取自 `is_current=true AND is_primary=true` 的段（视图 `:66-68`）；若该人无此类段，`displayStatusSql` 的 `ELSE` 返回 **NULL** 而非 `'active'`。

**⇒ "关系 NULL" 不会被误判为在职或离职（符合规则），但会以"消失"和"状态空白"的形式表现。** 这是产品呈现问题，列入 OPEN DECISION。

### Q5. 从终态进入返聘，系统是恢复原段、创建新段，还是无一致规则？

**无一致规则。** 实测三条路径行为不同：

| 路径 | 行为 |
|---|---|
| W-03 `assignEmployee` | 新建段，`status='active'`（**不是 `reinstated`**），`is_current=true, is_primary=true` |
| W-04 `changeAssignmentStatus(status='返聘')` | 把**当前**段 status 改为 `reinstated`，**不创建新段**。但要求该段 `is_current=true`（`:507`）——若前一步是终态（已 `is_current=false`），此接口**直接返回"组织关系不存在或非当前记录"**（`:510-513`）⇒ 返聘在终态后**不可达** |
| W-10 replay 脚本 | 按花名册切段重建，`active`/`former` |

**⇒ 返聘场景当前实际不可用**：终态关闭段后，W-04 找不到 `is_current` 段而失败；W-03 虽能建段但状态是 `active` 而非 `reinstated`，且不改关系。**OPEN DECISION，且带一个 P1 级可用性缺陷。**

### Q6. 是否有接口只更新 `status` 而不写关系字段？

有，W-04 `PUT /org/:id/status`。它只在 `employee_assignment` 上操作，**完全不碰 `employment_relation`**。

**这是否违反已批准的单向关系？** 严格说不违反——A-02 禁止的是"由 `assignment.status` 反向改写 `employment_relation`"，W-04 确实没写关系字段。但它是**单向派生的"另一端"**：在缺少派生机制的前提下，W-04 成了唯一能产生中间态/终态的手段，而它留下的关系事实仍是旧的。

**前端可达性（重要事实）**：

| 应用 | `assignOrg` | `updateOrgStatus` | 关系字段编辑 UI |
|---|---|---|---|
| web-naive | 已定义（`api/hse/employee.ts:477`），`OrgTransferModal.vue:162` 调用 | **无 API 定义**（全文件无 `/org/.../status`） | 有（`index.vue:792-803`） |
| web-antd | 已定义（`:593`），`OrgTransferModal.vue:219` 调用 | 已定义（`:598`），但**全仓无任何 UI 调用点** | **完全没有**（全目录仅 1 处注释命中 `employment_relation`） |

**⇒ 当前没有任何用户可见入口能触发 `status` 的状态变更（含中间态与终态）。** `PUT /org/:id/status` 是**孤儿接口**：后端完整实现（事务、history、事件齐备），前端零消费。这解释了为什么 `assignment.status` 的实际取值分布几乎只有 `active`/`former`（后者来自 replay 脚本）。

**⇒ 同时注意"关系可改、状态不可改"的不对称**：web-naive 能改关系（W-01，不动任职段），却不能改状态（W-04 无入口）。这个不对称本身就在持续扩大双口径矛盾。

**需区分**：这是"已批准规则未实现"还是"必须保留的独立历史操作"——属 OPEN DECISION。技术侧只陈述事实：**接口存在、语义完整、无入口**。

### Q7. 同一人员多条任职段时，如何确定作用对象？误关/误改风险？

| 路径 | 定位条件 | 风险 |
|---|---|---|
| W-03 `assignEmployee` | `WHERE ea.employee_id=$1 AND ea.is_current=true AND is_deleted=false`，取 `rows[0]` | **若存在多条 `is_current=true`，只关第一条**，其余保持 current ⇒ 多当前段 |
| W-04 `changeAssignmentStatus` | `WHERE ea.id=$1 AND ea.is_current=true`（按 **assignment.id**，不按 employee_id） | 相对安全（精确到段）；但若前端传错 id 会改错人 |
| W-05 `deleteEmployee` | `WHERE employee_id=$1 AND is_current=true`（**全量**，无 LIMIT） | 关掉所有 current 段 ✓ |
| W-07 `employeeImportService` | `WHERE employee_id=$1 AND is_current=true`（全量） | 关掉所有 current 段，但**不写 `end_date`** ⇒ 留下 `is_current=false` 且 `end_date=NULL` 的段 |
| W-08 `employeeImportV2Service` | `WHERE employee_id=$1 AND is_current=true AND is_primary=true` | **只关 primary 段** ⇒ 若存在 `is_current=true, is_primary=false` 的段，它会**保持 current**，与新插入的 primary 段并存 ⇒ 双当前段 |

**⇒ 风险确认存在：W-08 是"误留历史当前段"的主要来源；W-03 在脏数据下会漏关。**

### Q8. 若 `is_current` 与 `status` 本身已矛盾，自动派生如何处理？是否扩大错误？

**当前无自动派生，所以不扩大。** 但这是未来实现时必须前置处理的**前置条件**，因为现有矛盾数据会被派生逻辑二次加工：

|---|---|---|
| `status='active'` 且 `is_current=false` | W-05（删员工）、W-07（导入关旧段不改 status）、W-08（重置 current 不改 status）、W-10（归档全部） | 派生前必须先明确"历史已关闭段是否要改 status"，否则派生只影响 current 段，历史段仍矛盾 |
| `status='inactive'` 且 `is_current=true` | 理论可能（W-04 若 `event_date` 为未来日期也不改 is_current？实际终态必改） | 需定义优先级：`is_current` 还是 `status` 为准 |

### 11.3 三条最重要的发现（按严重度）

**① 月度花名册导入（W-08）会批量制造双口径矛盾（P0 级）**

`employeeImportV2Service.js:1023-1055`：无论员工关系是「辞职」「死亡」「退休」，只要出现在月度花名册里，其任职段就被无条件关闭并重建为 `status='active', is_current=true, is_primary=true`。而 `ROSTER_HEADER_MAP:45-61` **根本没有「用工关系状态」列**，导入侧读不到关系，也就无从判断。

⇒ 每执行一次月度导入，所有终态人员的任职段都会被"复活"为 active，而关系字段保持终态 ⇒ 矛盾面积随导入次数累积。**任何 A-02e 派生机制在这个入口修好之前都无法在生产上生效。**

**② 关系字段的变化完全无痕（P1 级）**

`updateEmployee` 可以写 `employment_relation`（走白名单校验），但：不碰任职段、不发事件（`changedFields:534` 白名单不含该字段）、不写 `employee_history`。

⇒ 关系从「正式员工」改成「辞职」，系统中除 `employee` 表那一列外**没有任何痕迹**，且任职段仍是 active。这与"关系是权威事实"的定位不匹配。

**③ 状态变更接口是孤儿，返聘路径实际不可达（P1 级）**

`PUT /org/:id/status` 后端实现完整（事务 + history + 事件 + 终态/中间态分支），但 `updateOrgStatus` 在 web-antd 有 API 定义却**零 UI 调用**，web-naive **连 API 定义都没有**。

且该接口按 `ea.id AND is_current=true` 定位段（`:507`），终态后段已 `is_current=false` ⇒ **返聘操作会直接返回"组织关系不存在或非当前记录"`（`:510-513`）**。返聘在终态后不可达，与 `STATUS_MAP['返聘']='reinstated'` 的可用性假设矛盾。

- ❌ 不得宣称"自动派生已实现"——当前**零派生**（§六 Q1）。
- ❌ 不得宣称"业务规则已批准"——§八 全部为 `OPEN DECISION`。
- ❌ 不得宣称"数据一致性问题已消除"——存量规模未核实（DB-INT-04）。
- ❌ 不得宣称"数据库集成通过"——零连接。
