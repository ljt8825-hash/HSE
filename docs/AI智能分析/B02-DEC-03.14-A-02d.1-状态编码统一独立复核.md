## 0. 结论摘要

**结论：PASS WITH GAPS**

编码统一的**核心机制已正确落地且可验证**：写入白名单 + 归一、三种终态原因统一为 `inactive`、`is_current`/`end_date` 终态关闭在**唯一真实运行入口**中一致、中间态不自动关闭任职段、`former`/`retired` 只读兼容、未知值显式拒绝、`employment_relation` 零写入。

但发现 **1 项已证实的业务语义缺陷（D1，中风险）** 与 **5 项缺口（D2–D6）**，其中 D1 直接违反 A-02d 任务书 §三.1「终态原因是否仍可从权威关系字段或其他已存在可靠记录中准确识别」：

> 把「退休」归一为 `inactive` 之后，`employment_relation` 在本仓库代码中**根本不存在「退休」取值**（全仓仅 `'正式员工'` / `'辞职'` / `'死亡'` 三值 + NULL）。
> 因此规则前提「原因由 employment_relation 表达」对退休不成立 → 退休人员在人员列表中由「退休」降级显示为「离职」，且「退休」筛选对新数据永不命中。

该项不阻断 A-02d 主体，但应在 A-03/A-04 开始前修正或由业务方明确裁决（见 §8 最小修正建议 M1）。

## 7. 缺陷清单与最小修正建议

### D1（已证实 · 中 · 必须修正或裁决）退休原因丢失导致展示与筛选降级

- **现象**：`退休` → `inactive` 后，人员列表显示「离职」、「退休」筛选永不命中新数据。
- **证据链**：
  1. `employeeStatusDict.js:30` `'退休':'inactive'`；
  2. `employeeService.js:134` `CASE WHEN employment_relation IN ('辞职','死亡') THEN 'left' ELSE assignment_status END` → 退休者落 `ELSE 'inactive'`；
  3. 全仓 `employment_relation` 比较值仅 `'正式员工'/'辞职'/'死亡'`（9 个文件、14 处），**无「退休」**；
  4. 前端 `STATUS_LABEL.inactive='离职'`（`web-naive/.../employee/index.vue:66`）；
  5. `employeeService.js:95-101` 的 `retired` 筛选走 `ev.assignment_status='retired'`。
- **性质**：不是编码错误，而是**规则前提不成立**——A-02d 假设「原因由 employment_relation 表达」，但该字段在本系统中**不具备「退休」取值**。
- **最小修正建议（三选一，需业务裁决，本轮不改）**：
  - **M1-a**：把 `退休` 纳入 `employment_relation` 的合法取值（需业务确认花名册是否支持；涉及数据治理，非 DDL 可解决）；
  - **M1-b**：`employee_history.event_type` 已保留「退休」，读侧（`/employees` 列表）改为左连最近一条终态历史的 `event_type` 作为原因展示与筛选依据；
  - **M1-c**：若业务接受「退休并入离职」，则删除「退休」筛选项并同步口径说明，避免用户看到 0 结果。
  - 任一方案落地前，**不建议把 A-02d 的 `退休→inactive` 推广到其他入口**。

### D2（已证实 · 中低 · 建议修正）`employee_history.after_status` 语义降级 + 新旧同列不一致

- **现象**：`employeeAssignmentService.js:551` 把 `after_status` 从「原始业务语义」改为 `toStatusLabel(normalizedStatus)` ⇒ 辞职/死亡/退休三条历史均写「离职」；而改动前分别写「辞职/死亡/退休」。
- **影响**：`web-naive` 与 `web-antd` 的 `EmployeeHistoryDrawer` 均展示「状态：之前 → 之后」，同一条记录的事件标签显示「退休」、状态行却显示「离职」，自相矛盾；同列历史数据（旧=退休，新=离职）口径不一。
