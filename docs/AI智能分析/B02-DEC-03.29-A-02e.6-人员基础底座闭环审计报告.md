## A. 综合判定

**结论：FAIL**

判定依据（不是「有问题所以 FAIL」，而是「任务书要求的三项闭环能力有两项不成立」）：

1. **人员关系写入不闭环**。系统唯一的权威字段 `employee.employment_relation` 存在**两条互不知道对方存在的写入路径**：一条经任职段事务（`assignEmployee` / `rehireEmployee` / `changeAssignmentStatus`），一条经人员编辑接口（`updateEmployee`）直接改。两条路径之间**没有任何同步机制** —— 我已确认全仓 `sql/*.sql` 中**不存在任何 employee 相关触发器**（`grep "CREATE TRIGGER" | grep employee` 零命中），也不存在同步服务函数。因此「关系改了、段没动」是结构性结果，不是偶发缺陷。
2. **任职段写入不闭环**。三条导入路径中，两条不写 `employee_history`，一条关段时不写 `end_date`，另一条把系统日期 `CURRENT_DATE` 当业务日期写。任职变更是「有记录无历史、有时间轴倒挂、有系统时间冒充业务时间」。
3. **存在一处 P0 级数据破坏面**。`POST /api/hse/employee-import/v2/clear-all` 与 `/clear-all-cascade` 是**无 WHERE 条件的全表物理删除**，仅以 `requireRole('admin')` 保护，**无权限码、无二次确认码、无环境门禁、无审计日志**，且在当前正式前端 `web-naive` 的菜单里两击可达。这一项与「人员关系治理」同域（它抹掉的就是人与任职段），按任务书 P0 定义「数据破坏或关键业务越权」判定为 P0。

同时必须说清的**反面事实**（避免报告被读成「一切都坏了」）：

- 终态防复活的三道闸门（B1 普通分配、C1 V1/V2 导入）**源码真实存在且位置正确**，均在首次写之前拦截，拒绝即零副作用 —— 这一项 **PASS**。

- 10 个关键文件 `node --check` 全部 EXIT=0，**无语法级破损**。

#### D.1-b【P0】状态变更接口办理退休/辞职/死亡时，不改写权威关系字段

**事实与证据**

`employeeAssignmentService.changeAssignmentStatus`（`:860-955`）全流程只操作 `employee_assignment` 与 `employee_history`，**函数体内没有任何 `UPDATE employee SET employment_relation`**。而 `employeeStatusDict.js:39-41` 把三种终态全部归一为 `inactive`：

```js
'辞职': 'inactive',
'死亡': 'inactive',
'退休': 'inactive',   // 新业务不再写 retired
```

于是产生一组**不可调和的矛盾**：`employee_history.event_type = '退休'`、`employee_assignment.status = 'inactive'`、`employee.employment_relation = '正式员工'`（原值未动）。

**影响链（逐条可推导）**

1. `displayStatusSql`（`employeeStatusDict.js:329-337`）先判关系=`退休`（不成立）→ 再判 `IN ('辞职','死亡')`（不成立）→ **回落到段状态 `inactive`** → 列表显示「**离职**」而非「退休」。
2. 返聘资格 `rehireEmployee:655-658` 要求 `relation.trim() === '退休'` → **拒绝**。即「通过状态接口退休的人永远无法返聘」。
3. 终态闸门 `checkRelationAllowsAssignment`（`:396-404`）读关系 → 读到「正式员工」→ **放行** → 该"已退休"人员可继续被调岗建新段，完全绕过 B1 的防护意图。
4. 统计 `activeCount`（关系=正式员工）把此人**算作在职**。

**可达性（如实说明）**：`PUT /org/:id/status` 在 `routes/hse-employee/assignment.js:34` **已挂载可用**；但 `web-naive` **无任何调用点**（grep `org/.*status` 仅命中一处注释），`web-antd` 仅有 API 定义（`api/hse/employee.ts:598`）且**无调用方**。故当前为 **仅 API 可达**（持有 admin/safety_manager token 者可直接调用），不是 UI 可达。

**是否为当前真实问题**：是。属于「接口语义与数据模型不一致」，一旦被调用即产生不可逆的错误关系数据。

**修复节点建议**：A 节点。**验收标准**：终态三值必须同时写 `employee.employment_relation`（与段关闭在同一事务），或该接口对终态入参返回 `-4` 并指向正确流程（与当年封堵「假返聘」同一处理方式）。

```js
                                                  ↑ $10 = p.hire_date（原始入职日）
```

即每次导入对**每个已存在员工**都执行「关旧段（end_date=今天）+ 建新段（start_date=原始入职日）」。当同一份月度花名册被重复导入时：
- 旧段 `end_date = 今天`，新段 `start_date = 2020-xx-xx` → **新段开始早于旧段结束，时间轴倒挂**；
- 每导入一次多一段 → 段数量随月份线性膨胀。

这与既有台账中「assignment 重复语义 12,955 行」的现象**方向一致**（本轮不连接数据库，**不宣称**已证实该数字由本路径产生，仅记录为**首要候选根因**，须 DB-INT 验证）。

同时该路径**不写 `employee_history`**（`grep employee_history services/employeeImportV2Service.js` **零命中**），所以每一次切段都是「无历史的任职变更」。

```js
// assessmentScoringEngine.js:186 / :565
```

1. 资格失败是否在任何业务写入前返回 —— **是**（返聘/分配/导入三处均满足）。
2. 人员关系更新未命中是否停止 —— **是**（`rehireEmployee:748-756` 判 `rowCount === 0` ⇒ `ROLLBACK` + `-2`）。这是 B2.2 相对历史缺陷的实质改进。

6. COMMIT/ROLLBACK/release 是否遗漏 —— 上述 4 个事务型函数 **无遗漏**。

## L. 一句话结论

**人员底座的"防复活"已经做对了，但"关系怎么改"和"段怎么变"这两件更基础的事还没有收口** —— 关系能从编辑弹窗直接改而段不知道，段能从导入反复重建而历史不知道，系统最危险的"清空所有人"按钮没有任何审计。在这三件事闭合之前，人员底座不能作为三违、隐患、检查、培训、事故、考核的稳定引用源；先修 P0-1（高危端点），再裁 P0-2（关系收口方案），是本轮给出的唯一路径。
