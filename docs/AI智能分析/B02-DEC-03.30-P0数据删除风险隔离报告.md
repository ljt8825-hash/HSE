**与 03.29 报告的差异更正（1 处，必须先讲）**

03.29 报告写「`clearAllCascade` 会先查 `pg_constraint` 拿全部外键子表逐个 DELETE」，方向正确，但漏了一个副作用：它在删除前会执行

```js
for (const t of ['hse_deduction_adjustment', 'hse_assessment_audit_log']) {
  await client.query(`ALTER TABLE ${t} DISABLE TRIGGER USER`);
}
```

即**临时禁用防篡改触发器**（考核扣分调整、考核审计日志）。本轮据此把「未执行 `DISABLE TRIGGER`」单列为核心断言 B4，而不是只断言「没有 DELETE」。

**但必须给出边界，避免把风险说大**：PostgreSQL 的 `ALTER TABLE ... DISABLE TRIGGER` 是**事务性 DDL**，因此无论正常走 `ENABLE`，还是中途异常走 `catch` 里的 `ROLLBACK`，触发器状态都会被一并还原；即使连接中断，PG 也会在会话结束时回滚该事务。所以这**不构成持久性禁用风险**。代码层面仅剩一个可读性缺陷：`DISABLE` 与 `ENABLE` 没有放进 `finally`，而是依赖 `ROLLBACK` 兜底——若将来恢复该功能，应改为 `finally` 显式还原（已登记为 P3）。

另一处更正：03.29 写「无审计」，本轮逐行复核确认 `clearAll` / `clearAllCascade` 函数体内 **0 次 `auditLog`**（该 service 的 `auditLog` 只出现在 upload 成功、pendingResolve、batchImport 三处），结论成立。
