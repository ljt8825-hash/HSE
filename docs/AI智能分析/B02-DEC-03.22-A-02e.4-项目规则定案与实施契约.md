**F-2｜`END_DATE` 的正确范式在代码中已经存在，导入侧是偏离者。**

`ASG:406-411`：

```js
const endDate = new Date(start_date);
endDate.setDate(endDate.getDate() - 1);
// UPDATE ... SET is_current = false, end_date = $2 WHERE id = $1
```

旧段结束日 = 新段生效日 − 1 天。同一仓库内，`ASG:195-203` 的 `endCurrentAssignment(client, employeeId, endDate)` 也把 `endDate` 设计为**必传参数**、无默认值。

而 `IMP:1025` 写死 `end_date = CURRENT_DATE`，`IMP:1052` 写 `start_date = COALESCE($10, CURRENT_DATE)`。

⇒ 结论：**「业务日期不得兜底」不是需要新建的能力，而是导入侧绕过了既有正确能力**。`endCurrentAssignment` / `createAssignment` / `updateAssignmentStatus` 三个函数**全仓无任何调用方**（仅自身定义与 `module.exports` 导出），属死代码（详见 §7.2）。

**F-3｜关系字段可被直改，且完全不联动任职段、不留痕、不发事件。**

`EMP:497-502` 写入 `employment_relation` 时：

- 走 `validateRelationInput` 白名单（`DICT:255-265`）—— **校验正确**；
- 但使用 `pool.query` 单语句（`EMP:525-529`），**无 BEGIN/COMMIT**；
- **不写** `employee_history`；
- `EMP:534` 的 `changedFields` 白名单**不含** `employment_relation` ⇒ 连 `EMPLOYEE_INFO_UPDATED` 也不发。

后果是双向口径分裂：

|---|---|---|---|---|

**F-4｜导入侧关段范围与 `endCurrentAssignment` 不一致。**

| 位置 | 关闭条件 |
|---|---|
| `IMP:1025-1026` | `employee_id=$1 AND is_current=true AND is_primary=true AND is_deleted=false` |
| `ASG:199` | `employee_id=$1 AND is_current=true AND is_deleted=false` |

若某员工存在 `is_current=true AND is_primary=false` 的段（非主岗），导入**不会**关闭它，随后又插入一条 `is_current=true AND is_primary=true` 的新段 ⇒ 同一员工出现多条 `is_current=true`。`v_employee_current`（`DDL-A:262+`）取 `is_current=true AND is_primary=true`，此时视图只取主岗，表面正常；但 `ASG:295-302` `findCurrentAssignmentByEmployeeId` 用 `is_current=true` 不加 `is_primary` 限定、`ASG:169` 历史查询亦然 ⇒ **在同一份数据上，「当前」有三个不同定义**。

补充（与 F-5 联动）：`uk_emp_assign_primary` 的谓词含 `is_primary = true`，因此**不拦**「1 条 `primary+current` + N 条 `primary=false+current`」的组合 ⇒ 上述「多 current」不会被数据库发现。

**F-5｜唯一约束存在，但**覆盖不足**——它拦不住终态复活。**

`employee_assignment` 上有 `uk_emp_assign_primary`：

```sql
CREATE UNIQUE INDEX uk_emp_assign_primary ON public.employee_assignment USING btree (employee_id)
  WHERE ((is_primary = true) AND (is_current = true) AND (is_deleted = false));
```

证据：`.workbuddy/phase4/backup_before_v68_prod_20260729_184427.sql:71576-71579`（生产库 dump）。该索引是 **partial unique index，不是 CONSTRAINT** —— 查 `pg_constraint` 得 UNIQUE 约束 0 条，巡检会漏判为「无保护」。

**它保护什么**：同一员工最多 1 条 `is_primary=true AND is_current=true` 的主岗段。
**它不保护什么**：

| 情形 | 是否被索引拦截 | 后果 |
|---|---|---|
| 终态人（无 `is_current=true` 段）导入后新增 1 条 `primary+current` 段 | **不拦截**（新段是唯一命中者） | **复活成功** |
| 已有 1 条 `primary+current`，再插 1 条同类 | 拦截 | 报 `duplicate key ... uk_emp_assign_primary` |
| 已有 `is_current=true AND is_primary=false` 段，再插 1 条 `primary+current` | **不拦截** | 出现 2 条 current |
| 2 条 `primary=false AND current=true` | **不拦截** | 出现 2 条 current |

⇒ **任务书 §3.3「不能依赖当前唯一索引兜底」的准确结论是：约束存在且对「重复主岗」有效，但对「终态复活」完全无效。** 复活之所以能成功，恰恰因为终态人**没有**当前段——索引的前提条件不成立。这不是「缺少约束」，而是**约束的谓词与风险场景不匹配**，属结构性缺口。

**可复用的反证**：既有运行证据显示该索引确实在生效——`docs/191副/③决策结论/2026-10-01_batch35-38导入失败根因诊断.md:23` 记录「重复 INSERT 触发 `uk_emp_assign_primary` 唯一约束部分冲突 → failedCount>0」。即「正常在职人员的重复导入会被拦，终态人员的复活不会被拦」。**这两件事同时为真**，是本条最需要被理解的地方。

**方法论纠偏（本轮实际发生）**：初稿仅在 `server/` 目录检索 `CREATE UNIQUE`，且结果被 `Select-Object -First 30` 截断，遂误判为「全仓无该约束」。该索引定义在数据库侧（dump 中），不在 `server/` 的迁移脚本里。**教训与 2026-08 记录的方法学一致：全仓检索零命中前，必须先用已知命中点验证检索式。** 本文件已按复查结果改写，`BLOCKED-B03` 保留但含义改为「确认实例上索引是否仍存在（dump 为 2026-07-29 时点）」。

*（本条为纠偏后版本；初稿结论「不存在任何 UNIQUE 约束」已作废，不保留于正文。）*

## 3 退休编码定案（RT 系列）

### 3.1 决定采用三层模型（RT-01，`FROZEN`）

| 层 | 承载字段 | 职责 | 允许取值 |
|---|---|---|---|
| **L1 关系事实** | `employee.employment_relation` | 「这个人当前与公司的关系是什么」——**终态原因的权威来源** | `正式员工` / `辞职` / `死亡` / `退休` / `NULL`(待核实) / `待岗`(历史兼容) |
| **L2 段存储状态** | `employee_assignment.status` | 「这一段任职关系处于什么阶段」——只表达段生命周期 | `active` / `pending` / `secondment` / `unpaid_leave` / `inactive` / `reinstated`（+ 只读历史 `retired` / `former`） |
| **L3 展示状态** | 读侧派生（不落库） | 「界面上显示什么」 | `active`/`pending`/`secondment`/`unpaid_leave`/`inactive`/`retired`/`reinstated`/`former` → 中文标签 |

**核心判据**：`retired` 存在于 L2 的**历史兼容**与 L3 的**派生结果**，但**不作为 L2 的新写入值**。退休的「原因」只由 L1 承载。

依据：`DICT:39`（`退休→inactive`）、`DICT:50`（`retired→inactive`）、`DICT:62`（`retired→退休` 展示）、`DICT:71-73`（`WRITABLE_STATUS_CODES` 不含 `retired`）、`DICT:105-110`（`RELATION.RETIRED`）、`DICT:282-290`（`displayStatusSql` 关系优先）。

### 3.2 六个必答问题的逐项答案

任务书 §3.1 要求回答六项。逐项如下。

#### RT-02｜人员关系字段的合法值及其语义（`FROZEN`）

| 值 | 语义 | 写入 | 统计数据影响 |
|---|---|---|---|
| `正式员工` | 在职；具备考核对象资格；计入「总数/在职」 | 允许 | `ACTIVE_RELATION` |
| `辞职` | 终态原因 | 允许 | 计入「离职」 |
| `死亡` | 终态原因 | 允许 | 计入「离职」 |
| `退休` | 终态原因；**不并入离职** | 允许 | 单列「退休」 |
| `NULL` | **待核实**（合法状态，不是「未填」） | 允许（留空即写 NULL） | 不计入任何口径 |
| `待岗` | **历史兼容值**，属字段混用（待岗是 L2 中间态，不是 L1 关系） | 仅兼容写入，不推荐新增 | 不计入「正式员工」 |

依据：`DICT:105-141`、`DICT:255-265`。

`NULL` 的三条纪律（继承 A-01，`FROZEN`）：
1. 任何导入、批量、迁移逻辑不得为 `NULL` 推断或补值；
2. `NULL` 不入「总数/在职/离职/退休」任一统计口径（`EMP:98-101` 用 `knownRelationInSql` 显式列出已知值，天然排除 `NULL`）；
3. 前端展示为「待核实」，不得显示为任一具体原因。

#### RT-03｜组织关系段存储状态（`FROZEN`）

沿用 `DICT:71-95` 现有集合，不新增、不删除：

| 编码 | 类别 | 关段行为 |
|---|---|---|
| `active` | 常规 | 不关 |
| `pending` / `secondment` / `unpaid_leave` | **中间态**（`DICT:85`） | **不得**仅因状态名而自动关段 |
| `inactive` | **终态**（`DICT:79`） | 关段：`is_current=false` + `end_date` |
| `reinstated` | 常规（返聘新段，见 §4） | 不关 |
| `retired` | 只读历史 | 视为终态，**禁新写入** |
| `former` | 只读历史（`DICT:88`） | 不参与新业务 |

**明确决定**：`inactive` 作为 L2 的终态编码予以**保留**，不替换为 `retired`。

理由（针对任务书「除非代码证据表明它与既有正式规则存在无法兼容的实质冲突」）：

- 全仓检索不存在以 `status='inactive'` 为业务判据的写入或统计分支；12 处 `assignment_status = 'active'` 的消费方对 `inactive` 与 `retired` 两值均不命中 ⇒ 替换的收益为零、影响面为零。
- 退休的「原因可辨性」由 L1 解决（RT-04），不需要 L2 承担。
- `DICT:50` 已把 `retired` 直写归一到 `inactive`，若反向要求写 `retired`，会与 `DICT:50` 直接冲突。

⇒ **不新增 L2 编码，不引入 DDL**。

#### RT-04｜终态原因的权威来源（`FROZEN`）

**唯一权威 = `employee.employment_relation`。**

- `assignment.status = 'inactive'` **单独**不得决定展示为辞职/死亡/退休（`DICT:21-22` 已声明）。
- 三个终态原因之间**不可互换**：退休不得误标为离职（`DICT:135-141` 的 `LEFT_RELATION_VALUES` 显式排除退休）。
- `employee_history.after_status` 保留原因字面量（`DICT:313-319` `toHistoryStatusLabel`），使历史事件可辨原因。

#### RT-05｜`displayStatusSql` 的优先级（`FROZEN`）

采用现有实现，优先级**自上而下短路**：

```
1. employment_relation = '退休'                 → 'retired'
2. employment_relation ∈ ('辞职','死亡')         → 'left'
3. 否则                                          → assignment.status
```

依据：`DICT:282-290`。

档案维度另有 `profileStatusSql`（`DICT:297-306`），在 `retired` / `left` 之后追加 `is_deleted → inactive`，其余 `active`。两者**必须同时遵守同一优先级**，不得只改其一。

**风险声明（`PROPOSED-P1`）**：第 3 分支直接透出 `assignment.status`，若关系为 `NULL` 且段为 `inactive`，展示为「离职」——这是**推断**，与 RT-02 第 3 条「待核实不得显示为具体原因」冲突。当前不改（改动会影响 1,951 名历史辞职人的展示），登记为 `PROPOSED`，需在 Batch A 单独评估。

#### RT-06｜列表 / 详情 / 统计 / 筛选的统一显示规则（`FROZEN`）

| 场景 | 规则 | 现位置 |
|---|---|---|
| 列表列 `org_status` | `displayStatusSql` | `EMP:149` |
| 档案页状态 | `profileStatusSql` | `PRF:151` |
| 筛选 `status=active` | `employment_relation = '正式员工'` | `EMP:104-105` |
| 筛选 `status=left` | `employment_relation ∈ ('辞职','死亡')` | `EMP:106-107` |
| 筛选 `status=retired` | `employment_relation='退休' OR assignment_status='retired'`（**并集**） | `EMP:108-113` |
| 筛选 `status=pending/secondment/...` | `assignment_status = <code>` | `EMP:114-118` |
| 默认（无状态筛选） | 仅 `employment_relation='正式员工'` | `EMP:119-122` |
| 统计卡「总数」 | `knownRelationInSql`（含退休） | `EMP:98-101` |
| 统计卡「在职/离职」 | `ACTIVE_RELATION` / `LEFT_RELATION`（退休不计入离职） | `EMP:210-213` |

**「统计与下钻同源」校验（必须保持）**：统计卡「退休」的人次，与 `status=retired` 筛出的行数，必须由同一判据产生。当前两者都表达为「关系=退休 ∨ 段=retired」，**同源成立**。Batch A 若改动任一侧，必须同步另一侧，并在测试中断言两侧相等。

#### RT-07｜历史数据的兼容方式（`FROZEN`）

| 数据类型 | 兼容方式 |
|---|---|
| `assignment.status = 'retired'`（历史） | 读兼容：`DICT:62` 展示为「退休」；筛选走 `EMP:112` 的并集；**不批量改写** |
| `assignment.status = 'former'`（历史） | 读兼容：`DICT:67` 展示中性「历史段」；不推断为辞职/离职；**不新增、不批量改写、不删除** |
| `employment_relation = NULL`（历史） | 保持待核实；展示/统计均不进具体口径 |
| `employment_relation = '待岗'`（历史混用） | 保留写入兼容（`DICT:123`），不纳入正式取值 |

**禁止**：任何形式的「历史数据一次性对齐」批量 UPDATE。历史修复必须走独立数据治理方案（`FROZEN`，见 DT-07）。

### 3.3 关于「同一码值 `retired` 承担两种语义」的决定（RT-08，`FROZEN`）

现状：`retired` 既是「L1 关系=退休 派生的 L3 展示值」，又是「L2 段存储的历史值」。两者语义不同、码值相同。

**决定：不拆分，视为同义合并。**

理由：

1. 两者在**所有消费端的可见行为完全一致**——都表示这个人/这段关系是「退休」，中文标签都是「退休」（`DICT:62`）；
2. 拆分需要新增 L3 专用码（如 `rel_retired`），将同时改动 `DICT`、两套前端 `employee-status.ts`、`STATUS_TAG` 色板、以及所有 `retired` 字符串比较点，**收益为零、回归风险为全量**；
3. 未来的区分需求由 L1 直接满足（需要知道「是关系退休还是段退休」时，查 `employment_relation` 即可），不需要在 L3 编码上再分叉。

**约束**：任何新增代码**不得**依赖「`retired` 一定是段存储值」或「`retired` 一定是派生值」这两个假设中的任何一个。判断依据必须显式取字段（`DICT:282-290` 的 SQL 已遵守）。

### 3.4 退休语义映射总表（RT-09，`FROZEN`）

| 业务事件 | L1 关系 | L2 段 status | L2 is_current / end_date | L3 列表展示 | 统计口径 | 历史事件 |
|---|---|---|---|---|---|---|
| 在职 → 退休 | `退休` | `inactive` | `false` / 业务退休日 | 退休 | 退休（不计离职） | `event_type='退休'`，`after_status='退休'` |
| 历史数据（段=retired，关系为空） | `NULL` | `retired` | 已是历史值 | 退休 | 退休 | 不改写 |
| 退休 → 返聘 | `正式员工` | 旧段不动；新段 `reinstated` | 旧段 `false`；新段 `true` | 返聘 | 在职 | 新增 `event_type='返聘'`，旧「退休」事件保留 |

## 4 返聘定案（RH 系列）

### 4.1 业务模型（RH-01，`FROZEN`）

**返聘是独立业务动作，不是「把已关闭的段改回 active」。**

形式化定义：

```
返聘(员工 E, 生效日 D, 目标组织/岗位 P) :=
  前置：E 当前处于终态（L1 ∈ {辞职,死亡,退休} 或 无 is_current=true 段 且 存在终态段）
  动作（同一事务）：
    A1. 旧段：保持 status='inactive'（或历史 'retired'）、is_current=false、end_date=<原终态日>
        —— 不修改、不删除、不重开
    A2. 新段：INSERT status='reinstated'、is_current=true、is_primary=true、start_date=D
    A3. 关系：UPDATE employee SET employment_relation='正式员工'
    A4. 历史：INSERT employee_history(event_type='返聘', event_date=D, after_status='返聘')
    A5. 事件：publishEmployeeEvent(EMPLOYEE_REHIRED) —— 新增类型，见 RH-06
  后置断言：E 有且仅有 1 条 is_current=true；该条 is_primary=true；start_date=D 且 > 旧段 end_date
```

### 4.2 逐条决定

#### RH-02｜旧段保留（`FROZEN`）

旧段**不得**修改 `status`、`is_current`、`end_date`。依据：任务书 §3.2 第 1 条；`DICT:79` 终态语义。

**禁止的替代方案**：当前 `changeAssignmentStatus:507` 按 `ea.id AND ea.is_current=true` 定位，终态后该段已 `is_current=false`，调用必返 `-2 组织关系不存在`（`ASG:510-513`）。**不得**为让该接口「能用」而放宽为「找任意段并改回 active」——那等价于把历史终态抹掉，且丢失 `end_date`。

#### RH-03｜新段四字段一致性（`FROZEN`）

| 字段 | 值 | 一致性要求 |
|---|---|---|
| `status` | `reinstated` | 必须在 `WRITABLE_STATUS_CODES`（`DICT:71-73`，已含） |
| `is_current` | `true` | 全员工仅此 1 条为 true |
| `is_primary` | `true` | 与 `is_current` 同真；不得出现 `is_current=true AND is_primary=false` 残留 |
| `start_date` | 返聘生效日 D | **必填业务日期**，禁 `CURRENT_DATE` 兜底（DT-02） |

#### RH-04｜关系层表达：重置为「正式员工」（`FROZEN`）

这是本节点最关键的决定，必须单独说明。

**问题**：若返聘只建新段、不改 L1 关系，则 `displayStatusSql` 第 1 分支（`DICT:286`）命中 `employment_relation='退休'`，界面**继续显示「退休」**，统计继续把该人算作「退休」——违反任务书 §3.2「不允许只新增组织关系段而继续显示退休」。

**决定**：返聘必须把 `employment_relation` 重置为 `正式员工`。

**理由**：

1. `employment_relation` 的语义是**当前关系事实**，不是历史（历史在 `employee_history`）。一个人被返聘后，「当前与公司的关系」就是正式员工，写「退休」是事实错误。
2. **不新增任何关系枚举值**。`正式员工` 已在 `RELATION_VALUES`（`DICT:113-115`）与 `WRITABLE_RELATION_VALUES`（`DICT:126-128`）中，`validateRelationInput` 直接放行。这满足任务书「没有证据时不得直接新增正式枚举值」的要求——**返聘不需要新增值**。
3. 原终态原因不丢失：`employee_history` 中 `event_type='退休'/'辞职'/'死亡'` 的历史记录**原地保留**，返聘新增一条 `event_type='返聘'`。原因可追溯性由历史表提供，不需要关系字段继续持有旧原因。

**代价与缓解**：关系被覆盖后，若有人问「这个人退休过吗」，唯一途径是查历史表。缓解措施（`FROZEN`）：Batch B 必须在员工详情页的「人事变动历史」中保证返聘记录可见（`ASG:169-193` `getAssignmentHistory` 已存在，需确认其覆盖 `employee_history`）。

#### RH-05｜`displayStatusSql` 是否需要新增返聘分支（`FROZEN`）

**决定：不新增分支。**

- RH-04 执行后关系为 `正式员工`，`displayStatusSql` 落到第 3 分支 `ELSE assignment_status` ⇒ 返回 `reinstated` ⇒ `DICT:63` 映射为「返聘」。行为已正确。
- 若强行新增 `WHEN relation='返聘'` 分支，会与 RH-04 冲突（关系里根本没有「返聘」值），且引入新的不可能状态。
- 兜底：若 RH-04 因故未生效（关系仍为旧终态），展示会停在旧终态——**这是安全失败**（宁可显示退休，不可显示在职）。

**约束（写入 Batch B 验收）**：必须有一条测试断言「返聘后 `displayStatusSql` 返回 `reinstated`」，以证明 RH-04 与 RH-05 联合生效。

#### RH-06｜事件与留痕（`FROZEN` 规则；事件类型名 `PROPOSED`）

- `employee_history` 必须写：`event_type='返聘'`、`event_date=D`、`before_status=<旧终态中文>`、`after_status='返聘'`。
- `eventMap`（`ASG:537-540`）已含 `'返聘':'返聘'`，可复用。
- **现状缺陷（F-6 关联）**：`ASG:564` 的 `resignedLabels = ['离职','辞职','死亡']` **不含「退休」** ⇒ 退休发布的不是 `EMPLOYEE_RESIGNED` 而是 `EMPLOYEE_STATUS_CHANGED`。这是既有不一致，登记为 `PROPOSED-RH2`：退休应发布何种事件类型，需与下游事件消费方一并评估，Batch B 不改。
- 新增 `EMPLOYEE_REHIRED` 事件类型：`PROPOSED`。若下游无消费方，可先复用 `EMPLOYEE_TRANSFERRED` 并在 payload 标记 `isRehire:true`，避免新增类型造成下游静默丢弃。

#### RH-07｜入口设计（`FROZEN` 设计层；实现归 Batch B）

**决定：新增独立动作 `rehireEmployee`，不改 `changeAssignmentStatus`。**

| 方案 | 判定 | 理由 |
|---|---|---|
| A. 改 `changeAssignmentStatus` 支持「无当前段则建段」 | **否决** | 混淆「状态变更」与「新建段」两种语义；该接口同时服务中间态切换（待岗/复岗），加建段逻辑会污染所有调用方；且其入参 `{id, status, event_date}` 不携带目标组织/岗位，无法建段 |
| B. 复用 `assignEmployee`（调岗）并加分支 | **否决** | `assignEmployee` 的语义是「调到某组织」，其 `eventType` 判定（`ASG:431`）与 `after_status` 硬编码（`ASG:434`）都以「在职人员调动」为前提；改造面等于重写 |
| C. **新增 `rehireEmployee`** | **采用** | 职责单一；参数可完整表达前置条件与新段字段；可独立测试；不触碰现有两个接口的既有行为 |

**接口形态（`PROPOSED`，实现时确认）**：`POST /api/hse/employee/org/rehire`，权限复用 `hse:personnel:create`（与 `/org/assign` 同级），入参 `{ employee_id, start_date, team_id, position_id, change_reason }`。

**前端可达性（`FROZEN` 要求）**：返聘入口必须在员工列表行操作中出现，且**仅当**该行 `org_status ∈ {left, retired, inactive}` 时可点。这同时解决 A-02e.3 记录的「`PUT /org/:id/status` 是孤儿接口」问题——不复活孤儿接口，而是提供有 UI 的正向入口。

#### RH-08｜`assignEmployee` 必须拒绝终态人员（`FROZEN`，P0）

现状 `ASG:368-479`：

```
L386 查 is_current=true 段 → 终态人 0 行
L408 关段分支被跳过（rows.length===0）
L421 INSERT ... 'active', is_current=true, is_primary=true   ← 无条件执行
L431 eventType = '入职'（因 0 行）
L434 after_status = '在职'（SQL 字面量，硬编码）
```

⇒ 终态人经「调岗」按钮即被复活为 `active`，且历史记成**「入职」**——审计上无法与真正的新入职区分。这是 F-1/② 路径。

**决定**：`assignEmployee` 在开启事务后、执行任何写操作前，必须判定员工当前关系：

- 关系 ∈ `{辞职,死亡,退休}` 或 存在终态段且无 `is_current=true` 段 ⇒ **返回 `{error:-4, message:'该员工已处于终态，请使用返聘流程'}`**，不做任何写操作。
- 中间态（`pending/secondment/unpaid_leave`）⇒ 允许调岗，但新段 `status` **必须继承原中间态**，不得重置为 `active`（见 IMP-05）。

**不得**用「前端隐藏按钮」替代后端判定。前端隐藏是体验优化，后端拒绝才是这条 P0 的实际防线。

|---|---|---|

## 5 V2 导入与终态保护（IMP 系列）

### 5.1 复活路径 ① 的真实执行顺序（任务书 §3.3 明确要求）

代码事实（`IMP:1021-1056`），逐语句还原：

```js
// ── 语句 1（L1023-1028）──
await client.query(
  `UPDATE employee_assignment
   SET is_primary = false, is_current = false, end_date = CURRENT_DATE, updated_at = CURRENT_TIMESTAMP

// 返回值未被接收（无 const res = ...；无 if (res.rowCount === 0)）

// ── 语句 2（L1049-1055）──

  `INSERT INTO employee_assignment
   (employee_id, org_unit_id, ..., is_primary, is_current, status, start_date, ...)

```

**逐问回答**：

| 问题 | 答案 | 依据 |
|---|---|---|
| UPDATE 命中 0 行时，INSERT 是否仍执行？ | **会执行**。两条独立 `await client.query`，INSERT 不读取 UPDATE 的 `rowCount`，无任何条件依赖 | `IMP:1023` 与 `IMP:1049` 之间无控制流 |

| INSERT 会成功吗？ | 会。`status='active'`、`is_primary=true`、`is_current=true` 均为合法值；`uk_emp_assign_primary` **不会拦**——终态人此刻没有 `is_current=true` 段，新插入的这条是唯一命中该索引谓词的行 | F-5；`backup_before_v68_prod_20260729_184427.sql:71576-71579` |
| 复活后界面显示什么？ | **取决于 L1 关系**：关系=`退休` → 显示「退休」（假象）；关系=`辞职/死亡` → 显示「离职」；关系=`NULL` → `ELSE assignment.status='active'` → **显示「在职」** | `DICT:282-290` |
| 是否存在事务保护？ | 单行在 `SAVEPOINT` 内（`IMP:1064`），失败仅回滚该行（`IMP:1067-1069`），不阻断整批 | `IMP:1065-1072` |

⇒ **本条的实质风险不是「数据被删」，而是「终态人员在库里悄悄多出一条 active 当前段」，且是否可见完全取决于关系字段是否为空。** 关系为空的历史终态人（待核实人群）会直接显示为在职。

### 5.2 三条复活/失真路径汇总

| # | 路径 | 触发条件 | 结果 | 是否留痕 | 可见性 |
|---|---|---|---|---|---|
| ① | V2 导入 | 终态人在本期名册中 | 新增 `active+current+primary` 段 | 否（无 history） | 关系为 NULL 时显示「在职」 |
| ② | 调岗 `/org/assign` | 对终态行点「调岗」 | 新增 `active+current+primary` 段 | 是，但记成**「入职」** | 关系非 NULL 时被关系遮蔽 |
| ③ | 编辑页改关系 | 把关系从终态改回正式员工 | 段仍 `inactive+非current` | 否 | 显示「离职」，但统计算「在职」 |

路径 ③ 是「假在职」，与 ①② 的「假复活」方向相反，但同样破坏口径一致性。

### 5.3 导入规则（IMP-01~IMP-09）

#### IMP-01｜导入前终态闸门（`FROZEN`，P0）

对每个 `employeeId`，在**执行任何写操作之前**（即在 `IMP:1023` 之前），执行一次判定：

```sql
-- 判定条件（逻辑表达，非最终 SQL）
终态 := (
  employee.employment_relation IN ('辞职','死亡','退休')
  OR (  EXISTS(段 status IN ('inactive','retired')) AND NOT EXISTS(段 is_current=true) )
)
```

**双条件缺一不可**：

- 只看关系 ⇒ 关系为 `NULL` 的终态人漏网（正是最危险人群）；
- 只看段 ⇒ 关系已标终态但段未关闭的「假退休」人漏网（F-3 产物）。

命中 ⇒ 该行走 IMP-02 冲突路径。

#### IMP-02｜冲突路径（`FROZEN`）

| 项 | 规则 |
|---|---|
| 默认动作 | **不复活**。跳过该行的段写入（不 UPDATE、不 INSERT） |
| 记录 | 计入返回体的 `conflicts` 数组：`{row_num, employee_id, employee_name, reason:'terminal_conflict', relation, last_status}` |
| 批次状态 | `partial_completed`（`IMP:1080` 现有机制已按 `failedCount>0` 判定，需扩展为 `failedCount+conflictCount>0`） |
| 其他行 | 不受影响（savepoint 隔离保持不变） |
| 是否允许人工强制 | **不允许**在本批次内强制。若确需复活，必须走 RH-07 的返聘接口 |

**明确禁止**：把冲突行「自动按名册重建为 active」作为默认路径。

#### IMP-03｜不得静默覆盖中间态（`FROZEN`）

现状：`IMP:1049-1055` 对**所有**员工无条件插入 `status='active'`。若某人当前段为 `pending/secondment/unpaid_leave`，导入后即被重置为 `active`。

**决定**：导入不得改变中间态。
- 名册未表达状态 ⇒ 名册**无权**决定状态（O-1/D-1 只说明名册是人员版本权威，不说明它是状态权威）。
- 中间态继承细则（组织/岗位变化时新建段应继承何种 status）标 `PROPOSED-IMP1`：建议「继承原中间态」，因名册无状态信息、默认 `active` 属无据推断。

#### IMP-04｜时间轴约束（`FROZEN`，承接 D-5）

| 约束 | 内容 |
|---|---|
| T-1 | 旧段 `end_date` = 新段 `start_date` − 1 天（对齐 `ASG:406-411` 既有正确实现） |
| T-2 | 禁止 `end_date = CURRENT_DATE` 与 `start_date = hire_date` 并存导致倒挂（`IMP:1025` + `IMP:1052` 现状） |
| T-3 | 新段 `start_date` 必须 > 该员工既往任何段的 `end_date`（无重叠） |
| T-4 | `start_date` 缺失 ⇒ 走 IMP-05，不得 `COALESCE(..., CURRENT_DATE)` |

#### IMP-05｜业务日期缺失处理（`FROZEN`，承接 D-6）

`IMP:1052` 的 `COALESCE($10, CURRENT_DATE)` **必须移除**。替代规则：

| 情形 | 处理 |
|---|---|
| 名册有 `hire_date` 且有批次业务生效日 | `start_date` = 批次业务生效日（**不是** `hire_date`，理由见 DT-04） |
| 名册无 `hire_date`、有批次业务生效日 | 同上；`hire_date` 仅留档不建段 |
| 批次无业务生效日 | **该批次不得进入正式导入**。需在批次创建阶段强制填写（`PROPOSED`：`employee_import_batch` 增加 `business_effective_date` 列，属 Batch D，需 DDL ⇒ 见 `BLOCKED-B01`） |

#### IMP-06｜不依赖唯一索引兜底（`FROZEN`）

`uk_emp_assign_primary` 存在（F-5），但只覆盖「重复主岗」，**不覆盖终态复活**，且不覆盖 `is_primary=false` 的 current 段堆叠。因此：

- 幂等性与终态保护必须由**应用层**保证，不得把「数据库会拦住」当作防线；
- 具体地：不得在导入逻辑中依赖「插入冲突会报错」来发现终态复活——终态复活**不会**冲突；
- `IMP-01` 的双条件闸门是唯一实际防线；
- 该索引是否仍存在于当前生产/dev 实例（dump 为 2026-07-29 时点），标 `BLOCKED-B03`；无论是否存在，本条决定不变。

#### IMP-07｜关段范围统一（`FROZEN`）

导入侧的关闭条件必须与 `ASG:199` 对齐：`is_current = true AND is_deleted = false`（**去掉 `is_primary = true` 限定**），否则残留多 current（F-4）。

同时规定「当前段唯一性」的唯一权威定义（`FROZEN`）：

> **当前段** := `is_current = true AND is_deleted = false`。
> 若存在多条，数据即视为异常，不得由任一查询自行挑一条「看起来对」的。

`v_employee_current` 的 `is_primary=true` 限定（`DDL-A:262+`）是**视图投影选择**，不是当前段定义。`ASG:295-302`、`ASG:169` 需在 Batch E 统一。

#### IMP-08｜导入与审批的边界（`FROZEN`）

> 名册导入 ≠ 正式人事关系变更审批。

⇒ 导入**无权**：
- 创建返聘（RH-07 专属）；
- 改变 `employment_relation`（`IMP:990-1006` 现不写该字段，应保持）；
- 覆盖中间态（IMP-03）；
- 为 `NULL` 关系补值（RT-02）。

#### IMP-09｜运行时 DDL 不属本轮范围（`FROZEN` 边界）

`IMP:596 ensurePendingColumns()` 与 `IMP:618 ensureViewFields()` 会在运行时执行 DDL。此为既有 P1 风险，**本轮不定案、Batch C 不得触碰**，避免把导入改造与运行时 DDL 治理混在同一批。

## 6 日期语义与时间轴（DT 系列）

### 6.1 已冻结前提（不重开）

DEC-01 `:221-222`：D-5「人员历史关系由业务有效日期控制」、D-6「系统登记时间与业务生效时间必须分离」。二者为**已冻结禁止性前提**，本文件不设「是否同意」选项。

### 6.2 决定

#### DT-01｜两类时间的字段归属（`FROZEN`）

| 类别 | 字段 | 语义 |
|---|---|---|
| **业务时间** | `employee_assignment.start_date` / `end_date`、`employee_history.event_date`、`employee.leave_date` | 业务上「何时生效」，必须由业务输入 |
| **系统时间** | `created_at`、`updated_at`、`imported_at`、`uploaded_at`、`completed_at` | 系统「何时记录」，由 `NOW()`/`CURRENT_TIMESTAMP` 产生 |
| **禁用** | 用系统时间填充任一业务时间字段 | —— |

#### DT-02｜禁止兜底（`FROZEN`）

以下模式在业务日期字段上**一律禁止**：

- `COALESCE(<业务日期>, CURRENT_DATE)`
- `<业务日期> = CURRENT_DATE` 作为默认写入
- `start_date DATE NOT NULL DEFAULT CURRENT_DATE`（`DDL-A` 建表默认，属 DDL 层兜底）

**已存在的违规点**：`IMP:1025`、`IMP:1052`。`DDL-A` 的列默认标 `BLOCKED-B02`（需 DDL 才能移除，DB-INT 授权后处理）。

#### DT-03｜前端不得预填系统日期（`FROZEN`）

| 文件 | 现状 | 目标 |
|---|---|---|
| `MODAL-N:62` / `:184` | `startDate = ref<number>(Date.now())` / `resetForm()` 内 `Date.now()` | 初值 `null` |
| `MODAL-N:147` | `if (!startDate.value)` 必填校验 | 因初值非空，**永不触发** | 初值置 `null` 后该行自然生效 |
| `MODAL-A:128` / `:243` | `startDate = ref<Dayjs>(dayjs())` / `dayjs()` | 初值 `null` |
| `MODAL-A:204` | `if (!startDate.value)` | 同上 |

**这是「用前端预填系统日期掩盖业务日期缺失」的实例**，任务书 §3.4 第 3 条明确禁止。

#### DT-04｜`hire_date` 的语义边界（`FROZEN`）

`hire_date`（名册「入职日期」）语义 = **首次入职日**。它**不是**：

- 本次调岗生效日；
- 本期花名册业务生效日；
- 返聘生效日。

**现状缺陷**：`IMP:1052` 用 `COALESCE($10, CURRENT_DATE)`，`$10 = p.hire_date`。若名册的入职日期是 2019-03-01，则每次月度导入都会新建一条 `start_date=2019-03-01` 的段 ⇒ 所有段起始日相同 ⇒ **时间轴失去意义**，且与旧段的 `end_date=CURRENT_DATE` 直接倒挂。

**决定**：`hire_date` 仅用于员工**首次建档**时的首个任职段；后续任何导入的重建段，`start_date` 取批次业务生效日。

#### DT-05｜各路径的日期来源（`FROZEN`）

| 路径 | 当前行为 | 目标行为 | 缺失输入处理 |
|---|---|---|---|
| V2 导入建段 | `COALESCE(hire_date, CURRENT_DATE)`（`IMP:1052`） | 批次业务生效日 | 无生效日 ⇒ 批次不得提交（IMP-05） |
| V2 导入关段 | `CURRENT_DATE`（`IMP:1025`） | 新段 `start_date − 1` 天 | —— |
| 调岗 `/org/assign` | `start_date` 必填（`ASG:375`）；旧段 `end_date = start_date−1`（`ASG:406-411`） | **保持**（既有正确范式） | 缺 `start_date` ⇒ 已拒绝 |
| 状态变更 `/org/:id/status` | `event_date` 必填（`ASG:496`） | **保持** | 缺 ⇒ 已拒绝 |
| 编辑页改关系 | 无日期参与 | 终态时 `end_date = leave_date`（业务输入） | `leave_date` 缺失 ⇒ 见 DT-06 |
| 前端调岗弹窗 | 预填系统日（DT-03） | 强制业务输入 | 空 ⇒ 前端必填拦截 + 后端拒绝 |

#### DT-06｜`leave_date` 与终态日的绑定（`PROPOSED`）

现状：`EMP:503-506` 把 `leave_date` 作为普通字符串字段写入，与 `assignment.end_date` 无任何联动。

**方向**：终态原因的 `end_date` 应与 `leave_date` 同源。但因当前 `leave_date` 存储为字符串（`String(...).trim()`），且历史数据质量未知，细则标 `PROPOSED-DT1`：Batch E 实施前须先核 `leave_date` 的实际类型与填充率（需 DB，或从 `DDL` 与 `EMP:544-546` 推断为文本列）。

#### DT-07｜历史日期修复不批量覆盖（`FROZEN`）

- 禁止对现存 `end_date`（16,826 条失真 + 3,238 条 NULL，见 DEC-01 `:188`）执行批量 UPDATE；
- 修复必须单独立项，包含：可修复判据、逐条依据、回滚方案、抽样验证；
- 本文件**不**为历史修复提供任何 SQL。

### 7.3 决定

#### TX-01｜关系变更必须同事务 + 必留痕（`FROZEN`，P0）

`updateEmployee` 写 `employment_relation` 时，必须：

1. 包裹 `BEGIN/COMMIT`（当前无，`EMP:525`）；
2. 同一事务内派生段动作（见 TX-02）；
3. 写 `employee_history`；
4. 发事件（`EMPLOYEE_STATUS_CHANGED` 或专用类型）。

**不得**以「前端已有二次确认」替代后端事务与留痕。

#### TX-02｜关系变更到段动作的派生规则（`FROZEN`）

| 关系变化 | 段动作 |
|---|---|
| 正式员工 → 辞职/死亡/退休 | 关闭当前段：`status='inactive'`、`is_current=false`、`end_date=<业务日期>` |
| 辞职/死亡/退休 → 正式员工 | **不在本接口建段**。返回 `{error:-4, message:'终态人员恢复在职须走返聘流程'}` |
| 终态原因 A → 终态原因 B（如 辞职→退休） | 允许，仅改 L1；段保持 `inactive` 不动；写历史 |
| 任意 → `NULL` | 允许（待核实）；**不**改段、**不**推断 |
| 正式员工 → 待岗（历史混用值） | 允许写入但不推荐；**不**改段（待岗是 L2 中间态，不是 L1 关系） |

**第 2 行是本节点最重要的防复活规则之一**：否则「改关系」会变成绕过 RH-07 的后门，产生「在职但无当前段」的第三种坏状态（F-3 表格末行）。

#### TX-03｜业务时间 vs 系统时间（`FROZEN`）

- `employee_history.event_date` = 业务时间，必填，无兜底（`ASG:496` 已实现）；
- `created_at` / `updated_at` = 系统时间；
- 事件 payload 的 `occurredAt`（`ASG:569`、`ASG:446`）当前用 `new Date().toISOString()`，**是系统时间而非业务时间** ⇒ 标 `PROPOSED-TX1`：需在 payload 中增加 `businessDate` 字段承载业务时间，`occurredAt` 保留系统时间语义。

#### TX-04｜事件必达性（`FROZEN`，明确「不承诺必达」）

现状：所有事件发布均包在 `try/catch` 内，失败仅 `console.warn`（`ASG:578-580`、`ASG:455-457`、`EMP:545-547`）。

**决定**：

1. **不引入 outbox 表**（需 DDL，且当前无证据表明下游依赖事件做关键闭环）；
2. 明确声明：**事件为「尽力而为」投递，不构成必达保证**；
3. 因此**任何统计、考核、闭环判定都不得以「是否收到事件」为唯一依据**（这条本身就是红线）；
4. 失败日志从 `console.warn` 升级为 `console.error` 并带 `employeeId` + `type`（Batch E）；
5. outbox 列为 `BLOCKED-B04`（需 DB-INT 授权后方可评估）。

#### TX-05｜统一服务边界（`FROZEN` 目标态）

目标：人事关系与任职段的所有写操作，收敛到**单一服务模块**，内部提供三个原子动作：

| 动作 | 语义 | 复用者 |
|---|---|---|
| `applyStatusChange` | 中间态切换（待岗/复岗/借调/停薪留职） | `/org/:id/status` |
| `applyTermination` | 终态（关段 + 关系 + 历史 + 事件） | 编辑页改关系、状态变更 |
| `applyRehire` | 返聘（RH-01 的 A1~A5） | 返聘接口 |

**约束**：`applyTermination` 与 `applyRehire` 必须互斥且可判定——不得存在「既不是终止也不是返聘」的状态迁移路径。

本文件只定契约，重构归 Batch E。

#### TX-06｜死代码处置（`FROZEN`）

`endCurrentAssignment` / `createAssignment` / `updateAssignmentStatus` 三函数：

- **不得**在文档或汇报中称为「已实现的统一入口」；
- Batch E 决定：要么让路径真正调用它们（推荐，`endCurrentAssignment` 的「endDate 必传」设计正是 DT 需要的），要么删除；
- **禁止**保留它们同时又在内联 SQL 里重复实现同一逻辑（当前状态）。

### C1-RULE-02｜冲突原因

「存在终态段且无 `is_current=true` 段」用**任职段形态**反推**人员关系**，与下列已确立规则直接冲突：

| 依据 | 位置 | 冲突点 |
|---|---|---|
| 人员关系是权威字段，段状态单向派生 | `server/services/employeeStatusDict.js:5-7`（文件头 §1-§3） | 段形态不得反向定义关系 |
| 禁止用 `assignment.status`/`is_current` 推断关系 | DEC-01 `§3.2` 前提 O/D 系列；A-02e.4 附录 A `2-δ` | 同一禁止性约束 |
| NULL 关系 = 待核实，禁补值、禁推断 | `employeeStatusDict.js:250-259`（`validateRelationInput`） | 段关闭会被误读为「已离职」 |

按该分支实施会产生**两类误拦截**（均成员合法、可继续用工）：

1. **关系为 NULL + 当前段已关闭**的待核实人员（V2 导入关段后即为该形态）；
2. **关系为「正式员工」但任职段被误关**的人员（历史 `migration`/人工操作可产生）。

即：该分支会把「数据缺陷」当成「人员终态」，属**以缺陷判定业务**，故裁定不予实施。

该行含两个可分离的条件，本次分别裁定：

| 子条件 | 原文片段 | 裁定 |
|---|---|---|
| ① 关系取值范围 | `L1 ∈ {辞职,死亡,退休}` | **收窄**：返聘资格**仅限** `退休`（`SUPERSEDED` 部分范围，被 `B2-RULE-03` 取代） |
| ② 段形态推定 | `或 无 is_current=true 段 且 存在终态段` | **整体废止**（`SUPERSEDED`，与 `C1-RULE-01` 同源，见 `B2-RULE-02`） |

### B2-RULE-02｜冲突原因

**（1）子条件 ② 与 `C1-RULE-01` 同一缺陷，只是条款位置不同。**

`C1-RULE-01` 裁定的是 `§RH-08` `:444` 的同一句式；`§RH-01` 前置条件里存在**同义表述**，当时未被覆盖（A-02e.5-B2.1 已将其登记为 `GAP-B2-1`）。若按 `§RH-01` 字面实施返聘，会把以下两类**合法在册人员**误判为返聘对象：

1. 关系为 `NULL`（待核实）+ 当前段已被关闭者（V2 花名册切段的常见形态）；
2. 关系为「正式员工」但任职段被误关者。

返聘是**高副作用动作**（改关系 + 建段 + 写历史），比普通分配更不允许建立在「段形态推定」之上。

**（2）子条件 ① 与人事常理、与现有终态语义冲突。**

`§RH-01` 把 `辞职`、`死亡` 一并列为可返聘终态，与下列事实不符：

| 依据 | 内容 |
|---|---|
| `employeeStatusDict.js:145-147` | `TERMINAL_RELATION_VALUES` 把三种原因并列为终态**原因**，但「终态原因」≠「可逆」 |
| `employeeStatusDict.js:153-155` | `LEFT_RELATION_VALUES` 明确把 `辞职/死亡` 归为「离职口径」，与 `退休` 分列 |
| 业务事实 | 「死亡」在人事语义上不可逆；「辞职」属本人主动解除，重新入职应走**新入职**而非「返聘」 |

> 说明：本条**不改变** `§RH-01` 对「返聘是独立业务动作」的核心定义（那部分继续有效并已落地）；
> 仅收窄**适用对象**，并废止其中唯一的推定分支。

### B2-RULE-03｜最终采用的规则（`FROZEN`）

返聘资格判定**唯一入口**：

```
employee.employment_relation 去首尾空白后 === '退休'   ⇒ 允许返聘
其余一切取值（辞职 / 死亡 / 正式员工 / 待岗 / 未知历史值 / NULL / 空串 / 全空白） ⇒ 拒绝，零写入
```

实现载体：`employeeAssignmentService.rehireEmployee`（单事务），资格判定只读 `employee.employment_relation`。

| 取值 | 处置 | 文案要点 |
|---|---|---|
| `退休` | 放行 | — |
| `辞职` / `死亡` | 拒绝 `-4` | 「不属于可返聘的终态；返聘仅适用于退休人员」 |
| `正式员工` | 拒绝 `-4` | 「并非退休终态，无需返聘；如需调整组织请走调岗」 |
| `NULL` / `空串` / 全空白 | 拒绝 `-4` | 「待核实，禁止由返聘流程代为推断或补值」 |
| 其它未知历史值（如 `待岗`、`内退`） | 拒绝 `-4` | 回显真实值，不猜测、不归一 |

**禁止用于判定的信息**：`assignment.status`、`is_current`、是否存在终态段、段关闭时间、姓名、统计/展示值。

### B2-RULE-04｜「退休」的判定与 `§RH-04` 的关系

- 返聘成功后人员关系按 `§RH-04`（`FROZEN`）重置为 `正式员工`，**不新增任何关系枚举值**；
- 原终态原因由 `employee_history` 承载（`event_type` 历史记录原地保留），不靠关系字段继续持有；
- `employment_relationship_status`（历史死列）**不得**作为返聘后权威关系，返聘流程不读不写该列。

### B2-RULE-05｜`reinstated` 的入口约束（`FROZEN`）

`reinstated` 仍是合法的任职段编码（`WRITABLE_STATUS_CODES` 成员），但**只能由返聘动作写入**：

- 载体：`employeeStatusDict.ACTION_ONLY_STATUS_CODES` + `isActionOnlyStatus()`；
- 通用状态变更接口 `PUT /org/:id/status`（`changeAssignmentStatus`）对其返回 `-4`，并指向 `POST /org/rehire`；
- 理由：该接口只改段状态、不建段、不改关系，写入 `reinstated` 必然产出「段说返聘、关系说退休/在职」的畸形数据（A-02e.5-B2.1 §5 证据），且 `PUT /org/:id/status` 定位条件为 `is_current=true`，终态人员本就命中 0 行。
