## 3. 源码依据与实际 diff

### 3.1 列表派生标记（唯一后端改动）

`server/services/employeeService.js:153-158`：

```sql
-- 返聘入口资格标记（A-02e.5-D1）：**只读派生布尔**，不落库、不参与写入。
-- 唯一 true 来源是 employee.employment_relation 去空格后等于「退休」——
-- 与 employeeAssignmentService.rehireEmployee 的资格判定（String(relation).trim() === '退休'）同源；
-- 关系为 NULL / 辞职 / 死亡 / 未知值一律 false（COALESCE 保证不会返回 NULL）。
-- 复用 RELATION.RETIRED 常量，禁止在此硬编码中文取值。
(COALESCE(trim(e.employment_relation), '') = '${RELATION.RETIRED}') AS is_retired_relation,
```

设计取舍（三条候选路径的对比）：

| 方案 | 是否满足 §2「关系为空不得显示」 | 副作用 | 采用 |
|---|---|---|---|
| A. 前端用 `org_status === 'retired'` | ✗ 会产生假阳性（见 §1.3） | 无 | 否 |
| B. 列表返回原始列 `e.employment_relation` | ✓ | **开启编辑页写路径**：`openEdit` 会拿到真值并回传 `updateEmployee`，使 A-02d 的「花名册比对」弹窗首次大规模触发，并把 P2-4（关系直接编辑无事务/无 history）的暴露面从「空值不写」变成「回写真值」 | 否 |
| C. 返回只读派生布尔 `is_retired_relation` | ✓ | 只增一个只读字段，不进入任何写路径；`employee/index.vue` 三个读 `row.employment_relation` 的位置行为不变 | **是** |

- `trim()` 与后端一致（后端为 `String(relation).trim()`），避免 `' 退休'` 出现「后端放行、前端不显示」的错位。
- `COALESCE(...)` 保证返回真实布尔：PostgreSQL 中 `NULL = '退休'` 结果为 `NULL`，若不加会返回 JSON `null` 而非 `false`。
- **fail-closed 特性**：若前端先行发布而后端未更新，字段缺失 → `canRehire` 恒 `false` → 入口不出现（宁可不显示，也不误显示）。

## 5. 实际 API 请求字段与响应处理（§4）

请求体（`buildRehirePayload`，`:162-178`，字段集合已被测试锁定为恰好 5 项）：

| 字段 | 取值来源 | 后端用法 |
|---|---|---|
| `employee_id` | 行 `row.id` | 锁行 + 资格判定 |
| `team_id` | 部门树节点 id（与调岗同源） | `resolveOrgUnitId` 解析为 `hse_org_unit` |
| `position_id` | 岗位下拉 | 新段 `position_id`（**前端强制必填**） |
| `start_date` | 用户选择 → `YYYY-MM-DD` | 新段 `start_date` 与 `employee_history.event_date`（必须同日，否则历史关联不上） |
| `change_reason` | 常量 `'返聘'` | 新段 `remark` + 审计文案 |
| `remark` | 可选，非空才发 | `employee_history.remark` |

**不发送**：`employment_relation`、`employment_relationship_status`、`status`、`is_current`、`is_primary`、`org_unit_id`、`userId/operator`（已测断言）。操作者身份由后端 `req.user` 决定，前端无权指定。

响应处理：

- 成功（`code=0`，`buildDetailResponse(..., '返聘成功', {camelCase:true})`）→ `message.success` → 关闭弹窗 → `emit('success')` → 父级 `loadData()+loadStats()`。**不做任何本地关系/状态赋值**。
- 失败：响应拦截器（`api/request.ts:80-124`）对 `code !== 0` 抛错，`errorMessageResponseInterceptor` 取
  `responseData.error ?? responseData.message` 提示；同时弹窗内 `NAlert` 展示 `extractRehireError()` 提取的同一条后端原文。
  → 覆盖 §4 列举的全部失败类型，文案均为后端原文，例如：
  - `-4` 非退休：`员工用工关系为「辞职」，不属于可返聘的终态；返聘仅适用于「退休」人员。`
  - `-4` 仍有当前段：`员工仍有 1 条 is_current=true 的任职段（ID=9），与「退休」关系矛盾…`
  - `-4` 时间轴：`返聘生效日期（2026-01-01）必须晚于原任职段结束日期（2026-03-01）…`
  - `-3` 组织解析失败：`返聘必须指定目标组织（org_unit_id 或 team_id/project_id 等组织参数）…`
  - `-1` 服务器异常 / 数据库未连接：`数据库未连接` 或异常 `message`
- 兜底：仅当后端未给 message 时用「返聘失败，请稍后重试或联系管理员」，且**过滤** axios 的 `Request failed with status code ...` 这类无信息量文案（已测）。
