## 5 关键实现说明

### 5.1 `rehireEmployee` 的事务边界与写入顺序

单 `client` + `BEGIN/COMMIT`，任一写失败整体 `ROLLBACK`。顺序固定，并被测试逐项断言（`A1`）：

```
BEGIN
 1. SELECT id, name, employment_relation FROM employee WHERE id=$1 ... FOR UPDATE   ← 行锁
 2. [资格] relation(trim) === '退休' ？否 ⇒ ROLLBACK + -4
 3. SELECT ... FROM employee_assignment WHERE employee_id=$1 AND is_current=true     ← 有 ⇒ 数据异常 -4
 4. SELECT ... FROM employee_assignment WHERE employee_id=$1 ORDER BY start_date DESC LIMIT 1  ← 旧段只读
 5. [时间轴] prevEnd(=end_date||start_date) < start_date ？否 ⇒ ROLLBACK + -4
 6. SELECT ... FROM hse_org_unit / resolveOrgUnitId                                  ← 目标组织必须可解析
 7. UPDATE employee SET employment_relation='正式员工', updated_at=NOW()             ← 判 rowCount=0 ⇒ -2
 8. INSERT INTO employee_assignment (status='reinstated', is_current=true, is_primary=true, start_date=D)
 9. INSERT INTO employee_history (event_type='返聘', event_date=D, before_status='退休', after_status='返聘')
COMMIT
10. publishEmployeeEvent('EMPLOYEE_REHIRED')   ← COMMIT 之后，失败仅告警
```

要点：

- **顺序不是随意排的**：`-4/-2` 分支全部发生在第 7 步之前，因此「资格拒绝 ⇒ 零业务写入」可直接断言，不必依赖回滚（`B` 组 8 例）。
- **`FOR UPDATE` 是并发防线**：重复/并发返聘被行锁串行化，后到者读到的关系已是「正式员工」⇒ `-4`（`C10`/`C11`）。唯一索引 `uk_emp_assign_primary` 谓词（`is_primary AND is_current AND NOT is_deleted`）虽能拦第二条主岗，但**不作为前提**（`IMP-06` 结论不变）。
- **`UPDATE 0 行` 显式判错**：即便已锁行，仍判 `rowCount===0` ⇒ 回滚，避免 B2.1 揭示的「UPDATE 未命中仍继续 INSERT」同构缺陷（`C3`）。
- **旧段零改动**：全程无 `UPDATE employee_assignment`、无 `DELETE`（`A4`），旧段信息只作为 history 的 `before_*` 取值被读取。

### 5.3 旧接口处置

```js
// ASG:867-875
if (isActionOnlyStatus(normalizedStatus)) {
  return { error: -4, message: '「返聘」不是状态变更动作，本接口不再支持；请使用返聘流程 POST /api/hse/employee/org/rehire…' };
```

- 用 `-4`（业务冲突）而不是 `-3`（参数非法）：入参在业务上是合法状态名，只是走错接口，`-3` 会诱导调用方去改参数名。
