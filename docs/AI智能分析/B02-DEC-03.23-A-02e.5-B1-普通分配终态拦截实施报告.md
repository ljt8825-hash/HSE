### 2.2 修改前的真实控制流（缺陷形态）

`assignEmployee` 修改前（`ASG:409` 起，原始代码）：

```js
  if (!employee_id) return { error: -3, message: '员工ID不能为空' };
  if (!start_date) return { error: -3, message: '开始日期不能为空' };

  // 验证员工存在
  const empResult = await pool.query(`SELECT id, name FROM employee WHERE id = $1 AND is_deleted = false`, [employee_id]);
  if (empResult.rows.length === 0) return { error: -2, message: '员工不存在' };

  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    const currentOrgResult = await client.query(`SELECT ... WHERE ea.employee_id = $1 AND ea.is_current = true ...`);
    if (currentOrgResult.rows.length > 0) { /* 关旧段 */ }
    // 无条件建段
    INSERT INTO employee_assignment (...) VALUES (..., 'active', true, true, ...)
    const eventType = currentOrgResult.rows.length === 0 ? '入职' : '调岗';
    INSERT INTO employee_history (..., after_status) VALUES (..., '在职', ...)
```

关键事实：**「员工是否为终态」在整条链路上从未被读取**。终态人员没有 `is_current=true` 段 ⇒ 关段分支被跳过（`rows.length===0`）⇒ 无条件 INSERT 一条 `active + is_current + is_primary` ⇒ 历史事件被记成 **「入职」**、`after_status` 为 SQL 字面量「在职」⇒ 审计上无法与真实新入职区分（03.22 F-1 路径②）。

## 4 判定矩阵（实现即规格）

| `employment_relation` 原值 | 判定 | 依据 |
|---|---|---|
| `辞职` | **拒绝 -4** | `TERMINAL_RELATION_VALUES` |
| `死亡` | **拒绝 -4** | 同上 |
| `退休` | **拒绝 -4** | 同上（D1 定案：退休是正式关系取值） |
| `' 退休 '`（含首尾空格） | **拒绝 -4** | 先 `trim` 后判定（防脏空格绕过） |
| `正式员工` | 放行 | 正式值 |
| `待岗` | 放行 | DICT 历史兼容值；**待岗是段中间态被误写进关系字段的遗留**，不得当作终态 |
| `NULL` / `undefined` / `''` / 纯空格 | 放行 | = 待核实；**不推断、不补值** |
| 其它历史遗留/未知取值（如 `劳务派遣`） | 放行（fail-open） | 无证据不得判定为终态；未知值治理属数据治理，见 §8-⑤ |
| 段状态 `inactive/retired`（关系为正式/空） | **不参与判定** | 任务书 §3.2「不得以任职记录状态反推」 |

拒绝时的返回体：

```js
{ error: -4, message: '员工用工关系为「退休」，属于终态，禁止通过调岗/分配入口重新建立任职记录；返聘须走独立的返聘流程（尚未开放），如需恢复请先由人事处理用工关系。' }
```

> 措辞刻意写明「返聘流程尚未开放」，避免让使用者去找一个 B2 尚未交付的入口（03.22 RH-07 明确返聘入口属 B2）。

## 5 规则冲突登记（任务书 §2 强制项）

### CONFLICT-1｜03.22 `RH-08` 第二判定条件与任务书 §3.2/§7.2 冲突 ⇒ **未实施**

| 项 | 内容 |
|---|---|
| 契约原文 | 03.22 `:444`：「关系 ∈ `{辞职,死亡,退休}` **或 存在终态段且无 `is_current=true` 段** ⇒ 返回 `{error:-4 …}`」 |
| 冲突条款 | 任务书 §3.2：「不得根据人员姓名、**历史任职记录**、当前状态、统计结果或其他间接信息推断终态关系」；§7.2：「**不以任职记录状态反推人员关系**」；DICT `:21-22`：「`assignment.status = inactive` 单独**不得**决定展示为辞职/死亡/退休」 |
| 为何不能实施 | ① 「存在终态段」= 用 `employee_assignment.status` 反推关系，正是上位规则禁止的动作；② 会**误封**两类合法人员：(a) 关系 `NULL`（待核实）且因 2026-09-06 花名册切段而 `is_current=false` 的存量人员——被当成终态后将永久无法正常入职/调岗，且任务书 §3.3 禁止把 NULL 转成具体关系值来「解决」；(b) 关系为 `正式员工` 但段被误关的历史畸形数据（03.22 F-3 反向畸形）——在职人员被拒。 |
| 处置 | **只实施关系判定那一条**（`ASG:390-400`），第二条件**不实现**，登记为 `BLOCKED-B1-1`。 |
| 合理内核如何覆盖 | 退休/辞职/死亡在 A-05 规则下**必须**写 `employment_relation`；只要关系已写，第一条件即命中。真正「关系未写 + 段已关」的人群，缺的是**关系回填**，属 A-02e.5-A（关系事务化）与数据治理，不能靠段状态猜测（否则制造第二类错误）。 |
| 解除条件 | 若业务方坚持要覆盖「关系未写」人群，须先由 A-02e.5-A 交付「关系必填/回填」规则，届时该人群自然消失；在此之前任何「按段猜终态」的实现都会违反 §3.2。 |

### DIFF-1｜闸门位置比契约更靠前（非语义冲突，登记备查）

03.22 `:442` 要求闸门「在开启事务后、执行任何写操作前」；本实现放在 `pool.connect()` **之前**（`ASG:429` vs `:434`）。

- 效果更强：拒绝时**不取连接、不开事务、无 ROLLBACK**，因此「零副作用」可被直接断言（`pool.connect` 未被调用），而不是只能断言「回滚过」。
- 语义不变：拒绝结果、错误码、消息、可写路径全部一致。
- 附带收益：不为一次纯校验多占一个连接（该接口由 `admin/safety_manager` 手动触发，并发低，但仍避免无谓占用）。

**未发现**其它规则冲突。`DICT` 值域、`.env`、DDL、迁移文件均未触碰。
