### 4.2 `reinstated` 的真实对象与语义（任务书 §3.6 要求先确认）

`reinstated` **不是** `employment_relation` 的取值。证据：

| 事实 | 位置 |
|---|---|
| `RELATION` 只有 4 值：`正式员工` / `辞职` / `死亡` / `退休` | `DICT:105-110` |
| `RELATION_VALUES` 同上 4 值；`WRITABLE_RELATION_VALUES` = 4 正式值 + `待岗`（历史兼容） | `DICT:113-115`、`DICT:126-128` |
| `validateRelationInput('reinstated')` 必然返回 `{ok:false}` | `DICT:277-287`（不在白名单） |
| `reinstated` 在 `WRITABLE_STATUS_CODES`（`assignment.status` 可写白名单） | `DICT:71-73` |
| `reinstated` **不在** `TERMINAL_STATUS_CODES`（= `inactive`,`retired`） | `DICT:79` |
| `reinstated` **不在** `INTERMEDIATE_STATUS_CODES`（= `pending`,`secondment`,`unpaid_leave`） | `DICT:85` |
| 展示映射 `reinstated → 返聘` | `DICT:63` |
| `employee_history.event_type` 注释枚举含「返聘」 | `hse_employee_master_v59_migration.sql:206-207,232` |

**结论**：`reinstated` 是「任职段的第四类状态」——既不属终态（不关段），也不属中间态（DICT 未列入）。它的存在本身说明**系统曾设想用段状态表达返聘**，但没有配套的关系写入 ⇒ 必然产生 4.4 的畸形。

### 4.4 假返聘：`PUT /org/:id/status` 的三重矛盾

这是本节点最重要的代码事实。逐层还原：

**第一层：它声称支持返聘**

```js
// ROUTE-ASG:27（server/routes/hse-employee/assignment.js）
// PUT /org/:id/status — 人员状态变更（待岗/复岗/离职/退休/返聘）
router.put('/org/:id/status', requireRole('admin','safety_manager'),
           requirePermission('hse:personnel:update'), changeAssignmentStatus);

// ASG:544
const validStatuses = ['在职','待岗','借调','停薪留职','离职','辞职','死亡','退休','返聘'];
```

**第二层：它对终态人员必然失败**

```js
// ASG:556-566
SELECT ea.id, ... FROM employee_assignment ea
 WHERE ea.id = $1 AND ea.is_current = true AND ea.is_deleted = false   // ← 定位条件
...
if (orgResult.rows.length === 0) return { error: -2, message: '组织关系不存在或非当前记录' };
```

而「进入终态」正是由**同一个函数**把段关掉的：

```js
// ASG:574-579
if (isTerminalStatus(normalizedStatus)) {
  UPDATE employee_assignment SET status=$2, is_current=false, end_date=$3 ...  // ← 自己关的段
}
```

⇒ **闭锁**：`退休 → 段 is_current=false → 再请求「返聘」→ 定位 0 行 → -2`。系统内没有任何路径能解开。

**第三层：即使第二层被绕过，它只改段、不改关系**

```js
// ASG:580-587（else 分支：中间态 / 在职 / 返聘）
UPDATE employee_assignment SET status=$2, updated_at=NOW() WHERE id=$1   // 只改 status
```

`employment_relation` 全程未被触碰（该函数内无任何 `UPDATE employee`）。后果由 `displayStatusSql` 决定：

```js
// DICT:304-312
CASE WHEN rel = '退休' THEN 'retired'
     WHEN rel IN ('辞职','死亡') THEN 'left'
     ELSE statusColumn END
```

⇒ 关系仍为「退休」时，展示**永远**是「retired」，无论段状态写成什么。

**第四层：无测试锁定**

`ASG:565` 的 `-2` 文案在 `server/__tests__/` **零命中**。唯一的返聘相关测试是：

```js
// d1:380-390
it('返聘 → reinstated：保持原有行为（不关闭任职段）', async () => {
  const client = makeClient(ORG_ROW);   // ORG_ROW.status='active'，is_current 段【存在】
  const res = await assignmentService.changeAssignmentStatus({ id:11, status:'返聘', ... });
  expect(upd[1][1]).toBe('reinstated');
  expect(upd[0]).not.toContain('is_current = false');
});
```

该用例的前提 `ORG_ROW`（`d1:60-62`）是**在职人员的当前段**，与「终态人员返聘」的真实场景**恰好相反**。它记录的不是返聘能力，而是**「把在职人员的段状态改成 reinstated」这一畸形操作被允许**。

**判定**：`PUT /org/:id/status` 的「返聘」是**假返聘**，且其测试把缺陷当基线。B2 必须正面处置（见 §9.5）。

```
入参：{ employee_id, start_date, group_id|region_id|enterprise_id|project_id|team_id, position_id, change_reason?, remark?, userId }
必填：employee_id, start_date, 至少一个组织层级 id, position_id
```

**前置断言（全部在 `BEGIN` 之前或之内第一句，任一失败即拒绝、零写入）**：

| # | 断言 | 判定依据 | 依据来源 |
|---|---|---|---|
| P1 | 员工存在且 `is_deleted=false` | `SELECT id,name,employment_relation` | `ASG:419-423` 同范式 |
| P2 | **`isTerminalRelation(relation) === true`** | `DICT:262-267` | `C1-RULE-03`（唯一出口） |
| P3 | `start_date` 非空且为合法日期 | 参数校验 | `RH-03` |
| P4 | `org_unit_id` 解析结果非空 | `resolveOrgUnitId` 返回值 | 防 DDL 冲突（§7.2） |
| P5 | **不存在 `is_current=true` 的段**（在事务内 `SELECT ... FOR UPDATE` 复查） | 段形态 | 见下方说明 |
| P6 | 旧段 `is_current=false` 且 `status ∈ {inactive, retired}` | 段形态 | `RH-02` |

> **P5/P6 与 `C1-RULE-03` 的关系（必须显式区分，否则 B2 会陷入教条）**：
> `C1-RULE-03` 禁止的是「**用段形态判定人员为终态**」（即：段关了 ⇒ 认定这个人离职了）。
> P5/P6 的用途相反——它是「**拒绝**」条件（已有在职段 ⇒ 不可返聘），不产生任何「关系认定」，也不写入关系字段。
> 二者的区别是：**禁止用段形态去"认定事实"，允许用段形态去"限制动作"**。
> P5 是 `uk_emp_assign_primary` 的应用层前置（`IMP-06` 要求），P6 是 `RH-02`「旧段不得改」的可验证化。

**P2 的边界（任务书 §3.3 / §3.4 要求）**：

| 关系值 | 返聘是否允许 | 理由 |
|---|---|---|
| `辞职` / `死亡` / `退休` | ✅ 允许（这是返聘的目的） | `isTerminalRelation` 精确命中 |
| `NULL` / `''` | ❌ **拒绝**，提示「关系待核实，请先补录用工关系或使用普通分配」 | NULL ≠ 终态，不得当作返聘对象；也不得自动补值 |
| `正式员工` | ❌ **拒绝**，提示「该员工已是在职人员，请使用调岗」 | 已是正式员工，无需返聘 |
| `待岗`（历史兼容） | ❌ 拒绝，同上理由 | 非终态 |
| 其它未知值 | ❌ 拒绝，提示先核实 | 无证据 |

⇒ **返聘的对象集合 = `TERMINAL_RELATION_VALUES` 的补集之外，且仅限该集合本身**。NULL 与中间态走普通分配（B1 已放行），形成清晰分工。

### 9.3 事务内语句顺序（设计）

```
BEGIN
  S1  SELECT ... FROM employee WHERE id=$1 AND is_deleted=false FOR UPDATE          -- 锁住员工行
  S2  SELECT ... FROM employee_assignment WHERE employee_id=$1 AND is_current=true   -- P5 复查
  S3  SELECT ... FROM employee_assignment WHERE employee_id=$1 AND status IN ('inactive','retired')
        AND is_current=false ORDER BY end_date DESC LIMIT 1                          -- P6 取旧终态段
  S4  UPDATE employee SET employment_relation='正式员工', updated_at=NOW() WHERE id=$1
        （是否同时清 leave_date → 见 GAP-B2-2，默认**不清**）
  S5  INSERT INTO employee_assignment
        (employee_id, org_unit_id, position_id, supervisor_id, status, is_current, is_primary, start_date, remark, created_by)
        VALUES ($1,$2,$3,$4,'reinstated',true,true,$5,$6,$7)
  S6  INSERT INTO employee_history
        (employee_id, event_type, event_date, before_dept_id, after_dept_id, before_position_id, after_position_id, before_status, after_status, remark, approver_id)
        VALUES ($1,'返聘',$2,$3,$4,$5,$6,$7,'返聘',$8,$9)
        -- before_status = 旧终态原因中文（退休/辞职/死亡），D2 语义
        -- after_status  = '返聘'（RH-06）
COMMIT
  E1  publishEmployeeEvent({ type: <待定>, employeeId, occurredAt, payload:{ fromRelation, toRelation:'正式员工',
        fromStatus, toStatus:'返聘', startDate, isRehire:true } })
  A1  auditLog({ action:'create', module:'人员返聘', description:'返聘: 员工X(ID=..) 退休→返聘 生效日=..' })
```

**后置断言（`RH-01:361`，建议在 `COMMIT` 前执行，失败即 `ROLLBACK`）**：
- 该员工 `COUNT(*) WHERE is_current=true` **恰好为 1**；
- 该段 `is_primary=true`；
- `start_date = D` 且 `D > 旧段 end_date`。
