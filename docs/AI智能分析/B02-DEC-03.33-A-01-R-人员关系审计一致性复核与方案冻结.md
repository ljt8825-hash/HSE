## 0. 结论摘要（先看这一节）

### 0.1 一句话结论

A-01 报告的**修复方向正确**（收口编辑接口 + 终态双写），但**取证口径有 6 处必须纠正**；其中两处严重到会改变实施方案：

1. **「只有一条业务写入通道」不成立**。实测 HTTP 业务写入 **2 条**（W1 编辑、W6 返聘），另有 **3 个可执行脚本**直接写关系（W10/W11/W12），导入路径 **0 条**。「一条」只在「普通人员编辑」这一限定语下成立。

### B.1 C-1｜「只有一条业务写入通道」（原 §0.1）

**原表述**：

> 「人员关系字段 `employee.employment_relation` 当前**只有一条业务写入通道**（人员编辑接口 `PUT /employees/:id`）」

**矛盾证据（原报告自证）**：同一报告 §B.3 写「写关系字段：仅 W1（业务接口）、W6（返聘专用动作）、W10（一次性回填脚本）」；§C.1 表中「写入方」列亦写 `W1 / W6 / W10`。§0.1 与 §B.3/§C.1 **互相否证**。

**修正后的准确表述（建议替换 §0.1 首句）**：

> 人员关系字段 `employee.employment_relation` 当前存在 **5 处写入点**：  
> ① **HTTP 业务接口 2 处** —— 普通人员编辑 `PUT /api/hse/employee/employees/:id`（W1）、返聘 `POST /api/hse/employee/org/rehire`（W6）；  
> ② **可手工执行的 Node 脚本 3 处** —— 关系回填 `scripts/import-employment-relation.cjs`（W10）、园区一次性数据补丁 `scripts/_apply_p1_park_org_20260927.cjs`（W11，未跟踪）、SYNC-GATE 回归夹具 `scripts/p2b1e0804syncgate_tests.cjs`（W12，DEV-only）；  
> ③ **导入路径 0 处** —— V1 两条入口与 V2 批次导入均不写该字段（已逐字段核对列清单，并有测试断言）。  
> 其中**唯一可由常规人员维护界面触达**的写入通道是 W1；W1 **无事务、不改任职段、不写人事历史、不发事件**。而唯一会改任职段的终态动作（`PUT /org/:id/status`）**完全不写关系**。二者互为镜像。

**为什么必须这样改**：W6 是完整事务化实现（`FOR UPDATE` → 写关系 → 建段 → 写历史 → `COMMIT`），把它排除在「通道」之外，会让读者以为「系统里再没有正确的关系写入范式」；W10 是现行关系数据的**来源**（1291 正式 / 1951 辞职 / 152 NULL 的历史口径），把它排除在「通道」之外，会让「收口后关系不可再被写」这一承诺失去完整性——脚本仍然是绕过口。

**修正后的准确表述**：

> **隐患**：不读 `employee.employment_relation`，因此**不受 #5（关系终态 + 段仍 current）影响**；但隐患统计的**部门维度与岗位维度**依赖「责任人当前任职段」（`hazardService.js:571-582`、`:584-596`，均 `is_current = true`）。⇒ **#9 畸形（关系仍正式员工、段已关闭）会使责任人在部门/岗位统计中落入 NULL 桶**，隐患总数不变、分组失真。此处既有结论「无影响」应改为「无关系依赖，但有当前段依赖」。

11. 提交事务。
