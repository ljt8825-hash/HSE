## 3. 后端事务逐项审计（源码头对头）

被测函数：`server/services/employeeAssignmentService.js` → `terminateEmployee(params)`（**:1039**）。

### 3.1 关系闸门（§4.1）— ✅ 合规
- 只读 `employee.employment_relation`（**:1084-1086** 取 `beforeRelation`）。**不读段形态反推**（注释明确要求，**:1019**、**:1088**）。
- NULL / 空串 / 空白 → `beforeRelation` 为空 → **-4 拒绝**（**:1089-1096**），不推断、不补值。
- `isTerminalRelation(beforeRelation)` 命中（辞职/死亡/退休）→ **-4 拒绝重复登记**（**:1097-1103**）。
- 非「正式员工」（`beforeRelation !== RELATION.FORMAL`）→ **-4 拒绝**（**:1104-1111**），故待岗等历史兼容值被挡。
- **不接受笼统「离职」**：`TERMINATION_RELATION_MAP`（**:997-1001**）仅含 辞职/死亡/退休；`'离职'` 非键 → `terminalRelation` 为 `undefined` → **-3 拒绝**并显式提示（**:1050-1057**）。
- **不会写入 reinstated**：映射目标仅为 `RELATION.RESIGNED/DECEASED/RETIRED`（**:119-124**），无 reinstated 取值。

### 3.2 任职段闸门（§4.2）— ✅ 合规
- `SELECT ... WHERE employee_id=$1 AND is_current=true AND is_deleted=false FOR UPDATE`（**:1114-1120**）：排除软删段。
- **必须恰好 1 条**：0 条 → -4（禁止补造，**:1121-1128**）；>1 条 → -4（**:1129-1137**）。
- 时间轴：`segmentStart` 存在且 `effectiveDate < segmentStart` → -4 防倒挂（**:1142-1149**）。
- `status='inactive'` 与字典/消费者兼容：见 §4。

### 3.3 事务原子性（§4.3）— ✅ 合规
- 单个 `client`（`pool.connect()`，**:1066**）+ `BEGIN`（**:1068**）→ 全部写经 `client.query`，**无 `pool.query` 旁路**（各步均 `client.query`）。
- 写入顺序固定：锁员工 → 关系闸门 → 锁段 → 时间轴 → UPDATE employee → UPDATE assignment → INSERT history → INSERT sys_operation_log → COMMIT（**:1017-1027** 注释 + 源码对齐）。
- `UPDATE employee` rowCount===0 → `throw`（**:1158-1161**，防「关系未更新仍关段」）。
- `UPDATE assignment` rowCount===0 → `throw`（**:1170-1173**，防「段未关」）。
- 审计 INSERT（**:1210-1225**）**未套独立 try-catch**，失败即抛 → 进外层 catch → ROLLBACK ⇒ **审计失败不会静默吞掉**，且审计与业务写同事务提交（非内存事件）。
- `COMMIT`（**:1227**）后事件发布（**:1230-1249**），事件失败仅 `console.warn`、不回滚已完成事务（**:1247-1249**）。
- `catch → ROLLBACK; throw`（**:1268-1270**）；`finally → client.release()`（**:1271-1273**）。
- **无事务结束后二次 ROLLBACK**：早返回路径先 `ROLLBACK` 再 `return`（不抛），外层 catch 不被触发；COMMIT 后事件在独立 try 内，不回灌外层。✅

### 3.4 审计数据真实性（§4.5）— ✅ 合规
- 操作人取自 `req.user`/`req.ip`/`req.headers`（controller **:129-132**），不接受 body 注入。
- `sys_operation_log` INSERT 含 `user_id`/`username`/`ip`/`user_agent`/`status_code=200`/`detail(JSON)`（**:1210-1225**）；`detail` 记录 `beforeRelation→afterRelation`、`eventDate`、`employeeId`、段状态前后。

- **结论**：`TERMINATION_SEGMENT_STATUS='inactive'`（**:1008**）与字典设计及现有消费者完全兼容，C-04 成立。

## 5. 并发一致性分析（§4.4）

锁序与现网接口对比（`employeeAssignmentService.js`）：
| 函数 | 员工行锁 | 段锁 | 写关系 | 建段 |
|---|---|---|---|---|
| `terminateEmployee`（**:1066-1120**） | FOR UPDATE（**:1071**） | FOR UPDATE（**:1114**） | ✅ | ✗ |
| `rehireEmployee`（**:627**，注释 **:604**） | FOR UPDATE | （读当前段，无 FOR UPDATE） | ✅ | ✅ |
| `assignEmployee`（**:419-475**） | **无 FOR UPDATE**（读 **:429** 不锁） | **无 FOR UPDATE**（读 **:449**、UPDATE **:471** 仅 `WHERE id`） | ✗ | ✅ |
| `changeAssignmentStatus`（**:868-924**） | 无（按段 id 操作） | 按段 id（UPDATE **:913**） | ✗ | ✗ |

- **重复终态登记**：`terminateEmployee` 在事务内（BEGIN 后）重新读 `employment_relation`（**:1071→1097**），员工行 FOR UPDATE 串行化并发请求。首个提交后关系变终态，第二个的锁后重读命中 `isTerminalRelation` → -4。✅ 自身串行化成立。
- **终态登记 × 人员分配（assignEmployee）**：`assignEmployee` 关系闸门在 `BEGIN` **之前**（**:439**，零副作用设计），读的是**已提交**关系；若 terminate 尚未提交，assign 读到的仍是"正式员工"→ 放行。但两者都会触及同一段行：`terminate` 持有段 FOR UPDATE，`assign` 关闭该段的 UPDATE（**:471**，无 `is_current` 守卫）会**阻塞等待** terminate 提交；提交后 assign 的 UPDATE 覆盖 `end_date` 并**再插一条 `is_current=true` 新段** ⇒ 理论上可形成"关系=终态 + 新活跃段"畸形。
  - **性质**：此风险来自 `assignEmployee` 的**前置零副作用闸门设计**（A-02e.5-B1 既有决定），**非 A-02A 引入**；`terminateEmployee` 自身实现正确且自串行化。需**特定并发交错 + 人工同时操作同一人**才会触发，属运维级边角情形。
  - **处置建议**：归 A-02B / 分配接口加固（将 assign 的关系闸门移入事务、锁后重读；或 assign 关段 UPDATE 加 `WHERE is_current=true` 守卫）。**不在 A-02A 范围**，记为 P3 观察项。
- **终态登记 × 状态变更（changeAssignmentStatus）**：后者只改段、不建段、不写关系，且对同段 id 的 UPDATE 会等待 terminate 的段锁 → 串行化，不会产出"终态 + 新活跃段"。✅
- **死锁**：terminate 与 rehire 同为"员工锁→段锁"顺序，一致；与 assign/changeStatus 因后者不持员工锁，不会形成环。✅ 无死锁风险。
