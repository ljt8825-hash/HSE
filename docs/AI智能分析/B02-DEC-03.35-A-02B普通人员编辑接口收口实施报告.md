## 0. 判定结论

**判定：PASS（含 1 项方法学纠正，非阻断）。**

普通人员编辑接口（W1：`PUT /api/hse/employee/employees/:id`）已收口——只要请求体显式携带 `employment_relation`，后端在「任何业务更新之前」以既有业务冲突码 `-4` 明确拒绝，不静默忽略、不产生部分更新；前端（web-naive）关系字段降级为只读展示且请求体不再携带该字段，并保留 TerminalModal / RehireModal 专用入口。并发边角（assignEmployee 与 terminateEmployee 的竞争窗口）已确认源码可证真实缺陷，并实施最小必要修复（事务内 FOR UPDATE 复核栅栏）+ 针对性单测。

**方法学纠正（非阻断，须记录）**：任务书要求「核查 web-antd 是否真实存在可调用编辑入口」。先前节点仅凭一次 grep「零命中」即得出「web-antd 无真实编辑入口、无需改造」结论，属方法学失误——未先以已知命中点校验检索式（本项目反复出现的教训：全仓检索零命中必须先拿已知命中点验证检索式）。本次直接读源码确认：**web-antd 确实存在真实可调用编辑入口 `EmployeeEditModal.vue`**，但经逐行核验其表单模型与请求体均不携带 `employment_relation`，故实质性结论（web-antd 不泄漏该字段、无需改造）成立；后端闸门作为纵深防御兜底。详细见 §5。

## 5. web-antd 实际调用链核验（方法学纠正 + 实质结论）

|                                           |                |                                                                                                               |
| ----------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------- |
| **检索式纠正**：先前节点 grep \`employment_relation | updateEmployee | employees/:id\` 在 web-antd 目录返回「零命中」，据此断言「web-antd 无真实编辑入口、无需改造」。本次以已知命中点反查，确认该 grep 因检索式过窄而漏检，重新全仓检索得到真实调用链： |

  - 该组件被 `web-antd/src/views/hse/employee/index.vue:158`（模板）+ `:188`（import）**真实装载**，是 web-antd 侧真实可调用编辑入口。

## 6. assignEmployee 并发边角核验及处理结论（第四阶段）

**缺陷确认（源码可证，真实存在，非本节点引入）**：

- `assignEmployee`（`employeeAssignmentService.js:444`）原关系闸门位于 `pool.connect()` / `BEGIN`（`:446`）**之前**（`:439-442`，零副作用快拒）。
- 竞争窗口：「闸门读关系（无锁）」→「`BEGIN`」之间存在可被 `terminateEmployee` 插入的间隙。
- `terminateEmployee` 在 `BEGIN` 后 `SELECT ... FOR UPDATE` 锁员工并改关系为终态后提交；若此后 `assignEmployee` 才 `BEGIN`，其事务内**不重锁员工、不复核关系**，会继续为「已终态人员」新建 `is_current=true` 的 active 任职段，造成 `employment_relation`（终态）与 active 任职段不一致。
- 该缺陷与 03.34-R 标记的观察（P1 并发边角）一致，本次以源码行号（`:439` 前置闸门 / `:471` 关段 UPDATE 无 `is_current` 守卫）确认可证。

**最小必要修复（事务内 FOR UPDATE 复核栅栏）**：

- `employeeAssignmentService.js:455-467`：在 `BEGIN`（`:446`）之后、关旧段 / 建新段之前，新增：
  ```js
  const txEmpResult = await client.query(
    `SELECT id, name, employment_relation FROM employee WHERE id = $1 FOR UPDATE`, [employee_id]);
  if (txEmpResult.rows.length === 0) { ROLLBACK; return {error:-2,...}; }
  const txRelationGuard = checkRelationAllowsAssignment(txEmpResult.rows[0].employment_relation);
  if (!txRelationGuard.ok) { ROLLBACK; return {error: BIZ_CONFLICT, ...}; }
  ```
- 锁序与 `terminateEmployee` 一致（先员工后段），二者因此被串行化：谁先拿员工行锁谁先执行，后者重读到的必是已提交的终态关系。
- **未重构分配服务、未改无关规则、未加 DB 字段、未扩大修复面**——仅补事务内复核栅栏。
