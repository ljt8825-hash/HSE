## 1. 结论摘要

A-02d.1 复核发现的 D1 是**规则前提不成立**，不是编码写错：A-02d 把「退休」归一为 `inactive`，并规定"终止原因由 `employment_relation` 表达"，但全仓 `employment_relation` 只被拿来比较 `'正式员工' / '辞职' / '死亡'`，**代码里没有「退休」这个取值**。结果退休者：

- 列表显示「离职」（改前 `employeeService.js:134` 的 `CASE WHEN relation IN (辞职,死亡) THEN 'left' ELSE assignment_status` 落到 `ELSE`）；
- 筛「离职」筛不出（不在 `IN ('辞职','死亡')` 内）；
- 筛「退休」也筛不出（该分支查 `assignment_status='retired'`，而新数据是 `inactive`）。

**即退休人员成为数据黑洞。** 本轮按业务裁决把「退休」纳入 `employment_relation` 正式取值，并把读侧口径改为"先看关系事实、再看任职段状态"。

**关键前置结论：不需要任何 DDL。** `employee.employment_relation` 为 `character varying(40)`，`employee` 表唯一约束是 `PRIMARY KEY (id)`，全库无 `CHECK`、无 `CREATE TYPE` 枚举、无外键（证据见 §3.1）。因此 §三 的"若模型不允许则停止实施"门槛未触发。

## 4. 约束与调用链证据

### 4.1 `assignment.status = inactive` 为什么不能单独决定原因

改前三处派生（`grep -n "THEN 'left'"` 改前命中 3 处）：

```
employeeService.js:134        CASE WHEN e.employment_relation IN ('辞职','死亡') THEN 'left' ELSE ev.assignment_status END AS org_status
employeeProfileService.js:94  CASE WHEN e.employment_relation IN ('辞职','死亡') THEN 'left' ELSE ev.assignment_status END AS status
employeeProfileService.js:137 CASE WHEN e.employment_relation IN ('辞职','死亡') THEN 'left'
                                   WHEN e.is_deleted THEN 'inactive' ELSE 'active' END AS status
```

三处都以"关系事实"为第一判据、`assignment.status` 为回退——**方向是对的，只是缺了退休分支**。因此修复不是重写，而是**在 `left` 分支之前插入 `退休 → 'retired'`**，并复用前端已有的 `retired:'退休'` 标签（`web-naive` `STATUS_LABEL`、`web-antd` `OrgStatus` 均已含 `'retired'`）。

### 4.2 为什么选 `'retired'` 作为派生值

1. 前端两端都已存在 `retired:'退休'` 标签，**零前端改动即可正确显示**；
2. 旧数据 `assignment_status='retired'` 与本派生值同码 ⇒ 新旧数据在展示层天然统一，无需迁移；
3. `web-antd` 的 `OrgStatus` 类型已含 `'retired'`（`api/hse/employee.ts:19`），不破坏类型契约。

### 4.3 写入链（`updateEmployee`）

改前 `employeeService.js:478-480` 对 `employment_relation` **无任何校验**，任意字符串直接 `trim()` 落库。这是"关系事实"被污染的入口。改后经 `validateRelationInput`：

| 输入 | 结果 |
|---|---|
| `'正式员工' / '辞职' / '死亡' / '退休'` | 通过，原值落库 |
| `'待岗'` | 通过（**历史兼容**，见 §5.3 说明） |
| `'' / null` | 通过，落 `NULL`（表示待核实，不推断） |
| `'离职' / '在职' / 'active' / '正式工'` 等 | **拒绝**，返回 `{error:-3}` 并提示可选项 |

### 4.4 终态关闭链（`changeAssignmentStatus`）

改后（A-02d 已修）为**按归一后编码**判定终态，三个字段同一条 `UPDATE` 原子写：

```sql
UPDATE employee_assignment SET status = $2, is_current = false, end_date = $3, updated_at = NOW() WHERE id = $1
```

凭据：`employeeAssignmentService.js:521-531`。退休 → `status='inactive'`、`is_current=false`、`end_date=event_date`。**本轮未改此路径**，仅补测试（G6）。

### 5.3 一个必须记录的取舍：`待岗` 保留写入兼容

前端"用工关系状态"下拉里历史上有 `{ label: '待岗', value: '待岗' }`。按 A-05，「待岗」属 `assignment.status` 的中间态，**不是关系事实**，出现在关系字段里属字段混用。

但如果白名单直接拒绝「待岗」，会制造回归：历史 `relation='待岗'` 的员工在编辑**任何其他字段**时（表单总会提交该字段，`index.vue:373`），保存会被拒绝，或（若移除前端选项）被静默清空为 `NULL` —— 后者违反"不得静默丢弃"。

因此处置为：**`待岗` 保留写入兼容、但不进入正式取值集合，也不推荐新增写入**；是否清理属后续数据治理裁决（已登记 §9-G2）。这是本轮唯一"按现状妥协"的点，在此显式披露。

**该取舍的可见影响**：`knownRelationInSql` 使用 `WRITABLE_RELATION_VALUES`，因此「花名册全员」口径已包含 `待岗`。若存量存在 `relation='待岗'` 记录，`GET /employees/stats` 的"总数"卡数字会比改动前**变大**（改动前 `IN ('正式员工','辞职','死亡')` 会漏掉这些人）。这是口径完备性修复，不是统计规则变更；实际影响条数需连库确认（DB-INT-3/4）。
