## 3 退休编码冲突溯源（候选方向 D1）

### 3.1 结论先行

候选方向 D1「退休保留独立任职段状态编码 `retired`」与当前工作区实现**直接冲突**，冲突真实存在。但**冲突的根源不是任何一份报告写错**，而是两层原因叠加：

1. **概念混用**：`retired` 这个词在系统里同时指「存储编码」和「读侧派生展示值」两个不同对象，历史报告未逐处区分。
2. **文档漂移**：DEC-01 登记册的「已确认事实」栏记录的是 **10-28 的 HEAD 代码**；代码在 **10-29 被 A-02d 按任务书 §二.4 改过**，登记册未同步。

### 3.2 三个时点的代码事实（逐时点核实）

| 时点 | 代码位置 | `退休` 的存储编码 | 证据 |
|---|---|---|---|
| **T1：2026-10-28（DEC-01 登记时）** | `employeeAssignmentService.js` 本地 `STATUS_MAP` | **`'retired'`** | `git show HEAD:server/services/employeeAssignmentService.js` 实测（HEAD 仍为该版本，工作区已改）；DEC-01 `:562` 原文：`在职→active、待岗→pending、离职→inactive、退休→retired、返聘→reinstated` |

### 3.4 D1 的三个风险点（必须写进裁决前提）

#### 3.4.1 与已发出的业务规则直接对立

A-02d §二.4（任务书 B02-DEC-03.13 明文规定）为：「辞职 / 死亡 / 退休 的新业务终态统一编码为 `inactive`，终止原因只由 `employment_relation` 表达」。该规则已落地并在 A-02d.1～A-02d.4 四轮验收中被反复引用（03.15 `:313` 验收项 2 判 PASS）。

**D1 若采纳，等于撤回该条业务规则**，不是"补一个值"。撤回必须由原规则发布者书面确认，并同步修订：

- 03.15 验收项 2 的结论；
- 03.16 `:334` 的「设计要求」表述；
- A-02d.4 报告中「`inactive` 与 `retired` 分开显示」的口径解释（显示结果不变，但成因从"派生"变为"存储"）。

#### 3.4.2 业务前提尚无数据支撑

DEC-01 `P-02`（`:1794`）记录：**「退休在本单位是否实际发生」**现状为「`relation` 无"退休"值，`status='retired'` 0 行」，结论是「数据无样本 ⇒ 无法从系统推断」。

**⇒ 在业务尚未确认「退休是否真实发生」之前，为它选择存储编码是空中设计。**这一点必须由业务先答，否则两类编码选哪个都不影响现实。

#### 3.4.3 与 `A-03d` / `A-05c` 的选项域绑定

- `A-03d`（`:404`）：`status` 取哪个值 —— 统一 `inactive` / 沿用 `former` / **按原因分（辞职/死亡/退休各自值）**；
- `A-05c`（`:554`）：退休是否等同「永久离开」（即与辞职同动作）。

**D1 实质是在替 `A-03d` 预选第三项、替 `A-05c` 预选"不等同"。**按 DEC-01 §8 补充说明「以技术可实现性反推业务规则属偷换命题」，本报告**不代为选择**。

### 4.5 一个必须先解决的结构性问题

候选方向 D2 说「返聘原则上创建新的任职段」。但当前架构里，**"创建任职段"这件事与"关系字段"完全解耦**（A-02e.1 已证：关系写入 W-01 不碰任职段，任职段写入 W-03/W-08 不碰关系）。

**若只做"新建段"而不改关系**，会出现：

```
employee.employment_relation = '退休'        ← 关系仍是退休
employee_assignment (新段) status='active', is_current=true
                ↓ displayStatusSql 先判关系
org_status = 'retired'                        ← 列表显示「退休」
```

**即：新建段成功、`is_current=true`，但列表/档案仍显示「退休」，且统计把它算作"已离开"。**这不是 bug，是当前"关系优先"设计的必然结果。

**⇒ 返聘若采纳「新建段」，必须同步定义「关系字段是否、何时改回 `正式员工`」，否则返聘在界面上不可见。**这一条是本轮发现的最关键结构约束，也是 D2 无法只靠 `assignment.status` 解决的原因。

### 5.3 三处直接违反 D-5 / D-6 的实质缺陷

#### 缺陷 ①：V2 导入的「新旧段时间轴倒挂」（最严重）

```
:1025  旧段 end_date = CURRENT_DATE          ← 今天（2026-10-29）
:1052  新段 start_date = COALESCE(hire_date, CURRENT_DATE)
```

若该员工 `hire_date = 2020-03-01`，则结果为：

```
旧段：[------ 2020-03-01 ~ 2026-10-29 ------]
新段：[-- 2020-03-01 ~ NULL（现任）--]        ← 与旧段重叠 6 年
```

**每一次月度导入都在制造"两段同时覆盖同一时间段"的时间轴倒挂**，且 `is_current` 只标在新段上，旧段虽 `is_current=false` 但 `end_date` 落在今天之后的新段起点之后。

- 违反 D-5（历史关系应由业务有效日期控制）；
- 后果：任何"某人在某时点属于哪个组织"的追溯查询都会返回 2 条；
- **与 `C-01`（`start_date` 语义）、`C-02`（`end_date` 口径）直接绑定**，须先裁。

#### 缺陷 ②：`updateAssignmentStatus` 的 `endDate` 默认为 `null`

`employeeAssignmentService.js:261`：`async function updateAssignmentStatus(client, assignmentId, newStatus, endDate = null)`。

终态写入时 `end_date = $3`（`:275`），若调用方不传 `endDate`，则**段被关闭（`is_current=false`）但没有结束日期**。

- 现状**该函数是死代码**（导出但零调用，A-02e.1 W-12 已证）⇒ 当前无实际影响；
- 但它是"看起来正确"的封装，若未来被启用会立刻产生无 `end_date` 的终态段；
- 违反 D-5 的"由业务有效日期控制"。

#### 缺陷 ③：`employee_history.event_date` 的系统日期兜底

`employeeImportService.js:701`：`event_date = startDate || new Date().toISOString().slice(0, 10)`。

当 `hire_date` 缺失时，**人事事件的业务日期被静默替换为系统当天**。历史记录一旦写入不可区分"真实业务日"与"系统兜底日"。

- 违反 D-6（系统时间与业务时间必须分离）；
- 且 `employee_history.event_date` 是 `NOT NULL`（`hse_employee_master_v59_migration.sql:208`）⇒ 无法用 NULL 表达"业务日期未知"。

### 5.4 一条重要的边界：不得为了"统一"而强制所有操作同源

任务书 §五 明确：「不能仅为了统一代码而将所有操作强制套用同一种日期来源」。本轮实测已确认系统内确实存在**三类本质不同的日期语义**，不可合并：

| 语义 | 适用 | 为什么不能合并 |
|---|---|---|
| **事件发生日** | 辞职日、死亡日、退休生效日 | 客观事实，可能早于办理日（如 10-20 死亡、10-29 才登记） |
| **变更生效日** | 调岗生效日、返聘生效日 | 业务决定，通常为未来或当月首日 |
| **系统登记时点** | `created_at`/`updated_at`/`occurredAt` | 审计用途，必须真实不可伪造 |

**现状问题不是"三者混用"，而是第三类（系统时间）被用来填充第一、二类（业务日期）的空缺**（缺陷 ①②③ 的共同形态）。

### 6.2 复活终态人员的精确条件与 SQL

**触发条件（三者同时满足即复活）**：

1. 该员工出现在本批次 `employee_import_pending` 且 `status='approved'`（`:919`，自动匹配即 approved）；
2. 该员工 `is_deleted=false`（被匹配到，`:946-957`）；
3. 该行有可解析的组织（`orgAssigned` 为真）。

**执行序列**：

```sql
-- 步骤 1（employeeImportV2Service.js:1023-1028）
UPDATE employee_assignment
   SET is_primary = false, is_current = false, end_date = CURRENT_DATE, updated_at = CURRENT_TIMESTAMP
 WHERE employee_id = $1 AND is_current = true AND is_primary = true AND is_deleted = false;
-- ⚠ 不改 status。若该人原是终态（status='inactive', is_current 已 false），
--    本条 UPDATE 匹配 0 行 —— 不做任何事，也不会阻止下一步。

-- 步骤 2（:1049-1055）
INSERT INTO employee_assignment
  (employee_id, org_unit_id, operation_unit_id, position_id, supervisor_id, dept_name,
   is_primary, is_current, status, start_date, remark, created_at, updated_at)
VALUES ($1, $2, $3, $4, $5, $6, true, true, 'active', COALESCE($10, CURRENT_DATE), $11,
        CURRENT_TIMESTAMP, CURRENT_TIMESTAMP);
-- ⚠ status 字面量 'active'；is_current/is_primary 字面量 true ⇒ 无条件"复活"
```

**关键机制说明**：复活**不依赖**步骤 1 是否命中。即使该人已无 current 段（终态标准形态），步骤 2 仍会插入一条 `active + current + primary` 的新段。

**⇒ 每执行一次月度导入，所有出现在花名册中的终态人员就被"复活"一次，而 `employee.employment_relation` 原封不动 ⇒ 制造一次全量双口径矛盾。**

**叠加效应**：由于步骤 1 用 `end_date = CURRENT_DATE`、步骤 2 用 `start_date = hire_date`，每次复活还会叠加一个"时间轴倒挂"（§5.3 缺陷 ①）。**两个缺陷在同一个 SQL 块里，一次导入同时制造两类问题。**
