## 二、业务规则基线（用户已确认，BR-01～BR-09）

以下为用户明确确认的业务规则，**原样记录，本节点不得增删改**。每条后附【系统现状锚点】仅用于说明该规则与现有系统的对应关系，不构成规则本身的扩展。

### BR-01：组织与作业单元分离
- `hse_org_unit` 承担管理组织职责；`hse_operation_unit` 承担生产作业单元职责。
- 基层班组属于**独立生产作业单元**，不作为 `hse_org_unit` 管理组织节点。
- 村庄、村驻地、镇驻地及公园属于**作业范围或作业地点**，不当然成为组织节点或班组。
- 【锚点】与方案 B 双表分离方向一致；`leaderDashboardService.js:119` 的 `'park'` 组织类型判断为死分支（dev org_type 实存 town_center/department/center/company 四值，无 park）——作业地点不入组织节点获业务确认。

### BR-02：环卫作业组织层级
- 环卫作业中心下辖 **12 个乡镇作业中心**；乡镇作业中心是**正式管理组织节点**，隶属环卫作业中心。
- 各乡镇作业中心下辖基层班组，班组作为**独立作业单元**管理。
- **市政绿化作业中心及其直属队伍继续按既有业务架构处理，不得擅自套用环卫乡镇层级。**
- 【锚点】dev `hse_org_unit` 20 节点（1 根 + 19 子，parent_id 断链 0，04-02A §E1），12 个 town_center 与该层级吻合；hse_operation_unit 的 operation_center 12 条与管理组织 12 乡镇**双登记**现象，在 BR-01 框架下属"同一实体的管理面/作业面双登记"，04-02C 需按 §4.4 处理。

### BR-03：人员跨乡镇调整
- 甲乡镇 → 乙乡镇：结束甲乡镇原作业归属，建立乙乡镇新作业归属；**不保留双乡镇并行有效基层作业归属**；保留原任职历史。
- 当前业务**不存在**"保留甲乡镇作业归属、同时临时支援乙乡镇班组"的双归属模式。
- **管理组织关系与实际作业归属是不同业务维度，不得推断二者必然同时变化。**
- 【锚点】04-02A §6.2 将"跨管理组织的班组变化"直接等价于"调岗"，与"不得推断二者必然同时变化"冲突（见 §4-C02）。

### BR-04：同乡镇内部班组调整
- 甲乡镇一班 → 二班：**结束原班组归属 + 建立新班组归属 + 保留原归属历史**；不允许直接覆盖原归属而丢失历史。
- 原 04-02A "原地更新 operation_unit_id + 写 history"的设计**不能直接沿用**（用户明示），必须按关段新建重新设计。
- 【锚点】这是本节点最重的设计冲突（见 §4-C01）。

### BR-05：基层作业班组唯一归属
- 一个员工**同一时段只能有一个有效的基层作业班组归属**；不允许同时挂两个基层班组。
- 系统**应能够防止并发或重复操作**造成两个有效班组归属。
- **此规则仅约束基层作业班组归属，不得扩大为"员工所有管理组织关系只能有一个"。**
- 【锚点】现库 `employee_assignment.operation_unit_id` 无 FK、无 CHECK、无唯一约束（R1 任务2 实证）——BR-05 引入一项新的数据库约束设计输入（见 §4-C10）。

### BR-06：月度考核对象
- 公司每月统一对 **12 个乡镇作业中心**考核；每个乡镇中心**单独评分**，形成月度考核分数和排名。
- 每个乡镇作业中心下属的**全部班组均为月度考核对象**。
- 考核结果必须能够**关联到对应乡镇作业中心或班组**；班组考核明细应支持**问题追溯和责任落实**。
- **不得将乡镇及班组月度生产绩效考核与安环管理部 HSE 专项考核混为同一指标体系。**
- 【锚点】考核域既有定局（2728 指标行僵尸、6 套并行路由、3 套扣分算法）属存量治理问题；本规则为组织模型对考核域的**关联维度要求**（乡镇/班组两级、ID 精确关联、禁名称关联）。

### BR-07：乡镇作业中心负责人资格
- 12 个乡镇作业中心负责人**均为公司正式职工**；不存在劳务派遣、外包或其他非正式员工担任该职位的情形。
- 负责人应关联 `employee` 中的**真实员工身份**，不得仅以姓名文本作为负责人关系。
- 正式员工资格沿用已确认规则：以公司正式花名册明确标注"正式员工"为准，**NULL 不得自动认定为正式员工**。
- 【锚点】`hse_org_unit.manager_id` 现状无活消费者（04-01 explore-ou A3：仅未挂载的 hse-org-center.js:140/:171/:208 读写）；正式员工判定生成器 `employeeStatusDict.formalEmployeeEligibilitySql()` 已在 B-1-P1-03-02/R1 落地，可直接复用。

### BR-08：作业单元停用
- 作业单元**存在有效员工归属时不允许直接停用**。停用前流程：
  1. 以**权威花名册**核对当前归属人员；
  2. 先处理人员转移；
  3. 结束原作业归属并建立新归属；
  4. 确认没有有效人员归属后才允许停用。
- 停用**不得删除**历史任职段、历史考核记录和相关业务档案。
- 【锚点】R1 已新增"停用需校验无 current 段引用"规则（R1 :116），与 BR-08 兼容但缺花名册核对步骤（见 §4-C07）；全仓停用联动代码现状 = 未实现（R1 链路⑪）。

### BR-09：花名册是人员归属权威业务来源
- 人员当前归属以公司**正式花名册**中的归属关系为主。
- `employee` 是唯一人员身份主表；`employee_assignment` 是系统内**唯一权威任职历史段模型**。
- 花名册是业务来源，`employee_assignment` 是系统内归属历史存储模型，**二者职责不能混淆**。
- 花名册与系统记录不一致时，**应产生差异待核实，不得擅自覆盖或选择一个归属**。
- 身份匹配沿用已确认的身份匹配规则，**不得按姓名自动匹配**。
- 【锚点】B-1-P1 全系列已确立 phone→employee_code→name→fail-closed 解析链与 V2 审核机制；04-02A §7.3 导入映射白名单与本规则兼容，但缺"差异待核实"显式输出（见 §4-C08）。

## 四、逐项核查与修订建议

### C01（高）｜班组变化任职段处理方式 — 与 BR-04 直接冲突

- **原设计位置与原文**：
  - 04-02A :212「Q4 班组变化｜班组内变化（同一管理组织下换 operation_unit）= **更新当前段 operation_unit_id + 写 history**，不新建段」
  - 04-02A :323（M3 范围）「班组变化=更新段规则落地（§7-Q4，若业务确认）」
  - 04-02A :341「Q4｜…推荐 ①更新当前段 operation_unit_id+history ②一律关段新建 → 推荐 ①」
- **新规则**：BR-04——结束原班组归属、建立新归属、保留原归属历史，**不允许直接覆盖**。用户在任务书中**明示**"原地更新 + 写 history 的设计不能直接沿用"。
- **冲突机理**：原地 UPDATE 只保留"最终状态"，旧班组归属在 `employee_assignment` 粒度上消失；"写 history"若指人事变动史表（employee_history），其粒度与任职段不同，不能替代任职段历史。BR-09 同时确认 `employee_assignment` 是**唯一权威任职历史段模型**——历史只能存在于此表，故必须以段为单位保留。
- **修订建议（供 04-02C 设计）**：班组变化与调岗统一为同一段模型机制——**同事务内**：旧段 `end_date = 新段 start_date − 1`、`is_current = false`（保留 operation_unit_id 原值）；新段 `start_date` 起效、写入新 `operation_unit_id`、`org_unit_id` 按 BR-03 独立判定。原 04-02A :341 的推荐项由「①」改「②」；M3 范围 :323 的"更新段规则"同步改为"关段新建规则"。
- **对 04-02A/R1 的影响**：04-02A §6.2 Q4、§9-M3、§11-Q4 三处修订；R1 未对此项表态（R1 :109 修正的是写入链路缺失，与本冲突正交），无需修订。

### C02（高）｜跨乡镇调整被绑定为"调岗" — 与 BR-03 注意条款冲突

- **原设计位置**：04-02A :212「跨管理组织的班组变化 = 调岗」。
- **新规则**：BR-03——跨乡镇调整的**确定部分**是作业归属变化（结束甲 + 建立乙）；且"**管理组织关系与实际作业归属是不同业务维度，不得推断二者必然同时变化**"。原设计把"作业变化"和"管理组织段变化"耦合为一个动作。
- **修订建议**：跨乡镇调整设计拆为两个独立判定：①作业归属段（operation_unit_id）**必然**关段新建（BR-03 正文确定）；②管理组织段（org_unit_id）是否同步变化——BR-03 明确不推断，登记为未决（§7-U01）。04-02C 的调岗/作业调整接口必须支持两维度独立参数，不得强制联动。
- **对 04-02A/R1 的影响**：04-02A §6.2 Q2 行修订（"允许且是标准形态：org_unit_id + operation_unit_id 并存"的方向不变，但"跨管理组织=调岗"的等价表述删除）；R1 无需修订。

### C03（中）｜兼职/借调"按需启用非 primary 段"超出已确认范围

- **原设计位置**：04-02A :214「Q6 兼职/借调｜允许非 primary 段（uk 索引只锁 primary），is_primary=false｜现有索引设计已支持，待业务确认是否启用」；:342「Q5｜…①按需启用，暂不宣传功能｜**可继续**」。

- **对 04-02A/R1 的影响**：04-02A :342 "可继续"改为"未决，待业务确认"；:214 保留。

### C04（中）｜临时派驻"走 remark"默认方案降级为未决

### C05（中）｜月度考核"乡镇+班组"两级对象未进入数据模型设计

### C07（低）｜作业单元停用校验与 BR-08 兼容，补花名册核对步骤

- **原设计位置**：R1 :116「作业单元停用需校验『无 current 段引用』（146 条存量，停用前拦截或提示）——新增规则，M1 实现」。
- **新规则**：BR-08 四步流程：花名册核对 → 人员转移 → 结束原归属建新归属 → 确认无有效归属后停用；停用不得删历史。
- **核查结论**：R1 的"无 current 段引用校验"= BR-08 第 4 步的技术实现，**兼容**；差距在第 1 步——BR-08 要求停用前以**权威花名册**核对归属，仅校验 `ea.operation_unit_id` 可能漏掉"系统有段但花名册已调走/花名册在册但系统无段"两类差异（BR-09 差异待核实原则）。
- **修订建议**：M1 停用拦截实现为：①ea current 段引用校验（R1 已列）+ ②输出"该作业单元当前归属人员清单"供与花名册人工核对（差异进待核实清单，不自动判定）；③停用操作为软停用（status 变更），禁止物理删除、禁止级联改写历史段。
- **对 04-02A/R1 的影响**：R1 :116 规则保留，实现细化归 04-02C；04-02A 无修订。

### C08（低）｜导入设计缺"花名册差异待核实"输出

- **原设计位置**：04-02A :244（导入两条路：结构化 ID 直校验 / 映射规则表白名单；无法匹配进待处理）。
- **新规则**：BR-09——花名册与系统记录不一致时**产生差异待核实，不得擅自覆盖或选择一个归属**；`employee_assignment` 是系统内唯一权威任职历史段模型，与花名册（业务来源）职责不混淆。
- **核查结论**：:244 的映射白名单 + 待处理清单已覆盖"组织匹配"维度；差距在"人员归属"维度——导入结果须输出**花名册 ↔ 系统任职段差异清单**（如：花名册显示乙班组、系统 current 段为甲班组 → 差异待核实，不自动改段）。
- **修订建议**：04-02C 导入设计补差异核对输出物；V2 既有审核机制（import_batch 审核）为承载点。
- **对 04-02A/R1 的影响**：04-02A §7.3 补充项；R1 无需修订。

### C09（低）｜环卫→12 乡镇层级与 dev 实态一致；市政绿化需专门注记

- **核查结论**：BR-02（环卫作业中心下辖 12 乡镇作业中心，乡镇为正式管理组织节点）与 dev `hse_org_unit` 实态一致（04-02A §E1：20 节点、parent_id 断链 0、town_center 12）。无需修订。
- **补充约束**：BR-02 明确"市政绿化作业中心及其直属队伍按既有业务架构处理，不得套用环卫乡镇层级"——04-02C 设计组织树/考核/统计模板时，市政绿化分支不得复制"乡镇→班组"模板；dev 中 center(2) 值的双中心语义核对列入 04-02C 输入。
- **对 04-02A/R1 的影响**：无需修订原报告；新增约束归 04-02C。

### C10（中）｜双维度结构满足 BR，但 BR-05 引入新的唯一性约束设计输入

- **核查结论**：`employee_assignment.org_unit_id`（管理维度）+ `operation_unit_id`（作业维度）的双引用结构在 BR-01～BR-09 框架下**仍然成立**——BR-03/BR-05 恰好依赖"管理归属与作业归属是两个维度"才能表达。R1 任务2/任务3 的实态修正（无 FK、四链路未实现）维持有效。
- **新增设计输入（BR-05）**："同一时段只有一个有效基层作业班组归属 + 系统防止并发/重复操作"→ 现库 `operation_unit_id` **无任何唯一性保障**（R1 实证），应用层校验无法可靠防并发。04-02C/M2 须设计 DB 级约束，候选形态：partial unique index（类比既有 `uk_emp_assign_primary` 的 partial index 模式，B-1 人员域已实证其与 CONSTRAINT 的判别差异）——`WHERE operation_unit_id IS NOT NULL AND is_current AND NOT is_deleted`。具体形态（含历史段豁免、是否含 is_deleted 语义）归 04-02C 设计，本节点仅登记需求。
- **边界提醒（BR-05 明示）**：该约束**仅限作业班组维度**；管理组织维度（org_unit_id）的多段/非 primary 问题维持 C03 未决状态，不得借同一约束扩大。
- **对 04-02A/R1 的影响**：R1 任务2 实态记录不变；M2 范围（04-02A :315）补"operation_unit_id 唯一性约束"条目（修订建议，不改原文）。
