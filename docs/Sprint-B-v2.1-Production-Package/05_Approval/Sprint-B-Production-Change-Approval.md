## 二、变更目的

### 2.1 背景

当前系统存在两套人员-组织关系模型：

- **旧模型**：`hse_employee_relation` + `hse_employee_org`
- **新模型**：`employee_assignment`

两套模型并存导致：
1. 数据不一致风险
2. 维护成本增加
3. 前端代码逻辑复杂
4. 权限体系不统一

### 2.2 变更目标

完成组织模型迁移：

```
hse_employee_relation
          ↓
  employee_assignment
```

具体目标：
1. 将 `hse_employee_relation` 中的当前关系数据迁移至 `employee_assignment`
2. 恢复 `employee` 表中被软删除但被旧模型引用的员工记录
3. 冻结旧模型 `hse_employee_org`（只读）
4. 确保迁移前后数据一致性
5. 为前端代码切换到新模型奠定数据基础

## 五、回滚方案

### 5.1 回滚触发条件

出现以下任一情况，立即启动回滚：

1. 迁移 SQL 执行失败且无法在 10 分钟内修复
2. 数据一致性验证失败且影响范围 > 10%
3. 前端功能验证大面积失败（> 3 个核心功能）
4. 业务方报告严重数据错误

### 5.2 回滚策略

| 层级 | 策略 | 预计耗时 | 适用场景 |
|------|------|----------|---------|
| B-2 回滚 | 策略 2：恢复 UPSERT 覆盖记录 | ~ 5 分钟 | B-2 迁移失败 |
| B-0 回滚 | 策略 2：从持久化备份表回滚 | ~ 3 分钟 | B-0 恢复失败 |
| 全量恢复 | pg_restore 从备份恢复 | ~ 30 分钟 | 严重数据损坏 |

### 5.3 回滚步骤

```
1. 评估失败阶段（B-2 / B-0 / 全量）
2. 执行对应回滚 SQL（见 06_Rollback.sql）
3. 验证回滚结果
4. 通知相关人员
5. 记录回滚日志
6. 召开故障分析会
```
