## Codex 审核结论

执行报告 03 的最终审核结论是：**部分通过，需整改**。

已确认成立的部分：

1. Codex 实际复跑 `npm --prefix server run test -- --runInBand`，退出码为 `0`，结果为 13 个测试套件、184 个用例全部通过。
2. 默认 Jest 收集规则已收敛到 `*.unit.test.js`，集成配置已挂载 `globalSetup` 门控。
3. 开发模式管理员回退和 `permissions: ['all']` 已从 `vben-compat.js` 移除。
4. 导入写接口已增加角色限制，匿名健康检查响应已最小化。

报告 03 不能判定“通过”的原因：

1. `server/middleware/auth.js` 的 `requireRole(...allowedRoles)` 接收可变参数，但 `server/app.js` 的 `/metrics` 和 `/api/postgres/status` 使用 `requireRole(['admin'])`。此时 `allowedRoles` 实际为 `[['admin']]`，合法管理员也会得到 403。
2. 仓库中还有多处数组式调用，至少涉及 `hse-position-responsibility.js` 和 `hse-roster-import.js`。这不是两个端点的孤立问题，必须统一修复并回归。
3. `auth-gate.unit.test.js` 只验证两个诊断端点的匿名访问被拒绝，没有验证合法管理员成功访问，因此漏掉上述回归。
4. 公开路径的可选认证在 `authMiddleware` 内重复解析 JWT，未检查 Token 黑名单，且把原始 decoded payload 直接赋给 `req.user`。已登出的 Token 仍可能获得健康检查的认证详情。
5. `isTokenBlacklisted()` 查询异常时返回 `false`，即黑名单存储不可用时按“未拉黑”处理。Codex 复跑测试时已实际看到“黑名单查询失败”日志后请求继续返回 200/403，属于 fail-open。
6. `POST /api/auth/logout` 使用 `jwt.decode()` 而非验签结果写入黑名单；审计段还引用了块级作用域之外的 `token`，异常被空 catch 吞掉。`blacklistToken()` 又吞掉持久化失败，可能对外宣称登出成功但 Token 实际仍有效。
7. `GET /api/import/logs`、`config`、`template/:module`、`stats` 目前只有全局登录要求，没有模块角色限制；“导入模块已完成权限收口”的结论不成立。
8. `app.use('/uploads', express.static(...))` 位于 `/api` 鉴权之外。前端至少有两处直接访问 `/uploads/insurance/...` 的保单文件，敏感文件存在匿名直链风险；同时不能直接删除静态路由导致现有预览功能中断。

## 任务 1：统一修复 `requireRole` 调用契约

1. 全量搜索 JavaScript 后端中的所有 `requireRole(...)` 调用，列出数组式与可变参数式调用位置。
2. 在 `server/middleware/auth.js` 中统一调用契约，使以下两种既有形式都能正确工作：

```js
requireRole('admin', 'safety_manager')
requireRole(['admin', 'safety_manager'])
```

3. 允许做一层数组扁平化与去重，但必须验证每个角色是非空字符串。空角色集合、嵌套异常值或错误类型必须 fail-closed，不得意外放行。
4. 不要只修改 `app.js` 的两处调用，否则其他数组式调用仍然损坏。
5. 保持现有返回语义：未认证为 401，已认证但角色不允许为 403，允许角色调用 `next()`。
6. 根据现有角色映射明确诊断端点的授权角色：`system_admin` 和 `admin` 可以访问 `/metrics`、`/api/postgres/status`；`safety_manager`、`viewer` 等非系统管理员角色返回 403。若代码中的实际角色定义与此冲突，必须先在报告中给出证据，不得静默扩大权限。

## 任务 2：补齐角色与诊断端点回归测试

## 任务 3：合并认证解析路径并修复黑名单 fail-open

1. 消除公开路径中那段重复、弱化的 JWT 解析逻辑。普通认证与可选认证应复用同一套 Token 校验和 `req.user` 规范化规则。
2. 一个 Token 只有同时满足以下条件，才可形成认证身份：
   - 签名、有效期和 Token 类型正确；
   - 存在有效 `jti`；
   - 不在黑名单中；
   - 对需要认证详情的路径，当前用户仍存在且处于启用状态；
   - `req.user` 只包含明确允许的规范字段，不直接挂载原始 decoded payload。
3. 受保护接口的黑名单查询异常必须 fail-closed：不得调用 `next()`，返回不泄露数据库细节的 503 或统一认证错误，并在测试中锁定。
4. 公开健康检查的可选认证校验异常不得破坏匿名存活检查：当 Token 无效、过期、已拉黑、用户禁用/不存在或认证存储不可用时，继续按匿名响应，只返回最小字段，不得返回 `database`、`memory`、`ai`。
5. 合法、未拉黑、用户有效的 Token 才能获得认证健康详情；测试中必须 mock 所有查询，并确认不会连接真实数据库。
6. `/api/user/info`、`/api/access/codes`、`/api/auth/codes` 不得仅凭 Token 中可能过期的角色声明向已禁用、已删除或角色已变更用户返回旧权限。优先复用已验证的当前用户上下文，避免各路由自行形成不同认证标准。
7. 不得通过把黑名单检查整体移除、忽略异常或始终返回匿名来规避测试。

## 任务 4：修复登出与撤销语义

1. 保留“无 Token 登出幂等成功”的产品行为，但不得把未验签的 `jwt.decode()` 结果用于黑名单写入或审计身份。
2. 携带 Token 时，必须先验证签名、类型及必要声明，再使用可信的 `jti/userId/exp`。
3. 修复 `token` 变量作用域错误，禁止空 catch 静默吞掉代码缺陷；日志不得输出原始 Token。
4. `blacklistToken()` 持久化失败不能伪装为成功。对有效 Token 的撤销失败应返回明确、脱敏的失败结果，使客户端知道服务端会话未完成撤销。
5. 无效、伪造或过期 Token 的登出应保持幂等、不得写入黑名单，不得用其中声明写审计身份。
6. 检查 refresh 路径对黑名单查询异常的处理，确保刷新令牌不会在撤销存储异常时 fail-open。
7. 增加 mock 单元测试覆盖：无 Token、有效 Token、伪造 Token、已拉黑 Token、黑名单查询异常、黑名单写入异常、refresh 黑名单异常。
