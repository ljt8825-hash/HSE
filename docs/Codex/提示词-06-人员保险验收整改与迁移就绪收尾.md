## 四、任务 1：冻结并实现唯一的人员保险 API 写入契约

前端和后端统一使用以下 camelCase 业务契约；snake_case 只允许存在于后端数据库适配层和 SQL 中：

```ts
interface PersonnelInsuranceWritePayload {
  employeeId: number;
  insuranceType: string;
  coverageAmount?: number;
  premium?: number;
  startDate?: string | null;
  expireDate?: string | null;
  isCurrent?: boolean;
  policyNo?: string;
  remark?: string;
}
```

要求：

1. `POST /api/insurance/personnel` 使用专用 create schema，`employeeId` 必填、正整数；`insuranceType` 必填。不得再接受 `personnel_id`、`person_name`、`name`、`idCard` 来决定关联对象。
2. `PUT /api/insurance/personnel/:id` 使用独立 update schema，不能简单对 create schema 调用 `partial()` 后留下含混行为。默认不可修改所属人员；若保留显式换人能力，只能通过合法 `employeeId`，并从人员主数据刷新全部快照。
3. 写接口对未知字段采取可测试的严格策略。旧的 snake_case 或页面旧字段必须明确拒绝并返回稳定业务错误，不能被 Zod 静默剔除后以空值写库。
4. 在路由或局部服务中集中完成 camelCase 到数据库 snake_case 的一次映射。禁止页面自行发送数据库列名，也禁止同一路径同时混读多套字段名。
5. 前端 `createPersonnel`/`updatePersonnel` 使用严格的 `PersonnelInsuranceWritePayload`/更新类型，不再接受 `Partial<PersonnelItem>` 这种无法发现拼写错误的宽泛类型。
6. 返回 DTO 继续明确区分 `employeeId` 与保险记录 `id`；不得新增含混 ID。

## 九、任务 6：统一有效保单、临期、合规和同步状态口径

把日期/状态规则集中为可单测的纯函数或单一服务，并让主列表、筛选、统计、内存模式和必要 SQL 使用同一语义：

1. “当前有效”必须同时满足：记录存在、未删除、`is_current=true`、`start_date <= 当前业务日期 <= expire_date`。未来才生效、已失效或缺少必要日期的记录不得显示为当前已参保。
2. 有效记录的 `expire_date` 在当前业务日期至当前日期加 30 天之间（含边界）为 `expiring`；超过 30 天为 `insured`；已过期为 `expired`；没有可用当前保单或尚未生效为 `uninsured`。SQL 与 JS 的边界必须完全一致。
3. 确定性选单必须优先当前有效记录，再处理未来/历史记录，并以到期日、起期、ID 形成稳定排序；不能让一张未来保单遮住当前有效保单。
4. `hasInsurance`、主列表筛选、统计和合规计算不得仅依据记录 ID 是否存在；必须基于上述有效业务事实。
5. `syncStatus` 使用被选保险记录的快照姓名、部门、岗位与当前花名册比较：无任何关联保险为 `missing`；至少有一条且所有相关快照一致为 `synced`；任一不一致为 `unsynced`。雇主险和工伤险分别取快照后再汇总。
6. 主查询必须实际选出快照字段，格式化函数不得在 DB 模式恒定返回 `synced`。筛选和统计也要使用同一状态定义。
