# DeepSeek 执行提示词 01：阶段 1 运行基线收敛

你是本项目的高级全栈工程师。请在当前工作区实际执行本提示词，不要只给方案。

`G:\hse-dashboard\docs\Codex\执行报告-01-阶段1-运行基线收敛.md`

聊天回复只能作为摘要，Markdown 报告文件才是正式交付物。报告必须足以让未参与执行的 Codex 独立复核，不得只写“已完成”或省略失败信息。

在本轮报告通过 Codex 复核前，不得自行开始阶段 2，不得顺手处理权限、业务流程、页面改造或其他问题。

## 本轮目标

建立唯一、稳定、可重复的开发、测试和构建入口。

本轮只收敛运行基线，不开发新业务功能，不调整页面设计，不进行数据库结构或数据变更。

## 已知现状

1. `start-hse-v2.ps1` 声明后端端口为 `5666`。
2. `server/app.js` 默认端口为 `5666`，但现有实际环境可能配置为 `5800`。
3. 前端 `vite.config.ts` 将 API、上传和 WebSocket 代理固定到 `5800`。
4. `server/package.json` 同时存在 CommonJS 生产入口和遗留 TypeScript 构建入口。
5. `server/app.js` 在加载部分依赖环境变量的模块之后才调用 `dotenv.config()`。
6. 前端类型检查当前能够通过。
7. 后端 Jest 存在 `uuid` ESM/CommonJS 不兼容、无有效测试用例、mock 写法错误和缓存断言失败等问题。
8. 当前 Git 工作区存在大量用户修改及未跟踪文件，不是干净工作区。

以上是扫描结论，不可直接当作最终事实。修改前必须读取现有文件与差异进行确认。

## 强制约束

1. 开始前执行 `git status --short` 和相关 `git diff`，识别用户已有修改。
2. 不得撤销、覆盖、批量格式化或夹带修改用户现有内容。
3. 不得使用 `git reset`、`git checkout`、`git clean`、递归删除等破坏性命令。
4. 不得删除旧源码、SQL、文档、备份、调试脚本或未跟踪文件。
5. 不得执行数据库迁移、初始化、清空、回滚、演示数据生成或业务数据导入。
6. 不得修改业务接口语义、权限规则、数据模型或业务页面。
7. 不得创建或提交 Git commit，不得推送远端。
8. 所有手工文件修改使用 `apply_patch`。
9. 不得将真实密码、Token、密钥、数据库连接信息写入代码、报告或聊天输出。
10. 如目标文件已有用户修改，必须基于当前内容做最小增量修改，并在报告中注明。
11. 遇到无法确认是否连接生产数据库的测试，必须停止该测试，不得冒险执行。
12. 不得自行进入后续阶段。

## 任务一：确认并统一运行入口

1. 阅读根目录和后端 `package.json`、`server/app.js`、`start-hse-v2.ps1`、前端 `vite.config.ts` 及环境变量示例。
2. 确认 `server/app.js` 是否为当前唯一实际运行入口，并列出仍引用遗留 TypeScript 入口的位置。
3. 调整 `server/package.json`：
   - `start` 和 `dev` 必须指向真实运行入口。
   - 默认构建或启动不得指向不会用于部署的遗留 TypeScript 产物。
   - 如确需保留 TypeScript 能力，使用名称明确的 `legacy:*` 脚本，并不得让其成为默认交付入口。
4. 调整根目录 `package.json`，保证启动、构建、类型检查和测试命令与真实目录一致。
5. 只修正运行契约，不删除遗留实现。

## 任务二：统一端口配置

1. 采用以下默认约定：
   - 后端：`5666`
   - 前端：`5173`
2. 前端代理目标必须支持环境变量覆盖，未配置时默认使用 `http://127.0.0.1:5666`。
3. `/api`、`/uploads`、`/ws` 必须派生自同一个后端代理目标，WebSocket 协议需正确处理。
4. `start-hse-v2.ps1`、`server/app.js`、前端 `vite.config.ts`、`.env.example`、`.env.docker.example` 及直接相关启动说明必须一致。
5. 不得硬编码当前用户目录、个人工具目录或仅在本机存在的运行路径。
6. 不得读取或展示真实 `.env` 内容，只能检查所需变量是否存在。

## 任务三：修正环境变量加载顺序

1. 保证 `dotenv` 在任何读取 JWT、数据库、端口、CORS、上传目录或 AI 配置的模块加载之前执行。
2. 环境变量校验失败时必须给出明确错误并终止启动。
3. 不得降低现有 JWT、刷新令牌或数据加密密钥的强度要求。
4. 不得在日志和执行报告中打印真实环境变量值。
5. 检查测试环境是否通过安全的测试配置注入环境变量，不得依赖开发机的全局环境变量碰巧存在。

## 任务四：整理测试入口

1. 修复 `requestLogger` 对 `uuid` ESM 包的 CommonJS 兼容问题。优先使用 Node.js 内置 `crypto.randomUUID()`，避免为请求 ID 引入额外依赖。
2. 检查 `uuid` 是否还有其他实际使用点；只有确认无使用后才可从依赖中移除，并同步锁文件。
3. 只修复导致测试框架无法正常启动的基础问题，不在本轮大规模重写业务测试。
4. 对文件名符合 Jest 匹配规则、但实际是独立执行脚本且没有 Jest 用例的文件：
   - 不得重写其业务逻辑；
   - 应通过精确命名或 Jest 配置将其与自动测试分离；
   - 不得用大范围忽略规则掩盖真正测试。
5. 修复 `server/services/aiService.test.js` 中违反 Jest mock factory 作用域规则的问题，保持原测试意图。
6. 分析缓存测试失败属于实现缺陷还是断言过时；本轮只在证据充分且不改变业务语义时做最小修复，否则记录为后续问题。
7. 不得让测试连接或修改真实开发、验收或生产数据库。
8. 若没有隔离测试数据库，只运行纯单元测试与静态检查，并在报告中明确哪些集成测试未执行及原因。

## 任务五：验证

至少执行以下验证；无法安全执行的命令必须在报告中解释原因：

```powershell
node --check server/app.js
npm --prefix server run test
pnpm --dir "安全看板vben/apps/web-antd" run typecheck
pnpm --dir "安全看板vben/apps/web-antd" run build
git diff --check
git status --short
```

同时完成以下静态核查：

1. 搜索运行配置中的 `5666`、`5800`、`5173`，确认不存在互相冲突的有效配置。
2. 搜索所有默认启动、构建脚本，确认不会进入遗留后端入口。
3. 搜索 `dotenv.config()` 和环境变量读取点，确认加载顺序成立。
4. 搜索 `uuid` 的剩余引用，确认依赖处理完整。
5. 检查本轮实际修改文件，确认没有业务模块、数据库脚本和页面功能变更。

如果需要验证后端能否启动：

- 只能在确认不会占用或终止用户现有服务的前提下进行。
- 不得执行启动脚本中的端口清理或强制结束进程逻辑。
- 使用未占用的临时端口或仅做模块加载检查。
- 验证结束后必须正常终止由本轮启动的进程。

## 验收标准

1. 后端、前端与启动脚本的默认端口契约一致。
2. 前端代理可通过环境变量覆盖，三个代理入口使用同一目标来源。
3. 环境变量在依赖模块读取前完成加载。
4. 默认后端启动与构建脚本不再指向互相冲突的实现。
5. 前端类型检查和生产构建通过。
6. 后端测试至少能够正常进入 Jest 执行阶段。
7. 如后端测试仍失败，必须区分：测试基础设施失败、单元测试失败、集成环境或数据库依赖失败。
8. 没有修改业务功能、权限行为、数据库结构和用户无关文件。
9. 已生成规定的 Markdown 执行报告。
