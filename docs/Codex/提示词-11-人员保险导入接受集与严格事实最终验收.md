## 四、任务 1：把批内集合改成真正的“已接受最终事实”

1. 通用导入的批内检查必须按原始 `sourceRowNo` 处理 INSERT/UPDATE 候选，而不是先全部 INSERT 再全部 UPDATE。可构造统一候选列表：

```js
{ operation: 'insert' | 'update', item, sourceRowNo }
```

按源行号稳定排序后逐行校验，最终再拆回 `toInsert/toUpdate`。不得把上下文元数据塞回 dbRow。
2. active key 只有在以下全部通过后才能加入 accepted 集合：
   - active 纯函数为 true；
   - 没有已接受批内同 key；
   - 数据库冲突查询成功；
   - 数据库中无外部 active 冲突。
3. 因 `duplicate_active_policy`、`duplicate_check_failed`、重复 UPDATE 目标或其他错误被拒绝的行不得占用 accepted active key，也不得占用 accepted update target。
4. 同一 UPDATE 目标重复出现时，以原始文件顺序为准只接受第一条“完整通过校验”的行；第一条若因其他原因失败，后续行应独立校验，不能被失败行占位。
5. 非 active 行不占 active key；不同 employee/type 互不影响；UPDATE 仍必须 `excludeId=目标ID`。
6. 保持第 09/10 轮列白名单、原始行号、安全结构化错误、目标查询 fail-closed 和批量/逐条写入行为。

必须新增可达测试：

- 原始第 1 行 INSERT 因数据库已有 active 冲突被拒，原始第 2 行 UPDATE 正是该 existing 目标并以 excludeId 查无其他冲突：第 2 行必须允许 UPDATE，不能被第 1 行残留 key 拒绝。
