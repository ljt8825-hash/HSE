## 六、任务 3：统一业务日、选单和人员级状态集合

### 3.1 `Asia/Shanghai` 业务日

1. 明确人员保险业务时区为 `Asia/Shanghai`，提供单一、可注入当前时刻的业务日函数。不得再用 UTC `toISOString().slice(0, 10)` 代表中国业务日。
2. DB 查询不得依赖连接会话时区下的裸 `CURRENT_DATE`。可以统一传入同一个 `YYYY-MM-DD` 参数，或统一使用显式 `CURRENT_TIMESTAMP AT TIME ZONE 'Asia/Shanghai'` 表达式；无论选择哪种方式，主列表、COUNT、stats、选单、查重和 `expiring-soon` 必须一致。
3. 内存计算和同一请求内的 DB SQL必须使用同一个业务日语义。纯函数测试必须可固定时刻，禁止依赖测试机器当前日期。
4. 增加北京时间零点前后用例，例如同一 UTC 日期对应北京时间前一天/后一天的边界，证明业务日不会偏一天。

### 3.2 SQL 与内存确定性选单完全等价

1. 保留优先级：当前有效(0) > 当前标记的未来(1) > 当前标记的历史(2) > 停用/日期不完整/非法记录(3)。
2. SQL 未来和历史 CASE 分支必须与内存一样考虑 `is_current=true`。`is_current=false` 的未来、过期记录一律为 rank 3。
3. 同 rank 的 `is_current`、止期、起期、ID 排序及 NULL 规则必须逐项一致。
4. 建立表驱动矩阵测试，至少覆盖 active/future/expired/inactive-future/inactive-expired/incomplete，并分别验证纯函数 rank、比较器结果和生成的 SQL CASE 语义。只查找 SQL 是否包含某个片段不算等价性证明。

### 3.3 定义互斥的人员级状态

保留每个险种自己的 `insured/expiring/expired/uninsured` 子状态；人员主列表筛选和人员统计使用以下互斥优先级：

1. `expiring`：任一受支持险种存在当前有效且 0–30 天到期的被选保单。
2. `insured`：不属于 expiring，且至少一个受支持险种存在当前有效保单。
3. `expired`：没有任何当前有效保单，且至少一个受支持险种的被选记录是历史过期保单。
4. `uninsured`：以上均不满足，即无记录，或只有未来、停用、日期不完整/非法记录。

据此统一：

1. DB list/COUNT 的 `insuranceStatus`、内存筛选和格式化出的人员级状态必须完全一致且集合互斥。
2. stats 定义为：`covered = insured + expiring`，`expired = expired`，`pending = uninsured`，并满足 `total = covered + expired + pending`；`expiring30d` 是 covered 的子集。
3. `byType` 仍按各险种当前有效人数统计，不得把历史/停用记录计入。
4. 将互斥人员状态表达式收敛为共享 SQL 构造与共享 JS 纯函数，避免 list、COUNT、stats 分别手写。
5. 用同一人员同时拥有两种不同子状态的组合矩阵验证优先级，例如一个险种 insured、另一个 expiring 时人员级只能是 expiring；一个 expired、另一个 uninsured 时只能是 expired。
