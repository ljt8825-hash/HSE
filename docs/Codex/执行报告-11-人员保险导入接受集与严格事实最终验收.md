## 三、accepted 候选处理时序与 strict boolean 决策表

### 3.1 批内候选处理时序（任务 1，`import.js`）

```
预处理（resolveEmployee/险种规范化/is_current 默认 true）
  → 分类 toInsert/toUpdate（existingMap 识别 UPDATE 目标）
  → 统一候选列表 [{ operation: 'insert'|'update', item, sourceRowNo }]
  → 按 sourceRowNo 稳定排序（缺失行号放最后）
  → 逐行校验：
      1) operation=update → acceptedUpdateTargets 重复目标拒绝（仅首个"完整通过"占用）
      2) active 判定（isPolicyActiveOnBusinessDay，规范 boolean）
      3) active 时：batchActiveKeys.has(key) → duplicate_active_policy_in_batch
      4) DB 冲突查询（INSERT 无 excludeId；UPDATE excludeId=目标ID）
      5) 全部通过后才 batchActiveKeys.add(key) / acceptedUpdateTargets.add(targetKey)
      6) 任何失败行 continue 前不 add（失败行不占位、不阻断后续独立校验）
  → 拆回 checkedInsert / checkedUpdate（保持原源行序）
  → 写库（批量 INSERT / UPDATE，白名单列）
```

### 3.2 strict boolean 决策表（任务 2，`isPolicyActiveOnBusinessDay`）

字段优先级：**显式 camelCase `isCurrent` 优先**（仅当其 `undefined` 时回退 snake_case `is_current`）；禁止 OR。

| 传入 `{ isCurrent, is_current }` | active 判定 | 说明 |
|---|---|---|
| `isCurrent: true` | active | 显式 true |
| `isCurrent: false` | 非 active | 显式 false，**不被**同对象 `is_current: true` 覆盖 |
| `isCurrent: null` | 非 active | null 不提升 |
| `isCurrent: undefined` + `is_current: true` | active | 回退 snake_case |
| `isCurrent: undefined` + `is_current: false/null/undefined` | 非 active | false/NULL/undefined 均 inactive |
| 起止日期缺一 / start>expire | 非 active（日期合法性由各入口自己的校验处理，与冲突语义分离） | |
| 未来（start>day）/ 历史（expire<day） | 非 active → 不查 active 冲突 | 不被已有 active 误拦 |

### 3.3 空 employee 隔离（任务 2，`findActivePolicyConflictInMemory`）

只有 `record.employee_id` 为**有效正整数且严格等于目标员工**的记录参与冲突；`null/undefined/非法字符串/其他员工` 全部排除；不回退按姓名或旧 `personnel_id` 猜测。

## 四、批量续保事务序列与导入 outcome 表

### 4.1 批量续保 DB 事务序列（任务 3）

```
BEGIN
  → SELECT ... FOR UPDATE（锁定目标，合并依据在本事务中稳定）
  → 逐目标合并"更新后完整事实" + 日期顺序校验（失败 → 全校验完成后统一 ROLLBACK，零 UPDATE）
  → active 判定（is_current=null → 非 active → 不查冲突）
  → 批内 batchKeys + 外部冲突（excludeId=目标ID，opts.db=client）
  → 逐条 UPDATE；每条检查 rowCount===1：
      0 行或异常 → throw → 统一 catch → ROLLBACK + error(-1, '续保失败，请稍后重试')（不 COMMIT、不虚报成功）
  → 全部成功 → COMMIT → renewed=plans.length（实际成功条数）
finally → client.release()
```

### 4.2 导入 outcome 表（任务 4）

| 条件 | outcome | file_records.status | /confirm 消息 |
|-----|---------|--------------------|--------------|
| `wroteCount > 0` 且 `skipped===0` 且 `rowErrors` 空 | `imported` | `imported` | `入库成功: 新增X, 更新Y` |
| `wroteCount > 0` 且 `skipped>0` 或 `rowErrors` 非空 | `partial` | `partial` | `部分入库完成: 新增X, 更新Y, 跳过Z` |
| `wroteCount === 0`（存在跳过/错误或空结果） | `failed` | `failed` | `入库失败，未写入记录`（不含"入库成功"） |
| file_records 状态更新本身失败 | `success:false, error:'文件状态更新失败，请稍后重试'` | 不更新 | `error(-2, ...)`，仅服务端日志，不泄漏 SQL/host/port |

边界：本轮只收口**数据库原生导入路径**（`confirmImportNative`）；内存模式（`confirmImportMemory`）与 Python 导入路径不在本轮范围，报告如实说明。
