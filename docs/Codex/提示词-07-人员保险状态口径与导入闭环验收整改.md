## 四、任务 1：建立单一、可执行的有效保单与确定性选单规则

将人员保险的状态计算和选单排序收敛为共享、可单测的业务逻辑。DB SQL、内存模式和前端 DTO 必须遵循同一规则。

### 1.1 当前有效与状态

1. 当前有效必须同时满足：记录存在、`is_deleted=false`、`is_current=true`、`start_date` 和 `expire_date` 均有效、`start_date <= 业务日 <= expire_date`。
2. `is_current` 缺失、起期缺失、止期缺失、起期晚于止期均不得判为当前有效。
3. 当前有效且止期距离业务日 0–30 个自然日（含 0 和 30）为 `expiring`；大于 30 日为 `insured`。
4. 只有历史保单且止期早于业务日时为 `expired`；只有未来、停用、日期不完整或根本无有效事实时为 `uninsured`。若同时存在当前有效保单，必须以当前有效保单为准。
5. 日期按 `YYYY-MM-DD` 业务日比较，避免本地时区/UTC 转换造成前后一天偏差。测试固定业务日。

### 1.2 确定性选单

1. 每个 `employee_id + insurance_type` 必须优先选择当前有效保单，再按明确的未来/历史/停用优先级选择用于展示的记录，最后用止期、起期、ID 保证稳定排序。
2. SQL `ROW_NUMBER()` 的 `ORDER BY` 必须显式包含当前有效 `CASE`，不能只按 `is_current` 和最晚到期日。
3. 内存模式必须调用与 SQL 等价的比较器，不得“遍历到最后一条即覆盖”。
4. 同一被选记录的 ID、保单号、日期、保额、保费、`isCurrent` 和快照必须整体返回，禁止跨记录拼接。

## 五、任务 2：让主列表、筛选、统计、合规和同步真正使用同一口径

### 2.1 DB 主列表

1. 主查询、COUNT 查询和筛选必须复用同一组确定性选单子查询及有效性表达式。
2. `insured/expiring/expired/uninsured` 筛选与任务 1 完全一致，第 30 天只能属于 expiring，第 31 天起才属于 insured。
3. `uninsured` 必须能包含只有未来、停用或日期不完整保单的人员，不能只检查 `emp.id/inj.id IS NULL`。
4. `hasInsurance` 表示“当前有效参保”，不得表示“存在任意历史记录”。保留业务记录 `id` 供编辑历史记录，两者不得混淆。
5. 合规计算只能使用当前有效的工伤险/雇主险及有效保额，不能因过期或停用记录而合规。

### 2.2 `syncStatus`

1. 显示和筛选统一为：无关联保险记录 `missing`；相关被选记录快照全部一致 `synced`；任一快照不一致 `unsynced`。
2. 修复 DB 写死 `'synced'` 的筛选和内存只返回 missing 的筛选。
3. 筛选后的 COUNT、分页和 list 必须一致；不能先分页再在 JS 中过滤导致页数错误。

### 2.3 统计和旁路

1. `/personnel/stats` 按当前花名册“人数”统计，而不是保险记录数；covered、byType、expiring、expired、pending/uninsured 的含义写清并使用同一规则。
2. DB 与内存模式返回相同字段和同一人数口径。同一人多张历史保单不能重复计数。
3. `formatPersonnelIns`、详情、新建/更新响应、导出、`expiring-soon` 等人员保险旁路统一使用共享状态函数或明确的同义 SQL，不再保留仅按到期日的旧实现。
4. `expiring-soon` 必须要求当前有效，并参数化天数；禁止把整数直接插入 SQL 字符串。
