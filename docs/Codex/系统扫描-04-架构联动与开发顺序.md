# 系统扫描 04：架构、联动与开发顺序

## 结论

当前系统不适合继续按菜单逐页补功能，也不需要先重做 Vben Admin 组件。下一阶段应先完成**主数据收敛与跨模块关联基座**，再逐步完善业务模块，最后才开发依赖汇总数据的风险画像、预警、驾驶舱和 AI。

本次为静态代码扫描，不连接数据库、不执行迁移、不上传文件、不启动服务。结论说明的是“当前代码具备什么能力和什么风险”，不等同于生产数据已验证。

## 扫描范围与运行形态

- 生产后端唯一入口为 `server/app.js`，其注释明确将 `server/src/app.ts` 定义为归档的 legacy 入口。
- 后端存在 74 个 JavaScript 路由文件，`app.js` 注册了 89 个中间件/路由挂载点。
- 前端为 Vben Admin 的 `web-antd`，现有 138 个 Vue 页面和 34 个 HSE API 文件。
- 默认 Jest 只收集 13 个 `*.unit.test.js` 文件；此前复跑结果为 13 个套件、184 个用例通过。另有 63 个普通 `*.test.js` 文件不在默认门槛内。
- 26 个路由文件存在 `isConnected()`、`initMemoryData()` 或 `memoryStores` 降级逻辑。它们可支持本地演示，但不能作为“数据库业务流程已完成”的证据。

## 当前架构事实

### 1. 人员主数据已经有正确的目标模型

`server/sql/hse_employee_master_v59_migration.sql` 明确规定：

- `employee` 是唯一人员主表；
- 所有关联使用 `employee_id`；
- 组织关系由 `hse_employee_org` 管理，并可通过 `v_employee_current` 提供当前人员、组织、岗位视图；
- 花名册导入 V2 使用“工号 -> 身份证哈希 -> 手机哈希加姓名”的匹配优先级。

`server/routes/hse-employee.js` 已具备员工、部门、岗位、任职、证件、安全档案、培训、巡检、隐患等较完整 API，属于应保留的主数据中心。

### 2. 旧模型仍在运行，造成双轨数据

根目录 `sql/unified_schema.sql` 中仍保留 `personnel`、`personnel_insurance`、`training_records.personnel_id`、`accidents.personnel_id` 等旧模型。现有业务路由也同时读写这些字段。

这意味着系统不是“缺少人员联动”，而是同时存在：

```text
employee / v_employee_current / employee_id        新主数据模型
personnel / personnel_id / person_name              旧业务模型
```

后续开发若继续增加 `personnel_id` 或姓名关联，会使迁移成本持续上升。

### 3. 人员保险功能完成度高，但联动键不合格

人员保险页面已实现用户要求的业务展示：以 `v_employee_current` 的在职花名册为主体，左连接保险透视数据；没有保险记录时，雇主险和工伤险显示为未参保。该用户体验方向正确。

但后端当前将 `personnel_insurance` 按 `person_name` 分组，并以 `piv.person_name = ev.name` 连接花名册。同步接口同样以姓名匹配。姓名不是稳定主键，会在同名、改名、外部数据错别字或历史合并时错配。

前端详情页的“同步花名册”将雇主险/工伤险记录 ID 作为参数传给同步接口；该接口也按保险记录 ID 更新。命名为 `empId` 会误导维护者，不是人员 ID。当前功能可能可运行，但语义不清且无法成为其他模块的标准。

结论：人员保险应视为“业务页面完成、主数据联动需收敛”，不应重做 UI。

### 4. 车辆存在同表融合和双接口问题

`/api/insurance/vehicle` 直接将车辆资料和当前保险字段读写在 `vehicles` 表；`/api/vehicles` 又通过另一套 controller 暴露同一业务对象。事故模块也保存 `vehicle_id`，说明车辆应是稳定主数据。

现状适合先冻结 `vehicles.id` 为唯一车辆 ID，并梳理两个 API 的归属。是否拆出“车辆保险历史表”不宜在本轮贸然重写，但必须在主数据阶段做出明确设计：车辆主信息、当前保险状态和历史保单不能长期没有边界。

### 5. 部分业务模块已开始接入 `employee_id`

- 培训路由已增加 `employee_id`，可按身份证哈希解析人员，且部分统计基于 `v_employee_current`。
- 三违路由已尝试用身份证哈希或姓名解析 `employee.id`。
- 隐患路由已使用 `employee_assignment` 查询责任人的当前组织。
- 新版员工中心内的培训、巡检、隐患、证件、安全档案均直接使用 `employee_id`。

这些方向正确，但培训仍保留 `personnel_id/name/dept/position` 冗余字段；事故仍主要写 `personnel_id`；三违存在姓名回退。它们应成为主数据收敛后的第一批联动整改对象。

### 6. 分析类能力应后置

风险画像、驾驶员风险、考核分析、预警中心、智能分析、领导驾驶舱均已注册路由和页面，但依赖人员、车辆、事故、三违、培训、检查、隐患等源数据的一致性。

在主数据和业务事实未统一前，继续扩展这些模块会得到“页面完整、指标不可信”的结果。AI 路由中仍有明确 mock 问答；BI、供应链、AI 分析、IoT 等页面也存在“开发中”占位。它们不应进入近期主线。

## 模块状态判断

| 范围 | 当前静态判断 | 近期动作 |
| --- | --- | --- |
| 鉴权、公开接口、角色中间件 | 已有基础，但报告 03 发现真实回归与 fail-open 风险 | 先完成提示词 04 的基础契约整改，不扩大为生产安全专项 |
| 人员、组织、岗位、花名册导入 | 新主数据模型和接口较完整，是系统事实源候选 | 确认为唯一人员来源，停止新建旧人员关联 |
| 人员保险 | 列表与状态展示已完成，花名册为显示主体 | 将姓名关联改为 `employee_id`，保留快照字段仅作展示/历史 |
| 车辆与车辆保险 | 基础功能存在，但资料与保险字段融合，且有两套 API | 确定车辆主数据唯一入口与保险历史边界 |
| 培训、证书、人员档案 | 已部分接入 `employee_id` | 清理旧 `personnel_id` 写入，补齐迁移与回归测试 |
| 隐患、检查、三违、事故 | 有页面、路由和部分人员/车辆字段，但关联口径不一 | 按员工/车辆稳定 ID 收敛；先实现核心闭环再做统计 |
| 应急、目标职责、制度、标准化 | 路由和页面较多，多个路由有内存降级 | 不以“页面存在”判为已完成，待基础数据稳定后逐个验收 |
| 工作流、任务、通知、审计、统一导入 | 已有独立路由，属于横向能力 | 在核心业务闭环中接入，不单独大规模扩展 |
| 风险画像、预警、考核、驾驶舱、报告 | 框架和部分实现存在，强依赖源数据 | 冻结新增功能，后置到事实数据稳定后 |
| AI、BI、IoT、供应链 | 有预留接口或“开发中”页面 | 暂不排期为近期开发内容 |

## 推荐目标架构

```text
组织 / 岗位 ─────┐
                  ├── employee（唯一人员主表）── employee_id ── 保险、培训、证书、检查、隐患、三违、事故、考核、风险画像
花名册导入 ──────┘

车辆导入 ─────────── vehicles（唯一车辆主表）── vehicle_id ── 车辆保险、三检、维修、违章、事故、车辆风险

每个业务模块只保存“业务事实 + 主数据 ID”；姓名、部门、岗位、车牌等允许保留历史快照，但不得作为跨模块关联键。
```

人员保险的目标查询是：以当前花名册为左表，按 `employee_id` 左连接有效雇主险和工伤险记录，动态计算 `insured/uninsured/expiring/expired`。不为“未参保”创建虚假保险记录。

导入未知人员或未知车辆时应进入“待匹配/异常批次”，不能根据姓名或车牌模糊自动创建事实记录。人工确认匹配后才写入稳定 ID。

## 建议开发顺序

### 阶段 0：完成最小基础契约

先完成提示词 04 中的角色中间件、黑名单 fail-open、管理员成功测试、导入读取权限整改。该阶段只解决本地开发正确性，不把生产级监控、文件存储迁移或全量 RBAC 作为当前主线。

### 阶段 1：主数据收敛设计与迁移准备

1. 冻结 `employee`、`department`、`position`、`employee_assignment`/当前任职视图的责任边界。
2. 冻结 `vehicles` 的唯一 ID、车牌/VIN 的导入匹配规则和车辆状态规则。
3. 建立旧 `personnel`、`personnel_insurance.personnel_id`、培训、事故等表到 `employee_id` 的映射清单。
4. 只设计迁移和编写 mock/离线验证；在用户确认数据策略前不执行真实数据库迁移。

### 阶段 2：人员保险联动收敛

1. 为人员保险记录增加或确认稳定 `employee_id`，建立外键/索引/唯一性规则。
2. 将列表、统计、同步、批量生成、导入异常处理全部改为 `employee_id`。
3. 处理同名、改名、缺失匹配、重复保险、历史保单、离职人员和保单过期规则。
4. 修正前端详情同步参数，使用返回的人员主数据 ID，而不是保险记录 ID。
5. 用完整 mock 数据验证“花名册无保险、仅雇主险、仅工伤险、两险、过期、同名、改名、未匹配”八类场景。

### 阶段 3：车辆主数据与车辆保险边界

1. 确定 `/api/vehicles` 与 `/api/insurance/vehicle` 的单一写入责任，避免同一车辆被两套接口以不同语义修改。
2. 以 `vehicle_id` 连接事故、三检、维修、违章和保险。
3. 明确当前保险与历史保单的数据模型；先保证当前业务正常，再按迁移计划拆分历史，不做无验证的大重构。

### 阶段 4：核心业务事实联动

按以下顺序推进，每个模块完成“主数据选择、写入、查询、状态、异常、测试”闭环后再进入下一个：

1. 培训、证书、职业健康与人员档案。
2. 检查任务、检查记录、隐患及整改闭环。
3. 三违、事故及人员/车辆责任关联。
4. 应急、目标职责、制度/标准化等相对独立模块。

### 阶段 5：横向能力接入

将统一导入批次、附件、审计、任务、通知和工作流接入已完成的核心业务。此阶段重点是统一业务闭环，不是新增大量看板页面。

### 阶段 6：计算、预警与管理视图

当人员、车辆及核心业务事实可追溯后，再完成：

1. 人员/驾驶员/车辆风险画像与评分。
2. 预警规则和整改提醒。
3. 月度考核、分析中心和统计口径。
4. 驾驶舱、报告中心。

### 阶段 7：扩展能力与上线收口

最后处理 AI、BI、IoT、供应链等扩展能力，以及生产环境的文件访问、Token 生命周期、监控凭证、部署、备份恢复和安全验收。

## 页面与组件策略

Vben Admin 与 Ant Design Vue 已提供基础组件，不需要建立替代组件库。每个阶段只需选定已验证的列表页、详情页、复杂业务页作为页面样板，统一布局、查询区、表格、弹窗、状态标签和反馈方式。

业务组件仅在两个以上模块出现同一真实流程后再提取。例如：导入异常处理、人员选择、车辆选择、附件预览、状态流转记录。不要在主数据尚未稳定时提前抽象“万能联动组件”。

## 下一步

提示词 04 完成后，下一份 DeepSeek 提示词应为“人员主数据与人员保险稳定 ID 联动收敛”，而不是继续开发新的独立页面。该提示词必须先输出数据迁移影响清单和 API 契约，再实施代码；真实数据库迁移应等待用户确认后单独执行。
