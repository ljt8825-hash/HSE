## 2. 前端 authority 原状（审计结论）

审计 `apps/web-naive` 权限机制，回答 §5 四个问题：

1. **authority 按角色还是按权限码判断？**
   → **按角色（role-based）**。菜单生成走 `accessMode: 'frontend'`（`packages/@core/preferences/src/config.ts:5`），`generateAccessible` 用 `meta.authority`（角色数组，OR 语义）过滤 `userInfo.roles`。

2. **web-naive 是否存在成熟的权限码/角色门控写法？**
   → **存在**。多角色数组写法已是项目惯例，例如：
   - `hse-advanced.ts` / `hse-personnel.ts`：`authority: ['admin', 'safety_manager', 'safety_officer']`
   - 同文件：`authority: ['admin', 'safety_manager']`

3. **是否已有页面允许 `grid_inspector` 这种角色访问？**
   → 否。修改前全部现场管理路由均为 `authority: ['admin']`，无任何页面包含 `grid_inspector`。

4. **是否可以复用现有模式？**
   → **可以且必须**。直接把 `'grid_inspector'` 追加进既有角色数组，复用 OR 语义，不新建任何权限机制。

**角色来源链路（确认）**：
- `GET /api/user/info`（`server/routes/vben-compat.js:25`）返回 `roles: [user.role]`；
- `grid_inspector` 登录后 `userInfo.roles = ['grid_inspector']`；
- `guard.ts:95` `userRoles = userInfo.roles` → `generateAccessible(accessMode, {roles, routes})`；
- 故 `meta.authority` 含 `'grid_inspector'` 的路由对 `grid_inspector` 可见。
