2. 分析双机制（REVOKE vs BEFORE TRIGGER）：

### 维度 1：机制原理对比
- REVOKE 方案：撤销 hse_app_user 对 hse_employee_org 的 INSERT/UPDATE/DELETE 权限
  - 作用层级：PostgreSQL 权限系统
  - 覆盖范围：仅限 hse_app_user 角色
  - 绕过方式：其他角色（如 superuser）仍可写入
  - 可逆性：`GRANT` 即可恢复
- BEFORE TRIGGER 方案：在每行操作前拦截并 RAISE EXCEPTION
  - 作用层级：数据库触发器
  - 覆盖范围：所有角色（包括 superuser，除非显式 DISABLE TRIGGER）
  - 绕过方式：`ALTER TABLE ... DISABLE TRIGGER` 或 `DROP TRIGGER`
  - 可逆性：`DROP TRIGGER` 即可恢复

### 维度 2：优劣势对比表

| 维度 | REVOKE 方案 | BEFORE TRIGGER 方案 | 推荐 |
|------|------------|---------------------|------|
| 防御深度 | 权限层（仅应用用户） | 行级（所有角色） | |
| 绕过难度 | 低（superuser 可绕过） | 中（需 DISABLE TRIGGER） | |
| 可审计性 | 依赖 PostgreSQL 日志 | 可自定义错误消息 | |
| 对现有功能影响 | 应用立即报 permission denied | 应用收到自定义错误消息 | |
| 回滚复杂度 | GRANT 单命令 | DROP TRIGGER × 3 | |
| 与 Runbook 一致性 | 完全一致 | 不一致（Runbook 用 REVOKE） | |
| 与 P1-4/P3-2 一致性 | 不一致 | 完全一致 | |
| 执行复杂度 | 1 条 SQL | 约 200 行 SQL（含验证+回滚） | |
| 误通过风险 | 无（权限拒绝即拒绝） | 有（WHERE id=0 陷阱） | |

### 维度 3：冲突风险分析
- 如果两者都执行：REVOKE 先执行 → 应用写操作被权限拒绝 → 触发器不会被触发 → 触发器验证（Step 3.2-3.4）中的 INSERT 测试会因权限不足而失败，而非触发器拦截
- 建议：明确先后顺序，或者二选一。如果采用互补方案，REVOKE 应在触发器验证通过后、作为兜底手段执行
- 互补方案：触发器为主防御（行级全覆盖），REVOKE 为权限兜底（应用层快速失败）

3. 分析 SQL 自检 `WHERE id=0` 误通过陷阱：

- 解释误通过逻辑：
  ```
  -- Step 3.3: 验证 UPDATE 被阻止
  BEGIN;
    UPDATE hse_employee_org SET updated_at = NOW() WHERE id = 0;
    -- 如果 id=0 不存在 → 影响 0 行 → BEFORE UPDATE 触发器不触发
    -- → 不抛出异常 → 落入 EXCEPTION 块 → 误报"触发器正确阻止了 UPDATE"
  EXCEPTION WHEN OTHERS THEN
    RAISE NOTICE '✅ 验证通过: UPDATE 被正确阻止';
  END;
  ```
- 给出修复建议：
  - 方案 A：先查询一个真实存在的 id，再用于验证
    ```sql
    -- 先获取真实行 ID
    SELECT id INTO v_real_id FROM hse_employee_org LIMIT 1;
    -- 用真实 ID 验证
    UPDATE hse_employee_org SET updated_at = NOW() WHERE id = v_real_id;
    ```
  - 方案 B：先校验 id 存在性，若不存在则报错
    ```sql
    IF NOT EXISTS (SELECT 1 FROM hse_employee_org WHERE id = 0) THEN
      RAISE NOTICE '⚠️ id=0 不存在，无法验证触发器。请手动用真实行 ID 验证。';
    ELSE
      UPDATE hse_employee_org SET updated_at = NOW() WHERE id = 0;
    END IF;
    ```
  - 对比分析两种方案的优劣，推荐方案 A（更健壮）
