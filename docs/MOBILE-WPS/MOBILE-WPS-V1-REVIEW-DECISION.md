## 一、问题背景

NODE-01 真实浏览器端到端冒烟发现：

> 自查自纠类三违记录（发现人 = 整改人）在提交整改后进入 `PENDING_REVIEW`，
> 但 **没有任何账号可以对它执行复查**：
> - 分桶逻辑 `bucketOf` 把「待复查」记录分给**发现人**；
> - 详情页按「禁止自整改自复查」禁用复查入口；
> - 该记录对其他账号（含公司管理）分桶结果为 `NONE`。
>
> ⇒ **记录永久卡在「待复查」。**

无额外数据要求；只需在提交整改表单增加「复查人」选择项。

### 数据侧可行性：✅ 可支撑

- 候选池：1291 名正式员工（或限定为 62 名网格人员）。
- 组织、岗位字段 100% 完整，可按乡镇/岗位筛选候选人。

### 9.1 死结已由代码事实证明（不再是描述性结论）

新增只读审计用例 `apps/web-naive/src/api/mw/__tests__/review-gate.audit.spec.ts`，4/4 通过：

- `H1` 自查自纠提交整改后 `status=PENDING_REVIEW`，且 `reviewAccountId` **仍为空**；
- `H2` 发现人 `bucket=REVIEW` 但页面 `canReview=false`，其余账号 `bucket≠REVIEW`，
  **`bucket=REVIEW 且 canReview=true` 的账号数 = 0** ⇒ 清单维度无人可操作；
- `I1` 对照：转派场景（发现人 ≠ 整改人）下发现人可复查 ⇒ **有解**。

⇒ 上文「一、问题背景」的结论成立，且范围为：**仅当发现人 = 整改人时死结**。

### 9.2 🆕 新发现：越权漏洞（B-04）

`core/flow.ts` 的 `assertCanReview` **只校验记录状态，不接收也不校验操作人账号**。
用例 `H3` 证明：一个既非发现人、也非整改人的账号，直接调用复查即可把记录置为 `COMPLETED`。

⇒ 该问题**与选择 A/B/C/D 无关**，必须在接入真实账号前独立修复。

### 9.3 🆕 方案 D 检索到制度化配置（上文第五节需按此更新）

`server/config/hseRules/violation-rule.json`（v1.0.0 / 2026-07-25）`statusFlow.transitions`：

```json
{ "from": "待复查", "to": "已关闭", "action": "复查合格",   "roles": ["admin", "safety_manager", "dept_manager"] },
{ "from": "待复查", "to": "整改中", "action": "复查不合格", "roles": ["admin", "safety_manager", "dept_manager"] }
```

- 复查由 `admin / safety_manager / dept_manager` 执行，**`handler`（整改人）被排除**；
- ⚠️ 该 `statusFlow` **未被三违代码消费**（仅 `hazardService` 消费隐患侧的 `statusFlow`）；
- ⚠️ 正式员工中「安全」类岗位 **0 人** ⇒ `safety_manager` 角色当前无在职人员可映射；
- 「部门经理」2 人可作 `dept_manager` 候选；`admin` 语义需业务方定义。

⇒ 是否**按此配置执行**，仍需业务负责人确认（见决策栏「制度依据」）。
