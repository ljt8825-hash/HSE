## 3. 当前代码实际复查逻辑

代码中有**三处**互相不一致的复查判定，这是死结与越权漏洞的共同根因。

### 3.1 服务端状态断言：`assertCanReview`（`core/flow.ts:150-154`）

```ts
export function assertCanReview(record: ViolationRecord): void {
  if (record.status !== 'PENDING_REVIEW') {
    throw new FlowError('只有「待复查」状态的记录才能复查');
  }
}
```

> **只校验记录状态，不接收、也不校验操作人账号。** ⇒ 这是越权漏洞的直接来源。

### 3.2 清单分桶：`bucketOf`（`core/flow.ts:180-183`）

```ts
if (record.status === 'PENDING_REVIEW') {
  if (record.reviewAccountId === accountId) return 'REVIEW';
  if (record.discoverAccountId === accountId) return 'REVIEW';
}
```

> `reviewAccountId` 在 `reviewViolation` 执行前**永远是空字符串**（`index.ts:570` 才写入），
> 因此「待复查」记录在清单上**只会分给发现人**。

### 3.3 页面级判定：`record.vue:51-56`

```ts
/** 待复查且当前登录人不是整改责任人 ⇒ 可复查（避免自整改自复查） */
const canReview = computed(
  () => !!account.value && record.value?.status === 'PENDING_REVIEW' && !isRectifier.value,
);
```

> 只要**不是整改人**就能复查——没有「必须是发现人 / 上级 / 区域管理员」的约束。

### 3.4 三处逻辑的关系

| 层 | 判定 | 宽严 |
|---|---|---|
| 服务端 `assertCanReview` | 状态 = PENDING_REVIEW | **最宽**（任何人） |
| 页面 `canReview` | 状态 + 非整改人 | 中 |
| 清单 `bucketOf` | 发现人（或已复查人） | **最窄** |

⇒ **宽的能执行、窄的能看见**：发现人「看得见但做不了」（若他同时是整改人），其他所有人「看不见但做得到」（只要拿到链接）。
