# 拍照点「确定」后异常跳转 / 重新进入首页 —— 根因分析

- 分析对象：`frontend/check.html`（build `2026-09-21.68`，4211 行）
- 分析日期：2026-09-23
- 性质：只读分析，未改动任何代码

---

## 一、结论速览

现象「拍完点确定后被弹回首页」**不是一个页内跳转 bug，而是一次整页重载**。

链路是：

1. 调起系统相机时，页面被 Android WebView 因内存压力回收；
2. 用户点「确定」返回时，WebView 重新加载 `/check`；
3. 重载后 `boot()` 正常走完 → `enterHome()` → **必然先落到首页**（这是设计行为，不是异常）；
4. 能否从首页「续回」拍照页，完全取决于 `loadDraft()` 能否命中草稿；
5. 而草稿落盘时机太晚 + 有硬门槛，导致**每次检查的第一张照片必然没有草稿** → 于是稳定地停在首页。

所以「时常」的分布规律是：**新建检查后的第一张照片 = 必现；后续步骤 = 偶现**。

此外还有一条**独立的次生缺陷**：重载后页内 `viewStack` 归零，但浏览器历史里重载前的条目仍在，`showView` 的 `replaceState` 会改写当前条目，popstate 又会按残留的旧 state 渲染出陈旧视图 —— 这正是用户描述的「**异常跳转**」（区别于「重新进入首页」）。

### 阶段 2：调起相机

| `1766-1770` | 自动续传判定 | 命中才 `resumeCheck()` 回拍照页 |

### 阶段 4：自动续传的判定门槛（`1766-1770`）

```js
if(!autoResumeChecked){
  autoResumeChecked = true;
  const d0 = loadDraft();
  if(d0 && d0.draft.scenePhoto && Date.now() - d0.at < 5 * 60 * 1000) resumeCheck(d0.draft);
}
```

四道门槛必须**同时**满足：

| 门槛 | 位置 | 失败后果 |
|---|---|---|
| `autoResumeChecked` 未被消费 | `1766/1772` | 只有重载后**第一次** `enterHome()` 判定 |
| `loadDraft()` 非空 | `2381-2387` | 需 `o.at` 存在且距今 < `DRAFT_TTL_MS`（2 小时） |
| **`d0.draft.scenePhoto` 为真** | `1769` | **没拍到照片 = 绝不续传** |
| 存盘时间 < 5 分钟 | `1769` | 超 5 分钟只显示卡片，不自动回 |

`resumeCheck()`（`2389-2396`）固定 `showView("photo")`，不还原用户实际停留的步骤。

## 三、根因定位

### 🔴 D1（主因）草稿落盘时机太晚，且带硬门槛 —— 首次拍照必然无草稿

**问题位置**：`2374-2379`（`saveDraft`）+ `1769` / `2406`（两处 `scenePhoto` 门槛）+ `2419`（`startCheck` 清草稿）

```js
function saveDraft(){
  try{
    if(!draft || !draft.scenePhoto) return;   // ← 硬门槛：没照片就不存
    localStorage.setItem(DRAFT_KEY, JSON.stringify({ at: Date.now(), draft }));
  }catch(e){ /* 静默吞掉 */ }
}
```

`saveDraft()` 全库只有 3 个调用点（`2522` 拍照成功后 / `2678` / `2994`），**全部在照片压缩成功之后**。

于是形成一个闭环悖论：

> 草稿只在「照片成功进入页面」后才存在；
> 而页面被回收恰恰发生在「照片还没进入页面」的那一刻。
> ⇒ 需要草稿兜住的场景，草稿必然还不存在。

再叠加 `startCheck()` 的 `clearDraft()`（2419）：**每一次「开始检查」都把草稿清零**，所以每次检查的第一张照片都处于零保护状态。

这解释了为什么用户觉得「**时常**」而不是「必然」—— 拍到第 2 张、第 3 张时草稿已存在，就能被兜住；第一张必挂。

### 🔴 D2（次生主因）重载后页内历史栈与浏览器历史不一致 → 陈旧视图

**问题位置**：`1461-1488`（`showView`）+ `1489-1503`（`popstate`）

```js
if(viewStack.length === 0){
  viewStack = [name];                                  // ← 重载后必然走到这里
  history.replaceState({ h5view: name }, "", location.href);   // ← 改写「当前」条目
}
```

重载后 `viewStack` 是**新的空数组**，但浏览器的历史条目**一条没少**。于是：

1. 重载前所在的那条条目（state = `{h5view:'photo'}` 或 `'classify'`）被 `replaceState` **改写**为 `'home'`；
2. 更早的条目仍保留着 `{h5view:'photo'}` / `{h5view:'classify'}`；
3. 用户按返回键 → `popstate`（`1489`）拿到残留的旧 state → `showView('photo' / 'classify')`；
4. 而重载后 `draft` 是 `{}`（`1400` 行），`#scene-photo-box` 为空 → **渲染出一个空白拍照页 / 未选中的分类页**。

用户视角：**莫名其妙跳到了一个不该出现的页面** —— 即「异常跳转」。

同一处缺陷还导致：自动续传成功（`viewStack = ['home','photo']`）后，**第一次按返回键会回到首页而不是退出 H5**，因为下面那条条目的 state 已被改写为 `'home'`。用户会认为「又被弹回首页了」。

另外 `showView("home")` 的收拢逻辑：

```js
if(name === "home" && viewStack.length > 1 && viewStack[0] === "home"){
  history.go(1 - viewStack.length);   // ← 按 viewStack 长度算步数
  return;
}
```

`viewStack` 长度是**页内**计数，与浏览器实际可用条目数在重载后会脱节；步数超过可用范围时，浏览器可能直接退出 H5 页面。

### 🟠 D3（加剧）`compressImage` 仍保留一次全尺寸解码（48MB 峰值）

**问题位置**：`2466-2483`

```js
probe = await createImageBitmap(file);                       // ← 不带 resize = 全尺寸解码
const scale = Math.min(1, PHOTO_MAX_EDGE / Math.max(probe.width, probe.height));
...
try{ probe.close && probe.close(); }catch(e){}                // 释放太晚：峰值已经发生
probe = null;
const small = await createImageBitmap(file, { resizeWidth: w, resizeHeight: h, ... });
```

CF-WPS-59 消除了 `readAsDataURL` 的 4~8MB base64 和 `<img>` 的全尺寸位图，但 **probe 这一次仍然是 4000×3000×4B ≈ 48MB**。而这个峰值恰好出现在**页面刚从相机回来、内存最紧张的时刻** —— 也就是最容易被再次回收的时刻。二次回收 → 又一轮重载 → 又落首页，形成「拍一次掉一次」的观感。

注：`probe` 只为拿到宽高算缩放比。宽高完全可以从 `PHOTO_MAX_EDGE` 直接推（等比缩放到长边 800 即可），不需要一次全尺寸解码。

### 🟠 D4（加剧）`saveDraft` 缺少配额降级

**问题位置**：`2377` vs `1354-1366`

`saveDB()` 有完整降级（整体试写 → 丢弃 `syncState==='synced'` 记录的照片 → 返回 false），
而 `saveDraft()` 只有裸 `try/catch` **静默吞掉 `QuotaExceededError`**。

本机 localStorage 实测配额 4.75MB，而 `db.records` 里存着未同步记录的照片。配额紧张时：

> `saveDB()` 成功（靠丢老照片腾空间） → 但 `saveDraft()` 可能失败且**无声**
> ⇒ 用户以为拍上了，重载后草稿却不存在 → 落首页。

### 🟡 D5（待真机验证）`e.target.value = ""` 可能使 File 失效

**问题位置**：`3777-3778` / `3976-3977`

```js
$("#file-camera").onchange = e => { if(e.target.files[0]) compressImage(e.target.files[0], setScenePhoto); e.target.value = ""; };
```

`compressImage` 是**异步**的（内部 `await createImageBitmap`），而 `e.target.value = ""` 在**同一 tick 同步执行**。部分 Android WebView（尤其 X5）在清空 file input 后会让底层 Blob 失效 → `createImageBitmap(file)` 抛错 → `cb(null)` → `flashMsg("照片读取失败")`（`2515`）。

后果：**照片明明拍了，但既没进页面、也没落草稿** → 此时任何重载都会落首页。

### 🟡 D6 两套时间口径不一致

`DRAFT_TTL_MS = 2 * 3600 * 1000`（`2373`，草稿 2 小时有效）vs 自动续传窗口 `< 5 * 60 * 1000`（`1769`）。

现场相机调起 + 排队 + 拍照超过 5 分钟很常见，此时**草稿明明还在，却不自动续传**，只显示一张卡片 —— 用户仍然看到「回到首页」。

## 四、触发条件矩阵

| 条件 | 是否触发「回首页」 | 依据 |
|---|---|---|
| 新建检查后的第一张照片 + 页面被回收 | ✅ **必现** | D1：`clearDraft()` 后无草稿 |
| 第 2 张及以后照片 + 页面被回收 + 5 分钟内 | ❌ 可续回 | `1769` 命中 |
| 第 2 张及以后 + 超过 5 分钟 | ✅ 落首页 | D6 |
| localStorage 配额满 | ✅ 落首页 | D4 |
| 隐私模式 / WebView 禁存储 | ✅ 落首页 | `2378` 静默失败 |
| 照片压缩失败（D3/D5） | ✅ 落首页 | 无草稿可存 |
| 重载后按返回键 | ⚠️ 跳陈旧视图或回首页 | D2 |
| 相册上传（不走系统相机） | ❌ 一般不触发 | 页面不进入后台 |

## 六、修复方向建议

### P0-1：把草稿落盘提前到「进入拍照页」那一刻（治 D1）

`startCheck()` 里 `clearDraft()` 之后**立刻**写一份 `scenePhoto: null` 的草稿：

```js
draft = { scenePhoto: null, behavior: null, /* ... */ };
saveDraft({ allowEmpty: true });   // 新增开关
showView("photo");
```

同步放开两处门槛：

- `saveDraft()`：`if(!draft || (!draft.scenePhoto && !opt.allowEmpty)) return;`
- `enterHome()` 自动续传与 `renderResumeCard()`：把 `d0.draft.scenePhoto` 改为
  「有照片 **或** 草稿未超时且用户正在检查流程中」。

这样即使第一张照片就被回收，重载后也能自动回到拍照页，而不是首页。

### P0-2：把「回首页」改成「回离开前的位置」（治 D1 体验 + D2）

`resumeCheck()` 目前硬编码 `showView("photo")`（`2395`）。应改为：

- 草稿里记录 `lastView`（`photo` / `classify` / `vio` / `pick-person` / `confirm`）；
- `resumeCheck()` 按 `lastView` 恢复，照片与已选项都在，用户不用重走一遍。

### P0-3：重载后清理/校正页内历史（治 D2）

`showView` 的首次 `replaceState` 目前会抹掉重载前视图的身份。两种可选修法：

- **方案 A（推荐，最小改动）**：重载时在 `boot()` 开头做一次
  `history.replaceState({ h5view: "boot" }, "", location.href)`，
  让「首个落地视图」占用的是一条**中立**条目，从而不再改写重载前的 photo/classify 身份；
  并在自动续传完成后 `history.replaceState({h5view:'photo'})` 对齐。
- **方案 B（更彻底）**：给页内历史打版本戳
  （`{ h5view, ver: BUILD }`），popstate 时若 `ver` 与当前 build 不符则**忽略该 state 并继续回退**，
  杜绝陈旧视图被渲染出来。

同时把 `history.go(1 - viewStack.length)` 换成逐次 `history.back()` 直到落到 home，
避免步数越界把用户带出 H5。

### P1-1：消除 probe 的全尺寸解码（治 D3）

不必解码就能算缩放比 —— 目标是「长边 ≤ 800」，可以直接：

```js
const small = await createImageBitmap(file, { resizeWidth: PHOTO_MAX_EDGE, resizeQuality: "medium" });
// 用返回的 small.width/height 反推等比结果，再二次微调（或直接接受长边 800 的非等比近似）
```

若必须保持严格等比，改用 `file.size` 阈值 + 一次 `resizeWidth: PHOTO_MAX_EDGE` 的解码，
再按 `small.width/height` 比例算最终 canvas 尺寸，**全程不产生 48MB 位图**。

### P1-2：`saveDraft` 增加与 `saveDB` 同级的配额降级（治 D4）

```js
function saveDraft(opt){
  const payload = JSON.stringify({ at: Date.now(), draft, lastView: currentView });
  try{ localStorage.setItem(DRAFT_KEY, payload); return true; }
  catch(e){
    try{ saveDB(); }catch(_){}                  // 先让 saveDB 腾空间（会丢已同步记录的照片）
    try{ localStorage.setItem(DRAFT_KEY, payload); return true; }catch(_){}
    flashMsg("本机存储已满，草稿无法保存，请及时上传已完成的记录");
    return false;
  }
}
```

关键是**失败必须可见**（`flashMsg`），不能再静默。

### P1-3：修正 `input.value` 竞态（治 D5）

把清空动作移到压缩回调里：

```js
const input = e.target, file = input.files[0];
if(!file) return;
compressImage(file, (dataUrl) => { setScenePhoto(dataUrl); input.value = ""; });
```

并保留 `File` 引用到压缩结束。这一条建议先真机验证（X5 / Chrome Android 各测一次），
确认当前写法是否真的会导致 `createImageBitmap` 失败。

### P2-1：统一时间口径（治 D6）

自动续传窗口从 5 分钟放宽到与 `DRAFT_TTL_MS` 一致（或至少 30 分钟），
并把「草稿仍在但不自动续传」时的首页卡片做得更醒目（当前是一张普通卡片，现场人员容易忽略）。

### P2-2：补一条「拍照流程被中断」的埋点

当前没有任何手段区分「用户主动返回首页」与「被系统回收后落回首页」。
建议在 `boot()` 里读取一个 `sessionStorage` 标记（页面被 `pagehide` 时写入），
重载时若发现是「非正常离开」就上报一次，便于量化问题发生率与验证修复效果。
