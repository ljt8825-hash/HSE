## 二、结论速览

**账号分级、登录、权限边界、飞书落表这四块是好的；"指派 → 被指派人接收 → 处理 → 回传"这条闭环在系统里目前不存在。**

当前系统里的「转给责任乡镇」**不是一次跨账号的指派**，它只是在**指派人自己手机浏览器的 localStorage 里**给本条记录打了个标记（`rectifyMode: "transfer"`），然后把记录写进飞书台账时**把这个标记丢掉了**。被指派人的手机上不会出现任何待办，也没有任何通知通道。

## 四、未通过项：具体现象与出现位置

### B3 / B4 / B6 —— 被指派人收不到（最严重）

**现象**：
公司管理公司管理转派给乡镇经理后，乡镇经理账号登录，首页「待整改」计数 = 0，`db.records` 过滤 `(r.rectifierId === session.id || r.transferAdminName === session.name)` 结果 0 条。管理员甲同样 0 条。API 层 `GET /api/mobile/patrol/records` 返回也是 0 条。

**位置**：

| 位置 | 代码 | 说明 |
|---|---|---|
| `frontend/check.html:2647-2651` | `const rec = makeAndSync({ rectifyMode:"transfer", ..., transferAdminId: node.name, transferAdminName: node.name, ... })` | 转派动作只写**本机**记录；且把**姓名当 ID**存（`transferAdminId: node.name`） |
| `frontend/check.html:1349` / `1393` | `STORE_KEY = "hse_check_v1_" + session.id` | 本机库**按登录账号隔离**：公司管理写在 `hse_check_v1_133****0822`，乡镇经理读 `hse_check_v1_139****8533`，物理上就是两个库 |
| `frontend/check.html:1565` / `2737` | `r.transferAdminName === session.name` | "收到转派"的判定是**在本机库里按姓名匹配**，跨账号永远匹配不到 |
| `worker/index.js:2056-2059` | `patrolIsMine(fields, sub)` → `note.employeeCode === String(sub)` | 服务端判定归属只看「备注」里的 `巡查人ID`，即**创建者本人** |

**实测证据**：
```

乡镇经理  storeKey = hse_check_v1_139****8533   含 0 条
```

## 五、根因（架构层面）

```
公司管理手机                          服务端                        被指派人手机
┌──────────────────┐            ┌──────────────┐            ┌──────────────────┐
│ 转派 → 写本机      │  ──提交──▶ │ 飞书主台账     │  ──读取──▶ │ patrol/records   │
│ localStorage     │            │ (无转派字段)   │            │ 仅按创建者归属    │
│ hse_check_v1_刘  │            │              │            │ → 看不到          │
└──────────────────┘            └──────────────┘            └──────────────────┘
        ↑                                                              ↑
   指派关系只存在这里                                          这里永远收不到
```

三处断点，任意一处单独修都不够：

1. **存储层**：指派关系存在指派人本机 `localStorage`，且按账号隔离（`STORE_KEY`）。
2. **传输层**：提交给飞书的 body 丢弃了所有转派字段（`toPatrolBody`），飞书表也没有对应列。
3. **服务端**：没有待办/指派/通知接口；`patrolIsMine` 只认创建者。

## 六、修复建议（按优先级）

| 优先级 | 事项 | 要点 |
|---|---|---|
| **P0** | 建「整改待办」服务端实体 | 新增飞书表（或在主台账加列）：`指派人ID / 接收人ID / 接收人姓名 / 责任单位 / 状态 / 指派时间 / 完成时间`；新增 `POST /api/mobile/assign`、`GET /api/mobile/inbox`（按 `接收人ID` 过滤）、`POST /api/mobile/assign/complete` 三个接口 |
| **P0** | `toPatrolBody` 带上转派字段 | 把 `transferAdminId`（改成真实工号，不是姓名）、`transferTown`、`rectifyMode` 一并提交；同步扩 `FEISHU_FIELD_WHITELIST` |
| **P1** | 修正归属判定 | `patrolIsMine` 改为「创建者 OR 接收人」；`transferAdminId` 存工号而非姓名（现用姓名匹配，同名会串号） |
| **P1** | 被指派人待办入口 | 「待整改」改为拉取服务端 `inbox`，不再只扫本机 `db.records` |
| **P2** | 列表来源标签 | 台账卡片加「来自 XXX」标签；跨账号可见后才有意义 |
| **P2** | 通知提醒 | 至少做「进入 App 时拉取 inbox + 红点计数」；App 内推送需接入微信/短信通道 |

### 7.5 本轮踩到的两个坑（已修）

1. **`todoToRec` 漏了 `clientRequestId`** → 照片上传接口报错 → `await` 抛异常**中断**了后面的状态回写，整改做完了服务端却还是「待整改」。修：补幂等键 + 照片上传包 `try/catch`（照片失败不能连状态一起丢）。
2. **测试脚本自己补调接口掩盖了真实缺陷**：第一版 E9 靠手动补调 `complete` 才通过。已改为**纯靠 `submitRectify` 自动回写**验证。
