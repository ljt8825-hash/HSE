# 提示词-143 — 人员保险与花名册数据一致性优化

> 轨道：保险管理（/insurance）→ 子板块「人员保险」（personnel）  
> 前置条件：提示词-142 UI 改造已验收通过  
> 执行人：Senior Developer（高级全栈开发工程师 / 吴八哥）  
> 约束依据：`禁止类-模块聚焦与上下文锁定原则.md`（仅限 insurance 模块内部改动，不侵入花名册/employees 模块）

---

## 1. 问题诊断

提示词-142 验收过程中发现：`personnel_insurance` 表采用**快照式冗余存储** —— 在通过 `/personnel/generate-from-pending` 生成保险记录时，将 `employees` 表的 `name`、`department`、`position` 等字段复制写入 `personnel_insurance`。此后花名册发生变更（转岗、更名、部门调整），人员保险记录中的对应字段**保持原值不变**，导致：

- 列表展示的姓名/部门可能是过期数据
- U6 部门筛选器基于历史快照，与当前组织架构脱节
- 用户无法感知"信息已不同步"

---

## 2. 改造目标

在不修改 `employees` 表、不侵入花名册模块的前提下，实现：

1. **列表展示以花名册为准**：查询时实时关联 `employees`，姓名/部门/岗位优先取最新值
2. **保险数据独立保护**：保险类型、保额、起止日期、保单号等保险专属字段仍以 `personnel_insurance` 为准
3. **同步状态可视化**：用户可直观看到哪些记录与花名册不一致
4. **提供手动刷新入口**：单条或批量将花名册最新信息回写至保险记录

## 4. 关键实现细节

### 4.1 C1 关联查询 SQL 示例

```sql
SELECT
  p.*,
  e.name AS e_name,
  e.department AS e_department,
  e.position AS e_position
FROM personnel_insurance p
LEFT JOIN employees e
  ON e.id = p.personnel_id
  AND e.is_deleted = false
WHERE p.is_deleted = false
  /* 原有筛选条件 */
ORDER BY p.id ASC
LIMIT $1 OFFSET $2
```

### 4.2 字段优先级规则

| 字段                         | 关联后取值优先级                         | 说明      |
| -------------------------- | -------------------------------- | ------- |
| `name`                     | `e.name` > `p.person_name`       | 优先花名册   |
| `department`               | `e.department` > `p.department`  | 优先花名册   |
| `position`                 | `e.position` > `p.position`      | 优先花名册   |
| `insuranceType`            | `p.insurance_type`               | 保险专属，不变 |
| `coverageAmount`           | `p.coverage_amount`              | 保险专属，不变 |
| `startDate` / `expireDate` | `p.start_date` / `p.expire_date` | 保险专属，不变 |
| `policyNo`                 | `p.policy_no`                    | 保险专属，不变 |

### 4.3 syncStatus 判定逻辑

```javascript
function getSyncStatus(p, e) {
  if (!e || !e.id) return 'missing';
  const nameMatch = (e.name || '') === (p.person_name || '');
  const deptMatch = (e.department || '') === (p.department || '');
  const posMatch = (e.position || '') === (p.position || '');
  return (nameMatch && deptMatch && posMatch) ? 'synced' : 'unsynced';
}
```

### 4.4 性能考虑

- `employees.id` 应已有主键索引，`personnel_insurance.personnel_id` 需确认是否有索引；若未建，在优化前请先确认查询计划，如全表扫描则建议添加索引（索引属于表结构优化，如红线禁止则需评估实际数据量后决定）
- 当前 personnel_insurance 数据量不大（验证报告中显示在职员工数量级），LEFT JOIN 性能可接受

## 8. 风险提示

1. **无 personnel_id 的历史记录**：早期导入的数据可能 `personnel_id = null`，此类记录无法关联花名册，C1 会回退到原始快照值，属于正常行为
2. **employees 记录软删除**：若员工被软删除（`is_deleted = true`），LEFT JOIN 条件中的 `e.is_deleted = false` 会过滤掉该记录，此时表现同"花名册缺失"
3. **同名不同人冲突**：`personnel_insurance` 的冲突键 historically 是 `['name', 'id_card', 'policy_no']`，`personnel_id` 才是唯一关联标识；若历史数据 `personnel_id` 不准确，关联结果可能错位

> 以上风险属于存量数据质量问题，不在本提示词修复范围内；如需要数据清洗，请单独提出。
