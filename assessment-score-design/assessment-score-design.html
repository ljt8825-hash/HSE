积分记录表设计方案

围绕「自定义奖惩分数 + 多业务模块联动 + 自动出分」的考核系统，先调研开源项目 RankingBoard，再与本项目「月度安全履职考核」的真实表结构做逐字段对照，给出可落地的设计建议。

对标开源 gwokwong/RankingBoard 对照现状 hse_assessment_deduction 等五张表 生成日期 2026-08-27

1研究背景

此前检索发现，GitHub 上没有完全等同「自定义奖惩分 + 模块联动 + 自动出分 + 月度周期」的现成开源系统；其中事件幂等、定时兜底、评分引擎多为企业自研。在候选项目里，RankingBoard 是最贴近「积分制管理 + 审批 + 排名」的开源项，故选定它作为表设计参考。

需要说明：gwokwong/RankingBoard 仓库未公开任何建表脚本、实体类或数据库设计文档（仅 README、CHANGELOG、LICENSE 与 23 张界面截图）。因此本文第 2 章是其功能暗示的「通用参考模型」，而非该仓库原始字段；第 3 章起为本项目真实的建表定义与对比。

2RankingBoard 参考模型（功能推导）

README 明确其业务闭环："积分申请 → 多级审批 → 排名更新 → 福利兑换 → 数据分析"，并区分固定积分（学历/职称自动算分）与动态积分（任务/行为实时积分），支持积分补录与扣分替代罚款。据此可推导一套通用表模型：

表名职责关键字段
points_rule奖惩/固定项规则配置rule_code、rule_name、rule_type、points、is_fixed、start_date/end_date、status
points_apply积分申请 + 多级审批留痕user_id、apply_type、biz_id、points、status、approver_id、approve_time、approve_comment、reason
points_record积分流水（核心）user_id、change_type、points(正加负减)、balance_after、biz_id/biz_type、source、status、approve_by、remark
user_points_balance当前总积分（加速查询/排名）user_id、total_points、last_updated

⚠ 表名与列名为通用推导，非 RankingBoard 原始定义。其 README 也未说明「审批状态放独立申请表还是流水表」——这是它留给实现者的取舍。

3.2 事件幂等表 hse_assessment_event_log

-- RankingBoard 不具备的能力：跨模块事件消费的唯一性保障 CREATE TABLE IF NOT EXISTS hse_assessment_event_log ( id BIGSERIAL PRIMARY KEY, event_type VARCHAR(50) NOT NULL, event_key VARCHAR(200) NOT NULL, -- 如 VIOLATION_CREATED:123 payload JSONB, status VARCHAR(20) DEFAULT 'pending', related_cycle_id BIGINT, processed_at TIMESTAMPTZ, created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(), CONSTRAINT uq_assessment_event UNIQUE (event_type, event_key) -- 同一业务事件只消费一次 );

该表禁止 DELETE（触发器拦截），保证审计完整性；每日定时扫描作为幂等兜底，实时发布作为主链路。

5可落地的设计建议

建议一 · 补充 balance_after

在 hse_assessment_deduction 追加变端后快照 balance_after NUMERIC(6,2)，记录每次扣分生效后的累计结果，避免高分目标在查询明细时逐条重算，显著降低「扣分明细 ÷ 总分」推导的复杂度。

建议二 · 抽离规则配置表

将引擎内嵌的指标梯度（频率阈值 × 扣分分值）抽为独立配置表（如 hse_assessment_metric_rule），对齐 RankingBoard 的 points_rule + is_fixed 思想，使「自定义奖惩分数」真正可配置、可灰度。

建议三 · 沉淀周期汇总快照

参考其 user_points_balance / points_board，在冻结周期时沉淀 score_auto 快照（AUTO_TOTAL_SNAPSHOT），保证历史分数不随明细调整而漂移，满足审计口径。

核心取向：本项目在自动化出分链路（事件幂等、周期绑定、JSONB 溯源、防删审计）上已明显领先 RankingBoard；可主要借鉴其「实时余额快照」与「规则配置独立化」两点。不建议引入它偏「福利兑换/积分商城」的模块。

6结论

RankingBoard 提供了「积分制考核」参考价值（固定/动态积分并存、申请·审批·生效流程、积分补录、多级审批沉淀），但仓库层未开源表结构，且其偏「激励/兑换」而非「安全考核自動扣分」。本项目真实表设计在核心诉求上已覆盖甚至超出该模型的绝大部分字段，两者定位不同。

结论：不改动现有主链路，仅在后续迭代按第 5 章三条建议做增量增强即可；无需参照 RankingBoard 重建积分流水。
