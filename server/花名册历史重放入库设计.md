## 2. 重放语义（与现有 `performBatchImport` 的关系）

现有 `performBatchImport` 是**单文件"当前态"覆盖**：每导入立即把旧 current 置 `is_current=false,end_date=今天`，再插一条 current。它**无法表达"历史任职轨迹/离职推断"**，因此重放**不复用它**，而走一条**独立、只属于重放**的落库路径（新增后端命令/接口），**不动现有 13 字段 schema、不改现有路由**。

重放以"逻辑人"为单位（Dry-run 的并查集已导出），按段写任职：

| 段类型 | 落库 |
|--------|------|
| 首次任职（入职） | 新建 `employee` + `employee_assignment`(start=首次出现快照日期) |
| 部门/角色变更 | 旧段 `end_date=变更上界`、`is_current=false`；新段插入(start=变更下界) |
| 当前在职 | 最新一段 `is_current=true, is_primary=true` |
| 离职（离职表104） | 当前段 `is_current=false`、`end_date=离职表日期` |
| 离职（快照推断1614） | 当前段 `is_current=false`、`end_date=最后一次出现快照次日(上界)`，remark 注明"快照推断" |

`dept_name` = 归一化后的单位名；岗位粒度 = 角色类（粗分类），不写死 position_id（可空，保留原始 raw 文本进 remark 备用）。

### 2.1 单位/岗位规范映射（用户确认，抑制假变迁）
| 类别 | 规范单位 | 覆盖的历史叫法 |
|------|----------|----------------|
| 车队(驾驶员) | `车队` | 转运车辆 / 勾臂车 / 钩臂车 / 机械作业中心 → 车队的司机，从未变动过部门，仅叫法不同 |
| 乡镇作业中心(片区长) | `xx片区(xx乡镇作业中心)` | 老体系 `xx镇` 的 乡镇主管 / 人工片区长 = 新体系 乡镇作业中心经理（此为真正的升迁主线） |
| 乡镇班组(管理员) | `xx镇x班` | 老体系 `所属乡镇+二级乡镇`（如 xx镇 / xx镇x区） |
| 部门更名 | 以新体系为准 | 安环品质部→安环管理部；生产运营部→生产管理部 / 环卫作业中心 |

- **职能岗稳定原则**：项目管理层 / 人力综合部 / 财务部 / 安环管理部 / 生产管理部 / 环卫作业中心 的职能人员（项目总经理/经理/专员/会计等共23人）**默认视为稳定，仅当部门名在新体系别名集合内变化**才记变迁。特例（用户点明）：孟祥宇、王明轩 换部门；韩晓亮、刘菲 生产专员→人工片区长（注意：这是**环卫作业中心**的人工片区长，**≠乡镇作业中心经理**，不属于升迁主线）。

## 3. 与存量（1328 employee / 6567 assignment）的归并与风险

按方案 §7-4：**新数据覆盖岗位/部门/上级，不重建重复人员**。即：
- 以 `id_card_hash` / `employee_code` 命中存量 `employee` 行 → 复用其 id，不新建；重放后其历史任职段写入该 id。
- 未命中 → 新建 `employee`。

### ⚠️ 风险（必须在你拍板前说清楚）
1. **mass 覆盖员工关系**：重放会把现有 1312 人 / 6567 条 assignment 的关系全部重建为"66份快照推导"版本，并追加离职标记。凡**引用 `employee_assignment` 的下游模块**（`v_employee_current`、评分引擎的人员归属、目标职责、驾驶员管理等）将随本次重放被整体改写。
2. **1312(现状) vs 1293(最新) 的差异人**：现状在职里约有一批人不在 2026.9.1 快照——重放将按归并把它们从在职打为离职/历史。**这些改动在生产侧是常态**，但需要你知晓其影响面。

### 建议的处理（降低影响，供选）
- **方案甲（推荐）**：先把现有 `employee_assignment` **整体软删归档**（`is_deleted=true`，保留行以审计/回滚），再按重放结果重建 current 与轨迹。`employee` 行本身尽量复用。
- **方案乙**：仅重放"新增/离职/变更"增量，现状在职保留——但这样 1312≠1293 的问题无法收敛，历史轨迹与当前态会并存冲突。

## 4. 交付物与批次

- **一次重放 = 一个批次**（写入 `employee_import_batch`，type/import_source 标记 `history_replay`），统计见 §6，异常行进 `employee_import_pending` 待审（沿用现有审批流转）。
- 落地为：`server/routes/hse-employee-import-v2.js` 新增 `GET /source-files`（已有）+ `POST /replay/history`（新增，仅 admin），或在 `server/scripts/` 提供**独立一次性 Node 脚本（离线执行，产出 SQL 事务，含回滚 dump）**。**推荐脚本方式**：重放是低频一次性操作，不进常规 web API，避免长期暴露写接口。

## 5. 回滚方案（核心）

1. **Phase 0 快照**：执行前把 `employee`、`employee_assignment`、`employee_import_pending`、`employee_import_batch` 全量导出为
   `server/backups/roster_replay_20260906_<ts>.sql`（`pg_dump --table=...`）或建同名备份表 `employee_bak_20260906` 等。
2. **单事务 + savepoint**：重放整体在一个事务内，失败 `ROLLBACK` 全量还原；每逻辑人用 savepoint 隔离。
3. **回滚命令**：`server/scripts/rollback-roster-replay.cjs` 可从快照表/`is_deleted` 恢复原状。
4. **验收即回滚开关**：重放完成但未通过 §6 校验时，回滚不切换，不对外可见。
